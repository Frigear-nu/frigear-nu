---
title: Admin
description: Generic admin area - guarded shell, dashboard and navigation that other modules contribute to.
---

A generic admin area with **no domain features**: an `admin` layout with a sidebar, a guarded dashboard page and the
registries other modules plug into. Use it as the back office of a site; domain admin UIs (forms, events, OAuth
applications, users, ...) stay in their own modules and register here. It needs `@frigear-nu/ui`, `@frigear-nu/menu` and
`@frigear-nu/widget` (see below).

:module-runtime{client}

::note
**Requires** [`@frigear-nu/module-kit`](/modules/platform/module-kit), [`@frigear-nu/ui`](/modules/interface/ui) (the page components
every admin page is built from), [`@frigear-nu/menu`](/modules/interface/menu) (the sidebar is the `admin.nav` menus),
[`@frigear-nu/widget`](/modules/interface/widget) (the dashboard is the `admin.dashboard` area) and `nuxt-auth-utils` (the
signed-in user is shown in the account menu).
**Optional** [`@frigear-nu/authorization`](/modules/identity/authorization), used for the role guard, and
[`@frigear-nu/account`](/modules/identity/account), which provides the account menu in the sidebar footer.

`@nuxt/ui` is not declared as a module dependency, but the layout and components are built on Nuxt UI, so the host
installs it.
::

## Quick setup

```bash
pnpm add @frigear-nu/admin @nuxt/ui
```

```ts
export default defineNuxtConfig({
  modules: ['@nuxt/ui', '@frigear-nu/authorization', '@frigear-nu/admin'],
  admin: {
    settings: {
      roles: ['admin', 'manager'],
    },
  },
})
```

## Options

All options live under `admin.settings`.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `base` | `string` | `'/admin'` | Path prefix of the area. A trailing slash is trimmed. |
| `dashboard` | `boolean \| string` | `true` | The dashboard page at `base`. `false` turns it off (other modules' pages still get the layout); a string is a custom path. |
| `roles` | `string[] \| false` | `['admin']` | Roles allowed into the area, applied as a route rule on `<base>/**`. `false` sets no rule: guard the area yourself. |
| `layout` | `boolean` | `true` | Gives every page under `base` the `admin` layout unless it picked its own; an app's own `app/layouts/admin.vue` replaces the module's. `false` registers no layout and sets no rule. |

Behaviour of the generated route rules:

- **Guard**: `{ roles }` on `<base>/**`, only when `@frigear-nu/authorization` is installed. Without it nothing guards the
  pages on the client and a warning is logged. An explicit rule of yours wins. API routes are guarded by the modules
  that own them.
- **Layout**: `{ appLayout: 'admin' }` on `<base>` and `<base>/**` (the dashboard at `base` itself is not matched by
  the wildcard, so it gets its own rule). A rule of yours wins.
- **Locales**: with `@nuxtjs/i18n` the rules are repeated for each `/<locale>` prefix.
- **Account menu**: unless `dashboard` or `roles` is `false`, an "Admin" entry is added to the `account.dropdown` menu,
  shown only to users holding one of the roles.

## App

### Navigation groups

The sidebar is three groups, each read from its own [menu](/modules/interface/menu) path. `ADMIN_NAV_GROUPS` (from
`@frigear-nu/admin/utils`) lists them in display order:

| Group | Menu path | Put here |
| --- | --- | --- |
| `overview` | `admin.nav.overview` | The dashboard. |
| `manage` | `admin.nav` (root) | What staff manage every day: users, events, forms, groups, documents. This is the default group. |
| `settings` | `admin.nav.settings` | Configuration: OAuth applications, integrations. |

The layout reads all three in one `useMenu('admin.nav.*')` call and renders them as labelled sections (Overview has no
label; Manage and Settings do). A new feature goes into an existing group; a new group needs a
reason (see [UX patterns](/guide/ux-patterns/layouts-and-navigation#admin-back-office)).

### Registries

Modules never import the admin module at runtime. The sidebar is just a menu, so the way to add an entry is a
[runtime menu source](/modules/interface/menu#contributing-from-a-module) (see
[extension points](/guide/concepts/extension-points)): a module registers a `runtime/menus.ts` file that pushes items
into the group's menu path with `extendMenuItem`. It works whether or not `@frigear-nu/admin` is installed.

```ts
// module.ts
import { addOptionalMenuSource } from '@frigear-nu/module-kit/utils'

addOptionalMenuSource(nuxt, { file: resolver.resolve('./runtime/menus'), menu: 'admin' })
```

```ts
// runtime/menus.ts
import { defineMenuItem, defineMenuSource, extendMenuItem } from '@frigear-nu/menu/utils'

export default defineMenuSource(() => {
  const config = useRuntimeConfig().public.forms

  // Manage group (the root of `admin.nav`)
  extendMenuItem('admin.nav', defineMenuItem({
    id: 'forms-admin',
    label: 'Forms',
    labelKey: 'forms.menu.admin.label',
    icon: 'i-lucide-clipboard-list',
    to: config.pages.admin,
    order: 30,
  }))

  // Settings group
  extendMenuItem('admin.nav.settings', defineMenuItem({
    id: 'forms-settings',
    label: 'Form settings',
    icon: 'i-lucide-settings-2',
    to: '/admin/forms/settings',
  }))
})
```

For static entries known at build time there is sugar over `extendMenu`, plus the dashboard helpers. They come from
`@frigear-nu/admin/utils`:

```ts
import { extendAdminNav, extendAdminDashboard, adminRoute } from '@frigear-nu/admin/utils'

extendAdminNav(nuxt, { label: 'Forms', to: adminRoute(nuxt, 'forms'), icon: 'i-lucide-clipboard-list', order: 20 })
extendAdminNav(nuxt, { label: 'OAuth applications', to: adminRoute(nuxt, 'oauth'), icon: 'i-lucide-key-round' }, 'settings')
extendAdminDashboard(nuxt, { component: resolver.resolve('./runtime/app/widgets/Submissions.vue'), order: 10 })
extendAdminDashboard(nuxt, { component: resolver.resolve('./runtime/app/widgets/SubmissionCount.vue'), order: 10 }, 'top')
```

| Export | Signature | Purpose |
| --- | --- | --- |
| `extendAdminNav` | `(nuxt: Nuxt, items: MenuItem \| MenuItem[], group?: 'overview' \| 'manage' \| 'settings') => void` | Adds sidebar entries at build time: `extendMenu(nuxt, '<group path>', ...)`. `group` defaults to `'manage'`. |
| `extendAdminDashboard` | `(nuxt: Nuxt, widgets: WidgetDefinition \| WidgetDefinition[], position?: 'top' \| 'main' \| 'side') => void` | Adds dashboard widgets to one of the three dashboard areas (below); `position` defaults to `'main'`. |
| `adminRoute` | `(nuxt: Nuxt, ...segments: string[]) => string` | Path below the configured base: `adminRoute(nuxt, 'events', ':id')` is `/admin/events/:id`. Use it so defaults follow the host's `base`. |
| `ADMIN_NAV_GROUPS` | readonly list | The groups in display order, with the menu path each reads (table above). |
| `ADMIN_NAV_MENU` | `'admin.nav'` | Menu name of the sidebar (the Manage group). |
| `ADMIN_DASHBOARD_AREA` | `'admin.dashboard'` | Widget area of the main dashboard column. |
| `ADMIN_DASHBOARD_TOP_AREA` | `'admin.dashboard.top'` | Widget area of the stat row. |
| `ADMIN_DASHBOARD_SIDE_AREA` | `'admin.dashboard.side'` | Widget area of the narrow side column. |

A module can also call `extendMenu` / `extendWidgets` directly, without depending on this package.

### Dashboard areas

The dashboard is three [widget](/modules/interface/widget) areas, so modules fill it without the admin module knowing them:

| Area | `position` | Layout | Put here |
| --- | --- | --- | --- |
| `admin.dashboard.top` | `'top'` | Row of up to four cards (`span` works) | One `StatCard` per widget: a number with a label and icon. |
| `admin.dashboard` | `'main'` | Wide column below the stats (full width when the side column is empty) | Lists and tables, e.g. `ListCard`. |
| `admin.dashboard.side` | `'side'` | Narrow column next to it, stacked | Short `ListCard`s. |

Widgets load their own data (`useLazyFetch`, so the page doesn't wait) and receive no context. Without widgets in any
of the areas, the dashboard shows a shortcut card for every entry of the Manage and Settings groups.

### Runtime config

`runtimeConfig.public.admin` holds the resolved values:

```ts
type PublicModuleOptions = {
  base: string
  dashboard?: string // undefined when the dashboard is off
}
```

### Layout and page

| Name | Purpose |
| --- | --- |
| `admin` layout | The shared [`AppShell`](/modules/interface/ui/app-shell) fed with the admin menus: a collapsible, resizable sidebar and a navbar over the page body. |
| Dashboard page | `admin-dashboard` at the dashboard path: a `PageHeading` and the three widget areas above. Skipped if a page already exists at that path. |

Define `app/layouts/admin.vue` in your app (or a layer) and it replaces the module's layout: the module only registers
its own when no `admin` layout exists, and the route rule still applies the layout by name, so every page under `base`
renders in yours. `settings.layout: false` removes the layout entirely: no layout is registered and no rule is set.

The `admin` layout is a thin wrapper around `AppShell` from `@frigear-nu/ui`, the same shell the
[account area](/modules/identity/account#layout) uses. The layout reads the menus and passes them in (raw paths, the shell
localises them); the chrome belongs to the shell:

- **Sidebar**: the brand tile and title (cookie `dashboard-sidebar-admin`), the ⌘K search button, the grouped navigation (Overview, **Manage**, **Settings**) and, in the
  footer, a "Back to the site" link and the **account menu** (`AccountMenu` from [Account](/modules/identity/account), when
  installed: it shows the signed-in user and a colour-mode switch under **Appearance**).
- **Navbar**: the sidebar collapse button, a muted "Administration › Users" eyebrow (the area, then the active section)
  and, with more than one locale, `LanguageSelect`. The eyebrow is not a heading: every admin page renders its own
  `PageHeading`, which is the page's only `<h1>`. There is no colour-mode button in the navbar: appearance lives in the
  account menu.
- **Width**: the body is centred at `max-w-7xl`; a page that needs the full width (the form builder) sets
  `definePageMeta({ wide: true })`.
- **⌘K**: the palette has one group per navigation group, listing the same entries, so everything in the sidebar is
  searchable. `AccountMenu` and `LanguageSelect` are resolved by name, so a host's own versions win and neither is
  required.
- Links are built with `useNavLinks`, so they keep the visitor's locale prefix and the active entry is highlighted.

### Components

The admin pages are built from the shared components of [`@frigear-nu/ui`](/modules/interface/ui): `PageHeading`, `PageToolbar`,
`TableCard`, `RowMenu`, `SectionCard`, `DescriptionList`, `StatCard`, `ListCard` and `FormSlideover`. Use them directly; [UX patterns](/guide/ux-patterns/pages) shows how a list, a detail page and a form are put together.

The nine deprecated `Admin*` aliases (`AdminPage`, `AdminPageHeader`, ...) have been removed. Replace them with the
shared components: `AdminPage` is a plain
`<div class="flex flex-col gap-4">`, `AdminPageHeader` is `PageHeading` (`back` becomes `breadcrumb`, the `links` slot is
`actions`), `AdminSection` is `SectionCard`, `AdminToolbar` is `PageToolbar`, `AdminEmpty` is `<UEmpty variant="naked">`,
`AdminTable` is `TableCard` around a `UTable`, `AdminStatCard` is `StatCard`, `AdminKeyValue` is `DescriptionList` (missing
values read "Not set" instead of an en dash) and `AdminListCard` is `ListCard`.

Modules that ship admin pages declare `@frigear-nu/admin` as an optional module dependency and
[`@frigear-nu/ui`](/modules/interface/ui) as a dependency; a host that enables those pages installs both.

### Page conventions

Every admin page follows the [UX patterns](/guide/ux-patterns/pages): lists, detail pages, slideover forms behind a
`use<Entity>Actions()` composable, confirmed destructive actions, toasts and translated text (see also
[forms and actions](/guide/ux-patterns/forms-and-actions) and [text and formatting](/guide/ux-patterns/text-and-formatting)).

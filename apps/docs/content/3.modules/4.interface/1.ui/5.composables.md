## Confirmations

```ts
interface ConfirmDialogOptions {
  title: string
  description?: string
  confirmText?: string // default 'Confirm'
  cancelText?: string // default 'Cancel'
  destructive?: boolean // style the confirm button as destructive
}

useConfirmDialog(): (options: ConfirmDialogOptions) => Promise<boolean> // true = confirmed, false = cancelled
```

`useConfirmDialog` is built on Nuxt UI's `useOverlay`. The dialog is not dismissible by clicking outside or pressing
escape, so the promise only resolves through the Cancel or confirm button; it is destroyed once it closes.

Every destructive action follows one convention: the title names the record, the description says what else is
affected, the confirm button names the verb and the object, and `destructive: true` styles it red.

```vue
<script setup lang="ts">
const confirm = useConfirmDialog()

async function removeApplication(app: { id: string, name: string }) {
  const confirmed = await confirm({
    title: `Delete ${app.name}?`,
    description: 'Every token issued to it stops working. This cannot be undone.',
    confirmText: 'Delete application',
    destructive: true,
  })
  if (!confirmed) return
  await $fetch(`/api/admin/oauth-server/applications/${app.id}`, { method: 'DELETE' })
}
</script>
```

## Errors, actions and clipboard

```ts
errorMessage(e: unknown, fallback: string): string // see below
errorToToast(e: unknown, overrides?: Partial<ToastProps>): Partial<ToastProps> // an error toast carrying errorMessage(e); the default title is English
useErrorToast(): (e: unknown, title?: string) => void // the translated entry point: toast.add(errorToToast(e, { title })), default title translated

useAction(): {
  busy: Ref<boolean>
  run<T>(fn: () => Promise<T>, options?: { success?: string, error?: string }): Promise<T | undefined>
}

useCopyToClipboard(): { copy(text: string, message?: string): Promise<boolean> } // copies and shows a "Copied" (or `message`) toast; false on failure
```

- `errorMessage` reads, in order, `data.message`, `data.statusMessage`, `response._data.message`, `statusMessage` and
  `message`, so it understands `$fetch` errors, `createError` payloads and plain `Error`s. The server's own message
  wins. `fallback` is required and is returned when there is nothing to read.
- `errorToToast` is a pure util, so its default title ("Something went wrong.") is English. In components use
  `useErrorToast()`: it titles the toast with `title` or the translated `patterns.genericError`.
- `useAction().run` sets `busy` while `fn` runs, shows the `success` toast (a title string) when it resolves, shows an
  error toast titled `error` (default: the translated generic error) when it throws, resolves `undefined` then, and
  always clears `busy`. It replaces hand-written try / catch / saving blocks.
- `useCopyToClipboard` uses VueUse's `useClipboard` under the hood.

```vue
<script setup lang="ts">
const { busy, run } = useAction()
const { copy } = useCopyToClipboard()

const revoke = (id: string) => run(() => $fetch(`/api/auth/me/tokens/${id}`, { method: 'DELETE' }), { success: 'Token revoked' })
</script>
```

## Loading data that survives navigation

```ts
useCachedFetch<ResT, DataT = ResT>(url: string | Ref<string> | (() => string), options: UseFetchOptions & {
  key: MaybeRefOrGetter<string> // required: names the cache entry
  ttl?: number                  // ms a remembered response is reused on mount; omitted = until refresh()
}): {
  data: Ref<DataT | undefined>  // undefined until the first response; there is no `default`
  status, error, refresh, execute, clear
  loading: ComputedRef<boolean> // status === 'pending' && data === undefined: nothing to show yet
} // and awaitable: `await useCachedFetch(...)` resolves once the first response is in

primeCachedFetch(key: string, data: unknown): void // remember a response loaded some other way
clearCachedFetch(keys?: string | string[] | ((key: string) => boolean)): void // forget them, e.g. on sign-out

loadBootstrap(scope: string, options?: { ttl?: number }): Promise<void> // one request primes an area's keys
resetBootstrap(scope: string): void // forget the area's bootstrap and the entries it primed
```

Nuxt drops `useFetch` data once the last component using a key unmounts, so leaving a page and coming back used to
blank it and flash the empty state until the refetch landed. `useCachedFetch` wraps `useFetch` and remembers each
response by `key`. On mount it takes data from, in order:

1. the server's response in the payload, while hydrating (and remembers it);
2. the remembered response, while it is younger than `ttl`;
3. a request. Until it lands, an older remembered response stays on screen, so a refetch never blanks the page.

`refresh()`, `refreshNuxtData()` and watchers always ask the server and update the remembered response. Only the
browser remembers responses, so the cache adds nothing to the SSR payload. `primeCachedFetch` on the server puts the
data in that request's payload instead, where `useCachedFetch` finds it while rendering and again while hydrating.

- There is no `default`: a failed request leaves `data` `undefined` (or the last good response) and sets `error`, so
  it can never look like an empty result. Derive lists with `data.value ?? []` and check `error` before showing an
  empty state.
- `loading` is Nuxt's `pending` minus background refreshes: `true` only while there is nothing on screen yet. It is
  named `loading` so it does not clash with `useFetch`'s deprecated `pending`.
- `await` it in pages, so SSR renders the data. Widgets and components that share a page can use it without `await`
  and render a skeleton from `loading`.
- Composables built on it can stay awaitable too: return `Object.assign(fetched.then(() => api), api)` so a page can
  `await useMyThing()` while a widget calls `useMyThing()` directly.

```vue
<script setup lang="ts">
const { data, error, loading } = await useCachedFetch<TicketDto[]>('/api/events/me/tickets', {
  key: 'events:tickets:mine',
  ttl: 60_000,
})
const tickets = computed(() => data.value ?? [])
</script>

<template>
  <SectionCard v-if="loading" loading />
  <UEmpty v-else-if="error" icon="i-lucide-circle-alert" :description="errorMessage(error)" />
  <UEmpty v-else-if="!tickets.length" icon="i-lucide-ticket" title="No tickets yet" />
  <TicketList v-else :tickets="tickets" />
</template>
```

## One request for an area: `loadBootstrap`

An area that shows several modules' data for the signed-in user (the account pages: membership, tickets,
applications) loads it in one request instead of one per module. Modules register a provider for the area's scope
with [`registerBootstrapProvider`](/modules/platform/module-kit/registries-and-menus#bootstrap-providers), under the key their composable already
passes to `useCachedFetch`. The area calls `loadBootstrap(scope)` from a route middleware: it fetches
`GET /api/auth/bootstrap?scope=<scope>` and primes each returned key, so the composables render without a request of
their own.

- **Server:** the data goes into the payload. The page's `useCachedFetch` calls read it while rendering, and the
  browser reads it while hydrating.
- **Hydration:** no request; the entries are remembered for the pages visited next.
- **Client navigation:** a request only when the last bootstrap is older than `ttl` (default one minute). Keep `ttl`
  at or below the `ttl` of the composables it primes, so they always find a fresh entry.
- **Failures:** it never throws. When the request fails, or a provider was left out, those composables fetch from
  their own endpoints as before.
- **A middleware, not the layout:** a layout sets up once and stays mounted while the visitor moves between the
  area's pages, and its setup is not guaranteed to finish before the page's. A route middleware runs before every
  page of the area sets up, on the server and on each client navigation.
- **Sign-in and sign-out:** call `resetBootstrap(scope)` when the signed-in user changes. The account module does
  this for `account`.

```ts
// runtime/app/middleware/bootstrap.ts, added to the area's routes with a route rule
// (`appMiddleware: { 'my-area-bootstrap': true }`)
export default defineNuxtRouteMiddleware(async () => {
  if (useUserSession().loggedIn.value) await loadBootstrap('my-area')
})
```

## Formatting and links

```ts
// utils: pure functions; accept a Date, an ISO string or a timestamp. `locale` defaults to English
formatDate(value, locale?): string
formatDateTime(value, locale?): string
formatTime(value, locale?): string
formatDateRange(start, end, locale?): string

useFormat(): { locale, timeZone, date, dateTime, time, dateRange, money } // the formatters with the locale and the app time zone already bound
// money(15000, 'DKK') is formatMoney from @frigear-nu/ui/money with the locale bound; amounts are in minor units

useLocaleLink(): {
  localize(to: string): string // prefixes the active locale when @nuxtjs/i18n is installed; unchanged otherwise
  strip(path: string): string // removes a leading locale code
  isActive(to: string, options?: { exact?: boolean }): boolean // the current route is `to` or below it
}

useNavLinks(items: MaybeRefOrGetter<MenuItem[]>, options?: { exact?: string[] }): ComputedRef<NavigationMenuItem[]>
```

- Always format dates and money through `useFormat()` so they follow the active locale. Set `frigearUi: { timeZone: 'Europe/Copenhagen' }` in the host `app.config.ts`: without it a UTC server and a visitor's browser format the same instant differently (hydration mismatch).
- `useLocaleLink` is not called `useLocalePath` so it never clashes with `@nuxtjs/i18n`'s own composable. Use it for
  every link a module builds, so a visitor on `/da/...` stays under `/da`.
- `useNavLinks` turns menu items (from `useMenu`) into `NavigationMenuItem`s with a localised `to` and a computed
  `active` flag. Paths in `exact` only match exactly, for items such as a dashboard at the area's base path. The admin
  sidebar, the account navigation and the site header all use it.

## Status and styling

```ts
statusColor(status: string | null | undefined, overrides?: Record<string, StatusColor>): StatusColor
// success: published, active, trialing, paid, succeeded
// warning: pending, past_due, incomplete, scheduled
// error:   failed
// neutral: everything else

surfaceClass // 'bg-elevated/50 ring ring-default rounded-lg overflow-hidden', the frame of every card
tableUi(overrides?: TableUi, options?: { sticky?: boolean }): TableUi
// the shared UTable styling used inside TableCard: small muted headers, compact rows on desktop, taller on mobile,
// clickable rows. `overrides` replace single slots (`tableUi({ tr: '' })` for rows that open nothing); `sticky`
// lets the table scroll inside its card (pair it with `<UTable sticky>`)

numericColumn // column meta for numbers: right-aligned, tabular figures (`{ meta: numericColumn }`)
emptyCell(): VNode // the dimmed dash of a cell without a value
```

`statusColor` makes status badges the same colour on every page: `<UBadge :color="statusColor(event.status)" :label="event.status" />`.
Pass `overrides` to recolour a module-specific status.

## Tables

```ts
useTableSort(initial?: { id, desc } | null, state?: Ref<{ id, desc } | null>): {
  sort: Ref<{ id, desc } | null>
  sorting: WritableComputedRef<{ id, desc }[]> // UTable's shape: `v-model:sorting` for client-sorted lists
  query: ComputedRef<{ sort?, order? }> // for server-sorted lists
  header(id: string, label: string): () => VNode // a column's sortable `header`
  toggle(id: string): void
}

useTableQuery({ pageSize?, sort?, filters?, debounce? }): {
  page, pageSize, sort, // refs, kept in the URL (`?page=2&sort=name&order=asc`)
  search, // what the search input binds
  q, // `search` after a 300 ms pause
  filters, // reactive, one string per filter; a filter at its default stays out of the URL
  query, // what a server-paginated list sends to its API
  filtered, // the search or a filter narrows the list
  reset(): void // clears the search and the filters
}
```

`useTableSort` gives every sortable header the same ghost button and the same three steps: ascending, descending,
unsorted. `useTableQuery` keeps a paginated list's state in the URL and goes back to page 1 whenever the search, a
filter, the sort or the page size changes. Pass its `sort` to `useTableSort` so both share one state:

```ts
const { page, pageSize, search, sort: sortState, filters, query } = useTableQuery({
  sort: { id: 'createdAt', desc: true },
  filters: { role: 'all' },
})
const { header } = useTableSort(null, sortState)
const { data } = await useFetch('/api/admin/users', { query })
```

## Translated text and locale

```ts
useTranslatedLocale(): ComputedRef<string> // the visitor's locale; `en` without @nuxtjs/i18n
useTranslatedLocales(): ComputedRef<string[]> // locales content can be translated into; ['en'] without @nuxtjs/i18n
useTranslatedFallbackLocale(): ComputedRef<string> // the default locale, used when a text lacks the current one
useUiT(namespace: string): (key: string, fallback: string, params?: Record<string, string | number>) => string

stripLocale(path: string, codes: string[]): string // '/da/events' with ['da', 'en'] -> '/events'
```

`useUiT` is an optional-i18n translator: it returns the message when `@nuxtjs/i18n` has the key, otherwise the English
fallback with `{name}` params replaced. The components use it, which is how every built-in string is translated
without making `@nuxtjs/i18n` required.

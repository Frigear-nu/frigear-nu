Operations holds the occasions Frigear works at, whether or not Frigear hosts them: "Roskilde 2027 bar operation", a
venue's autumn season. [Staff](/guide/concepts/glossary) create an operation, set its period, place and host, and move
it from planning to archived. It is the anchor the other [volunteering](/modules/volunteering) modules attach crew,
shifts, maps and help content to. For dated events with tickets, use [Events](/modules/features/events) instead.

The package is `@frigear-nu/operations`. It answers the `operation` [owner](/modules/volunteering#owners) of
[Audience](/modules/volunteering/audience).

## What you get

- **Pages**: the public page of a public operation at `/operations/:slug` (on by default, `pages.public: false` turns it
  off).
- **Admin area** (opt-in, with [Admin](/modules/interface/admin)): an operation list at `/admin/operations`, and an
  operation page at `/admin/operations/:id` with a Details tab and the tabs other modules add. The sidebar entry
  needs [Menu](/modules/interface/menu).
- **Server routes** (on by default): browse the public operations and the ones you take part in, and a staff API for
  operations and their status. The staff API is guarded by [`operations:manage`](#permissions).
- **Composables and helpers**: `useOperationActions`, `useOperationLinks` and the path builders `operationsApi`.
- **Hooks**: `operations:created`, `operations:updated` and `operations:status-changed`.
- **Emails.** None built in. Send one from `operations:status-changed`.

:module-runtime{server client}

::note
**Installed for you:** [Auth](/modules/identity/auth), [Audience](/modules/volunteering/audience),
[UI](/modules/interface/ui) and Module Kit.
**You add:** `@nuxthub/core`, and `@nuxt/ui` for the pages.
**Optional:** [Admin](/modules/interface/admin) for the admin pages, [Widget](/modules/interface/widget) for the tabs
of the operation page, [Menu](/modules/interface/menu) for the sidebar entry, [Events](/modules/features/events) to link
an operation to an event, and [Mobile](/modules/interface/mobile).

## Quick setup

::steps

### Install Operations

```bash
pnpm add @frigear-nu/operations @nuxthub/core
```

### Add it to nuxt.config.ts

List Widget and Menu (or Admin, which installs them) before Operations, so the tabs and the menu entry register.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/admin', '@frigear-nu/operations'],
  operations: {
    settings: {
      pages: { admin: true, adminOperation: true },
    },
  },
})
```

### Generate the migration

:::warning
Without a [migration](/guide/concepts/glossary) the `operations` table does not exist, and every request to it fails.
:::

```bash
pnpm db:generate
```

### Decide who manages operations

:::warning
Staff routes check permissions through [Authorization](/modules/identity/authorization). Without a role that holds
`operations:manage`, nobody can manage operations. The `admin` and `coordinator` roles hold it when your app defines
them.
:::

The module grants `operations:manage` to `admin` and `coordinator`, for the roles your app defines. Give it to a role
of your own by name:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  authorization: {
    roles: {
      organiser: { label: 'Organiser', grant: ['operations:manage'], inherit: ['user'] },
    },
  },
})
```

::

::callout{color="success" icon="i-lucide-check"}
**What you should see:** a signed-in coordinator opens `/admin/operations`, adds "Roskilde 2027 bar operation" and lands
on its page in `planning`. Marking it public shows it at `/operations/roskilde-2027-bar-operation` for everyone.
::

## Options

Options go under the `operations` key.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `settings.pages.public` | `string \| boolean` | `true` | The public page. `true` is `/operations/:slug`, `false` turns it off. |
| `settings.pages.admin` | `string \| boolean` | off | The staff operation list. `true` is `/admin/operations`. |
| `settings.pages.adminOperation` | `string \| boolean` | off | The staff operation page. `true` is `/admin/operations/:id`. |

**`settings.pages.*`** paths keep the parameters of the default, such as `:slug`. The admin pages need Admin.

## Permissions

Operations registers these permissions with [Authorization](/modules/identity/authorization). Staff routes call
`authorize(event, operationsAccess.permissions.manage)`.

| Name | Flags | Held by default | What it allows |
| --- | --- | --- | --- |
| `operations:manage` | | `admin` and `coordinator` | Create and edit operations, move them through their statuses and delete them. |
| `operations:read` | implicit | every signed-in user | Read the public operations and the ones you take part in. |

- **Scope:** `operations` expands to `operations:read`. A token with it can read operations and is refused every staff
  route.
- **Policy on `operations:read`:** an operation is readable when it is `public`, when its id is in the viewer's
  `operationIds` (the operations you take part in, see [Who takes part](#who-takes-part)), or when the caller holds
  `operations:manage`. It is the first policy a module registers itself (`addPolicies`, not the host's `server/policies.ts`).
- **Not readable is 404.** A non-public operation answers `404` to anyone who may not read it, the same as an unknown
  URL name, and only after the authentication checks.

## Server

Everything under `/api` is in the [Routes](#routes) section. This section covers what other modules build on.

### Who takes part

Operations stores no participants. `GET /api/operations/me`, the public list and the `operations:read` policy resolve
the viewer through [Audience](/modules/volunteering/audience) (`resolveViewer`) and read `viewer.operationIds`. The
modules that know who works where answer `audience:viewer:resolve`: [crew](/modules/volunteering) fills it in phase 3.
Until one does, `operationIds` is empty and a signed-in user sees the public operations only, and `/me` answers `[]`.

### Owner resolution

A module that owns records per operation (maps, FAQ, help center) asks Audience, without importing Operations:

```ts
const { label, exists } = await resolveOwner(event, { type: 'operation', id: operationId }, { hooks: useNitroApp().hooks })
```

Operations answers `audience:owner:resolve` for the `operation` type from a server plugin it always registers: `label`
is the operation's `name`, and `exists` is whether the id is found. It sets nothing for other owner types. The answer
is about existence, not access: check that with `authorize(event, permission, record)`.

### Status

An operation moves along `planning → active → wrapped_up → archived`, and `planning → archived` for a plan that never
happens. `archived` is final. Any other move is `409` with the code `invalid_status_transition`, and the response's
`data` holds `from` and `to`. The helpers `canTransition(from, to)` and `nextStatuses(from)` are exported from
`@frigear-nu/operations/utils`, so a UI offers only the moves that work.

The status route updates conditionally on the status it read, so two staff members moving one operation at once cannot
both succeed.

### Link to an event

`eventId` names an [Events](/modules/features/events) event. It is a plain column, not a foreign key: the id is checked
against the events table (`400` when it does not exist) only when Events is installed, and is accepted as it is
otherwise.

## App

### Pages

| Page | Path | For |
| --- | --- | --- |
| Public operation | `/operations/:slug` | Everyone, for operations with `public: true`. Anything else is a 404 page. |
| Operation list | `/admin/operations` | Staff with `operations:manage`. A status filter, search and sortable columns. |
| Operation page | `/admin/operations/:id` | Staff with `operations:manage`. Key facts, a Details tab and the tabs other modules add. |

The list's row menu offers Open, Edit, Change status and Delete in its own group. Archiving and deleting ask to confirm.
Creating and editing open the same slideover. Dates are entered in the browser's time zone.

### Composables

| Composable | What it does |
| --- | --- |
| `useOperationActions()` | `create`, `edit`, `changeStatus`, `remove` and `menu(operation)`, with toasts and confirmations. |
| `useOperationLinks()` | Locale-aware links to the public page and the admin pages. |

### Add a tab to the operation page

The staff operation page renders the `admin.operations` tab area of [Widget](/modules/interface/widget). Operations
registers **Details** there. Any module adds a tab from its `setup()`, without Operations knowing about it:

```ts
import { extendTabs } from '@frigear-nu/widget/utils'

extendTabs(nuxt, 'admin.operations', { id: 'crew', component: resolver.resolve('./runtime/app/tabs/Crew.vue'), label: 'Crew', order: 10 })
```

Each tab component receives `operation` as a prop, the response of `GET /api/admin/operations/:id`, and may emit
`refresh`. Without Widget, only the Details tab renders.

::caution
Hiding a tab is not access control. Check the tab's API calls with `authorize(event, 'operations:manage')` too.
::

## Hooks

Your app answers these [Nitro](/guide/concepts/glossary) hooks from a server plugin (`server/plugins/*.ts`).

| Hook | When | Payload |
| --- | --- | --- |
| `operations:created` | After an operation was created, always in `planning`. | `{ event, operation }` |
| `operations:updated` | After its fields were edited. A status move does not fire it. | `{ event, operation, previous }` |
| `operations:status-changed` | After a move along the life cycle. | `{ event, operation, from, to }` |

`operation` and `previous` are the staff DTO (`AdminOperationDto`). Operations answers `audience:owner:resolve`
itself, and does not answer `audience:viewer:resolve`.

## Routes

Routes the module registers, and who may call them. Typed path builders are exported as `operationsApi` from
`@frigear-nu/operations/api`.

| Route | Who | What it does |
| --- | --- | --- |
| `GET /api/operations` | Everyone | The public operations, and the ones you take part in when signed in. `?status=` filters; archived ones only with `?status=archived`. |
| `GET /api/operations/me` | Signed in | The operations you take part in (`viewer.operationIds`), whatever their visibility or status. |
| `GET /api/operations/:slug` | Everyone | One operation by URL name. Public ones for everyone, others for participants and staff, otherwise `404`. |
| `GET /api/admin/operations` | `operations:manage` | Paginated list with `status`, `q` (name in every language, and the URL name) and sort. |
| `POST /api/admin/operations` | `operations:manage` | Create an operation. `409` when the URL name is taken. |
| `GET /api/admin/operations/:id` | `operations:manage` | One operation. |
| `PATCH /api/admin/operations/:id` | `operations:manage` | Edit any field except the status. |
| `DELETE /api/admin/operations/:id` | `operations:manage` | Delete an operation. |
| `POST /api/admin/operations/:id/status` | `operations:manage` | Body `{ status }`. `409 invalid_status_transition` for a move that is not allowed. |

The URL names `me`, `new`, `edit`, `admin` and `api` are reserved. Responses are allowlisted DTOs with ISO dates; the
public one has no `createdAt` and `updatedAt`. The body of create and edit takes `slug`, `name`, `description`,
`hostName`, `hostUrl`, `startsAt`, `endsAt`, `schedule` (a [Schedule](/modules/platform/module-kit) of Module Kit),
`location` (`{ name, address?, lat?, lng? }`), `public` and `eventId`. The admin forms do not edit `schedule`, `lat` and
`lng`: the API stores them, and the forms keep what is stored.

## Database

Tables the module adds. Generate and commit a [migration](/get-started/database#migrations) after installing.

| Table | Holds |
| --- | --- |
| `operations` | `opr_` id, a unique `slug`, Translated `name` and `description`, `hostName`, `hostUrl`, `startsAt` / `endsAt`, an optional `schedule`, a `location` json, `status` (`planning`, `active`, `wrapped_up`, `archived`), `public` and an optional `eventId`. |

Translated texts are a string or a `{ da, en }` map. Operations has no participants table: see
[Who takes part](#who-takes-part).

## Translations

Override any string in your app's `i18n/locales/<code>.json`. The module registers `da` and `en` files under
`operations.*`. See [overriding module strings](/modules/platform/module-kit/i18n#overriding-module-strings-in-your-app).
Without `@nuxtjs/i18n`, the pages use `en`.

```json
{ "operations": { "admin": { "statuses": { "wrapped_up": "Done" } } } }
```

Key groups: `menu.*`, `permissions.*`, `scopes.*` and `admin.*` (with `admin.tabs.*`, `admin.statuses.*` and
`admin.statusActions.*`). Top-level keys include `notFound`, `when`, `where` and `hostedBy`.

## Not in this release

Two integrations wait for modules that do not exist yet. Each lands in a small follow-up pull request, in whichever
of the two modules lands second.

- **Dashboard items.** `operations.upcoming` for staff and "My operations" for volunteers, through `extendDashboard` of
  `@frigear-nu/dashboard`, behind `hasNuxtModule('@frigear-nu/dashboard')`.
- **Map kinds.** The `site` (geographic) and `venue-layout` (floor plan) kinds of `@frigear-nu/maps`, and creating a
  map from `operations:created` with `ensureMap`.

## Open questions

- Should an archived operation be read-only everywhere (shifts, crew), enforced by a shared policy? Today only the
  status machine treats `archived` as final.
- Does an operation ever need a `Schedule`, or is the start and end of a period always enough? The column exists and
  the API accepts it, but nothing reads it yet.

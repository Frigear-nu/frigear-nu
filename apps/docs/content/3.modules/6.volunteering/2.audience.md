title: Audience
description: Decides who may see a record, from one shared visibility shape, so FAQ, help center, maps and inbox answer the same way.

Audience decides whether the person looking may see a record. FAQ groups, help articles, maps and mailboxes store
their [visibility](/guide/concepts/glossary) in one shape, and Audience answers for all of them. It also gives the
volunteering modules two Nitro hooks: one to find out who is looking, and one to label a record's
[owner](/guide/concepts/glossary). For the permissions code checks, use [Authorization](/modules/identity/authorization)
instead.

The package is `@frigear-nu/audience`. It is a plain TypeScript library, not a Nuxt module: you import its functions
where you need them, in the browser, on the server or in a test.

## What you get

- **Composables and helpers** (import them):
  - `isVisible(visibility, viewer)` decides one record.
  - `narrowVisibility(group, item, ladders)` gives an item the visibility of its group AND its own.
  - `isNarrowerOrEqual(group, item, ladders)` tells an editor whether an item would widen its group.
  - `visibilitySchema` and `parseVisibility` validate the stored JSON.
  - `roleAtLeast(ladder, held, min)` compares two roles of a team kind.
- **Server helpers** (import `@frigear-nu/audience/server`): `resolveViewer` and `resolveOwner`, which call the
  hooks below.
- **Hooks**: `audience:viewer:resolve` and `audience:owner:resolve`, typed for every Nitro app that imports the server
  entry.

:module-runtime{server client}

::note
**Installed for you:** `zod`.
**You add:** nothing else. It is not added to `nuxt.config.ts`.
**Optional:** `h3` and `nitropack` (peer dependencies), for `@frigear-nu/audience/server`.
::

## Quick setup

::steps

### Install Audience

```bash
pnpm add @frigear-nu/audience
```

### Store a visibility

Add a `visibility` JSON column to your table, in both dialects.

```ts [schema.sqlite.ts]
import type { Visibility } from '@frigear-nu/audience'

visibility: text({ mode: 'json' }).$type<Visibility>(),
```

```ts [schema.postgresql.ts]
visibility: jsonb().$type<Visibility>(),
```

### Filter by viewer

```ts [server/routes/faq/groups.get.ts]
import { isVisible, narrowVisibility, parseVisibility } from '@frigear-nu/audience'
import { resolveViewer } from '@frigear-nu/audience/server'

export default defineEventHandler(async (event) => {
  const principal = await authorize(event, faqAccess.permissions.read)
  const viewer = await resolveViewer(event, {
    hooks: useNitroApp().hooks,
    user: principal.user,
    globalRoles: principal.user ? await getEffectiveRoles(event, principal.user) : [],
  })
  const groups = await listGroups(event)
  return groups.filter(group => isVisible(parseVisibility(group.visibility), viewer))
})
```

::

::callout{color="success" icon="i-lucide-check"}
**What you should see:** a signed-in user gets the groups with an empty visibility, plus the restricted groups their
roles allow. A group restricted to `{ "globalRoles": ["admin"] }` is missing for everyone else.
::

## Options

The package has no options.

## Visibility

A visibility is stored as JSON. Every key is optional.

```ts
type Visibility = {
  public?: boolean // everyone, anonymous visitors included
  globalRoles?: string[] // any of these global roles
  minTeamRole?: { kind: string, role: string } // a team role at or above `role` in the ladder of `kind`
  operationId?: string // takes part in this operation
}
```

`isVisible(visibility, viewer)` answers with these rules, in order:

1. `public: true` is visible to everyone, a `null` viewer included. The other keys are ignored.
2. Anything else needs a signed-in viewer: a viewer whose `userId` is set.
3. An empty visibility (`null`, `undefined`, `{}` or `{ public: false }`) needs nothing more.
4. Every key that is set must hold:
   - `globalRoles`: the viewer holds one of them. An empty list matches nobody.
   - `operationId`: the operation is in `viewer.operationIds`, or the viewer has a team role on a team the operation
     owns.
   - `minTeamRole`: the viewer has a grant of that kind whose role is at or above `role` in `viewer.ladders[kind]`.
     With `operationId` set too, only grants on that operation's teams count.

::caution
Visibility fails closed. A team kind without a ladder, a role missing from the ladder, or stored JSON that does not
match the schema hides the record. `parseVisibility` turns a malformed value into `NOBODY` (`{ globalRoles: [] }`).
::

An empty visibility means signed-in viewers, not everyone. Nothing becomes public by accident: an editor ticks
"public" to publish to anonymous visitors.

### Groups and items

An item can only narrow its group. The FAQ uses it for items in a group, and the help center for articles in a
category.

```ts
narrowVisibility(parent: Visibility | null | undefined, child: Visibility | null | undefined, ladders?: Record<string, readonly string[]>): Visibility
isNarrowerOrEqual(parent: Visibility | null | undefined, child: Visibility | null | undefined, ladders?: Record<string, readonly string[]>): boolean
```

| Parent | Child | Result of `narrowVisibility` |
| --- | --- | --- |
| any | empty | The parent: the item inherits. |
| `public: true` | any | The child. |
| restricted or empty | `public: true` | The parent: a public item cannot widen its group. |
| `globalRoles: A` | `globalRoles: B` | `globalRoles`: the roles in both A and B. |
| `operationId: x` | `operationId: x` | `operationId: x`. A different operation matches nobody. |
| `minTeamRole` | `minTeamRole` of the same kind | The higher of the two roles, read from `ladders`. |
| `minTeamRole` | `minTeamRole` of another kind | Nobody: one visibility cannot hold two kinds. |
| one key | another key | Both keys. |

Intersecting `globalRoles` is stricter than "any of A and any of B" when the lists only overlap. That errs towards
hiding. Without `ladders`, two different roles of one kind match nobody.

`isNarrowerOrEqual` is a key-by-key check for editors. It is `true` when everyone who passes the child also passes the
parent, and for an empty child, which inherits. Use it to warn before saving, and `narrowVisibility` to decide.

### Viewer

A viewer is everything the rules need about the person looking.

```ts
type Viewer = {
  userId: string | number | null // null: anonymous
  globalRoles: string[]
  teamRoles: TeamRoleGrant[]
  operationIds: string[]
  ladders: Record<string, string[]> // team kind → role keys, lowest first
}

type TeamRoleGrant = {
  ownerType: OwnerType
  ownerId: string
  teamId: string
  kind: string
  role: string
  source: 'explicit' | 'mapped'
}
```

`createViewer(partial)` fills in the empty lists. On the server, build it with `resolveViewer` instead.

## Owners

```ts
const OWNER_TYPES = ['operation', 'team', 'user', 'platform'] as const
type OwnerType = typeof OWNER_TYPES[number] | (string & {}) // other modules may add types
type OwnerRef = { type: OwnerType, id: string | null } // id is null for 'platform'
type OwnerLabel = string | Record<string, string> // the shape of Translated in @frigear-nu/ui
```

Tables store an owner as the `ownerType` and `ownerId` columns. [Volunteering](/modules/volunteering#owners) lists
which module answers for each type.

## Server

`@frigear-nu/audience/server` holds the hook contracts and two helpers. Pass `useNitroApp().hooks` to both: a plain
package cannot import Nitro's runtime outside a Nitro build.

```ts
resolveViewer(event: H3Event, options: { hooks: AudienceHookCaller, user: { id: string | number } | null, globalRoles?: string[] }): Promise<Viewer>
resolveOwner(event: H3Event, owner: OwnerRef, options: { hooks: AudienceHookCaller }): Promise<{ owner: OwnerRef, label: OwnerLabel | null, exists: boolean | null }>
```

- **`resolveViewer`** seeds `userId` and `globalRoles`, then calls `audience:viewer:resolve`. Pass the global roles
  from auth's `getEffectiveRoles`. An anonymous visitor gets an empty viewer without the hook.
- **`resolveOwner`** calls `audience:owner:resolve`. `label` and `exists` stay `null` when no module answers for the
  owner type.

Neither helper checks access. Check it with `authorize(event, permission, record)`, and let the owning module add a
[policy](/guide/concepts/auth-and-scopes#policies) for its owner type.

## Hooks

Modules answer these Nitro hooks from a server plugin (`server/plugins/*.ts`). Importing
`@frigear-nu/audience/server` anywhere in the app types them on `NitroRuntimeHooks`.

| Hook | Answered by | Context | What a listener does |
| --- | --- | --- | --- |
| `audience:viewer:resolve` | teams, crew, operations | `{ event, user, viewer }` | Adds to `viewer.teamRoles`, `viewer.ladders` and `viewer.operationIds`. |
| `audience:owner:resolve` | the module that owns `owner.type` | `{ event, owner, label, exists }` | Sets `label` and `exists` when `owner.type` is its own. |

```ts [server/plugins/audience.ts]
import type {} from '@frigear-nu/audience/server'

export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('audience:viewer:resolve', async ({ event, user, viewer }) => {
    if (!user) return
    // crew: the operations this user is crew on
    viewer.operationIds.push(...await listCrewOperationIds(event, user.id))
  })

  nitroApp.hooks.hook('audience:owner:resolve', async (ctx) => {
    // teams: label its own owner type
    if (ctx.owner.type !== 'team' || !ctx.owner.id) return
    const team = await findTeam(ctx.event, ctx.owner.id)
    ctx.exists = Boolean(team)
    ctx.label = team?.name ?? null
  })
})
```

::warning
Identify the user from `ctx.user`, never from the session on `ctx.event`. The session is empty for requests with a
bearer token.
::

These hooks replace per-module visibility hooks such as `faq:visibility` and `help-center:visibility`. A module may
still add an override hook of its own.

---
title: FAQ
description: Short bilingual questions and answers, managed once and shown in Markdown pages, custom pages and the mobile app, with per-group and per-item grants.
---

FAQ holds short questions and answers in groups, such as "Volunteering" or "Membership". [Staff](/guide/concepts/glossary)
write them in both languages under **Admin → FAQ**, decide who may see each group and question, and publish them. A page
then shows a group with one line of Markdown, a custom page fetches it with a composable, and the mobile app can give it a
tab. It replaces the hand-written FAQ cards in page frontmatter. For long articles and onboarding checklists use the
help center instead.

The package is `@frigear-nu/faq`. Who may read a group or an item is a grant list of [Grants](/modules/platform/grants),
and owners follow the [volunteering contracts](/modules/organisation/teams#owners).

## What you get

- **Content components**, registered globally so Markdown (MDC) resolves them: `Faq` (one group), `FaqGrid` and
  `FaqSectionList` (several groups, or inline cards) and `FaqCard`. `FaqCard`, `FaqGrid` and `FaqSectionList` are the
  components the website had in `app/components/content`, moved with the same props and markup.
- **Composables and helpers**: `useFaq`, `useFaqSearch`, `toFaqCardProps`, `useFaqGroupActions`, `useFaqItemActions`
  and the path builders `faqApi`.
- **Admin area** (opt-in, with [Admin](/modules/interface/admin)): a group list at `/admin/faq` and a group page at
  `/admin/faq/:id` with a sortable item list, a settings form and a preview. The sidebar entry needs
  [Menu](/modules/interface/menu).
- **Server routes** (on by default): the groups and answers a viewer may read, a search, and a staff API.
- **Hooks**: `faq:group:updated` and `faq:item:published`.
- **A mobile tab** (opt-in, with [Mobile](/modules/interface/mobile)).
- **Emails.** None.

:module-runtime{server client mobile}

::note
**Installed for you:** [Auth](/modules/identity/auth), [Grants](/modules/platform/grants), [UI](/modules/interface/ui) and
Module Kit.

## Quick setup

::steps

### Install FAQ

```bash
pnpm add @frigear-nu/faq @nuxthub/core
```

### Add it to nuxt.config.ts

List Admin (or Menu) before FAQ, so the pages and the menu entry register.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/admin', '@frigear-nu/faq'],
  faq: {
    settings: {
      pages: { admin: true },
    },
  },
})
```

### Generate the migration

:::warning
Without a [migration](/guide/concepts/glossary) the `faq_groups` and `faq_items` tables do not exist, and every request to
them fails.
:::

```bash
pnpm db:generate
```

### Decide who manages the FAQ

:::warning
Staff routes check permissions through [Authorization](/modules/identity/authorization). Without a role that holds
`faq:manage`, nobody can manage the FAQ. The `admin` and `coordinator` roles hold it when your app defines them.
:::

The module grants `faq:manage` to `admin` and `coordinator`, for the roles your app defines. Give it to a role of your own
by name:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  authorization: {
    roles: {
      editor: { label: 'Editor', grant: ['faq:manage'], inherit: ['user'] },
    },
  },
})
```

::

::callout{color="success" icon="i-lucide-check"}
**What you should see:** a signed-in coordinator opens `/admin/faq`, adds a group, adds a question in Danish and English,
publishes it, and sets the group to public. A page with `::faq{group="membership"}` then shows the group to everyone.
::

## Options

Options go under the `faq` key, in `settings`.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `settings.pages.admin` | `string \| boolean` | off | The staff group list. `true` is `/admin/faq`; a string is a custom path. The group page is `<path>/:id`. Needs Admin. |
| `settings.requiredLocales` | `string[]` | `['da', 'en']` | Languages a question and its answer need before it can be published. |
| `settings.schema` | `boolean` | `true` | Emit `FAQPage` JSON-LD for public groups. `false` turns it off. |
| `settings.contactComponent` | `string` | none | Name of a globally resolvable component the card renders for its `contact`. See [The contact button](#the-contact-button). |
| `settings.contactForm` | `string` | `'contact'` | Slug of the Forms form the built-in contact button opens. |
| `settings.mobileTab` | `boolean` | `false` | Add an FAQ tab to the mobile app. Needs Mobile. |

::note
**The admin pages are opt-in** (`pages.admin: true`), like the admin pages of [Forms](/modules/features/forms) and
[Events](/modules/features/events). The plan for this module had them on by default.
::

## Show a group in Markdown

The components are global, so a content page uses them in MDC without importing anything. A group is fetched by its URL
name (`slug`), and a group the viewer may not read, or one that does not exist, renders nothing.

```md [content/en/pages/membership.md]
::faq{group="membership"}
::

::faq-grid{groups="membership,volunteering"}
::

::faq-section-list{groups="volunteering"}
::
```

| Component | Takes | Renders |
| --- | --- | --- |
| `Faq` | `group` (a slug) | One group as a card. |
| `FaqGrid` | `groups` (slugs, comma separated or an array), `operation`, `items`, `contact`, `public` | The cards in a grid. |
| `FaqSectionList` | The same as `FaqGrid` | The cards one under the other. |
| `FaqCard` | `title`, `description`, `icon`, `to`, `faqs`, `links`, `contact` | One card, from props. |

Each question opens as a collapsible: the question is the button, the answer a quote below it, and an item's buttons
follow the answer. The `contact` prop adds a [contact button](#the-contact-button) to every managed card.

### Inline or managed

`FaqGrid` and `FaqSectionList` take `items` too, exactly the `FaqCardProps[]` the website keeps in page frontmatter, so
existing pages keep working unchanged. A page can mix both: the managed groups come first, then the inline cards.

```md [content/en/pages/board.md]
::faq-grid{groups="board" :items='meta.cards'}
::
```

```yaml [frontmatter]
cards:
  - title: Who is on the board?
    icon: i-lucide-info
    faqs:
      - title: Is it paid?
        details: No, the board is 100% volunteer.
```

Inline cards are not stored anywhere and have no grants. Anything that should be translated in the editor, or
shown only to some people, belongs in a managed group.

## Show a group on a custom page

`useFaq` fetches groups, and `toFaqCardProps` turns one into the props of `FaqCard` in the current language.

```vue [app/pages/volunteers.vue]
<script setup lang="ts">
const { groups, status } = await useFaq(['volunteering', 'roskilde'])
</script>

<template>
  <FaqGrid
    :items="groups.map(toFaqCardProps)"
    :loading="status === 'pending'"
  />
</template>
```

`useFaq(groups, options?)` takes a slug, an array of slugs or a comma separated list (none means every group the viewer
may read), and `{ operationId?, public?, lazy? }`. It returns `{ groups, items, status, error, refresh }`, built on
`useFetch`, so it works with server rendering. Its fetch key includes the signed-in user, so what a restricted group
showed to one person is never reused for the next one after a sign-in or sign-out. With `public: true` it asks for what
visitors read only: the key does not include the user, and the response is cacheable.

For markup of your own, read the groups directly:

```vue
<template>
  <section
    v-for="group in groups"
    :key="group.id"
  >
    <h2>{{ tr(group.title) }}</h2>
    <details
      v-for="item in group.items"
      :key="item.id"
    >
      <summary>{{ tr(item.question) }}</summary>
      <MDC :value="tr(item.answer)" />
    </details>
  </section>
</template>
```

`tr` is `useFaqTranslate()`. A searchable page uses `useFaqSearch`:

```ts
const { q, results, status } = useFaqSearch() // bind `q` to an input; `results` follow, debounced
```

`useFaqSearch(options?)` takes `{ delay?, minLength?, operationId?, public? }`. A slower earlier answer never replaces a
newer one, and a query shorter than `minLength` (2) clears the results.

## The contact button

A card's `contact` prop (`{ label, initial }`) adds a button at the bottom of the card. What it opens is decided by the
host:

1. **`contactComponent`**: the name of a component the card renders instead, with the card's `label` and `initial`. It
   must be resolvable by name, so register it globally (a component in `components/global/`, or `global: true` in
   `addComponent`). The website sets `'ContactFormModal'`, which keeps today's behaviour.
2. **Forms installed, no `contactComponent`**: a built-in `FaqContactButton` opens a modal with the form of the
   `contactForm` option (`contact` by default). It does not prefill the form; use a `contactComponent` for that.
3. **Neither**: no button.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  faq: { settings: { contactComponent: 'ContactFormModal' } },
})
```

## Search engines

Public groups add `FAQPage` JSON-LD to the page head, listing the questions and answers anonymous visitors can read, so
search engines can show them. Restricted groups and items are never in it. It comes from `useFaqCards`, which `Faq`,
`FaqGrid` and `FaqSectionList` use for managed groups. A page has **one** `FAQPage` block however many components it uses:
every component adds its public questions to the page's block, and a question shown twice is listed once (by item id).
Answers are converted to plain text first (links keep their text, Markdown marks and MDC component fences are removed); it
is a simple strip, not a Markdown parser. Turn it off with `settings.schema: false`.

## Who sees what

Every group and item stores who may read it as a grant list (`grants`) of [Grants](/modules/platform/grants). Any one
grant admits, and an empty list admits nobody: it is never "every signed-in person".

| Grant | Who reads it |
| --- | --- |
| `{ kind: 'public' }` | Everyone, without signing in. |
| `{ kind: 'role', role }` | Signed-in people holding that global role. |
| `{ kind: 'team', teamId, minRole }` | Signed-in people with at least that role on the team (with [Teams](/modules/organisation/teams)). |
| `{ kind: 'operation', operationId }` | Signed-in people who take part in the operation (with [Operations](/modules/volunteering/operations)). |
| `[]` | Nobody. Staff still see the group in the admin area. |

A new group starts with `[]`, so it shows to nobody until you add who may read it.

An item can only narrow its group. An item with `grants: null` inherits its group; an item with a list is read only by
people who read the group and match the item's list. So a public item in a restricted group stays hidden from visitors,
and a role-only item in a public group hides from everyone without the role. Only `published` items reach the public
API, whoever asks.

- **Through a permission.** Reads go through `grantsCanRead(event, 'faq:read', record)`: a group (or item) with a
  `public` grant is served without sign-in, and everything else goes through `faq:read` and its policy, which evaluates
  the record's grants. A token without `faq:read` sees what a visitor sees.
- **Checked on write.** The body takes the shape of a list; the handler checks it with `grantsValidate`, so an unknown
  kind, an invalid grant (`{ kind: 'role' }` without a role) or a team or operation that does not exist is a `400`. A grant
  that is already stored is not checked again, so a group whose team was deleted can still be edited. A stored grant of a
  kind no installed module knows admits nobody.
- **Owners.** A group can belong to the platform (the default) or to an operation or team. The owner is checked through
  Teams' `teams:owner:resolve` hook (Teams answers `team` and `operation`), so an unknown id is `400`. An owner type
  nobody answers cannot be verified and is refused as well. `?operation=<id>` on the public list returns the groups owned
  by that operation.

## Publish rule

An item is created as a **draft**. Publishing needs text in every language of `requiredLocales` (`da` and `en` by default)
in both the question and the answer; otherwise the route answers `409` with the code `missing_translations`, and
`data.missing` lists what is lacking:

```json
{ "missing": [{ "field": "question", "locales": ["da"] }] }
```

A plain string counts as no language: it is one text for every language, and the rule exists to make sure each language
was written on purpose. A published item keeps the rule: an edit that removes a language is refused the same way. The
editor shows what an item still lacks while you type.

## Admin

With Admin installed and `pages.admin` set:

| Page | Path | What staff do |
| --- | --- | --- |
| Group list | `/admin/faq` | Search groups, see how many questions are published, add, edit and delete groups. |
| Group page | `/admin/faq/:id` | Add and edit questions, publish and unpublish, reorder, change the group's settings, preview it. |

- **Questions** are a sortable list. Drag a row by its handle, or use the up and down buttons. The new order is saved with
  one request and shown at once; a refused order puts the list back.
- **Add and edit** open a slideover with the question and answer in every language (the answer has a Markdown preview), an
  icon, up to ten buttons and who may read it. A new question is a draft.
- **Who can see it**: Grants' `<GrantsEditor>`, with every installed grant kind in its "Add" menu. An item has a "Same as
  the group" switch; turned off, it starts an empty list that narrows the group.
- **Preview** renders the published questions in the same `FaqCard` the site uses.
- Deleting a group or a question asks first and says what else goes with it.

The sidebar entry (`faq-admin`, in `admin.nav`, icon `i-lucide-message-circle-question-mark`) shows to people with
`faq:manage`. Hiding it is not access control: every route checks `faq:manage` itself.

## Permissions

| Name | Flags | Held by default | What it allows |
| --- | --- | --- | --- |
| `faq:manage` | | `admin` and `coordinator` | Create and edit groups and items, publish, reorder and delete. |
| `faq:read` | implicit | every signed-in user | Read the groups and answers you are granted. |

- **Scope:** a token may use the named scope `faq` or `faq:read` itself. Either lets it read the FAQ and is refused every
  staff route.
- **Policy on `faq:read`.** The record (a group or an item) is readable when its grants admit the user. Public groups
  need no sign-in at all. A token without `faq:read` is treated as anonymous.
- **A bearer token that is invalid** is treated as no token: the caller sees what an anonymous visitor sees, not a `401`,
  because the public routes serve visitors.
- **Unreadable is 404.** `GET /api/faq/groups/:slug` answers `404` for a group the caller may not read, the same as for an
  unknown slug.

## Routes

Typed path builders are exported as `faqApi` from `@frigear-nu/faq/api`.

| Route | Who | What it does |
| --- | --- | --- |
| `GET /api/faq/groups` | Everyone | The groups the viewer may read, each with its published items they may read. `?slugs=a,b` (in that order), `?operation=<id>`, `?public=1`. |
| `GET /api/faq/groups/:slug` | Everyone | One group, or `404`. |
| `GET /api/faq/search?q=` | Everyone | Published items whose question or answer contains `q` in any language, 50 at most. `?operation=`, `?public=1`. |
| `GET /api/admin/faq/groups` | `faq:manage` | Paginated list with counts, `q` (title in every language, and the URL name) and sort. |
| `POST /api/admin/faq/groups` | `faq:manage` | Create a group. `409` when the URL name is taken, `400` for an unknown owner. |
| `GET` / `PATCH` / `DELETE /api/admin/faq/groups/:id` | `faq:manage` | Read, edit or delete a group (its items go with it). |
| `GET /api/admin/faq/groups/:id/items` | `faq:manage` | Every item of a group, drafts included. |
| `POST /api/admin/faq/groups/:id/items` | `faq:manage` | Add a draft item at the end of the group. |
| `POST /api/admin/faq/groups/:id/reorder` | `faq:manage` | Body `{ itemIds }`: exactly the group's item ids, each once, or `400 invalid_order`. |
| `PATCH` / `DELETE /api/admin/faq/items/:id` | `faq:manage` | Edit or delete an item. |
| `POST /api/admin/faq/items/:id/publish` | `faq:manage` | Publish. `409 missing_translations` when a required language is missing. |
| `POST /api/admin/faq/items/:id/unpublish` | `faq:manage` | Back to a draft. |

- **Search ignores case.** The term is lowercased in JavaScript, which knows Danish letters. postgresql lowercases the stored
  text too. sqlite's `lower()` and `LIKE` only fold ASCII, so the stored text is compared with the lowercase and the
  uppercase term (`øl` finds `ØL` and `Øl`); a stored text that mixes cases of non-ASCII letters differently from the term can
  be missed there. Search reads matches in batches until it has 50 visible hits or none are left.
- **Deleting and reordering use single statements.** A group's items go with it through the foreign key, and a reorder is one
  `UPDATE` with a `CASE`, so neither leaves a half-done change. No transaction is used, because NuxtHub's D1 driver has none.
- **`?public=1`** ignores who asks: it never reads the session, answers the same to everyone, and sets
  `Cache-Control: public, max-age=60, stale-while-revalidate=300`. The other answers are `private, no-store`.
- **Reserved URL names:** `search`, `groups`, `items`, `new`, `edit`, `admin` and `api`.
- **Responses** are allowlisted DTOs with ISO dates. The public DTO has no status, grants or audit data; an item says
  whether it `public`ly shows to visitors. Create and edit take `slug`, `title`, `description`, `icon`, `owner`
  (`{ type, id }`), `grants` and `sort` for a group, and `question`, `answer`, `icon`, `links` (`{ label, to, icon? }`,
  a path, `https://`, `mailto:` or `tel:` target) and `grants` (`null` inherits the group) for an item. `answer` is Markdown or MDC per language.
- **Errors** use the module toolkit's shape: `statusMessage` is the message, `data.code` a stable code
  (`missing_translations`, `invalid_order`, `conflict`, `not_found`, `forbidden`, `insufficient_scope`).

## Hooks

Your app answers these [Nitro](/guide/concepts/glossary) hooks from a server plugin (`server/plugins/*.ts`).

| Hook | When | Payload |
| --- | --- | --- |
| `faq:group:updated` | After a group was created, edited or deleted, or an item in it was added, edited, deleted, reordered, published or unpublished. A patch that changes nothing fires nothing. | `{ event, group }` |
| `faq:item:published` | After an item went from draft to published. Publishing a published item fires nothing. | `{ event, group, item }` |

`group` and `item` are the staff DTOs (`AdminFaqGroupDto`, `AdminFaqItemDto`); `group` is the state after the change, and
for a delete the last state. Purge a cache from `faq:group:updated`:

```ts [server/plugins/faq-cache.ts]
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('faq:group:updated', async ({ group }) => {
    // Key by `group.id`: the URL name can be edited, the id never changes.
    await useStorage('cache').removeItem(`faq:${group.id}`)
  })
})
```

Purging does not reach responses the browser or a CDN already holds: `?public=1` answers are cacheable for a minute
(`max-age=60`, then up to five minutes stale), so a published change can take that long to show on a page that asks for
them. That is deliberate; the other answers are never cached.

## Database

Tables the module adds. Generate and commit a [migration](/get-started/database#migrations) after installing.

| Table | Holds |
| --- | --- |
| `faq_groups` | `faq_` id, a unique `slug`, Translated `title` and `description`, `icon`, `ownerType` and `ownerId` (`platform` by default, no id), `grants` (JSON, `[]` by default), `sort` and the dates. Index on `(ownerType, ownerId)`. |
| `faq_items` | `fqi_` id, `groupId` (deleted with the group), Translated `question` and `answer`, `icon`, `links`, `status` (`draft` or `published`), `grants` (JSON, `null` inherits the group), `sort`, `updatedBy` and the dates. Index on `(groupId, sort)`. |

Translated texts are a string or a `{ da, en }` map.

## Translations

Override any string in your app's `i18n/locales/<code>.json`. The module registers `da` and `en` files under `faq.*`. See
[overriding module strings](/modules/platform/module-kit/i18n#overriding-module-strings-in-your-app). Without
`@nuxtjs/i18n`, the pages use `en`.

```json
{ "faq": { "admin": { "statuses": { "draft": "Not published" } } } }
```

Key groups: `menu.*`, `permissions.*`, `scopes.*`, `mobile.*` and `admin.*` (with `admin.grants*`,
`admin.ownerTypes.*` and `admin.statuses.*`).

## Mobile

With `settings.mobileTab: true` and [Mobile](/modules/interface/mobile) installed, the module adds an FAQ tab (`/faq`): every
group the signed-in person may read as cards, with a search above them. It is minimal on purpose; a richer help tab
comes with the help center.

## Testing notes

The e2e fixture runs on sqlite. The postgresql branch of the search (`jsonb_each_text`) and the postgresql
unique-violation code (`23505`, covered by a unit test of the error check only) have no end-to-end test. Grant kinds
other modules register are tested through a `club` kind the fixture registers itself, and owners through a fixture
listener of `teams:owner:resolve`, standing in for Teams and Operations.

## Not in this release

- **Website wiring.** Installing the module in `apps/website`, setting `contactComponent: 'ContactFormModal'`, deleting
  the website's copies of `FaqCard`, `FaqGrid` and `FaqSectionList`, and moving the frontmatter cards of `board.md` and
  `funding.md` into groups: a separate pull request, so the website's migrations are generated once.
- **Help center.** Showing FAQ groups in help categories. Help center depends on FAQ, never the other way round.
- **A Nuxt Content source** for public groups.
- **Dashboard.** An "Unanswered questions" item can come later from the inbox. FAQ adds none.
- **A role picker everywhere.** The `role` grant field lists roles when it can read the Authorization roles admin, and
  falls back to typed tags for editors who cannot.

## Open questions

- Should inline frontmatter cards stay long term, or should every page move to managed groups after the website
  migration? Today both work side by side.
- A published item that is edited stays published. Should an edit to a published item go back to review instead, or keep a
  history of who changed what? Only `updatedBy` is stored.
- Does a group owned by an operation need to appear in the operation's own pages, the way a map would? Nothing reads it
  yet beyond `?operation=`.

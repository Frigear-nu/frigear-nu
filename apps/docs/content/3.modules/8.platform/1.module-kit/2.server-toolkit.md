This page lists the helpers your module's route handlers use, so every module's API answers the same way. It is for
module authors, and the rules for using them are in [HTTP routes](/guide/best-practices/http-routes). Set up the module
first: [Overview](/modules/platform/module-kit).

Import the helpers from `@frigear-nu/module-kit/server`. They are not auto-imported, so they never clash with h3's own
helpers.

## Registering routes

`addModuleRoutes` registers all of a module's routes from one table in `setup()`. It comes from
`@frigear-nu/module-kit/utils`, not `/server`.

```ts
function addModuleRoutes(
  resolver: Resolver,
  routes: Array<{ method: 'get' | 'post' | 'put' | 'patch' | 'delete', path: string, file: string }>,
  options: { base: string },
): void
```

`file` is relative to `./runtime/server/routes/`. `path` is joined onto `base`, `''` is `base` itself, and a path that
starts with `/` ignores `base`. [Registering routes](/guide/best-practices/http-routes#registering-routes) has a full
example.

## Errors

Each helper returns an h3 error to `throw`, with the message in `statusMessage` and a snake_case code in `data.code`.
[Errors](/guide/best-practices/http-routes#errors) has the status and code of each, and examples.

| Helper | Purpose |
| --- | --- |
| `apiError(status, code, message, data?)` | Any status and code. |
| `badRequest`, `forbidden`, `notFound`, `conflict`, `notConfigured` | One status each, each with a default message. |
| `validationError(issues, message?)` | A 400 with one issue per field in `data.issues`. |

Two requests can pass a "slug is free" check together, so the unique index decides. Classify the database error and
answer the loser with the same 409:

| Helper | `true` for |
| --- | --- |
| `isUniqueViolation(error)` | A unique or primary-key violation: postgres `23505`, sqlite `SQLITE_CONSTRAINT_UNIQUE` / `_PRIMARYKEY`, D1's "UNIQUE constraint failed". |
| `isForeignKeyViolation(error)` | A foreign-key violation: postgres `23503`, sqlite `SQLITE_CONSTRAINT_FOREIGNKEY`, D1's "FOREIGN KEY constraint failed". |

Both follow the error's `cause` chain, since drizzle wraps driver errors. Any other constraint (NOT NULL, check) is
neither, so rethrow it.

```ts
const [row] = await db.insert(schema.teams).values(values).returning().catch((error) => {
  if (isUniqueViolation(error)) throw conflict('A team with this slug already exists.', { field: 'slug' })
  throw error
})
```

## Params

Two zod schemas validate ids the same way in every module. Pass them to h3's `getValidatedRouterParams`.

| Schema | Accepts |
| --- | --- |
| `idParams(name = 'id')` | A non-empty string. |
| `intIdParams(name = 'id')` | A positive integer, coerced from the path. |

```ts
const { id } = await getValidatedRouterParams(event, idParams().parse)
const { tokenId } = await getValidatedRouterParams(event, idParams('tokenId').parse)
const { id: userId } = await getValidatedRouterParams(event, intIdParams().parse)
```

## Pagination

These helpers turn a list query into a page, in the query keys that `useTableQuery` sends.
[Pagination](/guide/best-practices/http-routes#pagination) has a full list handler.

| Helper | Returns |
| --- | --- |
| `pageQuery({ sort, defaultSort?, defaultOrder?, defaultPageSize?, maxPageSize?, filters? })` | The zod schema of a list query. |
| `pageRange(query)` | `{ limit, offset }` for the query's page. |
| `paginate({ items, total, query })` | `Page<T>`: `{ items, total, page, pageSize }`. |
| `orderByQuery(columns, query, { tiebreaker })` | An `orderBy` from `query.sort` and `query.order`. |
| `likeContains(column, value)` | A case-insensitive "contains" search. |
| `likeEscaped(column, pattern)`, `escapeLike(value)` | The search behind it, with `%` and `_` escaped. |

**`pageQuery`** accepts `page` (from 1), `pageSize` (default 20, at most 100), `q`, `sort`, `order` and your `filters`
keys. `sort` defaults to `defaultSort` or the first name, and `order` to `desc`.

**`orderByQuery`** always sorts by the tiebreaker last, descending, so pages stay stable. Pass the id.

**`likeContains`** works on both [dialects](/guide/concepts/glossary). A `%` or `_` in the search is matched literally.

## Searching names and other texts

sqlite's `lower()` and `LIKE` fold ASCII letters only, so `likeContains` misses `Ølbar` for `ølbar`. A list that searches
names, titles or other free text keeps a normalised search column instead: the text folded in JavaScript on every
write, and searched with the term folded the same way.

| Helper | Purpose |
| --- | --- |
| `searchText(...values)` | The column's value: every text of `values` (a translated `{ da, en }` text gives every language) in Unicode lowercase (NFC), one per line. |
| `searchContains(column, term)` | The column contains `term`, folded the same way, with `%` and `_` matched literally. |
| `foldSearch(value)` | The folding on its own. |

Declare the column the same way in both schema files (they import nothing but drizzle), and write it wherever one of
its sources is written:

```ts [schema.sqlite.ts and schema.postgresql.ts]
searchText: text().notNull().default(''),
```

```ts
await db.insert(schema.operations).values({ ...values, searchText: searchText(values.name, values.slug) })
if (patch.name !== undefined) values.searchText = searchText(patch.name)
conditions.push(searchContains(schema.operations.searchText, query.q))
```

The migration that adds the column backfills existing rows in SQL. `lower()` folds ASCII only there too, so a stored
`Ø`, `Æ` or `Å` keeps its case until the row is next written or [`search:reindex`](#rebuilding-the-columns-searchreindex)
runs. Emails and slugs are stored lowercase already:
`likeContains` is enough for them.

| Column | Holds | Searched by |
| --- | --- | --- |
| `users.searchText` | the name | `searchUserRefs`, the users admin list, the crew list, inbox assignees |
| `operations.searchText` | the name in every language and the slug | the operations admin list |
| `teams.searchText` | the name in every language | the teams admin list |
| `help_articles.searchText`, `searchBody` | the title in every language and the slug; the body in every language | the help center search (title or body) and its admin list (title or slug) |
| `inbox_threads.searchText` | the subject (cleared when a thread is anonymised) | the inbox thread list |

### Rebuilding the columns: `search:reindex`

The Nitro task `search:reindex` recomputes every registered search column with the code the module runs on write, so
it fixes the rows a SQL backfill left with a capital `Ø`, `Æ` or `Å`, and the rows written before a change to how a
column is computed. It walks each table in pages ordered by `id`, rewrites only the rows whose value differs, and
returns and logs the counts per table (`scanned`, `updated`). It is idempotent: run it again and it updates nothing.
Every statement binds a handful of parameters, well under D1's limit of 100.

A module registers its table in `setup()` with `registerSearchIndex` (`@frigear-nu/module-kit/utils`), which adds the
task (and Nitro's `experimental.tasks`) with the first registration. The handler file's default export says how a
row's columns are computed, with the module's own write helper:

```ts [module.ts]
registerSearchIndex(nuxt, { name: 'operations', handler: resolver.resolve('./runtime/server/search-index') })
```

```ts [runtime/server/search-index.ts]
import { schema } from '@nuxthub/db'
import { defineSearchIndex } from '@frigear-nu/module-kit/server'
import { operationSearchText } from './utils/operations-search'

export default defineSearchIndex({
  table: schema.operations, // needs an `id` column
  columns: operation => ({ searchText: operationSearchText(operation) }),
})
```

Every column of the table above is registered this way (`users`, `operations`, `teams`, `help_articles`,
`inbox_threads`). `reindexSearchIndex(db, definition)` (`@frigear-nu/module-kit/server`) is the same walk for one
table, and `runSearchReindex()` / `fixtureSqlite(file)` (`@frigear-nu/module-kit/testing`) run the task in a `dev: true`
fixture and write a stale value into its sqlite file first.

**Running it in development.** With the dev server running, from the repo root:

```bash
pnpm --filter ./apps/website exec nuxt task run search:reindex
# or, the endpoint the CLI calls:
curl http://localhost:3000/_nitro/tasks/search:reindex
```

**Running it on Cloudflare Workers.** Nitro serves `/_nitro/tasks` and `nuxt task run` in development only: a deployed
worker has no endpoint that starts a task. A task runs there from a cron trigger, through `nitro.scheduledTasks`
(the website copies those crons into the worker's `triggers.crons` at build time). To run the reindex once, schedule
it in the app's `nuxt.config.ts`, deploy, let the trigger fire, and read the counts in the worker's logs
(`wrangler tail` or the dashboard's logs); then remove the entry and deploy again. Leaving it scheduled is harmless,
since a run that finds nothing to fix only reads.

```ts [nuxt.config.ts]
nitro: {
  scheduledTasks: { '30 4 * * *': ['search:reindex'] }, // add next to any existing crons
},
```

## Links that leave the app

Emails and pushes cannot ask `useLocaleLink` for the locale prefix. `localizePath(path, locale, i18n)` adds it from
the `@nuxtjs/i18n` options a module records at build time (`LocaleRouting`: `strategy`, `defaultLocale`, `locales`):
the prefix of `locale` with `prefix` and `prefix_and_default`, and with `prefix_except_default` unless it is the
default. `da-DK` and `en_GB` match their language; an unknown locale, no locale or no i18n leaves the path as it is.

```ts
const url = `${origin}${localizePath('/crew/status', user.locale, config.i18n)}`
```

## Lookups by a list of ids

Cloudflare D1 binds at most 100 parameters per statement, so an `inArray` lookup by a list of any length runs in
chunks.

| Helper | Purpose |
| --- | --- |
| `chunkParams(values, size?)` | `values` in lists of at most `size` (`D1_PARAM_CHUNK`, 90, by default). An empty list is no chunks. |
| `inChunks(values, query, size?)` | Runs `query(chunk)` once per chunk, one after the other, and joins the rows. |

```ts
const rows = await inChunks(teamIds, ids => db.select().from(schema.teams).where(inArray(schema.teams.id, ids)))
```

Lower `size` when the rest of the statement binds more than a few parameters, such as a multi-row insert
(100 divided by the columns per row). Joining chunks with `or(...)` in one statement binds them all again, so it does
not help.

## Responses and helpers

[Responses](/guide/best-practices/http-routes#responses) explains when to use each response helper.

| Helper | Purpose |
| --- | --- |
| `created(event, dto)`, `noContent(event)`, `isoDate(value)` | 201 with a DTO, 204 with no body, and dates as ISO strings. |
| `uniqueCopySlug(base, exists)` | The first free `<base>-copy`, `<base>-copy-2`, and so on. |
| `resolveSameOriginUrl(event, url, { fallback?, name? })` | A return URL on the request's origin, `fallback` when empty, `400` for another origin. |
| `sameOriginUrl(input, origin)` | The same check without an event. Returns the normalised URL, or `null`. |
| `applyBearerCors(event, options)` | CORS for callers with an access token on other origins. See [Bearer CORS](#bearer-cors). |
| `matchesPathPrefix(pathname, prefixes)` | Whether a path is under a prefix. `/api/` matches `/api` and `/api/x`, not `/apis`. |

## Bearer CORS

A browser app on another origin needs CORS headers to call your API with an access token. Examples are the
`capacitor://localhost` webview of a mobile app, or a single-page app. It must never get cookies across origins.
`applyBearerCors` adds exactly those headers, from a middleware, for the paths you choose:

```ts [server/middleware/api-cors.ts]
import { applyBearerCors, matchesPathPrefix } from '@frigear-nu/module-kit/server'

export default defineEventHandler((event) => {
  if (!matchesPathPrefix(getRequestURL(event).pathname, ['/api/'])) return
  const preflight = applyBearerCors(event, {
    origins: ['capacitor://localhost', 'https://localhost'],
    methods: ['GET', 'POST', 'PATCH', 'DELETE', 'OPTIONS'],
    allowHeaders: ['authorization', 'content-type', 'accept'],
    exposeHeaders: ['www-authenticate'],
  })
  if (preflight) return ''
})
```

| Option | Default | Header |
| --- | --- | --- |
| `origins` | required | `Access-Control-Allow-Origin`: the request's `Origin`, when listed exactly. `*` never matches. |
| `methods` | required | `Access-Control-Allow-Methods`, as an array or a string. |
| `allowHeaders` | `authorization, content-type` | `Access-Control-Allow-Headers`. |
| `exposeHeaders` | none | `Access-Control-Expose-Headers`, such as `www-authenticate`. |
| `maxAge` | `600` | `Access-Control-Max-Age`, in seconds. |

- It always adds `Vary: Origin`, so caches keep one response per origin.
- It sets the CORS headers only for a listed origin.
- It never sends `Access-Control-Allow-Credentials`.
- It answers an `OPTIONS` request from a listed origin with `204` and returns `true`, so the middleware ends it. Any
  other request returns `false` and continues.

The `cors.paths` option of [OAuth Server](/modules/identity/oauth-server) and
[OAuth Resource](/modules/identity/oauth-resource#cors) both use it.

## Testing routes

`@frigear-nu/module-kit/testing` has two helpers for end-to-end tests against a
[test fixture](/guide/concepts/glossary) started with `setup()` from `@nuxt/test-utils/e2e`.

| Helper | What it does |
| --- | --- |
| `apiClient({ cookie?, bearer? })` | Acts as one caller. |
| `.json<T>(method, path, body?)` | Resolves with the parsed body of a 2xx response, or `null` for 204. Rejects otherwise. |
| `.fetch(method, path, body?)` | Resolves with the raw `Response`, whatever its status. |
| `expectApiError(promise, status, code?)` | Asserts the request failed with `status`, and `data.code` when given. Resolves with the error body. |

[Testing routes](/guide/best-practices/http-routes#testing-routes) has an example.

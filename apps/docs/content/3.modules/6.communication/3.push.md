---
title: Push
description: Register phones, send push notifications to them, and let every user choose email, SMS or push for each kind of message.
---

Push lets your app reach a person's phone. The mobile app registers its device, your server code sends a push notification
to it, and a Notifications page lets each user choose which channels may reach them: email, SMS or push. A helper,
`notifyUser`, reads those choices and sends on the channels the user allows, so no module sends email, SMS or push on its
own.

The package is `@frigear-nu/push`. It sends to Android through Firebase Cloud Messaging (FCM) and to iOS through the Apple
Push Notification service (APNs). It talks to FCM with `fetch` and to APNs with `node:http2`, each with a signed token, so no provider SDK is installed. iOS
delivery therefore needs a Node runtime (see [APNs needs HTTP/2](#apns-needs-http2)).

## What you get

- **Server routes** (server mode, on by default): register, list and remove the caller's devices, and read and change the
  caller's channels. Staff routes list a user's devices and send a test push.
- **Server helpers** (server mode): `sendPush`, `notifyUser` and the `extendNotificationTopics` build-time function.
- **Account page** (server mode): `/account/notifications`, a table of every kind of message with a switch per channel.
- **Admin tab** (with [Admin](/modules/interface/admin) and [Widget](/modules/interface/widget)): a Devices tab on the
  admin user page, with a Send test push action.
- **Device side** (mobile): `usePushDevice()` and a plugin that registers the device when someone signs in, for a Capacitor
  app that uses [Mobile](/modules/interface/mobile).

:module-runtime{server client mobile}

::note
**Installed for you (server mode):** `@frigear-nu/module-kit`, [Auth](/modules/identity/auth),
[Users](/modules/identity/users), [Notify](/modules/communication/notify) and [UI](/modules/interface/ui).

**You add:** `@nuxthub/core` (server mode), and `@capacitor/push-notifications` in the mobile app.

**Optional:** [Admin](/modules/interface/admin) and [Widget](/modules/interface/widget) for the admin tab,
[Menu](/modules/interface/menu) and [Account](/modules/identity/account) for the account menu item, and
[Mobile](/modules/interface/mobile) for registration.

**In client mode** (a mobile app without a server) Push installs only Auth and Module Kit. It adds no tables, routes or
pages, and pulls in no server module.
::

## Two modes

Push follows the app's `authentication.mode`, like [Authorization](/modules/identity/authorization).

| | Server mode (the default) | Client mode (the mobile app) |
| --- | --- | --- |
| Where | The app that has the database and the routes | The Capacitor app that signs in at an issuer |
| Adds | Tables, routes, access, topics, the account page, the admin tab, `sendPush`, `notifyUser` | `usePushDevice()` and the sign-in plugin |
| Needs | `@nuxthub/core`, Users, Notify | Mobile (optional) and `@capacitor/push-notifications` |

The mobile app registers its device with the server's routes through its bearer token. The server sends the pushes.

## Quick setup

::steps

### Install Push on the server

```bash
pnpm add @frigear-nu/push @nuxthub/core
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/push'], // installs Users, Auth and Notify for you
})
```

:::warning
Without a [migration](/guide/concepts/glossary) the `push_devices` and `push_channel_preferences` tables do not exist, and
every route fails.
:::

### Generate the migration

```bash
pnpm db:generate
```

### Register the topics your module sends

A topic is one row of the Notifications page. A module adds its topics in its own `setup()`:

```ts [src/module.ts]
import { extendNotificationTopics } from '@frigear-nu/push/utils'

extendNotificationTopics(nuxt, [{
  id: 'shifts.reminder',
  label: { da: 'Vagtpåmindelser', en: 'Shift reminders' },
  defaults: { email: true, sms: false, push: true },
}])
```

### Send a notification

```ts [server/routes/api/remind.post.ts]
export default defineEventHandler(async (event) => {
  const result = await notifyUser(event, 42, {
    topic: 'shifts.reminder',
    email: { subject: 'Your shift tomorrow', body: '<p>You work 18:00 to 23:00.</p>' },
    sms: { body: 'You work 18:00 to 23:00.' },
    push: { title: 'Your shift tomorrow', body: 'You work 18:00 to 23:00.', url: '/shifts/42' },
  })
  return result // { channels: ['email', 'push'], skipped: { sms: 'disabled' } }
})
```

::

::callout{color="success" icon="i-lucide-check"}
**What you should see:** with no credentials the `log` driver writes the push to the server log, and the email goes
through your Notify email driver. `/account/notifications` lists the topic with its three switches.
::

## Credentials

Without credentials `sendPush` only writes to the server log (the `log` driver), so development needs no setup. Set the
credentials as private runtime config through environment variables:

| Variable | What it is |
| --- | --- |
| `NUXT_PUSH_DRIVER` | `log` or `providers`. Unset: `providers` once any credentials are set, otherwise `log`. |
| `NUXT_PUSH_FCM_SERVICE_ACCOUNT` | The whole service account JSON of your Firebase project (Project settings, Service accounts). |
| `NUXT_PUSH_APNS_KEY_ID` | The key id of your APNs authentication key (`.p8`). |
| `NUXT_PUSH_APNS_TEAM_ID` | Your Apple developer team id. |
| `NUXT_PUSH_APNS_TOPIC` | The app's bundle id, for example `nu.frigear.app`. |
| `NUXT_PUSH_APNS_PRIVATE_KEY` | The `.p8` key. Literal `\n` stand for line breaks, so it fits one line. |
| `NUXT_PUSH_APNS_SANDBOX` | `true` for development builds of the app: sends to `api.sandbox.push.apple.com`. |
| `NUXT_PUSH_TIMEOUT_MS` | How long one provider request may take. Default `10000`. A request that takes longer counts as failed. |

How the providers authenticate:

- **FCM** (HTTP v1): Push signs a short JWT (RS256) with the service account key, exchanges it for an OAuth access token
  and keeps the token until a minute before it expires. It sends to
  `https://fcm.googleapis.com/v1/projects/<project_id>/messages:send`.
- **APNs**: Push signs a JWT (ES256) with the key id and team id, keeps it for 50 minutes and sends to
  `https://api.push.apple.com/3/device/<token>` over HTTP/2, on one session per host that it reuses and closes when it
  idles or fails.

### APNs needs HTTP/2

APNs refuses HTTP/1.1, and the global `fetch` of Node speaks only HTTP/1.1. So Push sends to APNs through `node:http2`,
which it imports when the first iOS push goes out.

::caution
**Cloudflare Workers have no `node:http2` client.** There every iOS push fails (it counts as `failed`, never as a dead
token) and Push logs the reason once. Send iOS pushes from a Node runtime, or through a relay: call
`setPushHttp2Transport(transport)` from a Nitro plugin with a function that sends the request
(`{ origin, path, headers, body, timeoutMs }`) to your relay and answers `{ status, body }`. FCM only needs `fetch` and
works on Workers.
::

### Timeouts, dead tokens and misconfiguration

- **Timeouts.** Every provider request is aborted after `NUXT_PUSH_TIMEOUT_MS` (10 seconds). A timeout counts as
  `failed`, never as dead, and the next push tries again.
- **FCM dead tokens.** A device is revoked only for `UNREGISTERED`, or `INVALID_ARGUMENT` about the registration token
  itself. A bare `404` or `NOT_FOUND` can be a wrong project, so it is only `failed`.
- **APNs dead tokens.** A device is revoked for `410 Unregistered`. `400 BadDeviceToken` also means a sandbox token sent
  to production (or the other way round), so when **every** iOS device of one call gets it, none is revoked and a warning
  names `push.apns.sandbox` in the log. With a single iOS device a truly dead token is therefore never revoked: it fails
  until another iOS device of the same call is accepted.
- **One device failing never fails the call**, and a revoked device is not sent to again.
- **Misconfiguration is loud.** A service account that is not valid JSON, or an APNs key that cannot be read, makes
  `sendPush` throw instead of falling back to the `log` driver, so a broken deployment is noticed. The log driver is only
  chosen when no credentials are set at all.

## Options

| Option | Type | Default | What it does |
| --- | --- | --- | --- |
| `push.settings.driver` | `'log' \| 'providers'` | unset | How `sendPush` delivers. `NUXT_PUSH_DRIVER` overrides it. |
| `push.settings.pages.notifications` | `boolean \| string` | `true` | The account page. `true` mounts it at `/account/notifications`, a string at that path, `false` leaves it out. |
| `push.settings.autoRegister` | `boolean` | `true` | Register the device as soon as someone is signed in. `false` leaves it to your app. |

## Sending

### sendPush

```ts
sendPush(event, { userIds: [42], title: 'Shift tomorrow', body: 'You work 18:00', url: '/shifts/42', data: { shiftId: '42' } })
  // → { sent: 1, failed: 0, revoked: 0 }
```

`sendPush` sends to every active device of the users. `url` is a path in the app, which opens when the notification is
tapped. `data` values must be strings. It returns how many devices the provider accepted, how many failed, and how many
tokens were dead and are now revoked.

`title` and `body` can be one text per locale, `{ da: 'Vagt i morgen', en: 'Shift tomorrow' }`: each device gets the text for
the locale it registered with (`da-DK` finds `da`), else English. `notifyUser` takes the same for its `push` content.

With the `log` driver every device counts as sent. It writes the push title and the user and device ids to the server
log, never the body, and warns once when it is active in production, where it almost always means credentials are
missing.

### notifyUser

```ts
notifyUser(event, userId, { topic, email?, sms?, push? }): Promise<{ channels, skipped }>
```

`notifyUser` sends on a channel when all of these hold:

1. The topic offers the channel, and the user's choice (or the topic's default, until they choose) has it on.
2. You passed content for it.
3. The user can be reached: an email address, a phone number for SMS, a registered device for push.

Email goes through `dispatchEmailNotification` and SMS through `dispatchSMSNotification` from
[Notify](/modules/communication/notify), so the host app's drivers decide how they are delivered. An error on one channel is
logged and does not stop the others. An unknown topic throws: register it with `extendNotificationTopics`.

`skipped` says why a channel did not go out: `disabled`, `no_content`, `unavailable` or `failed`.

The `email` content takes `subject`, `body`, `text`, `replyTo` and also `template` (`{ name, props?, locale? }`) and `meta`,
which are handed to `dispatchEmailNotification` as they are, so an email that was sent with
`dispatchEmailNotification` before keeps its template and its meta when it moves to `notifyUser`. Keys you leave out are
not sent, not even as `undefined`.

::note
**SMS needs a phone number.** The `users` table has no phone column. Push reads an optional `phone` column that your
app adds with [`server/db/extend.<dialect>.ts`](/modules/platform/module-kit/database). Without it, SMS is always
`unavailable`. No SMS driver ships with Push: set `notify.sms.driver` in your `nuxt.config.ts`, and the `log` driver
stays in development.
::

### Why sendPush is its own API

Notify reserves `push.driver` but does not implement it, and a notification there has no recipient. So `sendPush` is its
own API.

## Topics and channel choices

`extendNotificationTopics(nuxt, topics)` (from `@frigear-nu/push/utils`) adds rows to the Notifications page.

| Field | Type | What it is |
| --- | --- | --- |
| `id` | `string` | Lower case words joined by `.`, `_` or `-`, such as `shifts.reminder`. The key the choices are stored under. |
| `label` | `string \| { da, en }` | The text the page shows. |
| `labelKey` | `string` | An i18n key tried before `label`. |
| `description`, `descriptionKey` | as above | A line under the label. |
| `defaults` | `{ email, sms, push }` | What applies until the user chooses. Required. |
| `channels` | `('email' \| 'sms' \| 'push')[]` | The channels the topic can use. Default: all three. A channel the topic does not offer is off, and its switch is disabled. |

Registering the same `id` again replaces the topic. The routes refuse a topic nobody registered.

- **Topic ids** start with the module name: `shifts.reminder`, `crew.status`. The topics each module sends are listed on
  its own page.
- **An unregistered topic throws** in `notifyUser`, so a typo fails in development.

### Send from a module that works without Push

A module that should also work without Push registers its topics only when Push is installed, and keeps one small
helper at its send sites. The helper calls `notifyUser` when Push is installed, and Notify's `dispatchEmailNotification`
and `dispatchSMSNotification` when it is not.

```ts [src/module.ts]
if (hasNuxtModule('@frigear-nu/push')) {
  const { extendNotificationTopics } = await import('@frigear-nu/push/utils')
  extendNotificationTopics(nuxt, topics)
}
```

The helper cannot import `notifyUser` without Push, so the module generates a small server module that re-exports it,
or exports `undefined` when Push is absent. Shifts (`#shifts/push`, `shiftsNotify`) and Crew (`#crew/push`,
`crewSend`) work this way.

Choices live in Push's own `push_channel_preferences` table, one row per user and topic. They are not stored with
[Preferences](/modules/identity/preferences): the mobile app reads and writes them with a bearer token, and the
Preferences routes are session only. A row holds all three channels, so changing a topic's defaults later does not move
users who already chose.

## The mobile app

Server mode owns the routes. The Capacitor app is a client of them.

::steps

### Install the plugin

```bash
pnpm add @capacitor/push-notifications
npx cap sync
```

Push imports the plugin itself, only when it is installed, so a build without it still works. Without it
`usePushDevice().supported` is `false`.

### Ask for the scope

A bearer token reaches the device routes only with the `push:devices` permission, so the app asks for it as a scope:

```ts [nuxt.config.ts of the app]
export default defineNuxtConfig({
  modules: ['@frigear-nu/mobile', '@frigear-nu/push'],
  authentication: {
    mode: 'client',
    client: {
      scopes: ['openid', 'push:devices'], // plus the scopes the rest of the app asks for
    },
  },
})
```

The issuer and the API need Push in server mode, so the scope exists there. A token without it gets
`403 insufficient_scope`.

### Set up Firebase and Apple

- **Android:** add your Firebase project's `google-services.json` to `android/app`, as the
  [Capacitor guide](https://capacitorjs.com/docs/apis/push-notifications) describes.
- **iOS:** in Xcode, add the Push Notifications capability to the app target. Create an APNs authentication key in the
  Apple developer account, and set the four `NUXT_PUSH_APNS_*` variables on the server. Use `NUXT_PUSH_APNS_SANDBOX=true`
  for builds installed from Xcode.
- To show a notification while the app is open on iOS, set `plugins.PushNotifications.presentationOptions` (for example
  `['badge', 'sound', 'alert']`) in `capacitor.config`.

The plugin returns the FCM token on Android and the APNs device token on iOS, which is what Push sends to.

### Register and unregister

With `@frigear-nu/mobile` installed, a plugin registers the device whenever someone is signed in: after a sign-in and when
a stored session is restored at start. It asks for permission, registers with the OS and sends the token to
`POST /api/push/me/devices`. Registering the same token again is harmless.

Set `push.settings.autoRegister: false` to ask at a better moment, and call it yourself:

```ts
const push = usePushDevice()
push.supported       // a native app with the plugin installed
push.permission      // 'unknown' | 'unsupported' | 'prompt' | 'granted' | 'denied'
await push.register()   // asks for permission when needed, resolves false without it
await push.unregister() // removes this device on the server and forgets the token
```

:::warning
Call `unregister()` **before** `useAuth().logout()`. The server removes the device with the signed-in user's token, which
is gone once the logout is done: the call then answers `401` and the phone stays registered to the previous user. A
phone that is registered by someone else later moves to them automatically, but until then it would still receive the
previous user's notifications.
:::

::

Push does not send web push to a website (a service worker).

## Account page and admin tab

`/account/notifications` shows every registered topic with a switch per channel. A switch saves at once. A channel the
topic does not offer is disabled. SMS is disabled until the user has a phone number, and a note says so when they have no
registered device for push.

The Devices tab on the admin user page lists the user's devices, revoked ones included, and has a Send test push action
that calls `POST /api/admin/push/test`. The action only shows for staff who hold `push:send`, and the test text follows
each device's language. The SMS note on the account page only shows when a topic offers SMS.

## Routes

Typed builders for every URL are in `pushApi` from `@frigear-nu/push/api`.

| Route | Needs | What it does |
| --- | --- | --- |
| `GET /api/push/me/devices` | `push:devices` | The caller's active devices, newest first. |
| `POST /api/push/me/devices` | `push:devices` | Registers a device: `{ platform, token, appId?, locale? }`. Answers `201`. |
| `DELETE /api/push/me/devices/:id` | `push:devices` | Removes one of the caller's devices (`204`). Another user's device answers `404`. |
| `POST /api/push/me/devices/unregister` | `push:devices` | Removes the caller's device by `{ token }` (`204`), also when it is unknown. |
| `GET /api/push/me/channels` | `push:devices` | The matrix: every topic with the caller's settings, `hasPhone` and `hasDevice`. |
| `PATCH /api/push/me/channels` | `push:devices` | Merges changes into the caller's channels, leaving the rest: `{ topics: { 'shifts.reminder': { push: false } } }`. An unknown topic is a `400`. |
| `GET /api/admin/users/:id/push-devices` | `push:manage` | A user's devices, revoked ones included. |
| `POST /api/admin/push/test` | `push:send` | Sends a test push to `{ userId }` and answers `{ sent, failed, revoked }`. |

A token is never part of a device in a response.

Registering a token that already exists moves it to the caller and makes it active again. A phone that changes hands
belongs to whoever signed in last.

## Permissions and scopes

| Permission | Who | What it allows |
| --- | --- | --- |
| `push:devices` | every signed-in user | Their own devices and channels. A policy keeps it to the user's own devices. |
| `push:manage` | the `admin` role | See other users' devices. |
| `push:send` | the `admin` role | Send a test push. |

The `push` scope holds `push:devices`. Use it, or the permission itself, in a token or in `authentication.client.scopes`.
See [Auth and scopes](/guide/concepts/auth-and-scopes).

## Hooks

| Hook | Context | When |
| --- | --- | --- |
| `push:device:registered` | `{ event, device }` | A device registered or registered again, after it is stored. `device` has no token. |

---
title: Inbox
description: Shared support inboxes. Staff read and answer messages from the contact form, email, WhatsApp, Messenger and Instagram in one place.
---

Inbox gives your staff shared mailboxes for the messages people send you: the website contact form, email, WhatsApp,
Messenger and Instagram. A message lands in a thread. Staff assign the thread, write internal notes, hide it from
lower roles and reply. The reply goes out through the channel the message came in on. Every view and reply goes into
an audit log. Closed threads are deleted after a retention period, and a contact's data can be exported or erased.

The package is `@frigear-nu/inbox`. Its mailboxes are owned by the platform or a team, and read by
[staff](/guide/concepts/glossary). To send email or SMS without expecting an answer, use
[Notify](/modules/communication/notify) instead.

## What you get

- **Admin area** (opt-in, needs [Admin](/modules/interface/admin)):
  - `/admin/inbox`, the thread list, filtered by mailbox, status, assignee and channel.
  - `/admin/inbox/threads/:id`, a thread with the conversation, a reply box and notes. It also has status, hide, the
    contact panel and an assignee picker that lists everyone with access to the thread. Contact details and email cc
    recipients need `inbox:pii`.
  - `/admin/inbox/settings`, the mailboxes and the channels connected to them.
  - An "Inbox" item in the admin sidebar, when [Menu](/modules/interface/menu) is installed.
- **Channels:** `form`, `email`, `whatsapp`, `messenger` and `instagram`. Modules add their own with `extendInbox`.
- **Webhooks:** `POST /api/inbox/webhooks/email`, and `GET` and `POST /api/inbox/webhooks/meta`.
- **Dashboard items** `inbox.unassigned` and `inbox.mine` on `crew.home`, when
  [Dashboard](/modules/interface/dashboard) is installed.
- **Push topic** `inbox.message` for the assignee, when [Push](/modules/communication/push) is installed.
- **Retention:** the Nitro task `inbox:retention`, run every night.

## Quick setup

::steps

### Install Inbox

```bash
pnpm add @frigear-nu/inbox
```

### Add it to `nuxt.config.ts`

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // Authorization brings the `role` grant kind the mailbox below uses.
  modules: ['@nuxthub/core', '@frigear-nu/users', '@frigear-nu/authorization', '@frigear-nu/forms', '@frigear-nu/inbox'],
  hub: { db: 'sqlite' },
  inbox: {
    mailboxes: [
      { key: 'support', name: { da: 'Support', en: 'Support' }, grants: [{ kind: 'role', role: 'coordinator' }] },
    ],
    // Channel secrets are declared here, empty, and set from the environment.
    secrets: { WHATSAPP_TOKEN: '' },
    settings: { pages: { admin: true, adminThread: true, adminSettings: true } },
  },
})
```

Set the webhook and channel secrets as environment variables, never in the config file:

```bash [.env]
NUXT_INBOX_EMAIL_WEBHOOK_SECRET=a-long-random-string
NUXT_INBOX_META_APP_SECRET=the-meta-app-secret
NUXT_INBOX_META_VERIFY_TOKEN=a-token-you-also-enter-at-meta
NUXT_INBOX_SECRETS_WHATSAPP_TOKEN=the-whatsapp-access-token
```

::warning
Without a migration, every inbox request fails: the tables do not exist yet.
::

### Generate and commit a migration

Inbox adds seven tables. Generate a [migration](/modules/platform/module-kit/database) and commit it.

```bash
npx nuxt db generate
```

### Connect the channels

Open `/admin/inbox/settings` as an admin and connect each channel to a mailbox:

- the contact form by its slug;
- the email address people write to;
- the WhatsApp phone number id;
- the Facebook page id;
- the Instagram account id.

## Options

Options go under the `inbox` key. The secrets also take environment variables, as above.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `mailboxes` | `InboxMailboxSeed[]` | `[]` | Mailboxes created on the first request when their key does not exist. They are never changed afterwards. |
| `channels` | `InboxChannelDefinition[]` | `[]` | The host's own channels, the same as `extendInbox`. |
| `email.webhookSecret` | `string` | none | The HMAC secret of the email webhook. Without it, the webhook answers 501 `not_configured`. |
| `meta.appSecret` | `string` | none | The Meta app secret that `X-Hub-Signature-256` is checked with. Without it, the Meta webhook answers 501 `not_configured`. |
| `meta.verifyToken` | `string` | none | The verify token Meta's subscription check sends. Without it, the check answers 501 `not_configured`. |
| `meta.apiBase`, `meta.apiVersion` | `string` | `https://graph.facebook.com`, `v21.0` | The Graph API that replies go to. |
| `meta.timeoutMs` | `number` | `10000` | How long a Graph API call may take. |
| `secrets` | `Record<string, string>` | `{}` | Channel account secrets by `secretRef`. Declare each ref empty and set it with `NUXT_INBOX_SECRETS_<REF>`. |
| `retention.days` | `number \| false` | `365` | Days a closed thread is kept when its mailbox sets none. `false` keeps them. |
| `retention.mode` | `'delete' \| 'anonymise'` | `'delete'` | Delete old threads, or keep them with their messages blanked. |
| `retention.cron` | `string \| false` | `'30 3 * * *'` | When `inbox:retention` runs. `false` registers it without a schedule. |
| `retention.batch` | `number` | `500` | The most threads one run handles, shared fairly between the mailboxes. |
| `retention.tombstoneDays` | `number` | `365` | Days the provider ids of messages retention removed are remembered, so a replayed webhook is not stored again. An erase's are kept for good. |
| `settings.pages.admin` | `string \| boolean` | off | The thread list. `true` is `/admin/inbox`. |
| `settings.pages.adminThread` | `string \| boolean` | off | The thread page. It must contain `:id`. |
| `settings.pages.adminSettings` | `string \| boolean` | off | Mailbox and channel settings. |
| `settings.dashboard` | `string \| false` | `'crew.home'` | The dashboard the two items go on. |

**Retention.** Each mailbox can set its own `retentionDays`. A mailbox without one uses `retention.days`. Inbox has no
retention table: a per-mailbox column and the module default cover it.

## Permissions

Inbox registers these permissions with [Authorization](/modules/identity/authorization).

| Name | Who holds it | What it covers |
| --- | --- | --- |
| `inbox:read` | Every signed-in user (implicit) | Threads of the mailboxes the policy lets them read. |
| `inbox:reply` | Every signed-in user (implicit) | Replies, notes and status, in the same mailboxes. |
| `inbox:assign` | `admin` | Assigning threads. |
| `inbox:hide` | `admin` | Hiding a thread from people below a role. |
| `inbox:manage` | `admin` | Every mailbox; creating, editing and deleting mailboxes; erasing contacts. |
| `inbox:pii` | `admin` (sensitive) | Contact email, phone and channel id; contact exports and erasure. |
| `inbox:channels` | `admin` | Connecting channels and naming their secrets. |
| `inbox-audit:pii` | `admin` (sensitive) | The audit log. |

**Session only.** Every inbox permission is `sessionOnly`: platform and team mailboxes hold outsiders' messages, so
they are never exposed to API tokens or OAuth apps, and every staff route answers a bearer with
`403 session_required`. There is no `inbox` scope.

The policy of `inbox:read` and `inbox:reply` allows:

- staff with `inbox:manage`;
- a team mailbox's leads;
- anyone the mailbox's grants admit.

## Server

How mailboxes, threads and channels behave, and the utils other modules call.

### Mailboxes

A mailbox has an owner: the platform, or a team (`ownerType: 'team'`, `ownerId` the team id, checked through Teams'
`teams:owner:resolve`). Who reads it besides staff is a grant list (Auth's [record audiences](/contribute/writing-a-module/access-control#record-audiences)) in
`grants`: any one grant admits, such as `{ kind: 'role', role: 'coordinator' }` (with
[Authorization](/modules/identity/authorization#role-grants)) or a `team` grant with a minimum role. A configured
mailbox whose grants name a kind no installed module registers stops the seeding, which is logged and retried.

- **Never public, never everyone with an account.** A mailbox holds outsiders' messages, so a `public` grant and a
  `signed-in` grant are refused (on create, on update and in `inbox.mailboxes`), and one stored anyway counts for
  nobody.
- **A platform mailbox must name who reads it.** An empty list is refused for it. If a stored one is empty anyway,
  nobody but staff reads the mailbox: an empty list admits nobody.
- **A team mailbox** is read by the team's leads (`isTeamLead` of [Teams](/modules/organisation/teams)). Its
  grants may add others.
- **Checked on write.** An unknown kind, an invalid grant or a team or operation that does not exist is a `400`
  (`grantsValidate`).

### Hidden threads

`POST .../hide` with `{ role }` sets `hiddenBelow`. From then on, only people who hold that global
role see the thread. Roles inherit along your role chain, so an admin who inherits `coordinator` sees threads hidden
below it. The role must be one the caller holds. Anyone else gets the same 404 as for an unknown thread, and the
thread is missing from their list. An assignee without the role is unassigned. `{ role: null }` shows the thread
again.

### Assignees

An assignee must be able to read and answer the thread themselves. The rule is evaluated for them, not
for the caller: they hold `inbox:reply` and the thread's `hiddenBelow` role, and they hold `inbox:manage`, lead the
team of a team mailbox, or are admitted by the mailbox's grants as themselves (`grantsMatch` with their own roles and teams). Anyone else is a
409 `assignee_no_access` (an unknown user is a 400).

The thread page's assignee picker lists those people: `GET .../threads/:id/assignees` evaluates the same rule for each
user, by name, and answers at most 50 (`?q` narrows by name). It looks at no more than 1,000 users per call, so on a
large user base search by name.

### Channels

| Channel | Address | Inbound | Replies |
| --- | --- | --- | --- |
| `form` | The form's slug | A listener on `forms:submitted` for forms with a `form` account | By email to the address the person gave, `Reply-To` the account's `config.replyTo` or the mailbox's email address |
| `email` | The address people write to | `POST /api/inbox/webhooks/email` | `dispatchEmailNotification` with `replyTo` the mailbox address and `[ibt_...]` in the subject |
| `whatsapp` | The WhatsApp phone number id | `GET` and `POST /api/inbox/webhooks/meta` | The Graph API with the account's token |
| `messenger` | The Facebook page id | The Meta webhook | The Graph API with the page access token |
| `instagram` | The Instagram professional account id | The Meta webhook | The Graph API with the token |

**Secrets never go into the database.** A channel account's `secretRef` names a secret, such as `WHATSAPP_TOKEN`. The
server reads it from the runtime config only, `inbox.secrets.WHATSAPP_TOKEN`, never from `process.env` directly. A ref
is upper case letters, digits and `_`, so it can only name an inbox secret. A `config` key that looks like a secret is
refused. Set the value with an environment variable that overrides the runtime config:

- **`NUXT_INBOX_SECRETS_<REF>`**, such as `NUXT_INBOX_SECRETS_WHATSAPP_TOKEN`. Nuxt only overrides keys that exist when
  the app is built, so declare each ref in `nuxt.config.ts` with an empty value: `inbox: { secrets: { WHATSAPP_TOKEN: '' } }`.
- **`NUXT_INBOX_SECRETS`**, a JSON object of refs and values, such as `{"WHATSAPP_TOKEN":"..."}`. It adds refs that were
  not declared.

::note
**Cloudflare Workers.** A Worker has no environment at build time: set the variables as Worker secrets
(`wrangler secret put NUXT_INBOX_SECRETS_WHATSAPP_TOKEN`) and declare the ref empty in `nuxt.config.ts` as above. The
inbox reads the runtime config per request, where the Worker's secrets are applied.
::

**The contact form.** Connect a form by its slug. Its answers are read from the fields `name`, `email`, `phone`,
`subject` and `message`. Change the keys with `config.fields`. A form without a `message` field lists every answer.
Submissions only come in through Forms' own submit route, with the form's access rules, and the `forms:submitted`
hook: the inbox has no webhook for the form channel.

**Channels fail closed.** Every inbound route needs its secret, and there is no unauthenticated default. Without
`email.webhookSecret`, `meta.appSecret` or `meta.verifyToken`, or a module channel's `inboundSecret`, the route answers
501 `not_configured` before it reads the request.

#### Email webhook

Point your email provider's inbound webhook (Postmark, Mailgun, SendGrid, Cloudflare Email Workers, ...) at
`POST /api/inbox/webhooks/email`. Map its payload to this JSON:

```json
{
  "messageId": "<CAF1234@mail.example.org>",
  "from": { "email": "kari@example.org", "name": "Kari Nordmann" },
  "to": "support@example.com",
  "cc": [{ "email": "ola@example.org", "name": "Ola" }],
  "subject": "Where is my ticket?",
  "text": "Hello, I never got my ticket.",
  "html": "<p>Hello, …</p>",
  "attachments": [{ "filename": "ticket.pdf", "contentType": "application/pdf", "size": 1200, "url": "https://…" }],
  "authenticated": true
}
```

::warning
**Pass the provider's sender verdict as `authenticated`.** Set it to `true` only when the email passed SPF, DKIM or
DMARC at your provider; inbound providers report it, for example in an `Authentication-Results` header. An email without it is treated as unverified: it always starts a new
thread and never renames a contact, so a forged sender cannot write into someone else's conversation.
::

Sign the raw body with `X-Inbox-Signature: sha256=<HMAC-SHA256 of the body with email.webhookSecret>`.

- **Wrong signature:** 401.
- **Larger than 1 MB:** 413 `payload_too_large` (the same limit applies to the Meta and module webhooks).
- **Not an email:** 400.
- **Every other case:** 200, so the provider stops retrying.
  - A new message: `{ status: 'received', threadId, messageId }`.
  - A redelivery: `{ status: 'duplicate' }`. A message is stored once per `messageId` and channel account.
  - An address no account has: `{ status: 'ignored', reason: 'no_account' }`.
  - A message retention or an erase removed: `{ status: 'ignored', reason: 'removed' }` (see Replays below).

**Routing.** The mailbox is found by the recipients in `to` and `cc`: every email account whose address is among them
gets the message, so a mailbox that is only copied still receives it, and one email to two connected mailboxes is
stored in each (two threads). The answer describes the first account's delivery; when more than one matched,
`deliveries` lists each, with its `mailboxId`.

`cc` (an address or a list) is stored with the message, without the mailbox's own address, and shown on the thread page
to people with `inbox:pii`. A reply goes to the contact and copies (Notify's `cc`) the people the contact's latest
authenticated email in the thread copied, as a reply-all would. The cc of an email that is not authenticated is kept
and shown, but never sent to: a forged sender cannot make your replies copy a list of strangers. Our own addresses are
left out: every email account's address and `config.replyTo`, the reply's `Reply-To`, Notify's sender and the
contact's own address. When that email copied nobody, the reply has no cc. The email driver must pass `cc` on; the
built-in ones do. The reply stores who it copied, and the thread page shows them on it, again only to people with
`inbox:pii`. Only valid email addresses are kept: a malformed `Cc` entry is dropped from the inbound message and so
never copied.

**The reply address is checked the same way.** A reply by email (an email or contact form thread) goes only to one
plain, valid address. A contact whose address is not one (`a@x.org, b@y.org`, a value with a line break) cannot be
answered by email: the reply is refused with 409 `no_reply_address`, as for a contact with no address.

An authenticated answer to a reply finds its thread by the `[ibt_...]` marker in the subject, when the thread is in
the same mailbox and the sender is its contact or has the contact's email address. That is how an emailed answer to a
contact form thread lands in that thread. An answer to a thread that retention or an erase anonymised starts a new
thread instead: a blanked thread never takes new content. Otherwise an authenticated email goes to the contact's latest
email thread that is not closed. Everything else starts a new thread. Control characters in subjects become spaces.
Attachments are kept as metadata and the provider's URL, never the bytes.

Each inbound message records the contact who sent it (`contactId` on the message) and whether it was authenticated.
An emailed answer filed in a contact form thread belongs to the form's contact, but its sender is the email contact;
export and erase find it by that (see [Privacy](#privacy)).

**Contact form senders are verified only by their own address.** Anybody can type someone else's email address into a
form, so a submission counts as verified only when a signed-in user typed their own account email. Then it may join
that contact's open thread, rename it and link it to the account (`userId`). Anything else, a submission without a
signed-in user or a signed-in user who typed another address, is unverified: it always starts a new thread, never
renames the contact and never sets its `userId`. A signed-in user who typed no address is keyed on their account
(`user:<id>`). A typed value that is not one valid address is not stored as the contact's email.

#### Meta: WhatsApp, Messenger and Instagram

One webhook URL serves all three: `/api/inbox/webhooks/meta`.

- **`GET`** is Meta's subscription check. It echoes `hub.challenge` when `hub.verify_token` matches
  `meta.verifyToken`, and answers 403 otherwise. The token is compared in constant time: both sides are HMAC-ed
  with a random key and the digests compared, so neither its length nor where it differs shows in the timing.
- **`POST`** is checked against `X-Hub-Signature-256` with the app secret.
  - A wrong signature gets a 401.
  - Otherwise it always answers 200 with counts: `{ received, duplicates, ignored, failed }`. Meta retries and backs
    off on errors, so a duplicate or an unknown account never gets an error.
  - Each message goes to the account at the phone number id, page id or Instagram id it was sent to.
    Meta's signature vouches for the sender, so a message joins the contact's latest thread that is not closed.
  - Read and delivery statuses and echoes of your own replies are skipped. Media arrives as a placeholder with the
    media id or link.

Replies call the Graph API with `fetch` and stop after `meta.timeoutMs`. When delivery fails, nothing is stored and
the caller gets a 502 `delivery_failed`. A missing token gives a 409 `channel_not_configured`.

**Meta prerequisites.** These take weeks, so start early:

- **Business verification** of your Meta Business account.
- **A WhatsApp Business number** in the Cloud API, and its phone number id. WhatsApp only delivers free text within
  24 hours of the person's last message. Outside that window it needs an approved template, so a late reply fails
  with `delivery_failed`.
- **App review** of a Meta app for the permissions that read and send messages:
  - Messenger: `pages_messaging`;
  - Instagram: `instagram_manage_messages`;
  - WhatsApp: `whatsapp_business_messaging`.
- **A webhook subscription** in the app: the URL above, your verify token, and the `messages` fields of the WhatsApp,
  Page and Instagram products.
- **A long-lived token** per account (a system user token for WhatsApp, a page access token for Messenger and
  Instagram), set as `NUXT_INBOX_SECRETS_<REF>` with the ref declared in `inbox.secrets`.

#### A channel of your own

A module adds a channel with `extendInbox` from `@frigear-nu/inbox/utils`. The adapter file default-exports
`defineInboxChannel`:

```ts [module.ts]
import { extendInbox } from '@frigear-nu/inbox/utils'

extendInbox(nuxt, {
  channels: [{ id: 'acme.sms', label: { da: 'SMS', en: 'Text message' }, icon: 'i-lucide-message-square', adapter: resolver.resolve('./runtime/inbox/sms') }],
})
```

```ts [runtime/inbox/sms.ts]
import { z } from 'zod'
import { defineInboxChannel, secretsEqual } from '@frigear-nu/inbox/utils'

const smsWebhook = z.object({ id: z.string(), from: z.string(), to: z.string(), text: z.string() })

export default defineInboxChannel({
  id: 'acme.sms',
  // The `inbox.secrets` entry the webhook is verified with. Declare it empty and set NUXT_INBOX_SECRETS_ACME_SMS_WEBHOOK.
  inboundSecret: 'ACME_SMS_WEBHOOK',
  // POST /api/inbox/webhooks/acme.sms: verify the request with the secret, then return the messages in it. The inbox
  // has read the body already, within its 1 MB limit, and passes it as `rawBody`.
  async inbound(event, { secret, rawBody }) {
    if (!(await secretsEqual(getRequestHeader(event, 'x-acme-token') ?? '', secret))) {
      throw createError({ statusCode: 401, statusMessage: 'Bad token' })
    }
    const body = smsWebhook.parse(JSON.parse(rawBody))
    // `authenticated`: the provider vouches for the sender, so the message may join the sender's open thread.
    return [{ address: body.to, contact: { externalId: body.from, phone: body.from }, externalId: body.id, body: body.text, authenticated: true }]
  },
  // Deliver a reply; throw to fail it (nothing is stored then).
  async send({ contact, message, secret }) {
    const sent = await $fetch<{ id: string }>('https://sms.example/send', { method: 'POST', headers: { authorization: `Bearer ${secret}` }, body: { to: contact.phone, text: message.body } })
    return { externalId: sent.id }
  },
})
```

`send` may also return `cc`, the email addresses it copied: they are stored on the reply (invalid ones are dropped)
and shown with `inbox:pii`.

An adapter with `inbound` must name its `inboundSecret`, an `inbox.secrets` entry, and verify the request with it
(`ctx.secret`). Until that secret is set, the webhook answers 501 `not_configured` and never calls `inbound`, so a channel
is never open by default. The inbox reads the body before it calls `inbound`, at most 1 MB whether or not the request
declares a `content-length` (413 `payload_too_large` otherwise), and passes it as `ctx.rawBody`: verify a signature
over it and parse it rather than reading the request again. A message without `authenticated: true` always starts a new thread. A registration with the
id of a built-in channel replaces it, so a host can swap an adapter.

### Privacy

- **Audit log.** These go in the log, with who did them:
  - views (once per person and thread in 15 minutes);
  - replies, notes, assignments, status changes and hiding;
  - exports, erasures and retention runs.

  `GET .../audit` lists only the entries whose subject the caller could see, as in the thread list. A thread's entries
  need its mailbox and its `hiddenBelow` role (a deleted thread's, the mailbox recorded with the entry). A retention
  run needs its mailbox. An export or erase needs at least one of the contact's threads.
- **One person, several contacts.** A contact is one identity on one channel, so a person who used the contact form
  and then answered by email is two contacts, and the email answer sits in the form contact's thread. Export and erase
  therefore cover the contact, every other contact with the same email address (`related` in the export), and the
  messages any of them sent in other contacts' threads (found by the message's sending contact).
- **Export** (`GET .../contacts/:id/export`) returns the details of the contact and its related contacts, every
  message sent or received in their threads, without internal notes, and from other contacts' threads only the
  messages they sent there. A partial export would answer an access request incompletely, so the caller must see every
  one of those threads, as for an erase: mailboxes they read, and no thread hidden below a role they lack. A contact
  none of whose threads they see is a 404. A contact with a thread hidden from them is refused with a 409
  `contact_threads_hidden`, and nothing of the contact is returned: someone who sees all of the threads exports it.
- **Erase** (`POST .../contacts/:id/erase`) removes the name, email, phone and channel id of the contact and its
  related contacts. Every thread of theirs is closed and its messages blanked: bodies, attachments, cc recipients and
  provider ids (`erased:<id>`). The messages they sent in other contacts' threads are blanked the same way, and those
  threads' previews refreshed. The threads stay, empty, as a record that something was answered. The answer counts
  `threads`, `messages` (in other threads) and `contacts`. A new message from the same person starts a new contact.
  - **All or nothing.** The contact's details belong to all their threads, so the caller must see every one of them. A
    contact with a thread hidden from the caller is refused with a 409 `contact_threads_hidden`, and nothing is erased:
    someone who sees all of the threads erases the contact.
- **Replays.** Webhook signatures carry no time, and an email payload has no reliable one, so a replayed request
  cannot be judged by its age. Instead, when retention or an erase removes a message, its provider id is kept as a
  tombstone: a SHA-256 of the channel account and the provider id, never the id itself, with the id of the contact who
  sent it. A webhook that delivers it again answers `ignored` (`reason: 'removed'`) and stores nothing.
  - Retention's tombstones are pruned by the retention run `retention.tombstoneDays` (365) after the removal. A replay
    after that is stored as a new message.
  - An erase's tombstones are kept for good, and an erase also keeps the tombstones of what retention removed of the
    person earlier: nothing erased comes back, however late the replay.
- **Form submissions and their files** are stored by [Forms](/modules/features/forms), not by the inbox, and are
  erased there. The inbox keeps only the submission's text and the files' names and Blob pathnames.
- Export and erase are session only, like every inbox route: no API token can call them.
- **Retention** runs as the task `inbox:retention`, every night at 03:30 unless `retention.cron` says otherwise.
  - It handles closed threads whose last message is older than their mailbox keeps them.
  - `delete` removes them with their messages, and contacts left without a thread or a message go too.
  - `anonymise` keeps them, closed, with their messages blanked as on erase. A contact left with only anonymised threads
    (their own and the ones they wrote in) is erased.
  - A run handles at most `retention.batch` threads, and deletes in chunks of 90 ids to stay within D1's limits. A
    backlog is worked off over several nights.
  - The batch is shared fairly: every mailbox with a retention period first gets an equal share, and what the others
    left goes to the mailboxes with more to do, so one busy mailbox never starves the rest. The result says `more:
    true` when a mailbox had more than the run could handle.
  - It also prunes retention's tombstones older than `retention.tombstoneDays` (an erase's stay).
  - On Cloudflare the cron is added to `wrangler.json` for you.
  - Run it by hand with `runTask('inbox:retention', { payload: { now, mode, batch } })`.

### Dashboard items

With [Dashboard](/modules/interface/dashboard) installed and the thread page on, Inbox adds two items to the dashboard
named by `settings.dashboard` (`crew.home` by default). Both need `inbox:read`, show on the web only and read
`GET /api/admin/inbox/summary`. They render nothing for someone who reads no mailbox.

| Item | Order | Shows |
| --- | --- | --- |
| `inbox.unassigned` | 70 | Open threads nobody is assigned to, with a link to the filtered list. |
| `inbox.mine` | 71 | Open threads assigned to me, with a link to the filtered list. |

Texts are under `inbox.dashboard`.

### Push topic

Inbox registers the topic `inbox.message` with [Notify](/modules/communication/notify#notifying-a-user) (push on by
default, email off, no SMS). When a message comes in on a thread with an assignee, the assignee hears about it through
`notifyUser`, with a link to the thread page, in the assignee's language (`users.locale`, English without one). The
text names neither the sender nor the message. An assignee who can no longer read and answer the thread (they lost
the mailbox's grant, `inbox:reply` or the role it is hidden below) hears nothing; the thread keeps them as its
assignee until someone reassigns it. The push reaches phones
with [Push](/modules/communication/push) installed, and the assignee can turn the email on (or the push off) on the
account page of [Preferences](/modules/identity/preferences#notification-channels).

## Hooks

Your app answers these Nitro hooks from a server plugin (`server/plugins/*.ts`).

| Hook | Context | When |
| --- | --- | --- |
| `inbox:message:received` | `{ event, thread, message }` | A message came in on a channel and was stored. A duplicate fires nothing. |
| `inbox:message:sent` | `{ event, thread, message }` | A reply went out and was stored. Notes fire nothing. |
| `inbox:thread:assigned` | `{ event, thread, assigneeId, previous }` | A thread got another assignee (`null` unassigns). |
| `inbox:thread:status-changed` | `{ event, thread, from, to }` | Staff changed the status, or a message reopened a pending or closed thread. |

## Routes

Path builders come from `@frigear-nu/inbox/api` (`inboxApi`). A thread the caller may not read answers the same 404
as an unknown one.

| Route | Who | What |
| --- | --- | --- |
| `GET /api/admin/inbox/summary` | `inbox:read` | Unassigned and own open threads, for the dashboard items. |
| `GET`, `POST /api/admin/inbox/mailboxes` | `inbox:read`, `inbox:manage` | The mailboxes the caller reads; creates one. |
| `GET`, `PATCH`, `DELETE /api/admin/inbox/mailboxes/:id` | `inbox:read`, `inbox:manage` | One mailbox. Deleting one with threads is a 409 `mailbox_not_empty`. |
| `GET /api/admin/inbox/threads` | `inbox:read` | Paginated threads, `?mailbox&status&assignee&channel&q`. `status` defaults to `active` (open or pending); `all` lists every status. `assignee` is `me`, `none` or a user id. |
| `GET /api/admin/inbox/threads/:id` | `inbox:read` | The thread, its messages and notes, and what the caller may do. In the audit log. |
| `PATCH /api/admin/inbox/threads/:id` | `inbox:reply` (status), `inbox:assign` (assignee) | Changes the status or the assignee. |
| `GET /api/admin/inbox/threads/:id/assignees` | `inbox:assign` | Up to 50 people who could be assigned the thread, `?q` by name. |
| `POST /api/admin/inbox/threads/:id/messages` | `inbox:reply` | Replies through the thread's channel, `{ body, status? }`. |
| `POST /api/admin/inbox/threads/:id/notes` | `inbox:reply` | An internal note. |
| `POST /api/admin/inbox/threads/:id/hide` | `inbox:hide` | `{ role }`: hides the thread below a role, or shows it again. |
| `GET`, `POST /api/admin/inbox/channels` | `inbox:channels` | Channel accounts. |
| `PATCH`, `DELETE /api/admin/inbox/channels/:id` | `inbox:channels` | One channel account. |
| `GET /api/admin/inbox/audit` | `inbox-audit:pii` | The audit log entries the caller may see, `?threadId&contactId&action`. |
| `GET /api/admin/inbox/contacts/:id/export` | `inbox:pii` | Everything stored about a contact, without internal notes. A 409 `contact_threads_hidden` when a thread of theirs is hidden from the caller. |
| `POST /api/admin/inbox/contacts/:id/erase` | `inbox:manage` and `inbox:pii` | Erases the contact: details removed, messages blanked, threads kept. A 409 `contact_threads_hidden` when a thread of theirs is hidden from the caller. |
| `POST /api/inbox/webhooks/email` | The HMAC signature | Inbound email. |
| `GET`, `POST /api/inbox/webhooks/meta` | The verify token, `X-Hub-Signature-256` | WhatsApp, Messenger and Instagram. |
| `POST /api/inbox/webhooks/:channel` | The channel's check with its `inboundSecret` | A module channel with an `inbound` reader. 501 `not_configured` without the secret. |

## Database

Tables the module adds. Generate and commit a [migration](/modules/platform/module-kit/database) after installing.

| Table | What it holds |
| --- | --- |
| `inbox_mailboxes` | `id` (`ibx_`), `key` (unique), `ownerType`, `ownerId`, `name`, `grants` (JSON, `[]` by default), `retentionDays`. |
| `inbox_channel_accounts` | `id` (`ica_`), `mailboxId`, `channel`, `address` (unique per channel), `config`, `secretRef`, `enabled`. |
| `inbox_contacts` | `id` (`icn_`), `channel`, `externalId` (unique per channel), `name`, `email`, `phone`, `userId`, `erasedAt`. |
| `inbox_threads` | `id` (`ibt_`), `mailboxId`, `contactId`, `channelAccountId`, `channel`, `subject`, `searchText` (the subject folded for search), `status`, `assigneeId`, `hiddenBelow`, `preview`, `lastMessageAt`, `anonymisedAt`. |
| `inbox_messages` | `id` (`ibm_`), `threadId`, `direction` (`in`, `out`, `note`), `authorId`, `body`, `attachments`, `cc`, `channelAccountId`, `externalId` (`<channel>:<provider id>`, unique per `channelAccountId`), `contactId` (the sender of an inbound message, indexed), `authenticated`, `createdAtMs`. |
| `inbox_audit` | `id` (`iba_`), `threadId`, `mailboxId` and `contactId` (all indexed), `actorId`, `action`, `data`. |
| `inbox_tombstones` | `key` (a SHA-256 of a channel account and a provider id that was removed), `contactId` (who sent it, indexed), `permanent` (written or kept by an erase: never pruned), `createdAt`. |

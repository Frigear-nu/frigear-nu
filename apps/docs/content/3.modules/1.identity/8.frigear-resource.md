---
title: Frigear Resource
description: Accept frigear.nu access tokens in any Frigear service, so one mobile app signs in once at frigear.nu and calls every service.
---

This [Nuxt module](https://nuxt.com/docs/4.x/guide/modules) turns a Frigear service (vouchers, shop, inventory, ...)
into an OAuth **resource server** for frigear.nu. The service runs no OAuth server of its own: the Frigear mobile app
signs in once at frigear.nu ([OAuth Server](/modules/identity/oauth-server#one-app-for-every-service)) and sends the access
token to every service. The module verifies it, finds or creates the user, and hands routes the usual
[Auth](/modules/identity/auth) principal with the granted scopes.

::note
**Requires** `@nuxthub/core`, `@frigear-nu/module-kit`, [`@frigear-nu/auth`](/modules/identity/auth) and
[`@frigear-nu/users`](/modules/identity/users); all are installed automatically.
::

## Quick setup

```bash
pnpm add @frigear-nu/frigear-resource @nuxthub/core
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/frigear-resource'],
  frigearResource: {
    issuer: 'https://frigear.nu',
    audience: 'frigear-services',
  },
})
```

Routes ask for the scope they need, exactly as for API tokens or sessions:

```ts [server/api/vouchers/index.get.ts]
export default defineEventHandler(async (event) => {
  const { user } = await requireAuth(event, { scopes: ['vouchers:read'] })
  return listVouchers(user.id)
})
```

A token without `vouchers:read` gets `403 insufficient_scope` (with `WWW-Authenticate: Bearer error="insufficient_scope"`);
an invalid, expired or foreign token gets `401` (`error="invalid_token"`). A signed-in session still passes, so the
service's own web pages keep working.

frigear.nu has to know the scopes: list them in its `oauthServer.scopes` with `service` (and `staffOnly` for staff
scopes), so they show up grouped on its consent screen.

## Options

Every option is also `runtimeConfig.frigearResource.<option>` and can be set per environment through
`NUXT_FRIGEAR_RESOURCE_<OPTION>` (lists comma separated).

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `issuer` | `string` | `https://frigear.nu` | The `iss` tokens must carry. |
| `audience` | `string \| string[]` | `frigear-services` | The `aud` tokens must carry (one of them): frigear.nu's `accessTokenAudience`. |
| `jwksUrl` | `string` | `<issuer>/.well-known/jwks.json` | Where the signing keys are read. |
| `userinfoUrl` | `string` | `<issuer>/oauth/userinfo` | Where an unknown user's profile is read. |
| `corsOrigins` | `string[]` | `capacitor://localhost`, `https://localhost` | Exact origins (never `*`) whose webviews may call the API with a bearer token. |
| `corsPaths` | `string[]` | `/api/` | Path prefixes the CORS headers apply to. |
| `forceId` | `boolean` | `runtimeConfig.frigear.forceId` | Use the frigear.nu id (`sub`) as the local user id. See [Users](#users). |
| `jwksCacheTtl` | `number` | `600` | Seconds the keys are cached. |

## How a token is checked

The resolver (`addAuthResolver`, order `50`) claims every JWT and accepts it only when:

- its header `typ` is `at+jwt` and it is signed with RS256 by a key in the issuer's JWKS. The keys are cached for
  `jwksCacheTtl`; a token with an unknown `kid` (the issuer rotated) refetches them, at most every 30 seconds;
- `iss` is the issuer, `aud` contains the audience, `exp` has not passed, and it has `sub` and `client_id`.

Anything else is left to the next resolver (the service's own API tokens, for example) and ends in `401`. The principal
is `{ kind: 'oauth', user, scopes, client: { id } }`: `scopes` is the token's `scope`, `client.id` the app's
`client_id`. ID tokens are never accepted.

Access tokens cannot be revoked at the service. They live as long as frigear.nu says (keep `accessTokenTtl` at 5 to 15
minutes); a user who loses access at frigear.nu stops getting new ones at the next refresh.

## Users

The user is the token's `sub`, the frigear.nu user id.

- **With `forceId`** (recommended, and the default when "Log in with frigear.nu" uses it): the local user has the same
  id. Tokens and logins find the same user.
- **Without it**, users are matched by email. The frigear.nu id is remembered per server instance.

A user the service has not seen is created the first time a token arrives: the module reads the profile from the
issuer's userinfo endpoint with that token (`email`, `name`, `picture`), so the app has to ask for the `email` scope.
Without an email the token is refused. Known users are not written to on requests.

## CORS

A webview of the mobile app runs on `capacitor://localhost` (iOS) or `https://localhost` (Android), so its calls to the
service are cross-origin. The module answers preflights and adds `Access-Control-Allow-Origin` for the configured
origins on `corsPaths`, with `Authorization` allowed and `WWW-Authenticate` exposed. It never sends
`Access-Control-Allow-Credentials`: cookies do not travel cross-origin, so a cross-origin call is always a bearer call.
The headers come from the shared [`applyBearerCors`](/modules/platform/module-kit#bearer-cors) of `@frigear-nu/module-kit/server`
(methods `GET, POST, PUT, PATCH, DELETE, OPTIONS`, headers `authorization, content-type, accept`, preflights `204`), the
same helper behind the OAuth server's [`cors.paths`](/modules/identity/oauth-server#calling-from-a-browser-on-another-origin).

## Not yet

[RFC 8707](https://www.rfc-editor.org/rfc/rfc8707) resource indicators: every service accepts every token of the shared
audience and relies on scopes to limit what it may do.

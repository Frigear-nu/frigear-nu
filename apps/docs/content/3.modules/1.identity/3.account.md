The account area as a [Nuxt module](https://nuxt.com/docs/4.x/guide/modules): an `account` layout (a settings page inside
the public site, with its own section navigation), and opt-in pages built with [`@nuxt/ui`](https://ui.nuxt.com) and the
[`@frigear-nu/ui`](/modules/interface/ui) page patterns over the self-service routes of [Users](/modules/identity/users) and the token
routes of [Auth](/modules/identity/auth). It owns no tables and registers no server routes of its own. The screens follow the
[UX patterns](/guide/ux-patterns/layouts-and-navigation).

::note
**Requires** `@nuxthub/core`, `@frigear-nu/module-kit`, [`@frigear-nu/auth`](/modules/identity/auth),
[`@frigear-nu/users`](/modules/identity/users) and [`@frigear-nu/ui`](/modules/interface/ui) (which brings `@nuxt/ui`). **Optional:**
[`@frigear-nu/menu`](/modules/interface/menu) (the account navigation, the dropdown and the overview page) and
[`@frigear-nu/widget`](/modules/interface/widget) (the `account.overview` widget area).
::

## Quick setup

```bash
pnpm add @frigear-nu/account @nuxthub/core
```

```ts
export default defineNuxtConfig({
  modules: [
    '@nuxthub/core',
    '@frigear-nu/users',
    '@frigear-nu/menu', // optional
    '@frigear-nu/account',
  ],
  account: {
    settings: {
      pages: {
        profile: true, // or a custom path, e.g. '/me'
        security: true,
        index: true, // the overview, only registered with @frigear-nu/menu
        documents: true,
        apiTokens: true,
      },
      documents: [
        { id: 'handbook', label: { da: 'Håndbog', en: 'Handbook' }, path: '/assets/files/handbook.pdf' },
        { id: 'crew', label: 'Crew plan', path: '/assets/files/crew.pdf', roles: ['admin', 'crew'] },
      ],
    },
  },
})
```

## Options

All options live under `account.settings`.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `layout` | `boolean` | `true` | Renders the account area in the `account` layout (see [Layout](#layout)); an app's own `app/layouts/account.vue` replaces the module's. `false` registers no layout and leaves it to the app. |
| `pages.index` | `string \| boolean` | off | The overview (summary, widgets, shortcuts). Needs `@frigear-nu/menu`; skipped with a warning without it. `true` = `/account`. |
| `pages.profile` | `string \| boolean` | off | Profile page (name, avatar, email). `true` = `/account/profile`. |
| `pages.security` | `string \| boolean` | off | Password and passkeys. `true` = `/account/security`. |
| `pages.documents` | `string \| boolean` | off | Lists `documents` for download. `true` = `/account/documents`. |
| `pages.apiTokens` | `string \| boolean` | off | Create and revoke personal API tokens. `true` = `/account/api-tokens`. Skipped when Auth has `apiTokens: false`. |
| `documents` | `AccountDocument[]` | `[]` | Files offered on the documents page. |

A page is enabled with `true` (default path), a custom path string, or left off. A page whose path already exists in
the app is not registered, so an app replaces a shipped page by declaring its own at that path.

```ts
type AccountDocument = {
  id: string
  /** A string, or a locale map (falls back to `en`, then the first value). */
  label: string | Record<string, string>
  /** Where the file is served from, e.g. `/assets/files/handbook.pdf`. */
  path: string
  icon?: string
  /** Only listed for users whose session `role` is one of these. Omit to list for every signed-in user. */
  roles?: string[]
}
```

::warning
`roles` only filters the list. A file served from `public/` can be fetched by anyone who knows its URL; put sensitive
files behind a server route if that matters.
::


### API tokens and email changes

The API tokens page lists the user's tokens in a table; **Create API token** opens a slideover with the name, scopes and
expiry (the button is in the page heading's actions), and the new token is shown once above the table with a copy button.
Revoking a token asks for confirmation.
Tokens are created through [Auth](/modules/identity/auth). When `users.settings.mcp` is on, the page also shows a "Connect to
MCP" card ([MCP](/modules/features/mcp)).

The profile page opens **Change email** in a slideover, and the security page's **Add passkey** (in the passkeys card
heading, with the optional name field) opens a slideover too.

Verified email changes are a setting of Users (`users.settings.verifyEmailChange`); point `users.settings.profilePath`
at the profile page, which shows the result. See [Users](/modules/identity/users#routes).

## Layout

Every page under `/account` (and `/<locale>/account`), plus any configured page path outside it, renders in the
`account` layout. The module sets this with an `appLayout` route rule, so pages other modules add under `/account`
(membership, tickets, applications) get it too, whenever they register. A page that sets `layout` in its own
`definePageMeta` keeps its choice.

The account area is a settings page inside the public site, like the account settings of GitHub or Stripe, not a
dashboard. The layout renders the app's `default` layout, so the site header and footer stay, and puts a centred
settings grid (`UContainer`, then `max-w-5xl`) inside it:

- on wide screens a sticky left column with the signed-in user (`UUser`, name and email) and a vertical navigation,
  `aria-label` "Account navigation", built from the `account` menu (`useMenu('account')`, through `useNavLinks`); the
  overview is only active on its own path;
- on narrow screens the same entries in a [`PageSectionSwitcher`](/modules/interface/ui#page-components) above the content;
- the page in the content column. The layout renders no heading: the page renders its own.

Without `@frigear-nu/menu` the navigation lists the enabled pages from `settings.pages` instead. An app without a
`default` layout still works: the account area then renders on its own. The document title defaults to the active
navigation entry; the page's heading sets its own. The app's `app.vue` must render `<NuxtLayout>` for any layout to
apply.

Define `app/layouts/account.vue` in your app (or a layer) and it replaces the module's layout: the module only registers
its own when no `account` layout exists, and the route rule still applies the layout by name, so every account page
renders in yours. No option is needed for that.

`settings.layout: false` removes the layout entirely: no layout is registered, no rule is set and the pages render in
whatever layout the app picks.
The shipped pages render their own `AccountHeader`, so they need no wrapper, but they bring no container either.

::warning
**Breaking:** the layout no longer renders `UPageAside` or a page heading, and
`definePageMeta({ heading: false })` and the `AccountHeaderRight` component are gone. Pages in your app or in other
modules must render their own `PageHeading` (or `AccountHeader`). A host override `Account/AccountHeaderRight.vue` is
never used any more: move it to `Account/AccountIdentity.vue` (see [Overriding parts](#overriding-parts)).
::

### Heading

Every account page renders its own heading as the first child of its root `<div class="flex flex-col gap-4">`.
`AccountHeader` is an opt-in page component for this: a [`PageHeading`](/modules/interface/ui#page-components) whose title is the
page's `title` meta, else the label of the `account` menu item the route belongs to (the longest matching path, so
`/account/membership/success` still reads "Membership"), else "Account"; the description comes from the same menu item.
`#actions` is passed through to the heading, and it sets the document title, which wins over the layout's default (the
active navigation label).

```vue
<template>
  <div class="flex flex-col gap-4">
    <AccountHeader>
      <template #actions>
        <UButton icon="i-lucide-plus" :label="t('create', 'Create API token')" @click="create()" />
      </template>
    </AccountHeader>
    <!-- sections -->
  </div>
</template>
```

A page another module adds needs its route and an `account` menu item for the navigation. Its heading is a
`PageHeading` with the same i18n keys as the menu item, so label and title cannot drift. It draws no container or
account navigation of its own.

## Overview

The overview (`pages.index`) shows an `AccountHeader` ("Overview"), a summary card (`UUser` with avatar, name and email,
plus `AccountIdentity`), then the
`account.overview` [widget area](/modules/interface/widget) when `@frigear-nu/widget` is installed, then a card with shortcuts to
every other entry of the `account` menu. Widgets receive the session `user` as a prop:

```ts
// In another module's setup()
import { extendWidgets } from '@frigear-nu/widget/utils'

extendWidgets(nuxt, 'account.overview', {
  id: 'next-ticket',
  component: resolver.resolve('./runtime/app/components/NextTicket.vue'),
  order: 10,
})
```

Use [`StatCard`](/modules/interface/ui#page-components) for numbers and `ListCard` for short lists, as on the admin dashboard.

## Server

The account pages call the self-service routes of [Users](/modules/identity/users#routes) through `usersApi`:
`PATCH /api/users/me` (profile), `PUT /api/users/me/email` and `PUT /api/users/me/password`. They require a cookie
session and answer the caller's profile.

## App

```ts
const { updateProfileDetails, changeEmailAddress, changePassword, pending, error } = useAccount()

await updateProfileDetails({ name: 'Ada Lovelace', avatar: 'https://example.com/ada.png' }) // avatar: null clears it
await changeEmailAddress({ email: 'ada@example.com' })
await changePassword({ currentPassword: 'old', newPassword: 'new-password', confirmNewPassword: 'new-password' })
```

Each call refreshes the user session afterwards; `pending` and `error` are refs.

```ts
const { items, links, current } = await useAccountNav()
```

`useAccountNav()` is what the layout, the heading and the overview read: `items` are the account navigation entries
(the `account` menu, or the enabled pages without the menu module), `links` the same as `UNavigationMenu` items
(localised, with `active`), and `current` the entry the route belongs to.

The module also auto-imports the components `AccountHeader`, `AccountIdentity` and `AccountMenu`.

### `AccountMenu`

The signed-in user's dropdown: the user (with a role badge for anything but `user`), the `account.dropdown` menu
(Account, Admin, sign out), and **Appearance** (light, dark or system, setting `useColorMode().preference`). Items with
`meta.roles` are only listed for users holding one of those roles, the entry for the area you are in is left out, and
items with `order` 99 or more (sign out) come last.

| Prop | Type | Purpose |
| --- | --- | --- |
| `block` | `boolean` | A full-width row (avatar, name, chevrons) for a sidebar footer, as in the [admin](/modules/interface/admin) shell. Without it, an avatar button for a site header. |
| `collapsed` | `boolean` | With `block`: only the avatar, for a collapsed sidebar. |

```vue
<AccountMenu />
<AccountMenu block :collapsed="collapsed" />
```

The colour mode lives here rather than in the header: set `header.colorMode: false` in the
[base layer](/modules/platform/base-layer) app config to drop the header toggle.

#### Overriding parts

The module's components have a lower priority than the app's, so a component with the same name in your app replaces
it. `AccountIdentity` is shown next to the user in the overview's summary card and nowhere else (by default a role badge
for anyone who is not a plain `user`, otherwise nothing); override it to show anything else, such as a member number or a
Frigear ID badge:

```vue
<!-- app/components/Account/AccountIdentity.vue -->
<template>
  <MyIdentityDetails />
</template>
```

### Menu contributions

With [Menu](/modules/interface/menu) installed, each enabled page adds an item. The `account` menu is the account navigation
(and the overview's shortcuts); `account.dropdown` is `AccountMenu`. `order` sorts within the menu.

| Item | Menu | Order | Page |
| --- | --- | --- | --- |
| `account` ("Account") | `account.dropdown` | -99 | `pages.index` |
| `account-overview` ("Overview") | `account` | 0 | `pages.index` |
| `profile` | `account` and `account.dropdown` | 10 | `pages.profile` |
| `security` | `account` | 20 | `pages.security` |
| `api-tokens` | `account` | 25 | `pages.apiTokens` |
| `documents` | `account` | 30 | `pages.documents` |

Other modules slot into the same menu: Membership ([Subscriptions](/modules/commerce/subscriptions)) at 15, Tickets
([Events](/modules/features/events)) at 40 and Applications ([OAuth Server](/modules/identity/oauth-server)) at 50. Pick an order between
these for a new page. The source is registered for the `account` menu.

## Page guard

With `@frigear-nu/authorization` installed, the module adds an `authenticated: true` route rule for `/account` and
`/account/**` (and each `/<locale>` prefix), so every page under it, including those other modules add (membership,
tickets, applications), is closed to guests. Set `authorization.redirectTo` to send guests to the login page instead of
a 401 error. Without the authorization module the pages are not guarded and the module logs a warning.

## Routes

None. The module registers no server routes.

## Translations

The module registers `da` and `en` locale files under the `account.*` namespace (key groups `title`, `menu.*`,
`profile.*`, `documents.*`, `security.*`; the full list is
`src/runtime/i18n/lang/en.json`; the layout and menu use `nav.*`, `appearance.*`, `overview.*` and `accountMenu`).
Without `@nuxtjs/i18n` the English defaults are used. Override strings in your app's
`i18n/locales/<code>.json`, see
[overriding module strings](/modules/platform/module-kit#overriding-module-strings-in-your-app):

```json
{ "account": { "profile": { "title": "My details" } } }
```

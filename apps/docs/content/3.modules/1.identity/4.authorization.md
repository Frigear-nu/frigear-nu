---
title: Authorization
description: Decides what a signed-in user may do, by role or by your own rules, on pages, server routes and in the interface.
---

Authorization decides what a signed-in user may do. You write each rule once, for example "only the author or an admin
may edit a post". Then you apply it to pages, server routes and buttons alike. Install it when your app has roles or
rules beyond "signed in". Who the user is comes from [Auth](/modules/identity/auth); which credential may do what is
explained in [Auth and scopes](/guide/concepts/auth-and-scopes).

The package is `@frigear-nu/authorization`. It also adds a `role` column to users. It works in both
[modes of Auth](/modules/identity/auth). In [client mode](/guide/concepts/glossary), the same rules only decide what the
app shows; see [Client mode](#client-mode).

## What you get

- **Route rules** (on by default): `roles`, `ability`, `guest`, `authenticated`, `scopes` and `sessionOnly` keys on Nuxt's `routeRules`, checked
  for pages and for `/api/**` requests.
- **Abilities** (on by default): rules written once with `defineAbility`, checked on the server with `authorize` and in
  the app with `<Can>`, as in [nuxt-authorization](https://github.com/barbapapazes/nuxt-authorization).
- **Composables and helpers**: `authorize`, `allows` and `denies` on the server, `useAuthorization()`, `<Can>` and
  `<Cannot>` in the app, and role helpers such as `canManageRole`.
- **A `role` column** on users (server mode), with the default `'user'`.
- **Roles admin** (opt-in with `rbac`, needs [Admin](/modules/interface/admin)): read-only pages at `/admin/roles` and a
  Permissions tab on the admin user page. See [The roles admin](#the-roles-admin).

:module-runtime{server client mobile}

::note
**Installed for you:** `@frigear-nu/module-kit`, [`@frigear-nu/auth`](/modules/identity/auth) and
[`@frigear-nu/users`](/modules/identity/users) (client mode: Module Kit and Auth only).

**You add:** `@nuxthub/core` in server mode.

**Optional:** none.
::

## Quick setup

::steps

### Install Authorization

```bash
pnpm add @frigear-nu/authorization @nuxthub/core
```

### Add it to nuxt.config.ts

This closes `/admin/**` to everyone without the `admin` role, and sends visitors to the sign-in page:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/users', '@frigear-nu/authorization'],
  routeRules: {
    '/admin/**': { roles: ['admin'] },
  },
  authorization: {
    redirectTo: '/login', // unauthenticated page visits; client mode defaults to the login path
  },
})
```

### Generate the migration

:::warning
Without a [migration](/guide/concepts/glossary), every write to the `users` table fails: the database lacks the `role`
column.
:::

The module adds a `role` column to `users` (see [Database](#database)). Generate a migration and commit it:

```bash
pnpm db:generate
```

Module authors do the same in every [test fixture](/guide/concepts/glossary) that installs it. See
[Database extensions](/guide/concepts/database-extensions).

### Write an ability and use it

Define the rule once in `shared/utils/abilities.ts`. It is auto-imported in the app and on the server:

```ts [shared/utils/abilities.ts]
export const editPost = defineAbility((user, post: Post) => user.id === post.userId || user.role === 'admin')
```

Check it in a server route, after authenticating:

```ts [server/api/posts/[id].put.ts]
import { idParams } from '@frigear-nu/module-kit/server'

export default defineEventHandler(async (event) => {
  await requireAuth(event) // 401 before anything is loaded
  const { id } = await getValidatedRouterParams(event, idParams().parse)
  const post = await findPost(id)
  await authorize(event, editPost, post) // throws 403 when denied
})
```

And show the button only to users who may use it:

```vue
<Can :ability="editPost" :args="[post]">
  <button>Edit</button>
</Can>
```

`findPost` and `Post` stand for your own code.

::

::callout{color="success" icon="i-lucide-check"}
**What you should see:** a visitor who opens a page under `/admin/` lands on `/login`, with the page in `?redirect=`.
A signed-in user without the `admin` role gets a `403` there.
::

## Options

Options go under the `authorization` key.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `abilities` | `string` | `shared/utils/abilities.ts`, else `shared/abilities.ts` | Path to the abilities file. |
| `resolvers.server` | `string` | session or bearer user | Path to a default-export `(event: H3Event) => Principal \| User \| null` that replaces the server resolver. A principal is `{ kind, user, scopes }` as `getAuth` returns it; a plain user counts as a cookie session. |
| `resolvers.client` | `string` | session user | Path to a default-export `() => User \| null` that replaces the app resolver. |
| `redirectTo` | `string \| false` | client mode: Auth's sign-in path | Where an unauthenticated page visit goes. |
| `rbac` | `boolean` | `false` | Turns on [roles and permissions](#roles-and-permissions) (server mode). |
| `roles` | `RbacConfig` | built-in `admin` > `user` | Shapes the roles: `hierarchy`, `inherits`, `grant`, `revoke`, `labels`, `descriptions`, `definitions`, `defaultRole`. |

**`abilities`.** You need it to refer to abilities by name in route rules and page meta.

**`redirectTo`.** The requested page goes along in `?redirect=`, checked by the shared
[redirect rule](/modules/identity/auth/reference#redirects). Auth's sign-in page sends the user back there. In server
mode without the option, or with `false`, a `401` error is shown instead.

## Roles and permissions

With `rbac: true` every user acts through their role (role-based access control, as in NIST RBAC):

- A **permission** is a scope name modules register with `addAuthScope` (`events:manage`, `tickets:read`), or a
  wildcard (`tickets:*`, `*`). `:pii` permissions are only held by name.
- A **role** holds permissions and **inherits** every permission of the roles below it.
- A user's **session** holds their role's permissions. An **API token** or **access token** holds the scopes it was
  given, capped at every request by what the role holds now.
- Users only see and get the scopes they hold: the token UI, OAuth consent and MCP tool lists leave the rest out.
- **Staff guards** follow the role: `defineStaffGuard({ scope: 'events:manage', ... })` lets in whoever's role holds
  `events:manage`, with no policy plugin. Host `*:authorize` hooks only add conditions.

### Where the roles come from

Three layers merge at build time, so most apps configure nothing:

1. **Built in:** `admin` (every permission, `:pii` included) above `user`. Unknown stored roles act as `defaultRole`
   (`user`), never as admin.
2. **Modules** say which roles get their scopes with `aggregateTo` (`tickets:read` → `user`; no `aggregateTo` → admin
   only) and may ship roles with `addAuthRole` (Events offers `eventmanager` with `events: { settings: { roles: true } }`).
3. **Your app** reshapes them under `authorization.roles`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  authorization: {
    rbac: true,
    roles: {
      // Most senior first: the rank (who may assign which role); each role inherits the next one…
      hierarchy: ['admin', 'manager', 'coordinator', 'eventmanager', 'crew', 'supplier', 'user'],
      // …unless it says otherwise: crew outranks supplier without getting supplier's permissions.
      inherits: { crew: ['user'] },
      grant: { coordinator: ['forms:manage', 'users:read'], manager: ['users:manage'] },
      revoke: { user: ['payments:write'] },
      labels: { eventmanager: 'Event manager' },
    },
  },
})
```

`revoke` takes a permission away from a role, and so from the roles above it, unless one of them is granted it again.
The build logs the permissions only `admin` holds.

### Build errors

The build stops when the role configuration would misrank roles or do nothing silently. Each error names the role or
permission and how to fix it.

| Error | Fix |
| --- | --- |
| An unknown role in `grant`, `revoke`, `inherits`, `labels`, `descriptions`, `defaultRole`, or a definition's `inherits` or `inheritedBy` | Define the role (in `definitions` or `hierarchy`) or fix the name. |
| An unknown permission | Use a registered scope name, a `resource:*` wildcard of one, or `*`. |
| A cycle in the hierarchy, or a role listed twice in `hierarchy` | Remove the loop or the duplicate. |
| `hierarchy` does not start with `admin` | Put `admin` first. Without `hierarchy`, `admin` already outranks every role. |
| `defaultRole: 'admin'` | Pick a junior role: every new user and every unknown stored role would be an admin. |
| `revoke.admin` | Remove it: `admin` holds every permission. |
| A revoked permission a wildcard of the role still covers (`events:*` and revoke `events:manage`) | Grant the specific permissions instead of the wildcard. |
| A revoked permission the role does not hold | Remove it from `revoke`. |

A role listed only in `hierarchy` is created with no permissions of its own, so you can name it in `grant`.

### The role a user acts as

The stored `users.role`, changed by `authorization:role` listeners. For example, an allowlist of admin emails:

```ts [server/plugins/authorization-role.ts]
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('authorization:role', (ctx) => {
    if (ctx.user.emailVerifiedAt && admins.includes(ctx.user.email)) ctx.role = 'admin'
  })
})
```

The users admin offers, and accepts, only roles ranked below the actor's own (admins may manage admins). Rank comes
from `hierarchy`, so it holds even where `inherits` stops permissions flowing up.

### Check permissions

- Server: `requireAuth(event, { scopes: ['events:manage'] })`, a staff guard, or `getAuthUserPermissions(event, user)`
  and `authUserCan(event, user, permission)` from `@frigear-nu/auth`.
- Route rules: `{ scopes: ['reports:read'] }` applies to sessions too, within the role's permissions.
- App: `useAuthorization().can('events:manage')` and `<Can permission="events:manage">`. They decide what the UI shows;
  the API decides what is allowed.
- `GET /api/authorization/me/permissions` answers `{ role, permissions }`.

### The roles admin

With `rbac: true` and [Admin](/modules/interface/admin) installed, [staff](/guide/concepts/glossary) can see the roles
and what each may do. The views are read-only: roles change in `nuxt.config.ts`.

| Page | What it shows |
| --- | --- |
| `/admin/roles` | Every role, most senior first, with its user count, and a tab with every permission against every role. |
| `/admin/roles/:name` | One role: each permission it holds and why (granted, inherited, ...), and its users. |
| Permissions tab of `/admin/users/:id` | What the user's role lets them do. Needs [Widget](/modules/interface/widget). |

The pages and [their routes](#routes) need the `roles:read` permission. Only `admin` holds it unless you grant it:
`grant: { manager: ['roles:read'] }`. The `authorization:authorize` hook can add conditions. A host route rule such as
`'/api/admin/**': { roles: ['admin'] }` still applies on top.

::caution
Turning `rbac` on removes full access (`*`) from sessions. A route that requires a scope the user's role does not hold
answers `403` from then on. Check the build log for permissions only `admin` holds before you switch it on.
::

## Server

Abilities are defined once and checked on the server with helpers that take the `event` first. Everything here is
auto-imported.

### Define abilities

`defineAbility`, `allow` and `deny` are auto-imported in the app and on the server. The first argument of an ability is
the resolved user. The rest are the arguments passed when checking.

```ts
// shared/utils/abilities.ts
export const isAdmin = defineAbility(user => user.role === 'admin')

export const editPost = defineAbility((user, post: Post) =>
  user.id === post.userId || user.role === 'admin' || deny({ message: 'Not your post' }))

// Let guests reach the policy (it receives `null`).
export const viewPost = defineAbility({ allowGuest: true }, (user, post: Post) => post.published || user?.id === post.userId)
```

Without `allowGuest`, [visitors](/guide/concepts/glossary) are denied before the ability runs.

```ts
type AuthorizationResponse = { authorized: boolean, statusCode?: number, message?: string }
type AuthorizerResponse = boolean | AuthorizationResponse | Promise<boolean | AuthorizationResponse>
type Authorizer<User = any> = (user: User, ...args: any[]) => AuthorizerResponse

interface Ability<User = any> {
  allowGuest: boolean
  original: Authorizer<User>
  execute: (user: User | null, ...args: any[]) => AuthorizerResponse
}

allow() // { authorized: true }
deny({ statusCode?, message? }) // statusCode defaults to 403
```

### Check on the server

```ts
await authorize(event, editPost, post) // throws an h3 error when denied (403 by default)
if (await allows(event, isAdmin)) { /* ... */ }
if (await denies(event, isAdmin)) { /* ... */ }
const user = await resolveAuthorizationUser(event) // the configured server resolver
```

### Roles in sessions and tokens

The default server resolver uses [`getAuth`](/modules/identity/auth/server#protect-a-route). So route rules and
abilities see cookie [sessions](/guide/concepts/glossary), API tokens and access tokens alike. Route rules also see
**how** the caller authenticated: a rule with `roles` or `ability` is [session-only by default](#bearer-credentials-and-scopes).

- A token carries no role. A bearer request loads the user from the database, so a role change, a ban or a deleted
  account applies to the next call.
- A cookie session is read again from the database on every request too, so a role change applies to the next
  request. A deleted account ends the session.
- The default app resolver reads the session user from `/api/_auth/session`, which answers the same fresh user.

### Pure helpers

`@frigear-nu/authorization/utils` exports functions that need no framework. The helpers above use them, and they are
useful in tests:

```ts
import {
  check, allows, denies, authorize, // (ability, user, ...args), no event
  matchRoute, resolveRule, evaluateRule, normalizeAuthorizeMeta,
  roleIsHigher, roleIsHigherOrEqual, canManageRole,
  AuthorizationError, createAuthorizationError, isAbility, ROUTE_RULE_KEYS,
} from '@frigear-nu/authorization/utils'

check(ability, user, ...args) // Promise<AuthorizationResponse>
matchRoute('/admin/**', '/admin/users') // true: '/x/**' prefix, '*' one segment, or an exact path
```

For apps with ranked roles, the role helpers take a hierarchy **from highest to lowest** rank. Unknown roles never
outrank or equal anything:

```ts
const roles = ['admin', 'manager', 'member', 'user'] as const
roleIsHigher(roles, 'manager', 'member') // true
roleIsHigherOrEqual(roles, 'member', 'member') // true
canManageRole(roles, 'manager', 'manager') // false: only strictly lower roles
canManageRole(roles, 'admin', 'admin', { equalAllowedFor: ['admin'] }) // true
```

## App

Components and composables that show or hide parts of the interface, and the route rules that guard pages and API
routes.

```vue
<Can :ability="editPost" :args="[post]">
  <button>Edit</button>
  <template #fallback><span>Read only</span></template>
</Can>
<Cannot :ability="isAdmin">You are not an admin.</Cannot>
```

`Can` accepts one ability, or an array that must all pass. With an array, `args` is an array of argument arrays.

```ts
const { allows, denies, authorize } = useAuthorization() // each is also auto-imported on its own
if (await allows(editPost, post)) { /* ... */ }
```

::warning
Checks in the app only shape the interface. Enforce permissions on the server with `authorize(event, ...)` or route
rules.
::

### Route rules

Rules are keys on Nuxt's native [`routeRules`](https://nuxt.com/docs/4.x/guide/concepts/rendering#hybrid-rendering).

- Patterns follow route rules: a `/admin/**` prefix, `*` for one segment, or an exact path.
- Every matching pattern contributes. Keys of more specific patterns override less specific ones.
- A global route middleware guards pages, also during server-side rendering.
- A Nitro middleware also enforces rules for `/api/**`. It matches the percent-decoded path the router dispatches on, so
  `/api/%61dmin/users` hits the `/api/admin/**` rule. An API path holding an encoded `/` (`%2F`), a `\` or a `.`/`..`
  segment is refused with a 400.
- Only pages and `/api/**` are enforced. A rule for another server route (`/mcp`, `/oauth/**`) matches no page and is not
  enforced on the server: the build warns about it. Guard such routes in their handler with `requireAuth`.
- `/api/admin/**` covers the staff API of every module (events, forms, payments, oauth-server, users, ...), so one rule
  guards all of them.

```ts
export default defineNuxtConfig({
  routeRules: {
    '/admin/**': { roles: ['admin'], ssr: false },
    '/api/admin/**': { roles: ['admin'] }, // every module's staff API lives here
    '/admin/login': { authenticated: false }, // opens a sub-route of a protected pattern
    '/billing': { ability: 'isAdmin' }, // export name from the abilities file; no arguments
    '/members/**': { authenticated: true },
    '/api/reports': { roles: ['admin'], scopes: ['reports:read'] }, // tokens with that scope pass too
    '/pricing': { guest: true },
  },
})
```

| Key | Meaning |
| --- | --- |
| `roles` | Allowed `user.role` values. `[]` clears an inherited restriction. |
| `ability` | Name of an exported ability that must allow the user. |
| `guest` | Let visitors reach the checks. The checks still apply. |
| `authenticated` | `true` requires a [signed-in user](/guide/concepts/glossary). `false` turns authorization off for the path. |
| `scopes` | Scopes an API token or access token must carry (`*` and `resource:*` count as usual). Lets bearer credentials through. |
| `sessionOnly` | `true` refuses every bearer credential with `403`. `false` accepts them. Defaults as described [below](#bearer-credentials-and-scopes). |

#### Bearer credentials and scopes

A rule checks the user's role, not what the credential was granted. So a rule with `roles` or `ability` is **session-only
by default**: an API token or access token gets `403`, even when its owner is an admin. Otherwise a token limited to
`profile:read` would pass `'/api/admin/**': { roles: ['admin'] }` with the full power of its owner.

- `scopes: ['reports:read']` lets bearer credentials through when they carry those scopes. `roles` and `ability` still
  have to match the owner.
- `sessionOnly: false` lets bearer credentials through with any scopes. Use it only when the handler checks scopes itself
  (`requireAuth(event, { scopes })`).
- A rule with neither `roles` nor `ability` (`{ authenticated: true }`) accepts any credential. Add `scopes` or
  `sessionOnly: true` to narrow it.
- Page rules run in the app and only see the session.

This is a change for hosts that sent bearer tokens through role rules: add `scopes` or `sessionOnly: false` to those
rules. Rules stay coarse. A handler that serves bearer callers should still call `requireAuth` with the scopes it needs.

A visitor gets `401`. A wrong role or a denied ability gets `403`. Per page, `definePageMeta` **replaces** the matching
route rules:

```vue
<script setup lang="ts">
definePageMeta({ authorize: isAdmin }) // an ability, an ability name, or { roles, ability, args, guest }
</script>
```

`definePageMeta({ authorize: false })` opens the page, whatever the route rules say.

```ts
interface RouteRule {
  roles?: string[]
  ability?: string | Ability
  args?: unknown[] // page meta only
  guest?: boolean
  authenticated?: boolean
  scopes?: string[]
  sessionOnly?: boolean
}
type AuthorizeMeta = string | Ability | RouteRule | false
```

::note
Nuxt's app-side route rules matcher only keeps a fixed set of keys. So the module collects the authorization keys from
`routeRules` and `nitro.routeRules` at build time. Rules added at runtime are not picked up.
::

### Sign-in paths

Auth's anonymous entry points are always reachable, so `'/**': { authenticated: true }` does not lock users out of
signing in. They come from `runtimeConfig.public.authentication.publicPaths`
([Auth reference](/modules/identity/auth/reference#anonymous-paths)):

- in server mode, the sign-in, sign-up and password-reset pages, `/auth/**`, `/api/auth/**` and `/api/_auth/**`;
- in client mode, the sign-in page and the callback.

How the exemption works:

- An exempt pattern resets the rule. Guards of **less specific** patterns stop there, for pages and for `/api`
  requests.
- An app rule for the **same or a more specific** pattern still applies. `'/api/auth/me/tokens': { roles: ['admin'] }`
  keeps working under the `/api/auth/**` exemption.
- With `@nuxtjs/i18n`, the page patterns are exempt under every locale prefix too (`/da/login`). API paths are not
  prefixed.

The list ships as `runtimeConfig.public.authorization.exempt`. Auth's pages carry no `authorize` page meta, because it
would beat an app's own rule for them.

### Client mode

With `authentication.mode: 'client'` (see [Auth client mode](/modules/identity/auth/client-mode)), the module runs in
the app only.

- The route middleware, `useAuthorization`, `allows` / `denies` / `authorize`, `<Can>` and `<Cannot>` work as in server
  mode, on the user of `useUserSession()`.
- There is no server side: no `role` column, no server resolver, no server helpers and no Nitro middleware.
- `user.role` is optional. It is the ID token's `role` claim, when there is one, or what `client.mapUser` returns.
- Until an async mapping finishes, and while it fails offline, a `roles` rule sees only the claim.

::caution
In client mode the guards shape the interface; they are not access control. See
[Security](/modules/identity/auth/client-mode#security).
::

## Hooks

Your app answers these Nitro hooks from a server plugin (`server/plugins/*.ts`).

| Hook | When | Payload |
| --- | --- | --- |
| `authorization:role` | The role a user acts as is resolved (sessions and tokens alike) | `AuthorizationRoleContext`: `ctx.user` is the stored user. Set `ctx.role` to change it. |
| `authorization:authorize` | Every request to the roles admin routes | `AuthorizationAuthorizeContext`. `allowed` starts as whether the role holds `roles:read`. |

```ts
interface AuthorizationAuthorizeContext {
  event: H3Event
  userId: number // identify the caller from this, never from the session
  allowed: boolean
}
```

## Routes

Routes the module registers, and who may call them. Paths come from `authorizationApi` in
`@frigear-nu/authorization/api`.

| Method | Path | Who | Answers |
| --- | --- | --- | --- |
| `GET` | `/api/authorization/me/permissions` (`me.permissions`) | signed in | The caller's role and permissions. |
| `GET` | `/api/admin/authorization/roles` (`admin.roles`) | `roles:read` | Every role, most senior first. |
| `GET` | `/api/admin/authorization/roles/:name` (`admin.role(name)`) | `roles:read` | One role and why it holds each permission. `404` for an unknown role. |
| `GET` | `/api/admin/authorization/roles/:name/users` (`admin.roleUsers(name)`) | `roles:read` | The users with that stored role, paginated. |
| `GET` | `/api/admin/authorization/permissions` (`admin.permissions`) | `roles:read` | Every permission against every role. |

The `/api/admin/authorization/**` routes exist only with `rbac: true`.

In server mode, the module adds one column to the `users` table through a

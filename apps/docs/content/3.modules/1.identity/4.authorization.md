title: Authorization
description: Policy-based authorization (abilities, route rules and <Can>) with a role column on users.
---

Policy-based authorization as a [Nuxt module](https://nuxt.com/docs/4.x/guide/modules): what an already-identified user
may do, through abilities, route rules and `<Can>`, plus a `role` column on users. Authentication stays in
[Auth](/modules/identity/auth). The design follows [nuxt-authorization](https://github.com/barbapapazes/nuxt-authorization):
policies are functions and a resolver (one for the app, one for the server) injects the current user. For how this fits
with scopes and staff guards, see [Auth and scopes](/guide/concepts/auth-and-scopes).

It works in both [modes of Auth](/modules/identity/auth). In client mode (a SPA or a Capacitor app) the same rules
decide what the app shows; see [Client mode](#client-mode).

:module-runtime{server client mobile}

::note
**Requires** `@nuxthub/core`, `@frigear-nu/module-kit`, [`@frigear-nu/auth`](/modules/identity/auth) and
[`@frigear-nu/users`](/modules/identity/users); all are installed automatically. With `authentication.mode: 'client'`
only `@frigear-nu/module-kit` and Auth are installed (`@nuxthub/core` is an optional peer).
::

## Quick setup

```bash
pnpm add @frigear-nu/authorization @nuxthub/core
```

```ts
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/users', '@frigear-nu/authorization'],
  routeRules: {
    '/admin/**': { roles: ['admin'] },
  },
  authorization: {
    redirectTo: '/login', // unauthenticated page visits; omit to show a 401 error
  },
})
```

```ts
// shared/utils/abilities.ts - auto-imported in the app and the server
export const editPost = defineAbility((user, post: Post) => user.id === post.userId || user.role === 'admin')
```

```ts
// server/api/posts/[id].put.ts
export default defineEventHandler(async (event) => {
  const post = await findPost(getRouterParam(event, 'id'))
  await authorize(event, editPost, post) // throws 403 when denied
})
```

```vue
<Can :ability="editPost" :args="[post]">
  <button>Edit</button>
</Can>
```

::warning
The module adds a `role` column to `users` (see [Database](#database)). Generate and commit a migration in your app and in
every fixture that uses it; see [Database extensions](/guide/concepts/database-extensions).
::

## Options

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `abilities` | `string` | `shared/utils/abilities.ts`, else `shared/abilities.ts` | Path to the abilities file. Needed to refer to abilities by name in route rules and page meta. |
| `resolvers.server` | `string` | session or bearer user | Path to a default-export `(event: H3Event) => User \| null` replacing the server resolver. |
| `resolvers.client` | `string` | session user | Path to a default-export `() => User \| null` replacing the app resolver. |
| `redirectTo` | `string` | - | Redirect target for unauthenticated page navigation, with the requested page in `?redirect=` (only same-site paths; [Auth](/modules/identity/auth)'s login page sends the user back there). Without it a `401` error is shown. |

## Defining abilities

`defineAbility`, `allow` and `deny` are auto-imported in app and server. The first argument of a policy is the resolved
user, the rest are the arguments passed when checking.

```ts
// shared/utils/abilities.ts
export const isAdmin = defineAbility(user => user.role === 'admin')

export const editPost = defineAbility((user, post: Post) =>
  user.id === post.userId || user.role === 'admin' || deny({ message: 'Not your post' }))

// Let guests reach the policy (it receives `null`).
export const viewPost = defineAbility({ allowGuest: true }, (user, post: Post) => post.published || user?.id === post.userId)
```

Without `allowGuest`, guests are denied before the policy runs.

```ts
type AuthorizationResponse = { authorized: boolean, statusCode?: number, message?: string }
type AuthorizerResponse = boolean | AuthorizationResponse | Promise<boolean | AuthorizationResponse>
type Authorizer<User = any> = (user: User, ...args: any[]) => AuthorizerResponse

interface Ability<User = any> {
  allowGuest: boolean
  original: Authorizer<User>
  execute: (user: User | null, ...args: any[]) => AuthorizerResponse
}

allow() // { authorized: true }
deny({ statusCode?, message? }) // statusCode defaults to 403
```

## Server

The server helpers take the `event` first and are auto-imported.

```ts
await authorize(event, editPost, post) // throws an h3 error when denied (403 by default)
if (await allows(event, isAdmin)) { /* ... */ }
if (await denies(event, isAdmin)) { /* ... */ }
const user = await resolveAuthorizationUser(event) // the configured server resolver
```

### Roles in sessions and tokens

The default server resolver uses [`getAuth`](/modules/identity/auth/server#protecting-a-route), so route rules and abilities apply to
cookie sessions, user API tokens and OAuth access tokens alike. A bearer request loads the user from the database, so
`role` is always current. A cookie session carries the user stored at login, so a role change reaches it after the next
sign-in (or when your code calls `setUserSession`). The default app resolver reads the same session user.

Policy hooks of other modules (`events:authorize`, `forms:authorize`, `users:admin:authorize`, `payments:authorize`,
`oauth:authorize`) receive `ctx.userId`. Identify the caller from it, not from the session on `ctx.event`, which is empty
for bearer requests.

### Pure helpers

`@frigear-nu/authorization/utils` exports framework-agnostic functions, used by the helpers above and useful in tests:

```ts
import {
  check, allows, denies, authorize, // (ability, user, ...args), no event
  matchRoute, resolveRule, evaluateRule, normalizeAuthorizeMeta,
  roleIsHigher, roleIsHigherOrEqual, canManageRole,
  AuthorizationError, createAuthorizationError, isAbility, ROUTE_RULE_KEYS,
} from '@frigear-nu/authorization/utils'

check(ability, user, ...args) // Promise<AuthorizationResponse>
matchRoute('/admin/**', '/admin/users') // true: '/x/**' prefix, '*' one segment, or an exact path
```

For apps with ranked roles, the role helpers take a hierarchy **from highest to lowest** rank; unknown roles never
outrank or equal anything:

```ts
const roles = ['admin', 'manager', 'member', 'user'] as const
roleIsHigher(roles, 'manager', 'member') // true
roleIsHigherOrEqual(roles, 'member', 'member') // true
canManageRole(roles, 'manager', 'manager') // false: only strictly lower roles
canManageRole(roles, 'admin', 'admin', { equalAllowedFor: ['admin'] }) // true
```

## App

```vue
<Can :ability="editPost" :args="[post]">
  <button>Edit</button>
  <template #fallback><span>Read only</span></template>
</Can>
<Cannot :ability="isAdmin">You are not an admin.</Cannot>
```

`Can` accepts one ability, or an array that must all pass (then `args` is an array of argument arrays).

```ts
const { allows, denies, authorize } = useAuthorization() // each is also auto-imported on its own
if (await allows(editPost, post)) { /* ... */ }
```

::warning
Client checks only improve the UI. Enforce permissions on the server with `authorize(event, ...)` or route rules.
::

### Route rules

Rules are keys on Nuxt's native [`routeRules`](https://nuxt.com/docs/4.x/guide/concepts/rendering#hybrid-rendering).
Patterns follow route rules (`/admin/**` prefix, `*` one segment, or an exact path). Every matching pattern contributes
and keys of more specific patterns override less specific ones. Pages are gated by a global route middleware (also
during SSR); rules for `/api/**` are also enforced by a Nitro middleware. `/api/admin/**` covers the staff API of every
module (events, forms, payments, oauth-server, users, ...), so one rule gates all of them.

```ts
export default defineNuxtConfig({
  routeRules: {
    '/admin/**': { roles: ['admin'], ssr: false },
    '/api/admin/**': { roles: ['admin'] }, // every module's staff API lives here
    '/admin/login': { authenticated: false }, // opens a sub-route of a protected pattern
    '/billing': { ability: 'isAdmin' }, // export name from the abilities file; no arguments
    '/members/**': { authenticated: true },
    '/pricing': { guest: true },
  },
})
```

| Key | Meaning |
| --- | --- |
| `roles` | Allowed `user.role` values (`[]` clears an inherited restriction). |
| `ability` | Name of an exported ability that must allow the user. |
| `guest` | Let unauthenticated visitors reach the checks (they still apply). |
| `authenticated` | `true` requires a logged-in user; `false` disables authorization for the path. |

Guests get `401`; a wrong role or a denied ability gets `403`. Per page, `definePageMeta` **replaces** the matching route
rules:

```vue
<script setup lang="ts">
definePageMeta({ authorize: isAdmin }) // an ability, an ability name, or { roles, ability, args, guest }
</script>
```

`definePageMeta({ authorize: false })` opens the page, whatever the route rules say.

```ts
interface RouteRule {
  roles?: string[]
  ability?: string | Ability
  args?: unknown[] // page meta only
  guest?: boolean
  authenticated?: boolean
}
type AuthorizeMeta = string | Ability | RouteRule | false
```

### Sign-in paths

Auth's anonymous entry points are always reachable, so `'/**': { authenticated: true }` does not lock users out of
signing in. They come from `runtimeConfig.public.authentication.publicPaths`
([Auth reference](/modules/identity/auth/reference#anonymous-paths)): in server mode the login, register and
password-reset pages, `/auth/**`, `/api/auth/**` and `/api/_auth/**`; in client mode the login page and the callback.

- An exempt pattern resets the rule: guards of **less specific** patterns stop there, for pages and for `/api` requests.
- An app rule for the **same or a more specific** pattern still applies. `'/api/auth/me/tokens': { roles: ['admin'] }`
  keeps working under the `/api/auth/**` exemption.
- With `@nuxtjs/i18n`, the page patterns are exempt under every locale prefix too (`/da/login`). API paths are not
  prefixed.

The list ships as `runtimeConfig.public.authorization.exempt`. Auth's pages carry no `authorize` page meta, which would
beat an app's own rule for them.

::note
Nuxt's app-side route rules matcher only keeps a fixed set of keys, so the module collects the authorization keys from
`routeRules` and `nitro.routeRules` at build time. Rules added at runtime are not picked up.
::

## Client mode

With `authentication.mode: 'client'` (see [Auth client mode](/modules/identity/auth/client-mode)) the module runs in
the app only:

- The route middleware, `useAuthorization`, `allows` / `denies` / `authorize`, `<Can>` and `<Cannot>` work as in server
  mode, on the user of `useUserSession()`.
- There is no server side: no `role` column, no server resolver, no server helpers and no Nitro middleware.
- `user.role` is optional. It is the id_token's `role` claim, when there is one, or what `client.mapUser` returns.
  Until an async mapping finishes (and while it fails offline), a `roles` rule sees only the claim.

::warning
In client mode the guards are UX, not access control. The tokens and the mapped user live in storage the device owner
can edit, so a route rule or a `role` only decides what to show. Bundled pages must not contain privileged data. Every
protected read and write goes to an API that checks `requireAuth` with scopes.
::

## Database

In server mode the module extends the `users` table through a [database extension](/guide/concepts/database-extensions) with one column:
`role` (`text`, not null, default `'user'`).

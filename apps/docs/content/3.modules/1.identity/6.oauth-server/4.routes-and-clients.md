## Routes

Paths are typed in `@frigear-nu/oauth-server/utils`: `oauthServerApi` for the module API
(`oauthServerApi.admin.application(id)`, ...) and `oidc` for the spec endpoints (`oidc.token`, ...). Use them instead of
string literals.

The OAuth / OpenID Connect endpoints keep their standard paths and answer spec-shaped bodies: `token` and `revoke` reply
`{ error, error_description }` (RFC 6749 §5.2) to every failure, including a malformed body (`400 invalid_request`).

| Method | Path | Auth | Status | Purpose |
| --- | --- | --- | --- | --- |
| `GET` | `/.well-known/openid-configuration` | none | 200 | Discovery document. |
| `GET` | `/.well-known/jwks.json` | none | 200 | Public signing keys. |
| `GET` | `/oauth/authorize` | none (signed-out users go to the login page) | 302 | Authorization request: validates it (`400` otherwise), checks access (`403`), then redirects to the consent page. |
| `POST` | `/oauth/authorize` | session only | 200 | The consent decision; answers `{ redirectUrl }` (the callback with `code` and `state`, or `error=access_denied`). |
| `POST` | `/oauth/token` | client credentials, or `client_id` for [public clients](#public-clients) | 200 | `authorization_code` and `refresh_token` grants. HTTP Basic or `client_id` + `client_secret` in the body. The response adds `refresh_token_expires_in` (seconds until the new refresh token expires; see [Session lifetimes](#session-lifetimes)). |
| `POST` | `/oauth/revoke` | client credentials, or `client_id` for [public clients](#public-clients) | 200 | Revokes a refresh token and the rest of its family (RFC 7009). |
| `GET` | `/oauth/userinfo` | bearer access token | 200 | Claims filtered by scope. |
| `GET` | `/api/oauth-server/consent` | session only | 200 | Data for the consent screen (`ConsentDto`); the query is the authorization request. |
| `GET` | `/api/oauth-server/me/applications` | session only | 200 | Applications the user may sign in to (`UserApplicationDto[]`). |
| `GET` | `/api/oauth-server/me/sessions` | session only | 200 | The user's [sign-ins in applications](#ending-sign-ins) (`OAuthSessionDto[]`), most recently active first. |
| `DELETE` | `/api/oauth-server/me/sessions/:id` | session only | 204 | Signs the user out of one sign-in (a refresh-token family). `404 not_found` when it is not theirs or already ended. |
| `DELETE` | `/api/oauth-server/me/sessions` | session only | 204 | Signs the user out of every application. |
| `GET` | `/api/admin/oauth-server/applications` | session + `oauth:authorize` | 200 | One page `{ items, total, page, pageSize }` of `AdminApplicationDto`; `page`, `pageSize` (max 100), `q` (name or client id), `sort` (`createdAt`, `name`, `priority`), `order`. |
| `POST` | `/api/admin/oauth-server/applications` | session + `oauth:authorize` | 201 | Create; returns `CreatedApplicationDto` (the secret, shown once). |
| `GET` | `/api/admin/oauth-server/applications/:id` | session + `oauth:authorize` | 200 | One application (`AdminApplicationDto`). |
| `PATCH` | `/api/admin/oauth-server/applications/:id` | session + `oauth:authorize` | 200 | Update; returns the application. Disabling it signs everyone out. `409 managed_by_config` for a config-owned field of a [configured client](#configured-clients). |
| `DELETE` | `/api/admin/oauth-server/applications/:id` | session + `oauth:authorize` | 204 | Delete, with its codes and refresh tokens. `409 managed_by_config` for a configured client. |
| `POST` | `/api/admin/oauth-server/applications/:id/secret` | session + `oauth:authorize` | 200 | Rotate the client secret; `{ clientSecret }` once (`400 bad_request` for public clients). |
| `POST` | `/api/admin/oauth-server/applications/:id/revoke` | session + `oauth:authorize` | 200 | Sign everyone out of the application; returns the application. |

The module API fails with the [toolkit errors](/modules/platform/module-kit/server-toolkit): `401`, `403 forbidden` (the
`oauth:authorize` gate), `404 not_found`, `400 bad_request`, and h3's `400` validation error for a malformed body or
query.

### How a sign-in works

```text
application ──▶ GET  /oauth/authorize?client_id&redirect_uri&response_type=code&state&code_challenge&code_challenge_method=S256[&scope&nonce]
                 not signed in ──▶ <login page>?redirect=/oauth/authorize?… ──▶ back here
                 role/access check (403 if denied) ──▶ /authorize?… (consent page)
user approves ──▶ POST /oauth/authorize {…, approved: true} ──▶ redirect to the application's callback with ?code&state
application ──▶ POST /oauth/token (code + code_verifier + client credentials) ──▶ access_token, id_token, refresh_token
```

- **PKCE (S256) is mandatory.** Applications are **confidential** clients with a secret, shown once when created, unless
  you register them as [public clients](#public-clients).
- **Redirect URIs are derived**, not free-form: `websiteUrl + callbackPath`, the application's explicit `redirectUris`, or
  its `previewUrlPattern` (`https://*.vercel.app`, where `*` is one hostname label). `https` is required except for
  `localhost`. Public clients may also list [native redirect URIs](#native-redirect-uris).
- **Refresh tokens rotate.** Presenting an already-used refresh token is treated as theft and revokes the whole family.
- Access is re-checked on every token exchange, `userinfo` call and API call, so disabling an application or removing a
  role also stops refreshes and API calls.
- **Access tokens are bare** (`sub`, `scope`, `client_id`, `aud`, `iss`, `exp`, `iat`, `jti`, header `typ: at+jwt`);
  identity claims (`name`, `picture`, `email`) live in the ID token and `userinfo`, per granted scope.
- Unsupported scopes are dropped; a request with no `scope` gets `openid profile email`, and one whose scopes are all
  unsupported is rejected with `400`.

### Public clients

A native app or single-page app cannot keep a secret: anything compiled into the app is public. Register it as a
**public client** (`clientType: 'public'`, or *Client type* in the admin form; it cannot be changed afterwards):

- It gets **no client secret**. `/oauth/token` and `/oauth/revoke` identify it by `client_id` alone
  (`token_endpoint_auth_methods_supported` lists `none`), and `createApplication` returns `secret: null`.
- **PKCE (S256) is what protects the code exchange**, exactly as for confidential clients. It is already mandatory.
- **Refresh tokens rotate** and a replayed one revokes the family, which is the compensating control for a refresh token
  that can be used without a secret. Tokens stay bound to the client they were issued to: another client cannot refresh
  or revoke them.
- Sending a `client_secret` to a public client is refused (`401 invalid_client`) rather than ignored, because it means the
  app was configured with the wrong kind of client. An empty `client_secret` field is accepted.
- Confidential clients are unchanged: without their secret every token and revoke request is `401`.
- **The website URL is optional.** A native app often has none: leave it out and the consent screen shows no website
  link, and only the listed `redirectUris` are accepted (at least one is required). A confidential client always needs
  one, since its callback is derived from it.

#### Unlisted applications

Turn off *Show in the users' application list* (`isListed: false`, or `listed: false` for a
[configured client](#configured-clients)) for an application users only open themselves, such as a mobile app. It is
left out of the [applications list](/modules/identity/oauth-server/server#app), the `oauth-server:mine` bootstrap key and the `my-oauth-applications` MCP
tool. Signing in works as before, and the admin table marks it **Unlisted**.

#### Native redirect URIs

A public client may add **custom-scheme redirect URIs** to `redirectUris`, for the app to receive the code after the
system browser step:

- a private-use scheme, preferably the reverse of a domain you control: `com.example.app:/callback` (RFC 8252 §7.1);
- a webview origin such as `capacitor://localhost/auth/callback`.

They are matched **exactly**: no prefixes, wildcards or query strings. Web and dangerous schemes (`javascript:`, `data:`,
`file:`, `blob:`, ...), credentials and fragments are rejected when the application is saved, and a confidential client
cannot use custom schemes at all. `https` redirects (for example universal / app links) work for both client types.

::warning
A custom scheme can be claimed by any app on the device, which PKCE makes harmless for the code itself, but where the
platform offers it prefer an `https` universal/app link as the redirect.
::

#### Calling from a browser on another origin

The webview of a Capacitor app runs at `capacitor://localhost` (iOS) or `https://localhost` (Android), so its requests to
this server are cross-origin. List those origins in `cors.origins`:

```ts
export default defineNuxtConfig({
  oauthServer: {
    cors: { origins: ['capacitor://localhost', 'https://localhost'] },
  },
})
```

- Only `/oauth/token`, `/oauth/revoke`, `/oauth/userinfo` and the `/.well-known` documents answer CORS requests, and only
  for listed origins. `/oauth/authorize` is a top-level navigation with the user's cookie session, and is never opened up.
- No `Access-Control-Allow-Credentials` is sent, so cookies never travel cross-origin; the app authenticates with
  its client id and bearer tokens.
- Origins must be exact (`scheme://host[:port]`). `*` is rejected when the app starts.

Your own API (the routes the app calls with the access token as `Authorization: Bearer`) is opened to the same origins by
listing its path prefixes in `cors.paths`:

```ts
export default defineNuxtConfig({
  oauthServer: {
    cors: { origins: ['capacitor://localhost', 'https://localhost'], paths: ['/api/'] },
  },
})
```

- Requests under a prefix get `Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS`,
  `Access-Control-Allow-Headers: authorization, content-type, accept` and `Access-Control-Expose-Headers: www-authenticate`
  (so the app can read why a token was refused). Preflights are answered `204`.
- `/api/` matches `/api` and everything below it, not `/apis`. `/oauth/authorize` stays closed even when a prefix covers it.
- Cookies still do not travel, so session-only routes (account settings, admin) answer `401` to cross-origin calls: only
  what an access token may do is reachable.
- The headers come from `applyBearerCors` in [`@frigear-nu/module-kit/server`](/modules/platform/module-kit/server-toolkit#bearer-cors), which
  you can use for a middleware of your own.

### Configured clients

An app that ships with its `client_id` compiled in (a mobile app, a single-page app) needs that id to be the same in every
environment. Define it in `clients` instead of the admin UI and it gets a **fixed id**:

```ts
export default defineNuxtConfig({
  oauthServer: {
    cors: { paths: ['/api/'] },
    clients: [{
      id: 'mobile',
      name: 'Example mobile',
      redirectUris: ['com.example.app:/auth/callback'],
      // Only accepted under `nuxt dev`: the app's dev server in a desktop browser.
      devRedirectUris: ['http://localhost:3001/auth/callback'],
      // The webviews' origins (the redirect URIs have none to derive).
      corsOrigins: ['capacitor://localhost', 'https://localhost'],
    }],
  },
})
```

| Field | Type | Default | Purpose |
| --- | --- | --- | --- |
| `id` | `string` | (required) | The `client_id`: 3 to 64 letters, digits, `.`, `_` or `-`, starting with a letter or digit. Not `app_…`, the prefix of created applications. |
| `name` | `string` | (required) | Shown on the consent screen and in the admin UI. |
| `type` | `'public'` | `'public'` | Only public clients (PKCE, no secret) can be configured: a secret does not belong in config. |
| `redirectUris` | `string[]` | (required) | Exact redirect URIs: https (http for localhost) or [native](#native-redirect-uris). |
| `devRedirectUris` | `string[]` | `[]` | Added to `redirectUris` under `nuxt dev` only. |
| `websiteUrl` | `string \| null` | derived | The application's origin. Defaults to the origin of the first web redirect URI; a native-only client has none (`null`). |
| `listed` | `boolean` | `true` | Shown in the users' [applications list](/modules/identity/oauth-server/server#app). `false` makes it [unlisted](#unlisted-applications). |
| `description`, `icon`, `allowedRoles`, `tags` | | | As for any application. |
| `refreshToken` | `{ idleTtl?, maxAge? }` | the global `refreshToken` | This client's [session lifetime](#session-lifetimes) in seconds, e.g. `{ idleTtl: 60 * 60 * 24 * 180 }` for a native app. |
| `allowLongBrowserSessions` | `boolean` | `false` | Silences the warning for a browser client above 7 days idle. |
| `corsOrigins` | `string[] \| false` | derived | Origins added to `cors.origins`. Defaults to the origins of the redirect URIs that have one (`https://app.example.com`, `http://localhost:3001`, `capacitor://localhost`); `false` adds none. |

- The list is checked when the app starts (an invalid id, redirect URI or origin is a build error) and again at runtime,
  where `NUXT_OAUTH_SERVER_CLIENTS` (JSON) can replace it. The CORS origins are added at runtime, so a client the
  override removes takes its origins with it. An invalid override is logged once; application lookups answer
  `500 not_configured`, while CORS falls back to `cors.origins` and same-origin requests are untouched.
- **Config is the source of truth when reading.** Each server instance creates the missing clients in
  `oauth_applications` on the first OAuth request (active; retried if the write fails), and from then on every lookup
  (authorize, token, admin list, the user's applications) takes the name, website, redirect URIs, roles, tags, listing and session lifetime from
  its own config, not from the row. Instances with different config (a rolling deploy, a preview or `nuxt dev` on the
  same database) therefore never overwrite each other: a dev server's `devRedirectUris` are never accepted by production.
- A native-only client (no web redirect URI and no login URL) is left out of the signed-in user's
  [applications list](/modules/identity/oauth-server/server#app): it has no website, so there is nothing to open.
- In the admin UI they carry a **Managed in nuxt.config** badge and `managed: true` in `AdminApplicationDto`. Staff can
  disable them (`isActive` is set only when created, so a disabled client stays disabled) and change the priority and
  login URL. Changing a config-owned field or deleting one answers `409 managed_by_config`; sending the current value is
  fine.
- An id that already belongs to a confidential application is left alone: the configured client is ignored (not
  managed, no CORS origins, editable as usual), with a warning in the server log.
- A client removed from `clients` is **not** deleted, so its users stay signed in: the server warns once, and it becomes
  an ordinary application you can edit or delete in the admin UI.

### Session lifetimes

Access tokens stay short (`accessTokenTtl`, 15 minutes). How long a user stays signed in to an application is decided by
its refresh tokens, with two limits in seconds:

- **`idleTtl`**: how long a refresh token lives unused. Every refresh rotates it into a new one with a fresh window, so
  an app that is opened regularly stays signed in.
- **`maxAge`**: how long a sign-in lives in total, counted from when the user signed in (`auth_time`), however often it
  is refreshed. `null` = no cap.

A new refresh token expires at `min(now + idleTtl, authTime + maxAge)`. The first match wins:

1. The application's own **Session length** and **Sign in again after** in the admin UI (`refreshIdleTtl` and
   `refreshMaxAge` in the admin API; `null` = inherit).
2. For a [configured client](#configured-clients), its `refreshToken` (config owns it: `409 managed_by_config` when
   edited).
3. The global `refreshToken` option: 30 days idle and no cap by default (`refreshTokenTtl` is its deprecated alias).

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  oauthServer: {
    refreshToken: { idleTtl: 60 * 60 * 24 * 30 }, // everyone else: 30 days unused
    clients: [{
      id: 'com.example.app',
      name: 'Example',
      redirectUris: ['com.example.app:/auth/callback'],
      refreshToken: { idleTtl: 60 * 60 * 24 * 180 }, // the native app: signed in while opened every six months
    }],
  },
})
```

The policy is read whenever a refresh token is created, so a changed one reaches existing sign-ins at their next
refresh; a sign-in already past a new, shorter `maxAge` is refused then (`400 invalid_grant`). The token response tells
the client `refresh_token_expires_in`, so it can warn before a forced sign-in.

Guardrails: both values are at most **two years**, so a forgotten device stops working by itself. The server tells
clients apart by what it already knows (`kind` in `AdminApplicationDto`): **native** is a public client whose redirect
URIs are all custom-scheme or loopback (the token lives in the keychain), **browser** a public client with a web
redirect URI or website (the token lives where any XSS can read it), **confidential** a server. A browser client above
7 days idle gets a warning in the admin form, and a configured one in the server log unless it sets
`allowLongBrowserSessions: true`.

### Ending sign-ins

Long sessions need ways to end them early. Each fires `oauth:token:revoked`:

- **The user**: `GET /api/oauth-server/me/sessions` lists their live sign-ins (application name and icon, signed in,
  last active, expires), `DELETE /api/oauth-server/me/sessions/:id` ends one and `DELETE /api/oauth-server/me/sessions`
  all of them (reason `signed_out`). [Account](/modules/identity/account) shows them as **Signed-in apps** on the
  security page.
- **A credential change**: when [Auth](/modules/identity/auth/reference#hooks) fires `auth:credentials:changed` (a
  password change or reset, an email change or its revert), every sign-in of that user ends (reason
  `credentials_changed`). Turn it off with `revokeOnCredentialChange: false`.
- **Staff**: disable the application or sign everyone out of it (`POST .../applications/:id/revoke`), or call
  `revokeUserGrants(userId)` from your own code.

```ts
type OAuthSessionDto = {
  id: string // the refresh-token family
  application: { id: string, name: string, icon: string | null }
  signedInAt: string
  lastActiveAt: string // the last refresh
  expiresAt: string
}
```

### The application side

Register the application in the admin UI (or with `createApplication`), then configure it with the **client ID**
(`app_…`) and **client secret**. The whole flow with `curl`:

```bash
# 1. PKCE pair
VERIFIER=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)
CHALLENGE=$(printf %s "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')

# 2. Open in a browser, sign in and approve. You are redirected to the callback with ?code=…&state=…
echo "https://id.example.com/oauth/authorize?client_id=$CLIENT_ID&redirect_uri=https://app.example.com/auth/frigear&response_type=code&state=xyz&scope=openid%20profile%20email&nonce=n1&code_challenge=$CHALLENGE&code_challenge_method=S256"

# 3. Exchange the code
curl -s https://id.example.com/oauth/token \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=authorization_code -d code="$CODE" -d code_verifier="$VERIFIER" \
  -d redirect_uri=https://app.example.com/auth/frigear

# 4. Refresh (the returned refresh_token replaces the old one)
curl -s https://id.example.com/oauth/token -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=refresh_token -d refresh_token="$REFRESH_TOKEN"

# 5. Userinfo
curl -s https://id.example.com/oauth/userinfo -H "Authorization: Bearer $ACCESS_TOKEN"
```

Verify the ID token with any JOSE library against the JWKS (`iss`, `aud` = client ID, `nonce`):

```ts
import { createRemoteJWKSet, jwtVerify } from 'jose'

const jwks = createRemoteJWKSet(new URL('https://id.example.com/.well-known/jwks.json'))
const { payload } = await jwtVerify(idToken, jwks, { issuer: 'https://id.example.com', audience: clientId })
```

## Database

Three tables, registered through `registerDatabaseTable`; `users` is untouched and the tables store the user id without a
foreign key. Client secrets, codes and refresh tokens are stored only as SHA-256 hashes.

| Table | Holds |
| --- | --- |
| `oauth_applications` | Name, `clientType`, website (empty for a public client without one) / login URL, preview pattern, extra redirect URIs, `allowedRoles`, `tags`, `priority`, `isActive`, `isListed`, `refreshIdleTtl` / `refreshMaxAge` (the session lifetime, `null` = inherit), hashed secret (a public client stores the hash of a random value nobody sees, so the column stays `NOT NULL`). |
| `oauth_authorization_codes` | Single-use codes (hash only), PKCE challenge, nonce, 10 minute lifetime. |
| `oauth_refresh_tokens` | Hashed refresh tokens grouped in families for rotation and reuse detection. |

## Translations

The module registers `da` and `en` locale files under the `oauthServer.*` namespace for the consent, admin and
applications pages (groups `menu`, `admin`, `form`, `credentials`, `applications` and `authorize`); every string on
those pages comes from them. Override strings in your app's `i18n/locales/<code>.json`, see
[overriding module strings](/modules/platform/module-kit/i18n#overriding-module-strings-in-your-app).

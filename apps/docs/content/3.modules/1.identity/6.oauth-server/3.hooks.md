OAuth Server knows nothing about your roles or your staff. Your app answers its hooks to decide who may manage OAuth
applications, who may sign in to which application, and what each token says. This page is for app developers, in server
mode only. Set up the module first: [Overview](/modules/identity/oauth-server).

## Hooks

Your app answers these Nitro hooks from a server plugin (`server/plugins/*.ts`).

| Hook | When it runs | What your listener does |
| --- | --- | --- |
| `oauth:authorize` | A staff request to manage applications needs a decision. | Sets `allowed = true` for [staff](/guide/concepts/glossary). **Denied by default.** |
| `oauth:user:roles` | The roles of a user are needed. | Pushes the roles onto `roles`. **No roles by default.** |
| `oauth:scope:staff` | A `staffOnly` scope is about to be granted. | Sets `allowed = true` for staff. **Denied by default.** |
| `oauth:application:access` | After the role check passed. | Sets `allowed = false`, and optionally `reason`, to refuse. |
| `oauth:claims` | An ID token, an access token or a userinfo response is built. | Changes `claims`. |
| `oauth:token:issued` | Tokens were issued, at a code exchange or a refresh. | Logs or audits. |
| `oauth:token:revoked` | A refresh token family was revoked. | Logs or audits. |

The first three are [policy hooks](/guide/concepts/glossary): they deny until your app allows.

::warning
Identify the user from `ctx.userId`, never from the session on `ctx.event`. The session is empty for requests that
carry a token, and `event` is missing for background calls.
::

Each hook receives one context object:

```ts
type AuthorizeContext = { event: H3Event, userId: number, allowed: boolean }

type StaffScopeContext = { event: H3Event, userId: number, scope: string, allowed: boolean }

type UserRolesContext = {
  event?: H3Event // undefined for background calls such as listUserApplications(userId)
  userId: number
  roles: string[] // several listeners add up
}

type ApplicationAccessContext = {
  event?: H3Event
  user: OAuthUser
  application: OAuthApplication
  roles: string[] // resolved through oauth:user:roles
  allowed: boolean // true when the role check passed
  reason?: string // shown to the user as the 403 message
}

type ClaimsContext = {
  user: OAuthUser
  application: OAuthApplication
  scope: string[] // granted scopes
  roles: string[]
  tokenType: 'id_token' | 'access_token' | 'userinfo'
  claims: Record<string, unknown> // standard registered claims are re-applied afterwards
}

type TokenIssuedContext = { userId: number, applicationId: string, scope: string[], grant: 'authorization_code' | 'refresh_token' }
type TokenRevokedContext = {
  applicationId: string
  userId: number | null
  reason: 'revoked' | 'reuse_detected' | 'user_grants_revoked' | 'signed_out' | 'credentials_changed'
}

type OAuthUser = { id: number, name: string, email: string, avatar: string | null } & Record<string, unknown>
```

## Resolving roles

Each OAuth application lists the roles that may sign in to it, in `allowedRoles`. A user may sign in when they hold at
least one of them. An empty list lets every signed-in user in.

The module has no role model. Your app pushes each user's roles onto `ctx.roles` in `oauth:user:roles`. Pick the tab
that matches how your app stores roles.

::warning
An application with a non-empty `allowedRoles` locks everybody out until your app answers `oauth:user:roles`.
::

::code-group

```ts [A role column on users]
// With @frigear-nu/authorization the `users` table has a `role` column
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId) // the users row, including host-added columns
    if (user?.role) ctx.roles.push(String(user.role))
  })
})
```

```ts [A separate user_roles table]
import { eq } from 'drizzle-orm'
import { db, schema } from '@nuxthub/db'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const rows = await db.select({ role: schema.userRoles.role })
      .from(schema.userRoles)
      .where(eq(schema.userRoles.userId, ctx.userId))
    ctx.roles.push(...rows.map(row => row.role))
  })
})
```

```ts [Derived from other data]
import { hasActiveSubscription } from '@frigear-nu/subscriptions/utils'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId)
    if (user?.email.endsWith('@frigear.nu')) ctx.roles.push('staff')
    if (await hasActiveSubscription(ctx.userId)) ctx.roles.push('member')
  })
})
```

```ts [A role hierarchy]
// `admin` implies `manager` implies `member`: expand so applications only list the lowest one.
const implied: Record<string, string[]> = { admin: ['manager', 'member'], manager: ['member'] }

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId)
    const role = String(user?.role ?? 'user')
    ctx.roles.push(role, ...(implied[role] ?? []))
  })
})
```

::

Roles are checked at the authorization request, on the consent page, on approval, at every token exchange and on
`userinfo`. So a user who loses a role is stopped at the next refresh.

## Who is an admin

The staff routes that manage applications call `requireOAuthAdmin(event)`. It answers `401` when nobody is signed in.
It answers `403` unless a listener of `oauth:authorize` sets `ctx.allowed = true`. The
[Quick setup](/modules/identity/oauth-server#quick-setup) has a listener that lets in users with the `admin`
[role](/guide/concepts/glossary).

## Enriching tokens and userinfo

`oauth:claims` runs for every token and for `userinfo`. Use it to add a role, a custom scope's data or a per-application
value. When it runs, the module has already added the standard profile claims for the granted scopes.

::note
The registered claims are applied again after your listener, so you cannot overwrite them. They are `iss`, `sub`,
`aud`, `exp`, `iat`, `nbf`, `jti`, `nonce`, `auth_time`, `scope` and `client_id`.
::

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:claims', async (ctx) => {
    // Access tokens stay bare, so only the ID token and userinfo get identity claims.
    if (ctx.tokenType === 'access_token') return

    ctx.claims['https://frigear.nu/claims/role'] = ctx.roles[0] ?? 'user'

    // A custom scope: list it in `oauthServer.scopes: ['groups']`, applications then request `scope=openid groups`
    if (ctx.scope.includes('groups')) ctx.claims.groups = ctx.roles

    // Per application
    if (ctx.application.tags.includes('shop')) ctx.claims.customer_id = await customerIdFor(ctx.user.id)

    // Remove something
    if (!ctx.scope.includes('email')) delete ctx.claims.email
  })
})
```

[Preferences](/modules/identity/preferences#oauth-claims) uses this hook to forward user preferences as claims.

## Vetoing access and auditing

`oauth:application:access` runs after the role check and can still refuse a user, for example a suspended account. Its
`reason` is shown to the user as the `403` message. `oauth:token:issued` and `oauth:token:revoked` only report, so use
them for audit logs.

```ts
export default defineNitroPlugin((nitro) => {
  // After the role check: e.g. only users with a verified email, or a suspended flag
  nitro.hooks.hook('oauth:application:access', (ctx) => {
    if (ctx.user.suspended) {
      ctx.allowed = false
      ctx.reason = 'Your account is suspended.'
    }
  })

  nitro.hooks.hook('oauth:token:issued', ({ userId, applicationId, grant }) => {
    console.info(`[oauth] tokens issued to user ${userId} for ${applicationId} (${grant})`)
  })
  nitro.hooks.hook('oauth:token:revoked', ({ applicationId, userId, reason }) => {
    console.warn(`[oauth] revoked ${applicationId}/${userId}: ${reason}`)
  })
})
```

---
title: OAuth Resource
description: Let a separate service accept the access tokens of an issuer, so one mobile app signs in once and calls every service.
---

Your mobile app talks to several services, such as vouchers, a shop and an inventory. People should sign in once, not
once per service. OAuth Resource lets a service accept the [access tokens](/guide/concepts/glossary) that an
[issuer](/guide/concepts/glossary) gave the app, so the service needs no sign-in of its own. If the service should be
the place where people sign in, use [OAuth Server](/modules/identity/oauth-server) instead.

The module is `@frigear-nu/oauth-resource`. [Identity](/guide/concepts/identity) shows where it fits.

## What you get

- **Server routes.** None of its own. Your routes that call `requireAuth` or `requireUser` accept the issuer's access
  tokens and get the usual [Auth](/modules/identity/auth) principal with the granted [scopes](/guide/concepts/glossary).
  On by default.
- **Users.** A user the service has not seen is created from the issuer's profile the first time a token arrives. On
  by default.
- **Cross-origin calls.** CORS headers on `/api/` for the webviews of a Capacitor app. On by default.
- **Pages, composables and emails.** None.

:module-runtime{server}

::note
**Installed for you:** [Auth](/modules/identity/auth), [Users](/modules/identity/users) and Module Kit.
**You add:** `@nuxthub/core`.
**Optional:** nothing.
::

## Quick setup

::steps

### Install the module

```bash
pnpm add @frigear-nu/oauth-resource @nuxthub/core
```

### Configure it in `nuxt.config.ts`

The defaults accept frigear.nu's tokens. Point `issuer` and `audience` at any issuer whose access tokens follow
RFC 9068, the JSON Web Token profile for access tokens.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/oauth-resource'],
  oauthResource: {
    issuer: 'https://frigear.nu',
    audience: 'frigear-services',
  },
})
```

:::warning
Without this step the issuer drops your service's scopes as unsupported. Tokens then lack them, and every route that
requires one answers `403`.
:::

### List the service's scopes at the issuer

The issuer has to know the scopes. List them in its `oauthServer.scopes`, each with a `service` name, so the consent
screen groups them under your service. Add `staffOnly` for scopes that only staff may get. See
[One app for every service](/modules/identity/oauth-server/server#one-app-for-every-service).

### Require a scope in a route

Routes ask for the scope they need, exactly as for API tokens or sessions:

```ts [server/api/vouchers/index.get.ts]
export default defineEventHandler(async (event) => {
  const { user } = await requireAuth(event, { scopes: ['vouchers:read'] })
  return listVouchers(user.id)
})
```

A signed-in session still passes, so the service's own web pages keep working.

::

::callout{color="success" icon="i-lucide-check"}
**What you should see:** a call with a valid access token that carries `vouchers:read` answers `200`. A token without
the scope answers `403 insufficient_scope`, with `WWW-Authenticate: Bearer error="insufficient_scope"`. An invalid,
expired or foreign token answers `401` (`error="invalid_token"`).
::

## Options

Options go under the `oauthResource` key.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `issuer` | `string` | `https://frigear.nu` | The `iss` that tokens must carry. |
| `audience` | `string \| string[]` | `frigear-services` | The `aud` that tokens must carry, any one of them. |
| `jwksUrl` | `string` | `<issuer>/.well-known/jwks.json` | Where the issuer's signing keys are read. |
| `userinfoUrl` | `string` | `<issuer>/oauth/userinfo` | Where an unknown user's profile is read. |
| `corsOrigins` | `string[]` | `capacitor://localhost`, `https://localhost` | Exact origins whose webviews may call the API with a bearer token. |
| `corsPaths` | `string[]` | `/api/` | Path prefixes the CORS headers apply to. |
| `forceId` | `boolean` | `runtimeConfig.frigear.forceId` | Use the issuer's user ID (`sub`) as the local user ID. |
| `jwksCacheTtl` | `number` | `600` | Seconds the signing keys are cached. |

**`audience`** matches the issuer's `accessTokenAudience`.

**`corsOrigins`** takes exact origins only, never `*`.

**`forceId`** is explained under [Users](#users).

### Runtime config

Every option is also `runtimeConfig.oauthResource.<option>`. Set it per environment with
`NUXT_OAUTH_RESOURCE_<OPTION>`, with lists comma separated.

::note
The module was renamed from `@frigear-nu/frigear-resource` in 0.1.6. The config key is now `oauthResource` (was
`frigearResource`), the runtime config is `runtimeConfig.oauthResource`, and the env vars are `NUXT_OAUTH_RESOURCE_*`
(were `NUXT_FRIGEAR_RESOURCE_*`).
::

## Server

The module adds no routes. It plugs into Auth, so your existing routes accept the issuer's tokens.

### How a token is checked

The module adds a token resolver to Auth (`addAuthResolver`, order `50`). It looks at every JSON Web Token (JWT) and
accepts it only when all of these hold:

- its header `typ` is `at+jwt`;
- it is signed with RS256 by a key in the issuer's [JWKS](/guide/concepts/glossary);
- `iss` is the issuer, and `aud` contains the audience;
- `exp` has not passed;
- it has `sub` and `client_id`.

The keys are cached for `jwksCacheTtl`. A token with an unknown `kid` means the issuer rotated its key, so the keys
are fetched again, at most every 30 seconds.

Any other token is left to the next resolver, such as the service's own API tokens, and ends in `401`. ID tokens are
never accepted.

The principal is `{ kind: 'oauth', user, scopes, client: { id } }`. `scopes` is the token's `scope`, and `client.id`
is the app's `client_id`.

::warning
The service cannot revoke an access token. A token lives as long as the issuer says, so keep `accessTokenTtl` at 5 to
15 minutes there. A user who loses access at the issuer stops getting new tokens at the next refresh.
::

### Users

The user is the token's `sub`, the user ID at the issuer.

- **With `forceId`**, the local user has the same ID, so tokens and sign-ins find the same user. This is recommended.
  It is the default when [Sign in with frigear.nu](/guide/concepts/glossary) uses it.
- **Without it**, users are matched by email. The issuer's ID is remembered per server instance.

Either way an existing user is matched by email only when userinfo has `email_verified: true`, and a local user
holding the ID under another email is never taken over; the token is refused instead.

A user the service has not seen is created the first time a token arrives. Known users are not written to on
requests.

::warning
The app must ask for the `email` scope. The module reads the profile (`email`, `name`, `picture`) from the issuer's
userinfo endpoint for a user it has not seen, and without `forceId` once per server instance. A profile without an
email gets the token refused.
::

### CORS

A webview of the mobile app runs on `capacitor://localhost` on iOS or `https://localhost` on Android. So its calls to
the service are cross-origin.

The module answers preflights and adds the CORS headers for the configured origins on `corsPaths`. It never sends
`Access-Control-Allow-Credentials`, so a cross-origin call is always a bearer call. The headers come from the shared
[`applyBearerCors`](/modules/platform/module-kit/server-toolkit#bearer-cors), the same helper behind OAuth Server's
[`cors.paths`](/modules/identity/oauth-server/routes-and-clients#calling-from-a-browser-on-another-origin).

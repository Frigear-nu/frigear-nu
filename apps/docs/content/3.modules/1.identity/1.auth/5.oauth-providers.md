This page shows how to turn on sign-in through an [OAuth provider](/guide/concepts/glossary), including Sign in with
frigear.nu, and how to keep the provider's tokens. For app developers; server mode only. Set up the module first:
[Overview](/modules/identity/auth).

## Turn on a provider

Every [nuxt-auth-utils provider](https://github.com/atinux/nuxt-auth-utils#supported-oauth-providers) signs in at
`GET /api/auth/<provider>`. That covers GitHub, Google, Auth0, Okta, Keycloak and Microsoft, among others. `oidc` covers
any other OpenID Connect provider.

A provider is off by default. It turns on, **per request**, once nuxt-auth-utils has its credentials. These are the
environment variables nuxt-auth-utils documents for the provider:

```bash
NUXT_OAUTH_AUTH0_CLIENT_ID=...
NUXT_OAUTH_AUTH0_CLIENT_SECRET=...
NUXT_OAUTH_AUTH0_DOMAIN=example.eu.auth0.com

# Any OpenID Connect provider
NUXT_OAUTH_OIDC_CLIENT_ID=...
NUXT_OAUTH_OIDC_CLIENT_SECRET=...
NUXT_OAUTH_OIDC_OPENID_CONFIG=https://sso.example.com/.well-known/openid-configuration
```

Without credentials the route answers `404` and the sign-in page shows no button. Register
`<origin>/api/auth/<provider>` as the callback URL at the provider.

List a provider in `settings.oauth` only to change it:

```ts
authentication: {
  settings: {
    oauth: {
      auth0: {
        label: 'Company SSO', // button label (default: the provider's name, translatable as `auth.oauth.<provider>.label`)
        icon: 'i-simple-icons-auth0', // iconify name
        signUp: false, // only sign in existing users; unknown emails go back to the sign-in page
        config: { scope: ['openid', 'profile', 'email'] }, // passed to the nuxt-auth-utils handler
        keepTokens: true, // keep its access and refresh tokens, see "Keeping provider tokens"
        trustEmail: false, // `true` trusts emails the provider does not flag as verified (see below)
      },
      github: false, // off, even with credentials
    },
  },
}
```

- Users are matched by email, and only when the provider says the address is verified: `email_verified: true` (OIDC
  providers, Google, Auth0, Okta, ...), `verified: true` (Discord), or a GitHub address (GitHub only shows verified
  ones). Anything else, including a provider that sends no flag (Facebook, Microsoft, Spotify, ...), is sent back to
  the sign-in page with `?error=oauth-unverified`: nothing is linked or created.
- `trustEmail: true` on a provider accepts its emails without a flag. Set it only for a provider that never hands out
  an address its user does not own, since a sign-in then opens the local account with that email.
- An unknown email gets a new account, marked verified, unless `signUp` is `false`.
- A local account that was never verified (someone registered the address with a password or a passkey and never
  followed the mail) loses that password, its passkeys, API tokens and kept tokens at the first verified sign-in.
  The same happens on a sign-in link (magic link) to it. Its own verification mail keeps them.
- With `oauth.frigear` on, the `NUXT_OAUTH_OIDC_*` credentials belong to
  [Sign in with frigear.nu](#sign-in-with-frigearnu). The plain `oidc` provider then needs listing too, for example
  `oidc: { label: 'Company SSO' }`.
- `GET /api/auth/providers` returns the buttons for the request: `[{ key, to, label?, icon?, external? }]`.
  `useLogin().oauthProviders` fills in the default labels and icons.

## Keeping provider tokens

By default a sign-in keeps none of the provider's tokens. Set `keepTokens: true` on a provider (`oauth.frigear` too) to
keep them. Your app can then call the provider as the user, also from a scheduled task or a bearer request, where there
is no session.

- Auth keeps the access token, the refresh token, the expiry and the granted scopes.
- They live in the `auth_oauth_tokens` table, one row per user and provider. `keepTokens` on any provider adds that
  table, so generate a migration for it.
- Every sign-in with the provider replaces the row. A step-up sign-in replaces the plain one.
- The token columns are encrypted with AES-GCM (WebCrypto) and bound to the provider.
- `deleteUserAuthData` removes them with the user. A re-keyed user (`forceId`) keeps them.

::caution
The encryption key is derived from `NUXT_AUTH_TOKENS_KEY` (`runtimeConfig.authTokensKey`), else from the deprecated
`NUXT_SESSION_PASSWORD` (kept so tokens encrypted with it stay readable), else from `NUXT_APP_SECRET`
([Secrets](/get-started/configuration#secrets)). Changing it, or `NUXT_APP_SECRET` while the key is derived from it,
makes the kept tokens unreadable, and users have to sign in again.
::

```ts
// The caller's tokens (event), or a user's by id (a task syncing with an admin's token). `null` when none are kept.
const tokens = await getOAuthTokens(event, 'frigear') // { accessToken, refreshToken?, tokenType?, expiresAt, scopes }

// A usable access token: refreshed first when it expired, `null` when there is none, it lacks one of `scopes`,
// or it cannot be refreshed.
const token = await getOAuthAccessToken(adminId, 'frigear', { scopes: ['users:read'] })

await revokeOAuthTokens(userId, 'frigear') // forget them ("disconnect")
```

An expired token is refreshed with its refresh token at the provider's token endpoint. Auth finds that endpoint through
OIDC discovery: frigear.nu's, or the `openidConfig` of an `oidc`-style provider
(`NUXT_OAUTH_<PROVIDER>_OPENID_CONFIG`). Other providers' tokens are used until they expire. One refresh runs at a time
per user and provider, because providers rotate refresh tokens and treat a replayed one as theft.

## Sign in with frigear.nu

[Sign in with frigear.nu](/guide/concepts/glossary) lets people sign in with their frigear.nu account on pull request
previews and in local development. Turn it on with `settings.oauth.frigear`. It registers `GET /auth/frigear`, an OIDC
sign-in against frigear.nu.

It is decided **per request**. It is active when `runtimeConfig.previewDeployment` is `true`, or when
`runtimeConfig.frigear.sso` has a client id. Otherwise the route answers `404` and the button is hidden.
Register `<origin>/auth/frigear` as the callback on frigear.nu. The redirect URI is always that path on the request
origin.

On Cloudflare Workers, when the issuer is a `*.workers.dev` Worker on the same account as the app, add the
`global_fetch_strictly_public` compatibility flag. Without it the server's fetch of the discovery document fails with
error 1042, and `/auth/frigear` answers `404`.

| Runtime config | Env var | Purpose |
| --- | --- | --- |
| `previewDeployment` | `NUXT_PREVIEW_DEPLOYMENT` | Turns the sign-in on without credentials. Set it yourself, for example from a CI marker. |
| `frigear.sso.url` | `NUXT_FRIGEAR_SSO_URL` | The [issuer](/guide/concepts/glossary) origin. Defaults to the frigear.nu origin. |
| `frigear.sso.clientId` | `NUXT_FRIGEAR_SSO_CLIENT_ID` | The id of your [OAuth application](/guide/concepts/glossary) at frigear.nu. |
| `frigear.sso.clientSecret` | `NUXT_FRIGEAR_SSO_CLIENT_SECRET` | Its client secret. Leave it empty for a [public client](#public-client). |
| `frigear.sso.scopes` | `NUXT_FRIGEAR_SSO_SCOPES` | Scopes every sign-in asks for, space separated. Default `openid profile email`. |
| `frigear.sso.stepUpScopes` | `NUXT_FRIGEAR_SSO_STEP_UP_SCOPES` | Extra scopes a sign-in may ask for with `/auth/frigear?scope=...`. Default none. |
| `frigear.forceId` | `NUXT_FRIGEAR_FORCE_ID` | Make the local `users.id` equal the frigear.nu id. Default `false`. |
| `frigear.roleMap` | `NUXT_FRIGEAR_ROLE_MAP` | frigear.nu role to local role, as an object (JSON in the env var). Default `{}`: no role is synced. |
| `frigear.defaultRole` | `NUXT_FRIGEAR_DEFAULT_ROLE` | The local role for a missing or unmapped role claim. Default `user`. |
| `frigear.syncRole` | – | Set `false` to stop syncing roles while keeping `roleMap`. On whenever `roleMap` maps a role. |
| `frigear.keepTokens` | `NUXT_FRIGEAR_KEEP_TOKENS` | Keep the frigear.nu tokens. Defaults to `oauth.frigear.keepTokens`. |
| `frigear.handoff.returnUrl` | `NUXT_FRIGEAR_HANDOFF_RETURN_URL` | A deep link the browser's "Signed in" page offers after a [browser handoff](#sign-in-in-the-system-browser), for example `myapp:/auth/return`. Default none. |
| `public.authentication.frigearSso` | `NUXT_PUBLIC_AUTHENTICATION_FRIGEAR_SSO` | Whether the build saw the credentials. |

**`frigear.sso.scopes`.** `openid` is always added.

**`frigear.syncRole`.** Declare it in your `runtimeConfig` to override it. Without a `roleMap` it does nothing (the
build prints a warning when it is `true`).

**`frigear.keepTokens`.** See [Keeping provider tokens](#keeping-provider-tokens). `oauth.frigear.keepTokens` also adds
the table, so turning `frigear.keepTokens` on at runtime only works with the table.

**`public.authentication.frigearSso`.** The button follows the route, through `GET /api/auth/providers`.

The credentials can also come from nuxt-auth-utils' `NUXT_OAUTH_OIDC_CLIENT_ID`, `NUXT_OAUTH_OIDC_CLIENT_SECRET` and
`NUXT_OAUTH_OIDC_OPENID_CONFIG`. Id and secret come as a pair: a `frigear.sso.clientId` never uses the
`NUXT_OAUTH_OIDC_CLIENT_SECRET`.

What happens at sign-in:

- A callback without a `state` that matches the browser's state cookie is sent back to the sign-in page with
  `?error=oauth-state`. The same holds for every provider at `/api/auth/<provider>`.
- The token response must carry an `id_token`, and userinfo must be about the same `sub`; otherwise the sign-in fails
  with `401`.
- The `id_token` is verified against the provider's `jwks_uri`, including issuer and audience. The keys are cached for
  an hour.
- Users are matched by email only with `email_verified: true` (a `@frigear-nu/oauth-server` issuer sends it from
  `emailVerifiedAt`). An unverified address that an account here already has is sent back to the sign-in page with
  `?error=oauth-unverified`. A free address gets a new account, verified only with the claim.
- A matched account that was never verified loses the credentials set before (password, passkeys, API tokens, kept
  tokens) and is marked verified.
- With `forceId`, Auth makes the local id match in one of three ways. It updates the user with that id and email,
  re-keys an existing user with the same (verified) email, or creates a user with that id. A local user that holds the
  id under another email is never taken over: the sign-in fails with `409`, and an admin has to sort the two out.
- On a re-key, rows that reference `users.id` follow. A different user that holds the id moves to the next free id.
- The optional `color_mode` claim (`light`, `dark` or `system`) is kept on the session as `frigear.colorMode`. It is
  applied once per sign-in.
- The optional `locale` claim (profile scope) is kept on the session as `frigear.locale` when it is one of the app's
  i18n locales (`en-GB` counts as `en`). With `@nuxtjs/i18n` it is applied once per sign-in with `setLocale`, so the URL
  prefix and cookie follow. [Users](/modules/identity/users#the-users-language) also stores it as `users.locale`.
- After the user is synced and before the session starts, the Nitro hook `auth:frigear:login` gets `{ user, claims }`:
  the verified id token's claims, filled in by userinfo about the same user. A listener that changes the stored user
  sets `ctx.user` to the stored row, so the session starts with it.

**Language.** With `@nuxtjs/i18n`, the sign-in sends the page's language as OIDC `ui_locales`, so frigear.nu opens its
sign-in and consent pages in it. The language comes from the locale prefix of the page the sign-in started on (a
same-origin `Referer`), else of `?redirect=`, else i18n's cookie (`detectBrowserLanguage.cookieKey`, the only source
under `no_prefix`). Under `prefix_except_default`, an unprefixed path is in the default locale. Without i18n, or when
nothing says, no `ui_locales` is sent. The browser handoff sends it too.

**The role claim.** With a `roleMap`, Auth sets the user's single sign-on roles at **every sign-in**. It reads the role claims of the
verified `id_token` only, never userinfo: the `role` claim, the namespaced `https://frigear.nu/claims/role`, then the
entries of `roles`. Every claimed role the map lists becomes a local role. A role the map does not list, or no claim
at all, gives `defaultRole` (nothing when it is `user`, which every user holds anyway). The roles are written through
the role provider with `source = 'sso'`: they replace the user's earlier `sso` rows, so a role removed at frigear.nu is
removed here at the next sign-in, and roles an admin assigned by hand are never touched. Without a `roleMap` no role is
synced. It needs [Authorization](/modules/identity/authorization/roles-and-requirements#assignment-and-its-rules) for
the table that stores them; without it nothing is stored. These claim names follow the current frigear.nu and will change when
this app becomes frigear.nu. On the issuer side, the host app adds the claim in the `oauth:claims` hook of
[OAuth Server](/modules/identity/oauth-server).

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  runtimeConfig: {
    frigear: {
      // Only these frigear.nu roles carry over; every other one, or none, becomes `user`.
      roleMap: { admin: 'admin', 'frigear-staff': 'manager' },
    },
  },
})
```

::warning
Map only the roles you trust frigear.nu (or the issuer behind `NUXT_OAUTH_OIDC_*`) to grant here. A role the map lists
is granted to anyone the issuer gives it to.
::

**Step-up.** A sign-in asks for `frigear.sso.scopes`. To ask for more only when needed, such as an admin connecting for
sync, allow the scope in `stepUpScopes`. Then send the user to `/auth/frigear?scope=users:read`, optionally with
`&redirect=/admin/sync`. Requested scopes outside the allowlist are ignored. With `keepTokens`, the step-up sign-in's
tokens replace the ones kept before.

::warning
frigear.nu decides what it grants. A scope for a permission the user does not hold, such as `users:read`, is dropped. Check the kept
`scopes` rather than assuming the step-up worked.
::

```ts
// oauth: { frigear: { keepTokens: true } }, NUXT_FRIGEAR_SSO_STEP_UP_SCOPES=users:read
const token = await getOAuthAccessToken(event, 'frigear', { scopes: ['users:read'] })
if (!token) throw apiError(403, 'frigear_not_connected', 'Connect frigear.nu for sync: /auth/frigear?scope=users:read')
const users = await $fetch('https://frigear.nu/api/admin/users', { headers: { Authorization: `Bearer ${token}` } })
```

### Public client

Without `frigear.sso.clientSecret` the app signs in as a public OAuth client: every sign-in uses PKCE (S256), and the
code exchange sends no secret (an empty `client_secret`, which OAuth treats as omitted). That works for a web app as
well as a desktop app, and keeps no secret in the deployment. With a secret, nothing changes.

Register the application at frigear.nu as a public client (no secret) with its redirect URI. For a desktop app whose
server listens on a random loopback port, register the loopback URI without a port:

```ts
// At the issuer (OAuth Server): a public client for a desktop app.
{ name: 'My desktop app', clientType: 'public', redirectUris: ['http://127.0.0.1/auth/frigear'] }
```

[OAuth Server](/modules/identity/oauth-server) then accepts `http://127.0.0.1:<any port>/auth/frigear` for it (RFC 8252,
§7.3). The app needs only `NUXT_FRIGEAR_SSO_CLIENT_ID`.

### Sign in in the system browser

A desktop app shows the app in a window (a webview) and cannot sign in there: passkeys at frigear.nu need the system
browser, and an embedded webview is never one. With `handoff: true` the window waits while the system browser signs in:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  authentication: {
    settings: { oauth: { frigear: { handoff: true } } },
  },
})
```

1. The sign-in page's frigear.nu button calls `useFrigearHandoff().start()`. It posts to
   `/api/auth/frigear/handoffs`, which stores an attempt (the `state`, PKCE verifier and nonce), sets an httpOnly
   cookie on the window bound to it, and answers the frigear.nu authorize URL.
2. The window opens that URL outside itself through the `auth:frigear:open` app hook (below), or `window.open` when no
   listener handles it.
3. frigear.nu sends the system browser back to `http://127.0.0.1:<port>/auth/frigear`. The server finds the attempt by
   its `state`, exchanges the code with the verifier, creates or links the user like every frigear.nu sign-in, and
   marks the attempt complete. The browser gets a small "Signed in" page and no session. With
   `frigear.handoff.returnUrl` the page tries that deep link once and offers it as a link.
4. The window polls `GET /api/auth/frigear/handoffs/:id` (backing off from 1 to 5 seconds). Once it is `complete`, it
   posts `/complete`, which starts the window's cookie session and answers `{ redirect }`.

No code or token travels in a URL to the window, and the deep link only brings the app forward: the window signs in
without it. The browser half is bound to the window by the attempt cookie (stored hashed, compared in constant time),
the PKCE verifier is stored encrypted (AES-GCM, with a key Nuxt derives from `appSecret`, the secret the cookie
sessions already use), and every attempt is single use and lasts 10 minutes. A refusal at frigear.nu (`access_denied`)
or a failed sign-in marks the attempt `failed`, which the window shows.

The handoff is only offered by a server reached on a loopback address, from a loopback address (`403
handoff_not_local` otherwise). On a shared server, someone could start an attempt and get a victim to finish its
browser half, which would sign the attacker's window in as the victim. Starting an attempt counts against the
`rateLimit.requests` of anonymous routes; polling, completing and cancelling an attempt allow 1,200 requests per attempt
and client in a `rateLimit.windowSeconds` window (`429 rate_limited` past it), room for a poll every half second for
the attempt's 10 minutes. `handoff: true` adds the `auth_frigear_handoffs` table, so generate a migration.

::note
The loopback check reads the client address with h3's `getRequestIP`, from the socket. Nitro's `bun` preset does not
pass the client address on, so a host that runs auth on Bun must set it on the request itself (the
[desktop](/modules/interface/desktop/local-mode) sidecar does); otherwise every attempt answers `403 handoff_not_local`.
::

Open frigear.nu in the system browser from a client plugin (a desktop shell does this for you):

```ts [plugins/frigear-handoff.client.ts]
import { openUrl } from '@tauri-apps/plugin-opener'

export default defineNuxtPlugin((nuxtApp) => {
  nuxtApp.hook('auth:frigear:open', async (ctx) => {
    await openUrl(ctx.url)
    ctx.handled = true // skip the default window.open
  })
})
```

A sign-in page of your own uses the composable directly:

```ts
const { isEnabled, state, pending, error, start, reopen, cancel } = useFrigearHandoff()
const redirect = await start({ redirect: '/dashboard' }) // a path once signed in, undefined when cancelled or failed
// state: 'idle' | 'waiting' | 'completing'; error: 'denied' | 'expired' | 'unverified' | 'failed' | null
```

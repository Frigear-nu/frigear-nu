## Protecting a route

`requireAuth` and `getAuth` are auto-imported in server code; use them instead of nuxt-auth-utils'
`requireUserSession`.

```ts
// server/api/tickets.get.ts
export default defineEventHandler(async (event) => {
  const { user } = await requireAuth(event, { scopes: ['tickets:read'] })
  return getTickets(user.id)
})
```

| Call | Behaviour |
| --- | --- |
| `requireAuth(event)` | The principal from any credential. `401` without a valid one. |
| `requireAuth(event, { scopes })` | Also needs every scope. `403 insufficient_scope` otherwise. Sessions pass. |
| `requireAuth(event, { sessionOnly: true })` | Cookie sessions only. `403 session_required` for tokens. |
| `getAuth(event)` | The principal or `null`. Never throws. |

```ts
type AuthPrincipal =
  | { kind: 'session', user: AuthUser, scopes: string[] }
  | { kind: 'user-token', user: AuthUser, scopes: string[], token: { id: string, name: string, prefix: string } }
  | { kind: 'oauth', user: AuthUser, scopes: string[], client: { id: string } }

interface RequireUserOptions {
  scopes?: string[]
  sessionOnly?: boolean
}
```

[Users](/modules/identity/users#server) builds `requireUser(event, options)` and `getUser(event, { scopes })` on
top, returning just the user.

Other server helpers:

```ts
mapUserToSession(storedUser) // strips the password hash and applies `session.mapper`; use it to refresh the session
getLoginPath(event) // the login page path (`pages.login`, else `/login`)
deleteUserAuthData(userId) // removes tokens, kept OAuth tokens, passkeys, reset codes and sign-in links (call when deleting a user)
```

Default to `sessionOnly` for anything that changes who the user is or how they sign in, and to `scopes` for reads and
actions an integration plausibly needs; see [Auth and scopes](/guide/concepts/auth-and-scopes). A token carries no role:
the user is loaded from the database on every bearer request, so a role change, a ban or a deleted account applies to the
next call. A cookie session holds a snapshot from login time (see
[Authorization](/modules/identity/authorization#roles-in-sessions-and-tokens)).

A request that carries a token a resolver claims (the user token prefix, `fnu_…` by default, or a JWT) and it is invalid, expired or revoked is
**unauthenticated** (`401`, `WWW-Authenticate: Bearer error="invalid_token"`), even with a valid session cookie.
Tokens no resolver claims, such as per-form `ffk_` tokens, are ignored and the other credentials apply.

## Policy gates

Staff gates are decided by the host through a Nitro hook, denied by default (the model is explained in
[Auth and scopes](/guide/concepts/auth-and-scopes)). A module defines them without knowing who is staff:

```ts
const gate = definePolicyGate('events:authorize')
await gate.assert(event, userId) // 403 `forbidden` unless a hook listener sets ctx.allowed = true

// A Nitro plugin that only offers these scopes to users the gate lets in
export default defineStaffScopes(['events:manage', 'events:pii'], gate.isAllowed)
```

| Method | Signature | Purpose |
| --- | --- | --- |
| `isAllowed` | `(event, userId, extra?) => Promise<boolean>` | Asks the host; never throws. |
| `assert` | `(event, userId, message?, extra?) => Promise<void>` | Throws 403 (`data.code: 'forbidden'`, `message` as `statusMessage`) unless allowed. |

`extra` is merged into the context the hook receives, so the host gets what it needs to decide (the users admin passes
`{ action, target, input }`). It cannot override `event`, `userId` or `allowed`. Type it with the gate's generic:
`definePolicyGate<{ action: string }>('users:admin:authorize')`. Only `ctx.allowed === true` allows: a truthy
non-boolean is denied.

### Staff guards

`defineStaffGuard` combines authentication with the module's staff scope and the gate, which is what most staff routes
need:

```ts
// src/runtime/server/utils/staff.ts
export const eventsStaff = defineStaffGuard({
  hook: 'events:authorize',
  scope: 'events:manage',
  message: 'You are not allowed to manage events.',
})

const { userId, principal } = await eventsStaff.require(event) // reads and ordinary edits
await eventsStaff.require(event, { sessionOnly: true }) // credential minting, refunds, billing
if (await eventsStaff.can(event, userId)) { /* MCP tools, menus */ }
```

`require(event, { sessionOnly? })` calls `requireAuth(event, { scopes: [scope], sessionOnly })` and then
`gate.assert(event, userId, message)`: 401 without a credential, 403 `insufficient_scope` / `session_required` from
`requireAuth`, 403 `forbidden` when the host denies. It returns `{ userId, principal }`, not the stored user (auth does
not depend on `@frigear-nu/users`); load the user's other columns with `loadAuthUser(userId)` when a route needs them.
`can(event, userId)` is the non-throwing check.

Host listeners must identify the caller from `ctx.userId`, never from the session on `ctx.event`: the session is empty
for bearer requests.

## Extending (build time)

A module's `setup()` can import these from `@frigear-nu/auth/utils`:

```ts
addAuthScope(nuxt, { name: 'reports:admin', description: 'Run reports', roles: ['admin'] })

addAuthResolver(nuxt, {
  name: 'my-tokens',
  prefix: 'mt_', // or `jwt: true`; one of the two is required
  resolver: resolver.resolve('./runtime/server/resolvers/my-token'),
  order: 100, // lower runs first
})

setAuthUserStore(nuxt, resolver.resolve('./runtime/server/user-store')) // first registration wins
```

```ts
// resolver: return a principal, or null when the token is invalid
export default async function (event: H3Event, token: string): Promise<AuthPrincipal | null> { … }
```

```ts
interface AuthUserStore {
  findById(id: string | number): Promise<AuthStoredUser | null>
  findByEmail(email: string): Promise<AuthStoredUser | null>
  create(values: AuthUserCreate): Promise<AuthStoredUser>
  update(id: number, values: AuthUserUpdate): Promise<AuthStoredUser | null>
  remove(id: number): Promise<void>
  /** Gives the user a new id, taking everything that references it along. */
  changeId(from: number, to: number): Promise<void>
}
```

The same helpers are also available as Nuxt build hooks, for modules that prefer hooks:

| Hook | Payload |
| --- | --- |
| `auth:resolvers` | `AuthResolverDefinition[]` (push to register) |
| `auth:scopes` | `AuthScopeDefinition[]` (push to register) |
| `auth:user-store` | `{ path?: string }` (set `path`) |

The utils also export `ALL_SCOPES`, `hasScope`, `hasScopes`, `isPiiScope`, `isGrantableScope`, `parseScopeString`,
`USER_TOKEN_PREFIX`, `generateUserToken`, `hashToken`, `parseBearer`, `looksLikeJwt` and `tokenStatus`.

## Scopes

Scopes are `resource:action` strings. `*` grants everything and `resource:*` every action of one resource. Personal-data
scopes (`resource:pii`) are the exception: neither `*` nor `resource:*` covers them, so a token only sees other people's
personal data when the user picked that scope by name. Sessions are full access, so [MCP](/modules/features/mcp) tools strip
personal data for them as well. Scopes only narrow: a token never does more than its owner can.

A scope is only offered to users who may use it: the token UI lists, and `POST /api/auth/me/tokens` accepts, just the
scopes available to the signed-in user. Restrict a scope with `roles`, or for other policy set `ctx.available = false`
in the `auth:scope-available` hook:

```ts
nitroApp.hooks.hook('auth:scope-available', (ctx) => {
  if (ctx.scope.name === 'reports:export') ctx.available = canExport(ctx.user.id)
})
```

```ts
interface AuthScopeDefinition {
  name: string
  description?: string
  /** Only users with one of these roles may pick the scope. Omit for every user. */
  roles?: string[]
}
```

Registered by the built-in modules:

| Scope | Module |
| --- | --- |
| `events:manage`, `events:pii`, `tickets:read`, `tickets:write` | [Events](/modules/features/events) |
| `forms:manage`, `forms:pii`, `forms:submit` | [Forms](/modules/features/forms) |
| `payments:read`, `payments:write`, `payments:manage` | [Payments](/modules/commerce/payments) |
| `subscriptions:read` | [Subscriptions](/modules/commerce/subscriptions) |
| `profile:read` | [Users](/modules/identity/users) (with `settings.mcp`) |
| `oauth:read` | [OAuth Server](/modules/identity/oauth-server) |

## User API tokens

Users create tokens (`fnu_…`) on the account page (`/account/api-tokens`, see [Account](/modules/identity/account)) or through
the API. Use one like this, for example from an MCP client:

```bash
curl -H "Authorization: Bearer fnu_…" https://example.com/api/tickets
```

- Only the SHA-256 of a token is stored, plus a prefix and the last four characters. A lost token is replaced, not
  looked up.
- Tokens are accepted in the `Authorization` header **only**; query-string tokens are ignored.
- Tokens can expire (`expiresInDays`, or `tokenTtlDays`) and be revoked. `lastUsedAt` is written at most every five
  minutes and a failure to write it never fails a request.

Tokens start with `fnu_` unless the host picks its own prefix (letters, digits, `_` and `-`). Changing it later
invalidates every token already issued: they are no longer claimed, so they are ignored like any unknown bearer token.

```ts
export default defineNuxtConfig({
  authentication: {
    apiTokens: { prefix: 'acme_' }, // or `false` to turn user API tokens off
  },
})
```

With `apiTokens: false` the `/api/auth/me/tokens` routes and the token resolver are not registered, and
[Account](/modules/identity/account) drops its API tokens page. The `auth_user_tokens` table stays, so turning tokens back on
needs no migration. OAuth access tokens are not affected.

## OAuth access tokens

With [OAuth Server](/modules/identity/oauth-server), an application the user signed in to calls the API as that user:
`principal.user` is the user and `principal.client.id` the application.

```ts
const principal = await requireAuth(event, { scopes: ['tickets:read'] })
if (principal.kind === 'oauth') console.log(`called by application ${principal.client.id}`)
```

The OAuth server accepts every registered API scope besides `openid profile email`. On every request the token is
checked against live state: the application must be active, the user must exist and still pass the application's role
requirement and the `oauth:application:access` hook, so disabling an application or changing a role cuts access
immediately. ID tokens are not credentials; only access tokens (`typ: at+jwt`) authenticate. The audience is the
application, so `aud` is not required to match this server; verification is signature (JWKS), issuer and type.

A static user token is enough for an MCP client that sends `Authorization: Bearer …` ([MCP](/modules/features/mcp)). Clients
that need the full OAuth flow also need protected-resource metadata
([RFC 9728](https://www.rfc-editor.org/rfc/rfc9728)) and dynamic client registration, which this module does not
provide.

## Auth emails

Magic link, verification and password reset emails are dispatched as `EmailNotification`s through
[Notify](/modules/platform/notify) (configure the delivery driver under the `notify` key). With
[Email Templates](/modules/platform/email-templates) installed, they are rendered from the module's Vue templates
(`auth-magic-link`, `auth-verify-email`, `auth-password-reset`). Override one by adding `app/emails/<name>.vue`.

Without templates, you can brand the magic link and verification emails by replacing subject/body in the `auth:email`
hook. Delete `ctx.notification.template` there if a template should not render over your body:

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('auth:email', (ctx) => {
    // ctx.type: 'magic-link' | 'verify-email'; ctx.data: { name, url }
    ctx.notification.subject = 'Velkommen til Frigear'
    ctx.notification.body = renderMyTemplate(ctx.data)
  })
})
```

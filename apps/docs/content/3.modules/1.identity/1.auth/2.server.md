This page shows how a server route learns who is calling and what they may do. It is for app developers who write
routes and for module authors. Server mode only. Set up the module first: [Overview](/modules/identity/auth).

An app in [client mode](/modules/identity/auth/client-mode) has no server of its own. The API it calls protects its
routes the way this page shows. That API accepts the app's [access token](/guide/concepts/glossary) through
[OAuth Server](/modules/identity/oauth-server) or [OAuth Resource](/modules/identity/oauth-resource).

## Protect a route

Call `requireAuth` first in a route that needs a signed-in user. It is auto-imported in server code. Unlike
nuxt-auth-utils' `requireUserSession`, it also accepts [API tokens](/guide/concepts/glossary) and access tokens.

```ts
// server/api/tickets.get.ts
export default defineEventHandler(async (event) => {
  const { user } = await requireAuth(event, { scopes: ['tickets:read'] })
  return getTickets(user.id)
})
```

| Call | Behaviour |
| --- | --- |
| `requireAuth(event)` | The [principal](/guide/concepts/glossary) from any credential. `401` without a valid one. |
| `requireAuth(event, { scopes })` | Also needs every scope. `403 insufficient_scope` otherwise. Sessions pass. |
| `requireAuth(event, { sessionOnly: true })` | Cookie sessions only. `403 session_required` for tokens. |
| `getAuth(event)` | The principal or `null`. Never throws. |

```ts
interface RequireUserOptions {
  scopes?: string[]
  sessionOnly?: boolean
}
```

The three kinds of credential, and what the principal holds for each, are explained in
[The principal](/guide/concepts/auth-and-scopes#the-principal). [Users](/modules/identity/users#server) builds
`requireUser(event, options)` and `getUser(event, { scopes })` on top. They return just the user.

::caution
Pass `sessionOnly: true` for anything that changes who the user is or how they sign in. Use `scopes` for reads and
actions an integration plausibly needs. [sessionOnly](/guide/concepts/auth-and-scopes#sessiononly) explains the rule.
::

How fresh the user's role is per credential is explained in
[Roles in sessions and tokens](/modules/identity/authorization#roles-in-sessions-and-tokens).

**A bad token is never ignored.** A request may carry a token that a resolver claims: the API token prefix (`fnu_…` by
default) or a JWT. When that token is invalid, expired or revoked, the request is **unauthenticated**, even with a valid
session cookie. The answer is `401` with `WWW-Authenticate: Bearer error="invalid_token"`. Tokens no resolver claims,
such as the per-form `ffk_` tokens, are ignored, and the other credentials apply.

### Other helpers

```ts
mapUserToSession(storedUser) // strips the password hash and applies `session.mapper`; use it to refresh the session
getLoginPath(event) // the sign-in page path (`pages.login`, else `/login`)
deleteUserAuthData(userId) // removes tokens, kept OAuth tokens, passkeys, reset codes and sign-in links (call when deleting a user)
```

## Define scopes

A [scope](/guide/concepts/glossary) limits what a token may do. [Scopes](/guide/concepts/auth-and-scopes#scopes)
explains wildcards and PII (personally identifiable information) scopes, which wildcards never include.

A module registers the scopes it understands with `addAuthScope` (see
[Extend Auth at build time](#extend-auth-at-build-time)). Your app adds its own with the `scopes` option.

A scope is only offered to users who may use it. The token page lists, and `POST /api/auth/me/tokens` accepts, only the
scopes available to the signed-in user. Restrict a scope with `roles`. For any other rule, set `ctx.available = false`
in the `auth:scope-available` hook:

```ts
nitroApp.hooks.hook('auth:scope-available', (ctx) => {
  if (ctx.scope.name === 'reports:export') ctx.available = canExport(ctx.user.id)
})
```

```ts
interface AuthScopeDefinition {
  name: string
  description?: string
  /** Only users with one of these roles may pick the scope. Omit for every user. */
  roles?: string[]
}
```

The built-in modules register these scopes:

| Scope | Module |
| --- | --- |
| `events:manage`, `events:pii`, `tickets:read`, `tickets:write` | [Events](/modules/features/events) |
| `forms:manage`, `forms:pii`, `forms:submit` | [Forms](/modules/features/forms) |
| `payments:read`, `payments:write`, `payments:manage` | [Payments](/modules/commerce/payments) |
| `subscriptions:read` | [Subscriptions](/modules/commerce/subscriptions) |
| `profile:read` | [Users](/modules/identity/users) (with `settings.mcp`) |
| `oauth:read` | [OAuth Server](/modules/identity/oauth-server) |

## Ask your app with a policy hook

A module never decides who is [staff](/guide/concepts/glossary). It asks the host app through a
[policy hook](/guide/concepts/glossary), a Nitro hook that is denied by default.
[Policy hooks](/guide/concepts/auth-and-scopes#policy-hooks) shows how your app answers one. In module code, the helper
behind the hook is `definePolicyGate`:

```ts
const gate = definePolicyGate('events:authorize')
await gate.assert(event, userId) // 403 `forbidden` unless a hook listener sets ctx.allowed = true

// A Nitro plugin that only offers these scopes to users the hook lets in
export default defineStaffScopes(['events:manage', 'events:pii'], gate.isAllowed)
```

| Method | Signature | Purpose |
| --- | --- | --- |
| `isAllowed` | `(event, userId, extra?) => Promise<boolean>` | Asks the host app. Never throws. |
| `assert` | `(event, userId, message?, extra?) => Promise<void>` | Throws 403 unless allowed: `data.code: 'forbidden'`, `message` as `statusMessage`. |

- `extra` is merged into the context the hook receives, so the host app gets what it needs to decide. User management
  passes `{ action, target, input }`.
- `extra` cannot override `event`, `userId` or `allowed`.
- Type `extra` with the generic: `definePolicyGate<{ action: string }>('users:admin:authorize')`.
- Only `ctx.allowed === true` allows. A truthy value that is not a boolean is denied.

::warning
A hook listener in your app must identify the caller from `ctx.userId`, never from the session on `ctx.event`. The
session is empty for bearer requests.
::

## Staff guards

Most staff routes need three checks: sign-in, the module's staff scope and its policy hook. A
[staff guard](/guide/concepts/glossary) runs all three. Each module defines one with `defineStaffGuard`:

```ts
// src/runtime/server/utils/auth.ts
export const eventsStaff = defineStaffGuard({
  hook: 'events:authorize',
  scope: 'events:manage',
  message: 'You are not allowed to manage events.',
})

const { userId, principal } = await eventsStaff.require(event) // reads and ordinary edits
await eventsStaff.require(event, { sessionOnly: true }) // credential minting, refunds, billing
if (await eventsStaff.can(event, userId)) { /* MCP tools, menus */ }
```

`require(event, { sessionOnly? })` calls `requireAuth(event, { scopes: [scope], sessionOnly })`, then
`gate.assert(event, userId, message)`. It fails in this order:

| Failure | Answer |
| --- | --- |
| No credential | `401` |
| Missing scope, or a token when `sessionOnly` is set | `403 insufficient_scope` or `403 session_required` |
| The host app denies | `403 forbidden` |

`require` returns `{ userId, principal }`, not the stored user, because Auth does not depend on Users. Load the user's
other columns with `loadAuthUser(userId)` when a route needs them. `can(event, userId)` is the check that never throws.

## User API tokens

Users create API tokens (`fnu_…`) on the account page (`/account/api-tokens`, see
[Account](/modules/identity/account)) or through the API. A script or an MCP client sends one like this:

```bash
curl -H "Authorization: Bearer fnu_…" https://example.com/api/tickets
```

- Only a hash (SHA-256) of a token is stored, plus a prefix and the last four characters.
- A lost token is replaced, not looked up.
- Send a token in the `Authorization` header **only**. Tokens in the query string are ignored.
- Tokens can expire (`expiresInDays`, or the `tokenTtlDays` option) and can be revoked.
- `lastUsedAt` is written at most every five minutes. A failure to write it never fails a request.

Tokens start with `fnu_` unless your app picks its own prefix. A prefix holds letters, digits, `_` and `-`.

::caution
Changing the prefix later invalidates every token already issued. Auth no longer claims them, so they are ignored like
any unknown bearer token.
::

```ts
export default defineNuxtConfig({
  authentication: {
    apiTokens: { prefix: 'acme_' }, // or `false` to turn API tokens off
  },
})
```

With `apiTokens: false`:

- the `/api/auth/me/tokens` routes and the token resolver are not registered,
- [Account](/modules/identity/account) drops its API tokens page,
- access tokens are not affected.

The `auth_user_tokens` table stays, so turning tokens back on needs no migration.

## OAuth access tokens

With [OAuth Server](/modules/identity/oauth-server), an [OAuth application](/guide/concepts/glossary) the user signed in
to calls your API as that user. `principal.user` is the user, and `principal.client.id` is the application.

```ts
const principal = await requireAuth(event, { scopes: ['tickets:read'] })
if (principal.kind === 'oauth') console.log(`called by application ${principal.client.id}`)
```

OAuth Server accepts every registered API scope besides `openid profile email`. Every request checks the token against
live state:

- the application must be active,
- the user must exist,
- the user must still pass the application's role requirement and the `oauth:application:access` hook.

So disabling an application or changing a role cuts access immediately.

- ID tokens are not credentials. Only access tokens (`typ: at+jwt`) authenticate.
- The audience is the application, so `aud` does not have to match this server.
- Verification checks the signature against the JSON Web Key Set (JWKS), the issuer and the type.

An MCP client that sends `Authorization: Bearer …` only needs an API token ([MCP](/modules/features/mcp)).
Clients that need the full OAuth flow also need protected-resource metadata
([RFC 9728](https://www.rfc-editor.org/rfc/rfc9728)) and dynamic client registration. This module provides neither.

## Customize the auth emails

Auth sends the emailed sign-in link, the address verification and the password reset as `EmailNotification`s through
[Notify](/modules/platform/notify). Configure the delivery driver under the `notify` key.

With [Email Templates](/modules/platform/email-templates) installed, the emails are rendered from the module's Vue
templates: `auth-magic-link`, `auth-verify-email` and `auth-password-reset`. Override one by adding
`app/emails/<name>.vue`.

Without templates, brand the sign-in link and verification emails in the `auth:email` hook by replacing the subject and
body. Delete `ctx.notification.template` there if a template should not render over your body:

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('auth:email', (ctx) => {
    // ctx.type: 'magic-link' | 'verify-email'; ctx.data: { name, url }
    ctx.notification.subject = 'Velkommen til Frigear'
    ctx.notification.body = renderMyTemplate(ctx.data)
  })
})
```

## Extend Auth at build time

This section is for module authors. A module's `setup()` can import these from `@frigear-nu/auth/utils`:

```ts
addAuthScope(nuxt, { name: 'reports:admin', description: 'Run reports', roles: ['admin'] })

addAuthResolver(nuxt, {
  name: 'my-tokens',
  prefix: 'mt_', // or `jwt: true`; one of the two is required
  resolver: resolver.resolve('./runtime/server/resolvers/my-token'),
  order: 100, // lower runs first
})

setAuthUserStore(nuxt, resolver.resolve('./runtime/server/user-store')) // first registration wins
```

A resolver turns a token into a principal:

```ts
// resolver: return a principal, or null when the token is invalid
export default async function (event: H3Event, token: string): Promise<AuthPrincipal | null> { … }
```

The user store is how Auth reads and writes users. [Users](/modules/identity/users) registers one:

```ts
interface AuthUserStore {
  findById(id: string | number): Promise<AuthStoredUser | null>
  findByEmail(email: string): Promise<AuthStoredUser | null>
  create(values: AuthUserCreate): Promise<AuthStoredUser>
  update(id: number, values: AuthUserUpdate): Promise<AuthStoredUser | null>
  remove(id: number): Promise<void>
  /** Gives the user a new id, taking everything that references it along. */
  changeId(from: number, to: number): Promise<void>
}
```

The same helpers are also Nuxt build hooks, for modules that prefer hooks:

| Hook | Payload |
| --- | --- |
| `auth:resolvers` | `AuthResolverDefinition[]` (push to register) |
| `auth:scopes` | `AuthScopeDefinition[]` (push to register) |
| `auth:user-store` | `{ path?: string }` (set `path`) |

The utils also export `ALL_SCOPES`, `hasScope`, `hasScopes`, `isPiiScope`, `isGrantableScope`, `parseScopeString`,
`USER_TOKEN_PREFIX`, `generateUserToken`, `hashToken`, `parseBearer`, `looksLikeJwt` and `tokenStatus`.

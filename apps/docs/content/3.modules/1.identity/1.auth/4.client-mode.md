With `authentication.mode: 'client'`, Auth makes a Nuxt app an OAuth **public client**: it signs the user in at an
issuer with the authorization code flow and PKCE, keeps the tokens in the browser or the device's Keychain / Keystore,
refreshes them, and calls your API with the access token. It runs in a browser SPA and inside a
[Capacitor](https://capacitorjs.com) webview, with no server and no database. The framework-agnostic core
(`@frigear-nu/auth/client-core`) works anywhere with `fetch` and WebCrypto.

The app code is the same as in server mode: `useUserSession()` says who is signed in, `useAuth()` holds the actions and
`$api` / `useApi()` call the API. Guards come from [Authorization](/modules/identity/authorization) in both modes.

:module-runtime{client mobile}

::note
**Requires** [`@frigear-nu/module-kit`](/modules/platform/module-kit), installed automatically. Client mode installs
none of server mode's dependencies (NuxtHub, nuxt-auth-utils, Notify, Menu). `@nuxt/ui` is optional and provides the
login and callback pages and `AuthSignInButton`. In a Capacitor app also install `@capacitor/app`,
`@capacitor/browser`, `@capacitor/preferences` and `@aparajita/capacitor-secure-storage`.
::

The OAuth-related modules split the work as follows; [Identity](/guide/concepts/identity) explains the whole picture.

| Module | Role | Where it runs |
| --- | --- | --- |
| [OAuth Server](/modules/identity/oauth-server) | The **issuer**: users sign in, apps are registered, tokens are issued. | The server of frigear.nu or your own. |
| Auth in client mode (this page) | The **app**: starts the sign-in, stores and refreshes the tokens, sends them to the API. | The browser or the phone. |
| [Frigear Resource](/modules/identity/frigear-resource) | The **resource server**: verifies the access token a service receives. | Each service the app calls. |
| [Mobile](/modules/interface/mobile) | The Capacitor shell. Installs Auth when `authentication` is configured. | The phone. |

Any OpenID Connect provider works as issuer: see [Use your own OAuth server](/guide/going-further/own-oauth-server).

::warning
For a server-rendered web app, keep server mode. Client mode moves the credential from an httpOnly cookie into
`localStorage` (or the Keychain on a device), where any XSS can read it in a browser, and the server cannot know who is
signed in. See [Security](#security).
::

## Quick setup

```bash
pnpm add @frigear-nu/auth @frigear-nu/authorization
# inside a Capacitor app also:
pnpm add @capacitor/app @capacitor/browser @capacitor/preferences @aparajita/capacitor-secure-storage
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxt/ui', '@frigear-nu/auth', '@frigear-nu/authorization'],
  authentication: {
    mode: 'client',
    client: {
      issuer: 'https://frigear.nu',
      clientId: 'my-app',
      scopes: ['openid', 'profile', 'email', 'offline_access'], // must contain 'openid'
      apiBase: 'https://api.example.com', // default: the issuer
      native: { scheme: 'com.example.app' }, // redirect URI com.example.app:/auth/callback
    },
  },
  // Guards are the app's: signed in everywhere. The login and callback pages stay open without a rule, and guests are
  // sent to the login page.
  routeRules: {
    '/**': { authenticated: true },
  },
})
```

Register a **public** client at the issuer with these exact redirect URIs:

- browser: `<origin>/auth/callback`, for example `http://localhost:3000/auth/callback`;
- native: `<scheme in lowercase>:/auth/callback`, for example `com.example.app:/auth/callback`.

The issuer must also allow the app's origins (`capacitor://localhost`, `https://localhost`, your dev origin) for CORS on
the token, revoke and userinfo endpoints. The full list is in [Use your own OAuth server](/guide/going-further/own-oauth-server).

```vue [app/pages/bills.vue]
<script setup lang="ts">
const { user } = useUserSession()
const { logout } = useAuth()
const { data: bills } = await useApi<Bill[]>('/api/bills')
</script>
```

## The mode

`authentication.mode` is `'server'` (the default) or `'client'`. Set it in the app's own `nuxt.config`, under the
`authentication` key. Auth, Authorization and Mobile pick their dependencies from it before Nuxt merges other modules'
defaults, so a mode set as inline module options or as another module's default fails the build. Other modules read it
with `resolveAuthMode(nuxt)` from `@frigear-nu/auth/mode`.

Client mode checks the app when it builds:

- **SSR is off.** Client mode sets `ssr: false`. An `ssr: true` in the app or one of its layers fails the build: the
  tokens live in the browser or the Keychain, so a server render would always be signed out.
- **`openid` is required.** The signed-in user comes from the id_token. Scopes without `openid` fail the build, also when
  they come from `runtimeConfig.public.authentication.client.scope`, and an env override is checked again when the
  client starts.
- **No server modules.** `nuxt-auth-utils` (it needs a server for its session endpoints) and
  [`@frigear-nu/users`](/modules/identity/users) (it needs a database) fail the build, and the error names the module
  that installed them. Modules that install Users (Account, Events, Payments, Subscriptions, Preferences) are server
  mode only.
- **Guards without Authorization.** `routeRules` with `authenticated`, `roles`, `guest` or `ability` but no
  `@frigear-nu/authorization` print a warning: nothing would check them.

## Options

Configured under `authentication.client`.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `issuer` | `string` | | Required (option or env). The issuer URL. |
| `clientId` | `string` | | Required (option or env). The public client's id. |
| `scopes` | `string[]` | `['openid']` | Requested scopes; must contain `openid`. Add `offline_access` for refresh tokens where the provider needs it. |
| `apiBase` | `string` | the issuer | Base URL of `$api` and `useApi`. |
| `apiOrigins` | `string[]` | the `apiBase` and issuer origins | Origins `$api` sends the bearer token to (set, it replaces the default). Any other origin gets none. The core's own `client.fetch` sends it to these plus `apiBase` and the issuer. |
| `onUnauthorized` | `'signOut' \| 'none'` | `signOut` | What a `401` that a forced refresh did not fix does: sign out and go to the login page (back afterwards), or only throw. |
| `redirectUri` | `string` | `<origin><callbackPath>` | The browser redirect URI. |
| `callbackPath` | `string` | `/auth/callback` | Path of the callback page and of the redirect URIs derived from it. |
| `native.scheme` | `string` | | Custom URL scheme, usually the app id. The redirect URI is `<scheme lowercase>:<callbackPath>`. An invalid scheme (for example with `_`) fails the build. [Mobile](/modules/interface/mobile) fills it in from `appId`. |
| `native.redirectUri` | `string` | | A full native redirect URI instead, for example a claimed `https` universal link. |
| `endpoints` | `Partial<OAuthEndpoints>` | discovered | `authorization`, `token`, `revocation`, `userinfo` and more; absolute or relative to the issuer. Win over discovery. |
| `discovery` | `boolean` | `true` | OpenID Connect discovery (`openid-configuration`, falling back to RFC 8414). `false` uses the [OAuth Server](/modules/identity/oauth-server) paths (`/oauth/authorize`, ...). |
| `authorizationParams` | `Record<string, string>` | `{}` | Extra authorization request parameters (`prompt`, `audience`, ...). |
| `storage` | `StorageOption` | `auto` | Where tokens live: `auto`, `secure`, `preferences`, `local`, `session`, `memory`, or a file path. See [Token storage](#token-storage). |
| `mapUser` | `string` | the claims mapping | Path to a file whose default export maps the signed-in user. See [The user](#the-user). |
| `userinfo` | `boolean` | `false` | The default mapping merges the issuer's `/userinfo` response too. |
| `redirect.login` | `string` | the login page | Where `onUnauthorized: 'signOut'` and a failed native sign-in send the visitor. |
| `redirect.afterLogin` | `string` | `/` | After a sign-in that started without a `returnTo`. A path on this site. |
| `redirect.afterLogout` | `string` | `/` | After `logout()`. A path on this site. |
| `dev.rewriteLoopback` | `boolean \| string` | `true` | In development on a device, `localhost` in the issuer and `apiBase` becomes the host the app was loaded from. A string sets the host. |
| `allowClientSecretInBundle` | `boolean` | `false` | Allow a build that embeds a client secret. See [Security](#security). |

The pages are the same options as in server mode, under `authentication.settings`:

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `pages.login` | `string \| boolean` | `true` (`/login`) | The login page (needs `@nuxt/ui`). A string sets another path, `false` none. On by default in client mode. |
| `pages.callback` | `boolean` | `true` | The callback page at `client.callbackPath` (needs `@nuxt/ui`). Client mode only. |

The other `settings` (password, magic link, passkeys, OAuth providers) are server mode only: in client mode every
feature flag in `runtimeConfig.public.authentication` is `false`, so code that checks them works in both modes.
`useAuthPages()` returns the login path in both modes.

Branding of the login page goes in `app.config.ts`:

```ts [app/app.config.ts]
export default defineAppConfig({
  authentication: {
    login: { title: 'Household bills', description: 'Sign in to continue.', logo: '/logo.svg', icon: 'i-lucide-wallet' },
  },
})
```

`logo` is an image path or `{ light, dark }`; `icon` shows when there is no logo. The page strings are in the
`auth.client` i18n namespace.

### Environment variables

Runtime config is `runtimeConfig.public.authentication.client`; the host's own values win over the module options.

| Variable | Option |
| --- | --- |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_ISSUER` | `issuer` |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_CLIENT_ID` | `clientId` |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_SCOPE` | `scopes`, as a space separated string |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_API_BASE` | `apiBase` |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_REDIRECT_URI` | `redirectUri` (browser) |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_NATIVE_REDIRECT_URI` | the native redirect URI |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_CLIENT_SECRET` | Development only, against a confidential client. `NUXT_PUBLIC_AUTHENTICATION_CLIENT_SECRET` works too. See [Security](#security). |

A list set in `runtimeConfig.public.authentication.client` (`apiOrigins`) replaces the module's. In a static build the
values are baked in when it is generated.

### Token storage

The `storage` option decides where tokens live; `auto` uses the Keychain / Keystore
(`@aparajita/capacitor-secure-storage`) on a device.

| Value | Where |
| --- | --- |
| `auto` | Secure storage on a device, `localStorage` in a browser. |
| `secure` | Keychain / Keystore; required on a device. |
| `preferences` | `@capacitor/preferences` (UserDefaults / SharedPreferences, not encrypted). |
| `local` / `session` | `localStorage` / `sessionStorage`. |
| `memory` | Signed out on every reload. |
| a file path | A file (relative to the app's `rootDir`, or a package) whose default export is a `TokenStorage` or a function returning one. |

An app with `@capacitor/core` but without the secure storage plugin **fails a production build** with `auto`: the tokens
would sit unencrypted. Install the plugin, or set `storage: 'preferences'` to accept that. On a device an install marker
wipes tokens that survived a reinstall. The Capacitor plugins are optional peers: only the installed ones are imported.

## App

```ts
const { ready, loggedIn, user, session, fetch, clear } = useUserSession()
const { status, authenticated, signingIn, login, completeLogin, logout, getAccessToken, isCallbackUrl, claims, getClient } = useAuth()
const { data } = await useApi<Bill[]>('/api/bills') // client only (`server: false`) by default
const me = await useNuxtApp().$api<Me>('/api/me')
```

| Name | What it is |
| --- | --- |
| `useUserSession()` | nuxt-auth-utils' shape. `ready` once the stored tokens were read, `loggedIn` only when signed in **and** there is a `user`, `user` (see [The user](#the-user)), `session` (`{ id, user }`, the id of the sign-in, kept across refreshes), `fetch()` (maps the user again, with a fresh userinfo; rejects when the mapping failed for a reason other than being offline, which keeps the claims mapping) and `clear()` (`logout({ redirect: false })`). `openInPopup()` throws. |
| `useAuth()` | `status` (`unknown`, `signed-in`, `signed-out`), `authenticated`, `signingIn`, and `login({ returnTo?, params? })`, `completeLogin(url?)`, `logout({ redirect? })` (`false` stays, a string goes there), `getAccessToken()` (refreshed when needed, `null` signed out or on the server) and `isCallbackUrl(url)`. Client mode only: `claims` (the id_token claims) and `getClient()` (the core client). |
| `useApi(url, options)` | `useFetch` through `$api`, client only by default. |
| `$api` | `$fetch` against `apiBase` with the bearer token for the `apiOrigins` only, and one forced refresh and retry on `401`. |
| `<AuthSignInButton return-to="/bills" />` | A sign-in button (needs `@nuxt/ui`). Emits `error`. |
| `/login`, `/auth/callback` | Pages (need `@nuxt/ui`). A page of the app at the same path wins. Without `@nuxt/ui`, build your own with `useAuth().login()` and `completeLogin()`. |

`user.id` is the issuer's `sub`, a string. Code that runs in both modes treats `user.id` as opaque: in server mode it
is the local user's id.

Inside a native app the plugin completes sign-ins from the cold-start URL (`App.getLaunchUrl()`) and from `appUrlOpen`
(callback URLs only: other deep links are left alone, and a link that answers no pending sign-in is ignored), and
refreshes the tokens on `resume`. A failed native sign-in goes to `redirect.login` with `?error=sign-in`.

## The user

The user comes from the id_token. A sign-in whose response has no valid id_token fails in `completeLogin`, and its
tokens are discarded. A stored session without readable claims (a corrupt store, another issuer or client) is signed
out and fires `auth:user-failed`. So `loggedIn` always means `user !== null`.

By default the user is mapped from the claims only, so a cold start offline still knows who is signed in:

```ts
{ id: sub, sub, name, email, avatar: picture, role }
```

`role` is set only when the token carries a string `role` claim. [OAuth Server](/modules/identity/oauth-server) adds
none by default; a host adds it with the `oauth:claims` hook.

`client.userinfo: true` merges the issuer's `/userinfo` response into that. `client.mapUser` maps the user yourself, and
may be async:

```ts [app/auth/map-user.ts]
import type { AuthClientUserContext } from '@frigear-nu/auth/client-core'

export default async ({ claims, userinfo, api }: AuthClientUserContext) => ({
  id: claims.sub,
  name: claims.name ?? '',
  role: (await userinfo()).role as string | undefined,
})
```

```ts [nuxt.config.ts]
authentication: { mode: 'client', client: { mapUser: './app/auth/map-user' } }
```

- `userinfo()` is fetched once per sign-in, again after `useUserSession().fetch()` or a refresh that changed the claims.
  It rejects a response whose `sub` is not the id_token's.
- `api` is `$api`, usable while a restored session is mapped at startup.
- Until an async mapping finishes, `user` is the claims mapping, so `loggedIn` never waits on the network. Mapping again
  within one sign-in keeps the previous result until the new one lands.
- A result that arrives after a logout or another sign-in is dropped.
- A failure fires `auth:user-failed` and leaves `user` at the claims mapping. A transient error (offline, `429`, `5xx`, a
  mapping that takes over 15 seconds) is retried at the next refresh. A `401` goes through `onUnauthorized`.

A `role` on the client is a hint for the UI, never a permission: see [Security](#security).

## Guards

Which pages need a user is the app's choice, through [Authorization](/modules/identity/authorization), as in server
mode. Nothing is protected by default.

```ts [nuxt.config.ts]
routeRules: {
  '/**': { authenticated: true }, // signed in everywhere
  '/about': { authenticated: false }, // except here
},
```

`definePageMeta({ authorize: false })` opens one page. Auth's login page and callback are exempt from less specific rules
such as `'/**'`, without a rule of yours; a rule of yours for that exact path (or a more specific one) still applies. In client mode the rules only decide what the app shows; the API decides what is
allowed.

A guest on a guarded page is sent to the login path (`client.redirect.login`, by default the login page) with the page
in `?redirect=`, and comes back there once signed in. Authorization's `redirectTo` changes the target; `redirectTo: false`
shows a `401` error instead.

## Hooks

Runtime hooks, called on the client with `useNuxtApp().hook(...)`. Client mode only:

| Hook | Payload | When |
| --- | --- | --- |
| `auth:signed-in` | `{ user, claims }` | After a sign-in completed and its user was mapped. Not when a stored session is restored. |
| `auth:signed-out` | `{ reason }` | After the session ended: `logout`, a rejected refresh token, the API refusing the tokens, or no identity. A stored session cleared at startup only fires `auth:user-failed`. |
| `auth:refresh-failed` | `{ error }` | A refresh failed but the session was kept (offline, server error, misconfigured client). |
| `auth:user-failed` | `{ error }` | The user could not be read: a stored session without identity (signed out), or a failed `mapUser` / userinfo mapping. |

## Security

- **Guards are UX, not access control.** The id_token is decoded without a signature check, and the stored tokens and
  the mapped user live in storage the device owner can edit. A route rule or a `role` in a client-mode app decides what
  to show, never what is allowed. Bundled pages must not contain privileged data. Every protected read and write goes to
  an API that checks [`requireAuth`](/modules/identity/auth/server#protecting-a-route) with scopes.
- **Server to client mode is a downgrade for a web app.** It moves the credential from an httpOnly cookie into
  `localStorage`, which any XSS can read. Use client mode for SPAs without a server and for Capacitor apps.
- **PKCE (S256), `state`, `nonce` and the `iss` check.** There is no client secret. Pending sign-ins are keyed by
  `state`, so a forged callback is ignored and never cancels a real sign-in, and two tabs can sign in at once. An
  authorization response with a wrong `iss` is rejected (RFC 9207).
- **id_token checks.** `iss`, `aud` / `azp`, `sub` and `nonce`, not the device clock. A refreshed id_token that fails
  them keeps the previous claims; the rotated tokens are always stored. Signatures are not verified: the token comes
  straight from the token endpoint over TLS (OpenID Connect Core 3.1.3.7). Resource servers must verify access tokens
  themselves, as [Frigear Resource](/modules/identity/frigear-resource) does.
- **Refresh rotation.** One refresh runs at a time (single-flight in the page, Web Locks across tabs), and the stored
  tokens are re-read under the lock so a tab never reuses a rotated token. A refresh token that was not rotated is kept.
- **Errors by kind.** `session` (an explicit `invalid_grant` or similar: signed out), `config` (`invalid_client`,
  issuer mismatch), `transient` (network, timeouts, `429`, `5xx`, a `4xx` other than `401` without an OAuth error body: the
  session is kept; a bare `401` is a `config` error) and `authorization` (a failed sign-in). Every request to the issuer times out after 15 seconds.
- **Bearer tokens go to allowed origins only** (`client.apiOrigins`).
- **Redirects stay on this site.** `returnTo`, `redirect.afterLogin`, `redirect.afterLogout` and `logout({ redirect })`
  are followed only when they are a path on this site (`isSafeRedirect`, the check every module shares).
  Authorization's `redirectTo` is used as configured and may be an absolute URL; `client.redirect.login` must be a path.
- **Secret guard.** `NUXT_PUBLIC_AUTHENTICATION_CLIENT_CLIENT_SECRET` is for `nuxt dev` against a confidential client. A
  production build fails when it, `NUXT_PUBLIC_AUTHENTICATION_CLIENT_SECRET` or
  `runtimeConfig.public.authentication.client.clientSecret` is set
  (`allowClientSecretInBundle: true` overrides this for throwaway builds). Outside development `clientSecret` is not
  declared at all, so a runtime env var cannot reach the bundle's config.

## Without Nuxt

```ts
import { createOAuthClient, webStorage } from '@frigear-nu/auth/client-core'

const client = createOAuthClient({
  issuer: 'https://frigear.nu',
  clientId: 'my-app',
  redirectUri: `${location.origin}/callback`,
  scope: 'openid offline_access',
  storage: webStorage(),
  attachTo: ['https://api.example.com'],
})
await client.authorize() // redirects
// on /callback:
const { returnTo } = await client.handleCallback(location.href)
const response = await client.fetch('https://api.example.com/me')
```

| Subpath | What it has |
| --- | --- |
| `@frigear-nu/auth/client-core` | The framework-agnostic client: `createOAuthClient`, `createSignInFlow`, storages, discovery, PKCE, the errors and the types (`AuthClientUserContext`, ...). |
| `@frigear-nu/auth/capacitor` | `createCapacitorOAuthClient` and `onCapacitorCallback` for a Capacitor app without Nuxt, and the adapters (`secureStorage`, `preferencesStorage`, `browserUserAgent`, `withInstallMarker`). |
| `@frigear-nu/auth/client-types` | Types only: `ClientModuleOptions`, `AuthClientPublicConfig`, `AuthAppConfig`, `StorageOption` and the core's types. |
| `@frigear-nu/auth/mode` | `resolveAuthMode(nuxt)` and `isSafeRedirect(value)`, free of `@nuxt/kit`, for other modules. |

`TokenStorage` and `AuthorizationUserAgent` are the extension points for another secure storage or an
`ASWebAuthenticationSession` user agent.

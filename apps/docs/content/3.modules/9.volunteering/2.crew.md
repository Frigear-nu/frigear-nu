---
title: Crew
description: Applications, approvals and invite links that turn people into an operation's crew, built on teams.
---

Crew is who works an operation: who applied, who is approved, and which team and role they hold. A volunteer applies
through a [form](/modules/features/forms) you choose for the operation, [staff](/guide/concepts/glossary) approve,
reject or waitlist them, and an invite link puts a BA on a bar directly. Everything a person holds is a team role in
[Teams](/modules/organisation/teams): an approved crew member is a member of one of the operation's teams. For who may
see what, use [Audience](/modules/organisation/audience); for the operations themselves,
[Operations](/modules/volunteering/operations).

The package is `@frigear-nu/crew`. It answers the viewer hook of Audience with the operations a person is approved
crew of.

## What you get

- **Volunteer pages** (on by default, each can be turned off): apply at `/crew/apply/:operationSlug`, your applications
  and places at `/crew/status`, and invite links at `/crew/invite/:token`. With [Menu](/modules/interface/menu), a "My
  crew" entry in the account menu. With [Mobile](/modules/interface/mobile), a Crew tab on the status page.
- **Admin area** (with [Admin](/modules/interface/admin) and [Widget](/modules/interface/widget)): a **Crew** tab on the
  operation page of Operations. It holds the applications table with filters, bulk approval and a member form, the
  invite links, and the settings of how the crew is recruited.
- **Server routes** (on by default): your own status, withdrawing, the apply page's data and accepting an invite, and a
  staff API for settings, members, decisions and invites.
- **Status emails** (on by default): a person is emailed when their status changes, from templates the host can
  override and an operation can rewrite.
- **Hooks**: `crew:member:applied`, `crew:member:approved`, `crew:member:rejected`, `crew:member:waitlisted` and
  `crew:member:withdrawn`.
- **Role presets**: a global `barmanager` is a BA and a global `crew` a bartender on the operation's teams, without
  adding anyone by hand.

## Quick setup

::steps

### Install Crew

```bash
pnpm add @frigear-nu/crew @nuxthub/core
```

### Add it to nuxt.config.ts

List Admin and Widget before Crew, so the tab registers. Operations and Teams need their admin pages for the tab to have
a page to live on.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/admin', '@frigear-nu/widget', '@frigear-nu/crew'],
  operations: { settings: { pages: { admin: true, adminOperation: true } } },
  teams: { settings: { pages: { admin: true, adminTeam: true } } },
  crew: {
    memberPlan: 'yearly',
  },
})
```

### Generate the migration

:::warning
Without a [migration](/guide/concepts/glossary) the crew tables and the columns Crew adds to `team_members` and `users`
do not exist, and every request to them fails. Crew extends tables it does not own, so generate the migration in your
app, with Teams, Users and Forms installed.
:::

```bash
pnpm db:generate
```

### Decide who manages the crew

:::warning
Staff routes check permissions through [Authorization](/modules/identity/authorization). Without a role that holds
`crew:manage`, nobody can approve anyone. The `admin` and `coordinator` roles hold it when your app defines them.
:::

### Make an application form

Create a form in [Forms](/modules/features/forms) that asks for a signed-in user (`access.auth: 'user'`) and stores its
submissions. Add a field with the key `phone` to collect phone numbers. Publish it.

### Set up the operation's crew

Open the operation, then its **Crew** tab. Choose the form under **Settings** and save. The first save creates a "Crew"
team for the operation when it has none, and the role presets.

::

::callout{color="success" icon="i-lucide-check"}
**What you should see:** a signed-in volunteer opens `/crew/apply/roskilde-2027`, fills in the form and gets an email.
The coordinator sees the application in the Crew tab and approves it. The volunteer now holds the role `volunteer` on
the Crew team at `GET /api/teams/me`, and the operation is in their `GET /api/operations/me`. A BA invite link added
from the same tab puts a person on the team as `ba` without an application.
::

## Options

Options go under the `crew` key.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `settings.pages.apply` | `string \| boolean` | on | The apply page. `true` is `/crew/apply/:operationSlug`; a path must contain `:operationSlug`. `false` turns it off. |
| `settings.pages.status` | `string \| boolean` | on | A volunteer's applications and places. `true` is `/crew/status`. |
| `settings.pages.invite` | `string \| boolean` | on | Accepting an invite link. `true` is `/crew/invite/:token`; a path must contain `:token`. |
| `settings.operationsTab` | `boolean` | `true` | Add the Crew tab to the `admin.operations` tab area. |
| `memberPlan` | `string` | none | A subscription plan key. With it, the presets add a rule that makes active subscribers volunteers. |
| `phoneField` | `string` | `phone` | The key of the form field that holds the phone number. |

**`memberPlan`** adds a `plan` mapping rule next to the global-role presets: a person with an active subscription to
the plan is a `volunteer` on every team of an operation that has presets. It only does something when
[Subscriptions](/modules/commerce/subscriptions) is installed. A volunteer through a mapping rule is not crew: they do
not take part in the operation.

**`phoneField`** names the field the phone number is read from. The number is saved on the user, so shifts and SMS can
reach them, and shown to staff with `crew:pii` only. A different field key in your form needs this option.

## Permissions

Crew registers these permissions with [Authorization](/modules/identity/authorization).

| Name | Flags | Held by default | What it allows |
| --- | --- | --- | --- |
| `crew:apply` | implicit | every signed-in user | Apply, see your own status, withdraw and accept an invite. |
| `crew:read` | implicit | every signed-in user | Read your own crew status, and the crew of the teams you lead (the `/api/crew` reads). |
| `crew:manage` | | `admin` and `coordinator` | Approve, reject and waitlist, move people, edit the settings and revoke invites. |
| `crew:pii` | sensitive | `admin` and `coordinator` | See emails, phone numbers and the answers of an application. |
| `crew:invite` | session only | `admin` and `coordinator` | Create invite links. |

- **Scope:** a token may use the named scope `crew` or `crew:read` itself. Either reads your own status, never the
  staff routes. `crew:pii` is usable as a scope too.
- **Why `crew:pii`:** staff who manage the crew see names and statuses. Emails, phone numbers and answers are personal
  data, so they sit behind a separate grant. It ends in `:pii`, so `crew:*` and `*` never cover it.
- **Why `crew:invite` is session only:** an invite link mints a credential that grants a role. Only a signed-in
  session creates one. An API token is refused with `403 session_required`, and `crew:invite` cannot even be a token
  scope.
- **Policy on `crew:read`:** a crew member is readable by the person, by the leads of their team (`ba` and up on a bar
  team, from `isTeamLead` of Teams) and by callers with `crew:manage`. The record is a membership
  (`{ userId, teamId }`). Anyone else gets `403`.

## Server

Everything under `/api` is in the [Routes](#routes) section. This section covers how the crew works.

### Applying

An application is a submission of the operation's form. Crew listens to `forms:submitted` and registers the person from
the submission's user id, so the form must ask for a signed-in user and store its submissions. Saving the settings
refuses a form that does not, and a form another operation recruits with.

A new application is a row of `team_members` on the operation's **default team**, with the team's lowest role and a
crew status of `applied`. It exists, and shows in the team for staff, but the person holds nothing: Teams gives a role
only to a row whose `status` is `null` or `active`, and an applicant's is `pending`.

- **One person, one row.** Applying again leaves the application as it is. A withdrawn application reopens as the same
  row. A rejected one stays rejected: only staff change that.
- **No application is taken** before `opensAt`, from `closesAt`, when the form is not published, or when the operation is
  wrapped up or archived. The apply page does not show the form then. A submission made anyway through the forms API is
  stored by Forms, but no crew row is created.
- **Private operations** take applications only from people who may read them (`operations:read`: they take part, or
  hold `operations:manage`). For anybody else the apply route answers `404`, so the operation's name and form do not
  leak, and a form submission registers nobody.
- **Redelivery is safe.** A submission that is stored on a crew row already, or is older than the person's last
  decision, registers nothing, so redelivering it from Forms' admin does not reopen a withdrawn application or send a
  second email. The phone number is saved only when an application registered somebody (a new row, or a reopened one).
- **The language** of the application is stored on the crew row and used for every email to that person afterwards.
- **People already on a team** of the operation (added by hand in Teams) are not registered again.
- **The phone number** in the `phone` field (`phoneField`) is saved on the user.

### Statuses

| Crew status | Teams `status` | Holds the role | How a person gets there |
| --- | --- | --- | --- |
| `applied` | `pending` | no | Applying. |
| `waitlisted` | `pending` | no | Applying over the capacity, or staff. |
| `approved` | `active` | yes | Staff, a promotion off the waiting list, or an invite. |
| `rejected` | `inactive` | no | Staff. |
| `withdrawn` | `inactive` | no | The person themselves. |

Staff move a person from `applied` to any of approved, rejected and waitlisted, from `waitlisted` to approved or
rejected, from `approved` to rejected or waitlisted, and from `rejected` to approved or waitlisted. A withdrawn person
has left: staff cannot move them, and they come back by applying again. Asking for the status a person has is a no-op.
Any other move is `409 crew_invalid_transition`.

Every change is a conditional update on the status that was read. When two requests race (a double click, an approval
against a withdrawal), the loser changes nothing: it gets the current row back and fires no hook and sends no email.
**Staff approval does not check the capacity**, and neither does an invite: both may take the crew past it.

Approving may also set the team (a team of the same operation) and the role (on that team's ladder). Staff can move an
approved person to another team or role without changing the status.

### Capacity and the waiting list

An operation may have a `capacity`: how many approved people it needs. Once the approved crew reaches it, a new
application is `waitlisted` instead of `applied`, with the next place on the list, when the waiting list is on. With the
list off it stays `applied`. Staff can approve beyond the capacity.

When a place frees up (an approved person withdraws or is rejected, or the capacity is raised) Crew promotes people off
the waiting list until the capacity is reached again, as if staff had approved them: the same hooks and the same email.
They go in the order they joined the list (then by when they applied), or, with **Earlier crew first**, earlier crew
first.

Only people the full crew waitlisted are promoted. Staff waitlisting is sticky: a person staff put on the list, whether
an applicant or an approved person they demoted, stays there until staff move them (`waitlistReason` is `manual`, as
against `capacity`). Each promotion is claimed with a conditional update and the capacity is checked again after the
claim, so several places freeing at once cannot overfill the crew.

### Earlier crew

A person is earlier crew when they are approved in an operation that started before this one. The staff list shows it,
filters by it (`?previous=true`) and sorts by it, and it is a `previousCrew` field of the member. It reads the crew
rows, there is no separate score. A person who withdrew or was rejected after being approved is not earlier crew.

### Invites

An invite is a link for a team of the operation and a role of its ladder: pick `ba` to invite someone as a lead. It has
a number of uses (1 by default) and may expire.

- The token is shown once, when the invite is created. The database keeps its SHA-256 hash and the first characters.
- Opening the link changes nothing. The person signs in and presses **Join the crew**, which calls
  `POST /api/crew/invites/:token/accept`.
- A use is claimed atomically: `uses < maxUses`, not revoked, not expired. A one-use link adds exactly one person, even
  when two open it at once. The other gets `410`.
- Accepting adds the person as `approved` with the invite's role. A person who is waiting or withdrew is moved onto the
  team on their existing row. Somebody approved anywhere in the operation, or holding a role there through Teams, gets
  `409 crew_already_member`, and a rejected applicant gets `409 crew_rejected`: staff's decision wins. No use is spent in
  either case.
- The use is given back only when writing the membership fails. A hook listener that throws afterwards does not give it
  back, since the person is on the team.
- The email goes out in the language of the request that accepted the invite.
- Revoking an invite stops the link. People who joined with it stay.

### Role presets

When the settings of an operation are saved **for the first time** with **Role presets** on (the default), Crew adds
owner-wide `team_role_mappings` rows for the operation: a global `barmanager` is `ba`, a global `crew` is `bartender`, and with
`memberPlan` an active subscription to the plan is `volunteer`. They are mapped grants: resolved when read, never
stored per person, and an explicit membership always beats them. A preset is skipped when the operation has a rule with the
same match already (whatever its role) and when its role is on no ladder. Presets are added once, and the choice is
recorded in `presets`: later saves never add presets, and turning them off removes nothing. Staff edit or delete the rules
in Teams, and a rule they removed is not added back.

### Default team

The first save of an operation's settings creates a team called "Crew" (kind `bar`) owned by the operation, when the
operation has no team. Applications land on the default team, which the settings let staff choose. Without a choice it is
the operation's first team. Staff then move people to other teams.

### Emails

When a status changes, the person gets an email through [Notify](/modules/communication/notify)'s
`dispatchEmailNotification`, from the template `crew-status-<status>` (`applied`, `waitlisted`, `approved`, `rejected`,
`withdrawn`). The templates are plain Vue files in `src/runtime/emails`, so a host overrides one by shipping a template
of the same name when [Email Templates](/modules/communication/email-templates) is installed. Without it the notification
goes out as built, with an HTML body and a plain text one.

The links in the emails use the configured site URL (`NUXT_PUBLIC_SITE_URL`, as Auth's emailed links do) and fall back
to the request's origin only when none is set. Each operation can turn an email off, or rewrite its subject and message, under **Settings** or `statusEmails` of the
settings API. Texts may be a plain string or per language, and may use `{{name}}`, `{{operation}}`, `{{team}}`, `{{role}}`
and `{{status}}`. A failing email is logged and never fails the change. No SMS is sent.

An application, a promotion off the waiting list and an invite each send the email of the status they end in: someone who
lands on the waiting list gets the waiting list email, not both.

### Push

With [Push](/modules/communication/push) installed, Crew registers the topic `crew.status` (email and push on by default, SMS
is not offered) and sends the status message through `notifyUser`, so a person can turn the email or the push off on their
account page. The push notification says the email's subject and message and opens `/crew/status`. An operation that turns a
status email off sends neither. Without Push the email goes out through Notify as before.

### Audience answers

Crew answers `audience:viewer:resolve` from a server plugin it always registers: the operations a person is approved
crew of go into `viewer.operationIds`. That is what fills `GET /api/operations/me` and the participation checks of
[Audience](/modules/organisation/audience). It identifies the user from `ctx.user`, and a failure leaves the viewer
without crew operations, never with more. Applied, waitlisted, rejected and withdrawn people do not take part.

### Team hooks

Teams fires `teams:member:*` from its own admin routes only, once per row change. When Crew changes rows it fires them
itself, with the same payloads, but they follow the **grant** instead of the row: `teams:member:added` when a person starts to hold a role (approved), `teams:member:removed`
when they stop, `teams:member:role-changed` when an approved person's role changes, and removed then added when an approved
person moves to another team. An applicant row has no grant, so it fires nothing in Teams; the crew hooks tell the story.

### Dashboard item

With [Dashboard](/modules/interface/dashboard) installed, Crew adds `crew.status` to `crew.home` (permission
`crew:read`, order 10): where the person applied or works, with a status badge, team and role, and a link to
`/crew/status`. It reads `GET /api/crew/me`, shows applications still in play first, and an empty state when the person
has not applied. Texts are under `crew.dashboard`.

## App

### Pages

| Page | Path | For |
| --- | --- | --- |
| Apply | `/crew/apply/:operationSlug` | A signed-in volunteer. Renders the operation's form, or says why there is none: not open yet, closed, already applied, rejected, already on a team. Signed-out visitors go to the sign-in page and back. |
| Status | `/crew/status` | A signed-in volunteer. Each operation they applied to or work at, with status, team, role and a Withdraw button, or Apply again after withdrawing. |
| Invite | `/crew/invite/:token` | A signed-in person with an invite link. The page changes nothing until they press Join. |

The pages are public routes (anonymous visitors see the sign-in page) and need `@nuxt/ui`. None of them is `/crew` itself,
which the mobile home tab of the dashboard module uses.

### Tab on the operation page

Crew adds a **Crew** tab to the `admin.operations` tab area of [Widget](/modules/interface/widget), before the Teams tab.
It reads the operation's record from the tab context and shows:

- **Applications and crew**: a table with filters (status, team, earlier crew) and search, sortable columns, row selection
  with **Approve selected**, and a row menu: Open application, Approve application, Move to waiting list, Reject
  application (confirms first). Opening a person
  shows their details, a form for team and role, and with `crew:pii` their application's answers.
- **Invite links**: a table with a status per link. **Create invite** opens a slideover and shows the link once, with a
  copy button. A link is revoked from its row menu, with a confirmation.
- **Settings**: the form (only forms the operation can use are offered), default team, capacity, waiting list, earlier crew
  first, the window, role presets (fixed once the settings exist) and the status emails. The tab reads what the caller may
  do from `GET /api/auth/me/access`, so the application's answers show only with `crew:pii`.

Turn it off with `settings.operationsTab: false`.

### Composables

| Composable | What it does |
| --- | --- |
| `useCrewActions()` | `approve`, `reject`, `waitlist`, `approveMany`, `open`, `createInvite`, `revokeInvite` and `menu(member, options)`, with toasts and confirmations. |
| `useCrewLinks()` | Locale-aware links to the apply, status and invite pages. |
| `useCrewTranslate()` | Reads a translated text in the current locale. |

## Hooks

Your app answers these [Nitro](/guide/concepts/glossary) hooks from a server plugin (`server/plugins/*.ts`).

| Hook | When | Payload |
| --- | --- | --- |
| `crew:member:applied` | After somebody applied, or applied again after withdrawing. | `{ event, operationId, member }` |
| `crew:member:approved` | After somebody joined: approved by staff, promoted or through an invite. | `{ event, operationId, member }` |
| `crew:member:rejected` | After an application was rejected, or an approved person was taken off. | `{ event, operationId, member }` |
| `crew:member:waitlisted` | After somebody is on the waiting list, over the capacity or by staff. | `{ event, operationId, member }` |
| `crew:member:withdrawn` | After somebody withdrew. | `{ event, operationId, member }` |

- `member` is the staff DTO with the email and phone number, whatever the caller may see, so a listener that forwards it
  decides what to share.
- Somebody who lands on the waiting list fires `crew:member:applied` and then `crew:member:waitlisted`.
- Crew also listens to `forms:submitted` and answers `audience:viewer:resolve`.

## Routes

Typed path builders are exported as `crewApi` from `@frigear-nu/crew/api`.

| Route | Who | What it does |
| --- | --- | --- |
| `GET /api/crew/me` | `crew:read` | Your crew status in every operation, any status. |
| `POST /api/crew/me/:operationId/withdraw` | `crew:apply` | Withdraw. `404` without an application, `409 crew_not_withdrawable` once rejected or withdrawn. |
| `GET /api/crew/operations/:operation/apply` | `crew:apply` | The form slug to render, or the reason not. `:operation` is the id or the URL name. `404` for a private operation the caller may not read. |
| `GET /api/crew/operations/:operation/members` | `crew:read` | The crew as the caller may read it, paginated like the staff list. Staff read all; team leads their own teams; others an empty page. |
| `GET /api/crew/members/:id` | `crew:read` + policy | One crew member: yourself, a lead of the team, or staff. |
| `POST /api/crew/invites/:token/accept` | `crew:apply` | Join the invite's team. `404`, `410 invite_revoked`, `invite_expired`, `invite_used`, or `409 crew_already_member`. |
| `GET /api/admin/crew/operations/:operationId/settings` | `crew:manage` | The settings, or the defaults (`source: 'default'`). |
| `PUT /api/admin/crew/operations/:operationId/settings` | `crew:manage` | Save the whole record. Creates the default team and presets. `400` for an unsuitable form, `409` for a form in use. |
| `GET /api/admin/crew/forms` | `crew:manage` | The forms an operation can recruit with: asking for a signed-in user, storing submissions, not used by another operation (`?operationId=` keeps its own). |
| `GET /api/admin/crew/operations/:operationId/members` | `crew:manage` | The whole crew, paginated, with `status`, `team`, `previous`, `q`, `sort`, `order`. |
| `POST /api/admin/crew/operations/:operationId/members/approve` | `crew:manage` | Approve `{ ids }` (up to 200). People that cannot be approved come back in `skipped`. |
| `PATCH /api/admin/crew/members/:id` | `crew:manage` | Move to `{ teamId?, role? }`. |
| `POST /api/admin/crew/members/:id/approve` | `crew:manage` | Approve, optionally `{ teamId, role }`. |
| `POST /api/admin/crew/members/:id/reject` | `crew:manage` | Reject. |
| `POST /api/admin/crew/members/:id/waitlist` | `crew:manage` | Put on the waiting list. |
| `GET /api/admin/crew/members/:id/submission` | `crew:pii` | The application's answers, with the form's labels. |
| `GET /api/admin/crew/operations/:operationId/invites` | `crew:manage` | The invite links, never their tokens. |
| `POST /api/admin/crew/operations/:operationId/invites` | `crew:invite` | Create `{ teamId, role, maxUses?, expiresAt? }`. The token is in this answer only. |
| `DELETE /api/admin/crew/invites/:id` | `crew:manage` | Revoke. |

Emails, phone numbers and the email search need `crew:pii`; without it the member has neither field. Reads that leads and
volunteers make live under `/api/crew`; `/api/admin/crew` is for staff.

## Database

Tables or columns the module adds. Generate and commit a [migration](/get-started/database#migrations) after installing.

| Table | Holds |
| --- | --- |
| `crew_settings` | One row per operation: `operationId`, `formId`, `defaultTeamId`, `capacity`, `waitlist`, `previousCrewFirst`, `opensAt`, `closesAt`, `statusEmails` (json), `presets`. |
| `crew_invites` | `civ_` id, `operationId`, `teamId`, `role`, `tokenHash` (unique), `prefix`, `maxUses`, `uses`, `expiresAt`, `createdBy`, `revokedAt`. |
| `team_members` (columns added) | `crewStatus`, `appliedAt`, `decidedAt`, `decidedBy`, `submissionId`, `waitlistPosition`, `waitlistReason` (`capacity` or `manual`), `locale`. A row with a `crewStatus` is a crew membership; rows added by hand in Teams have none. |
| `users` (column added) | `phone`, set from the application. |

Operation, team and user ids carry no foreign key: those tables belong to other modules. The extension files are
`team-members` and `users`, each with a `.postgresql.ts` twin, and the schema parity test covers them.

## Translations

Override any string in your app's `i18n/locales/<code>.json`. The module registers `da` and `en` files under `crew.*`.
See [overriding module strings](/modules/platform/module-kit/i18n#overriding-module-strings-in-your-app).

Key groups: `menu.*`, `mobile.*`, `permissions.*`, `scopes.*`, `admin.*` (with `admin.tabs.*`, `admin.statuses.*` and
`admin.inviteStatuses.*`), `apply.*`, `status.*` and `invite.*`. The email texts are per operation data, or the
templates.

## Testing notes

The e2e fixture runs on sqlite with Operations, Teams, Forms and Notify, without Authorization or Email Templates.
Roles come from a role provider by email, and the emails are captured by a `notify:email` listener over notify's log
driver. The postgresql branch of the earlier-crew query has no end-to-end test; the extension and schema twins are
checked by the parity test.

## Not in this release

- **A dashboard item for staff** (open applications to decide). `crew.status` is the volunteer's own.
- **SMS.** Only email goes out. Shifts adds reminders.
- **Website wiring.** The website adds the modules and the form; nothing here changes it.

## Open questions

- Should a person who was approved, then rejected, count as earlier crew? Today only a current `approved` row counts.
- Should promotion off the waiting list ask staff first instead of approving at once?
- Should an operation have several application forms, for example one per team?

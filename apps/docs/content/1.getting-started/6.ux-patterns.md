Every module that ships screens follows the same handful of patterns, so the app feels like one product no matter which
modules are installed. The building blocks live in [`@frigear-nu/ui`](/modules/ui); the admin shell is
[`@frigear-nu/admin`](/modules/admin) and the account shell is [`@frigear-nu/account`](/modules/account). This page is
the rulebook: read it before adding a page, and follow it when reviewing one.

::note
These are patterns, plus a light theme for the app areas: the shell sets the chrome tones (page, sidebar and navbar
backgrounds, a primary-coloured brand tile). Colours, fonts and radius still come from Nuxt UI and your app's
`app.config.ts`; the shared components only add structure and spacing.
::

## Layout and navigation

There are three areas, each with its own layout. A page picks its area by path, not by importing a layout.

| Area | Paths | Layout | What it is |
| --- | --- | --- | --- |
| Public site | everything else | `default` from the [base layer](/layers/base) | Header and footer. Public pages use `UContainer > UPage`. |
| Admin back office | `/admin/**` | `admin` ([Admin](/modules/admin)) | Dashboard shell: a collapsible sidebar with grouped navigation, a ⌘K palette and the account menu in the sidebar footer. |
| Account area | `/account/**` | `account` ([Account](/modules/account)) | The same shared `AppShell` from [`@frigear-nu/ui`](/modules/ui#app-shell) as admin, with the account navigation in the sidebar. |

Both app areas are thin layouts around `AppShell`, so they have the same chrome. Pages in them render their own
`PageHeading`; the layouts draw no heading.

### Admin back office

The sidebar navigation is grouped, and each group reads its own [menu](/modules/menu) path:

| Group | Menu path | Put here |
| --- | --- | --- |
| Overview | `admin.nav.overview` | The dashboard. |
| Manage | `admin.nav` (root) | The things staff manage every day: users, events, forms. |
| Settings | `admin.nav.settings` | Configuration: OAuth applications, integrations. |

New features go into one of these groups. A new group needs a reason, such as a whole new class of screens that
does not read as "managing" or "settings". The ⌘K palette lists the same groups, so a page that is in the navigation is
also searchable. Colour mode is not in the chrome: it lives in the account menu under **Appearance**.

The navbar shows a muted "Area › Section" eyebrow (for example "Administration › Users"), not a title, so the page's
`PageHeading` is the only `<h1>`. Pages that need the full width (the form builder) set `definePageMeta({ wide: true })`;
the default body is centred at `max-w-7xl`.

### Account area

`/account/**` renders in the `account` layout, which is the same `AppShell` as admin: no site header or footer, no
`UPageAside` and no `PageSectionSwitcher`. The sidebar has the brand, the navigation built from the `account` menu and,
in its footer, **Back to the site** and the `AccountMenu`. That is the one place the signed-in identity is shown; it is
not repeated in headings. On narrow screens the sidebar opens as a drawer from the navbar.

Every page renders its own heading as the first child of its root: `AccountHeader` for the pages of the account package
(a `PageHeading` filled from the current menu item), and `PageHeading` with the menu item's own i18n keys for pages other
modules add, so the label and the title cannot drift. `/account` itself is an overview: a summary card (`UUser` plus
`AccountIdentity`), the `account.overview` [widget](/modules/widget) area and shortcuts to the other pages. A module adds
a page by registering the route and an item in the `account` menu; it never draws its own account navigation.

### Public site

Public pages (events, forms, content) use `UContainer > UPage` with `UPageHeader` for the title and `UPageSection` for
bands. App pages, meaning everything in the admin and account areas, use `PageHeading` instead. Do not mix them: the
public header is a marketing-sized hero, `PageHeading` is a working title with actions.

## Pages

### Lists

A top-level entity gets a list page and a detail page.

- `PageHeading` with the entity's name and the primary action ("Add user", "New event") in `#actions`.
- `PageToolbar` with search and filters once the list is longer than about eight rows; leave it out for short lists.
- A `UTable` inside `TableCard`, with `tableUi()` for the shared table styling: small muted headers, compact rows on
  desktop, taller rows on mobile. Rows are clickable and open the detail page. Long lists add `sticky` and
  `tableUi({}, { sticky: true })` so the header stays in view while the table scrolls inside its card.
- A `RowMenu` in the last column for the row's actions (see [Forms and actions](#forms-and-actions)).
- Sortable columns use `useTableSort().header(id, label)`: a ghost button that cycles ascending, descending, unsorted.
- `TablePagination` goes in the card's `#footer` ("21–40 of 132", rows per page, pages). Server-paginated lists keep
  page, page size, search, sort and filters in the URL with `useTableQuery`, so a filtered list can be linked and
  survives a reload.
- An empty list is a `UEmpty` ([empty states](#empty-states)), not an empty table.

Loading never blanks a list that is already on screen. `TableCard :loading` shows skeleton rows on the first load
only; every load after that (the next page, a new sort, a search) passes `:refreshing`, which keeps the current rows
and dims them until the new ones arrive. The empty state only shows once a load succeeded with no rows, never while
`status` is `'pending'` (see [Loading](#loading)).

Cells follow the same conventions everywhere:

- The first column is a `TableIdentity`: the name, with a muted second line (an email, a slug) and an optional avatar
  or icon. Badges that belong to the name go in its `#badges` slot.
- Numbers are right-aligned with tabular figures (`meta: numericColumn`); dates use `useFormat()` in a
  `tabular-nums` span.
- A missing value is `emptyCell()`, a dimmed dash, not an empty cell.
- Status badges are `StatusBadge` (a `variant="subtle"` badge coloured with `statusColor`); `colors` overrides single
  statuses (`:colors="{ archived: 'warning' }"`).

```vue
<script setup lang="ts">
import type { TableColumn } from '@nuxt/ui'

const t = useModuleT('events')
const format = useFormat()
const actions = useEventActions()

const { page, pageSize, search, sort: sortState, query } = useTableQuery({ sort: { id: 'startsAt', desc: true } })
const { header } = useTableSort(null, sortState)
const { data, status } = await useFetch('/api/events', { query, default: () => ({ items: [], total: 0 }) })
const pending = computed(() => status.value === 'pending')

const TableIdentity = resolveComponent('TableIdentity')
const RowMenu = resolveComponent('RowMenu')
const columns: TableColumn<EventRow>[] = [
  {
    accessorKey: 'title',
    header: header('title', t('admin.title', 'Title')),
    cell: ({ row }) => h(TableIdentity, { title: row.original.title, description: row.original.location }),
  },
  { accessorKey: 'startsAt', header: header('startsAt', t('admin.starts', 'Starts')) },
  { accessorKey: 'capacity', header: t('admin.capacity', 'Capacity'), meta: numericColumn },
  { id: 'actions', cell: ({ row }) => h(RowMenu, { items: actions.menu(row.original), subject: row.original.title }) },
]
</script>

<template>
  <div class="flex flex-col gap-4">
    <PageHeading :title="t('admin.events', 'Events')">
      <template #actions>
        <UButton icon="i-lucide-plus" :label="t('admin.create', 'New event')" @click="actions.create()" />
      </template>
    </PageHeading>

    <PageToolbar>
      <UInput v-model="search" icon="i-lucide-search" :placeholder="t('admin.search', 'Search events')" />
    </PageToolbar>

    <TableCard :loading="pending && !data.items.length" :refreshing="pending && !!data.items.length">
      <UTable
        :data="data.items"
        :columns="columns"
        :ui="tableUi({}, { sticky: true })"
        sticky
        @select="(_, row) => navigateTo(`/admin/events/${row.original.id}`)"
      >
        <template #startsAt-cell="{ row }">
          <span class="tabular-nums">{{ format.dateTime(row.original.startsAt) }}</span>
        </template>
        <template #empty>
          <UEmpty variant="naked" icon="i-lucide-calendar" :title="t('admin.empty', 'No events yet')">
            <template #actions>
              <UButton :label="t('admin.create', 'New event')" @click="actions.create()" />
            </template>
          </UEmpty>
        </template>
      </UTable>
      <template #footer>
        <TablePagination v-model:page="page" v-model:page-size="pageSize" :total="data.total" />
      </template>
    </TableCard>
  </div>
</template>
```

A table in a tab or on a detail page sits in `TableCard :title` (with `#actions` for its primary action), the same header
as `SectionCard`; never a `flush` `SectionCard` around a `UTable`. Pass `tableUi({ tr: '' })` when the rows open nothing.

A short list that is loaded in one go sorts on the client: bind `useTableSort()`'s `sorting` with
`v-model:sorting` and leave out `useTableQuery` and `TablePagination`.

Pages have no wrapper component: the page root is a plain `<div class="flex flex-col gap-4">`.

### Detail pages

- `PageHeading` with a `breadcrumb` back to the list (`[Users, Ada Lovelace]`), a status `#badge` when the record has
  one, and the primary actions (outline `RowMenu` last) in `#actions`.
- Sections are `SectionCard`s. A form inside a section puts its Save button in the section's `#footer`
  (`type="submit"` with `form="<id>"`). Key facts are a `DescriptionList`.
- Inline settings forms use horizontal rows: each field is a `FormRow` (`UFormField orientation="horizontal"` with
  the label and its `description` hint on the left, the control on the right, stacked below `sm`), in a parent with
  `divide-y divide-default`. Short controls get `class="w-full sm:max-w-sm"`, long text (textareas, editors)
  `class="w-full"`. Slideover forms stay vertical.

  ```vue
  <SectionCard :title="t('password.title', 'Password')">
    <UForm id="change-password" :schema="schema" :state="state" class="flex flex-col divide-y divide-default" @submit="save">
      <FormRow name="newPassword" :label="t('new', 'New password')" :description="t('newHint', 'At least 8 characters.')" required>
        <UInput v-model="state.newPassword" type="password" class="w-full sm:max-w-sm" />
      </FormRow>
    </UForm>
    <template #footer>
      <div class="flex justify-end">
        <UButton type="submit" form="change-password" :loading="busy" :label="t('save', 'Change password')" />
      </div>
    </template>
  </SectionCard>
  ```
- Sections other modules can extend are [`WidgetTabs`](/modules/widget) (`extendTabs`); sections the page owns are
  `PageTabs`. See [which tabs to use](#tabs).
- A record that does not exist shows a `UEmpty` with a link back to the list, not a blank page (see
  [Failed, forbidden and not found](#failed-forbidden-and-not-found)).

### Tabs

Both tab components share one look (a bordered strip with an underline highlight), so a page never looks different
because of how it is built.

| Use | When |
| --- | --- |
| `WidgetTabs` | Other modules should be able to add sections to the page, such as the user detail page, where Payments or Membership appear when those modules are installed. The active tab is in `?tab=`. |
| `PageTabs` | The sections are fixed by the page itself (a form's builder, settings, access). Pass `items` with `to` for link tabs (each tab is a route), or `v-model` for state tabs. |

### Light entities

An entity with little of its own (a unit, an application) opens in a slideover instead of getting a detail page. The
open record lives in the URL query (`?application=<id>`), so ⌘K and other pages can deep-link to it.

### Divided list

A short list of records that is not a table (passkeys, documents, applications) is a `SectionCard flush` around a
`ul.divide-y.divide-default`. Each row is `li.flex.items-center.gap-3.px-4.py-3`: a leading icon or avatar, a
`min-w-0 flex-1` text block and a trailing button or `RowMenu`. Put the empty state inside the card as
`UEmpty variant="naked"`.

```vue
<SectionCard flush :title="t('documents.title', 'Documents')">
  <ul class="divide-y divide-default">
    <li v-for="doc in documents" :key="doc.id" class="flex items-center gap-3 px-4 py-3">
      <UIcon :name="doc.icon" class="size-5 shrink-0 text-muted" />
      <span class="min-w-0 flex-1 truncate font-medium text-highlighted">{{ doc.label }}</span>
      <UButton :to="doc.path" color="neutral" variant="outline" :label="t('documents.download', 'Download')" />
    </li>
  </ul>
</SectionCard>
```

### Page-wide draft

Most pages save per section: the form sits in a `SectionCard` and Save is in its `#footer`. When one draft spans the
whole page and several cards edit it (the form builder), Save stays in the `PageHeading`'s `#actions` instead, next to
the status. It is the only exception: the page still has one editor and one Save, never a Save per card.

### Overview pages

An overview shows numbers as `StatCard`s, each linking (`to`) to the list it summarises, then `ListCard`s for what
needs a decision: recent items, upcoming events. The admin dashboard and the account overview are both built this way
from [widget](/modules/widget) areas.

### Empty states

An empty state is a `UEmpty` that says what the thing is and offers the single action that gets you going: "No events
yet" and a "New event" button. Inside a card use `variant="naked"`. When a prerequisite is missing, point to it instead
of the action ("Add a ticket type first"). There is no separate empty-state component.

### Failed, forbidden and not found

A page whose data did not load shows a `UEmpty` as the page body (inside the page root, below the `PageHeading` when the
heading does not depend on the data). There are three shapes, all the default variant because they replace the body:

| Case | Icon | Title and description | Action |
| --- | --- | --- | --- |
| Failed (any other error) | `i-lucide-circle-alert` | "X could not be loaded", the `errorMessage(error, fallback)` | Neutral outline "Try again" (`i-lucide-rotate-ccw`) that refreshes |
| Forbidden (401, 403) | `i-lucide-lock` | "You are not allowed to see X" | None |
| Not found (404) | the entity's own icon (`i-lucide-user-x`) | "X not found" and a hint ("It may have been deleted.") | Neutral outline "All X", a link to the list |

```vue
<UEmpty
  v-if="error && !data"
  :icon="forbidden ? 'i-lucide-lock' : 'i-lucide-circle-alert'"
  :title="forbidden ? t('admin.forbidden', 'You are not allowed to see events') : t('admin.loadFailed', 'Events could not be loaded')"
  :description="forbidden ? undefined : errorMessage(error, t('admin.loadFailedHint', 'Try again in a moment.'))"
  :actions="forbidden ? [] : [{ label: t('retry', 'Try again'), icon: 'i-lucide-rotate-ccw', color: 'neutral', variant: 'outline', onClick: () => refresh() }]"
/>
```

Check `error && !data` so a failed background refresh does not replace rows that are already on screen.

### Loading

A page never says "nothing here" before it knows. The empty state, a "join" hero or a "not a member" message is a
claim about the data, so it only renders after a load succeeded and found nothing.

- **Pages await their data.** `await useFetch(...)` / `await useCachedFetch(...)` (or an awaitable module composable
  such as `await useMyTickets()`), so the server renders the page with its data and hydration shows the same thing.
  Never leave a page's main data un-awaited with `default: () => []`.
- **Data that should survive navigation uses `useCachedFetch`** (see [UI](/modules/ui#loading-data-that-survives-navigation)).
  Plain `useFetch` data is dropped when the page unmounts, so going back flashes the empty state while it refetches.
- **`useLazyFetch` (or an un-awaited fetch) only in widgets** and secondary parts of a page that must not hold up the
  render. They show a skeleton while loading: `SectionCard :loading`, `ListCard :loading`, `TableCard :loading`,
  `StatCard :loading`.
- **Gate on "pending and nothing to show"**: `status === 'pending' && !data` (or `useCachedFetch`'s `loading`), not on
  `status === 'pending'` alone, so a background refresh keeps the current content on screen.
- **Errors are not empty.** Do not swallow a failed request into default data; check `error` and show a `UEmpty` with
  the message (or a toast for a background refresh), so "you have no tickets" is never shown because a request
  failed.
- The skeleton has the size of what it replaces, so the layout does not jump when the data arrives.

## Forms and actions

### Create and edit

- Create and edit forms open in a `FormSlideover` containing a `UForm` with a zod schema. Short yes/no choices are a
  modal (`UModal`). Never inline a create form next to a table.
- Open forms through `useOverlay()`; the overlay resolves with the saved record (or `false` when cancelled), so the
  caller can navigate to it.
- Cancel is `color="neutral" variant="outline"` and the primary action comes last. `FormSlideover` does this for you.
- Hints belong in `UFormField`'s `description`, not in extra paragraphs.
- Slideover forms stay vertical (plain `UFormField`). Inline settings forms in a `SectionCard` use `FormRow` rows (see
  [Detail pages](#detail-pages)).

```vue
<!-- EventFormSlideover.vue -->
<script setup lang="ts">
const props = defineProps<{ event?: EventRow }>()
const emit = defineEmits<{ close: [saved: EventRow | false] }>()

const t = useModuleT('events')
const { busy, run } = useAction()
const state = reactive({ title: props.event?.title ?? '' })

const save = () => run(async () => {
  const saved = await $fetch<EventRow>(props.event ? `/api/events/${props.event.id}` : '/api/events', {
    method: props.event ? 'PATCH' : 'POST',
    body: state,
  })
  emit('close', saved)
}, { success: t('admin.saved', 'Event saved') })
</script>

<template>
  <FormSlideover
    form-id="event-form"
    :title="event ? t('admin.edit', 'Edit event') : t('admin.create', 'New event')"
    :submit-label="event ? t('admin.save', 'Save event') : t('admin.create', 'New event')"
    :loading="busy"
    @close="emit('close', false)"
  >
    <UForm id="event-form" :state="state" class="flex flex-col gap-4" @submit="save">
      <UFormField name="title" :label="t('admin.title', 'Title')" :description="t('admin.titleHint', 'Shown on the public page.')">
        <UInput v-model="state.title" />
      </UFormField>
    </UForm>
  </FormSlideover>
</template>
```

### Create button

The primary create button has `icon="i-lucide-plus"` and a label that names the object ("New event", "Add user"). The
page only calls `actions.create()`. The composable opens the `FormSlideover`, navigates to the detail page when the
entity has one, and returns the record, or `false` when cancelled; the page never navigates itself.

### One actions composable per entity

Every entity has a `use<Entity>Actions()` composable (`useUserActions`, `useEventActions`, `useFormActions`) that
owns create, edit and remove, the toasts and the refresh afterwards. It returns `menu(record)` for the row menu, so
every list and detail page offers the same actions in the same order. Pages stay thin. It lives in the module that owns
the entity, not in `@frigear-nu/ui`. Sub-entities that have no page of their own (an event's ticket types and add-ons)
get the same treatment in a composable of their own, whose menus skip Open: see `useEventCatalogActions`.

```ts
// composables/useEventActions.ts
export function useEventActions() {
  const t = useModuleT('events')
  const overlay = useOverlay()
  const confirm = useConfirmDialog()
  const toast = useToast()
  const { localize } = useLocaleLink()

  async function create() {
    const saved = await overlay.create(EventFormSlideover).open()
    if (saved) await navigateTo(localize(`/admin/events/${saved.id}`))
  }

  async function remove(event: EventRow) {
    const confirmed = await confirm({
      title: t('admin.deleteTitle', 'Delete {name}?', { name: event.title }),
      description: t('admin.deleteBody', 'Its tickets and attendees are deleted too. This cannot be undone.'),
      confirmText: t('admin.delete', 'Delete event'),
      destructive: true,
    })
    if (!confirmed) return
    try {
      await $fetch(`/api/events/${event.id}`, { method: 'DELETE' })
      toast.add({ title: t('admin.deleted', 'Event deleted'), description: event.title })
      await refreshNuxtData('events')
    }
    catch (e) {
      toast.add(errorToToast(e))
    }
  }

  const menu = (event: EventRow) => [
    [{ label: t('open', 'Open'), icon: 'i-lucide-arrow-right', to: localize(`/admin/events/${event.id}`) }],
    [{ label: t('admin.edit', 'Edit event'), icon: 'i-lucide-pencil', onSelect: () => overlay.create(EventFormSlideover).open({ event }) }],
    [{ label: t('admin.delete', 'Delete event'), icon: 'i-lucide-trash-2', color: 'error' as const, onSelect: () => remove(event) }],
  ]

  return { create, remove, menu }
}
```

### Row actions

Row actions go in a `RowMenu` (the `⋯` button) at the end of the row, with groups in this order: **Open** (and "View
public page") first, then the edits and extras, then the destructive action in its own group, coloured red. Icons:
Open `arrow-right`, Edit `pencil`, Duplicate `copy`, Archive `archive`, Delete `trash-2`. Detail pages build the menu with
`open: false` (they are already there), and sub-entities skip Open. There are no loose icon buttons in rows. Pass
`subject` so the button's accessible name reads "Actions for Ada Lovelace".

### Destructive actions

Destructive actions confirm with `useConfirmDialog({ destructive: true })`, never `window.confirm`. The title asks about
the record by name ("Delete Spring Gala?"), the description says what else is affected ("Its tickets and attendees are
deleted too"), and the confirm button names the verb and the object ("Delete event").

### Feedback and errors

- A successful action is a toast with a title and, when useful, the record's name as the description.
- A failed action is a toast built with `errorToToast(e)`, or `useErrorToast()` when you want a ready-made function.
  They read the server's message from the usual places and fall back to a translated generic message.
- Page-level problems that block the page (not found, forbidden) use `UEmpty`, not a toast.
- `useAction()` wraps the common "busy, try, toast on error" block; do not hand-write it again.

### Deep links instead of state hand-offs

A page that needs context from another page reads it from the URL or opens the right form directly. "Add ticket type"
on an event opens the form with the event preselected; a ⌘K entry links to `?application=<id>`. Do not pass state
through stores or `history.state`.

## Text

- Every string goes through `useModuleT('<namespace>')` with an English fallback, and the module ships `da` and `en`
  JSON (see [Module Kit](/modules/module-kit#translations-i18n)). Shared strings (Open, Edit, Delete, "Not set") come
  from `@frigear-nu/ui`'s `patterns.*` keys; see [overriding them](/modules/ui#the-patterns-strings).
- Buttons and menu items name the object: "Add unit", "Delete application", "Revoke token". Never bare "Add",
  "Delete" or "Save" unless the context is a section that is clearly about one thing.
- Format dates and money through `useFormat()` so they follow the active locale; do not call `toLocaleString` or
  `Intl` directly.
- Build links with `useLocaleLink().localize` so a visitor on `/da/...` stays under their locale.

## Checklist for a new page

1. Pick the area (admin, account or public) and register the route; add one item to the matching [menu](/modules/menu).
2. Use the heading for the area: `PageHeading` in app areas (every app page renders its own, account pages through
   `AccountHeader`), `UPageHeader` on public pages.
3. Lists are `TableCard` plus `UTable`, with a `RowMenu` and a `UEmpty`; details are `SectionCard`s with a breadcrumb.
4. Writes go through a `use<Entity>Actions()` composable and a `FormSlideover`; destructive ones confirm.
5. Strings go through `useModuleT` with `da` and `en` JSON; buttons name the object.
6. Check it in light and dark, at desktop width and at 375px.

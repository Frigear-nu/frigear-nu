The starter uses [NuxtHub](https://hub.nuxt.com/docs/database)'s database with Drizzle. Locally it is a SQLite (libsql)
file in `apps/web/.data/db/sqlite.db`, set in `nuxt.config.ts`:

```ts [apps/web/nuxt.config.ts]
export default defineNuxtConfig({
  hub: {
    db: {
      dialect: 'sqlite',
      driver: 'libsql',
      connection: { url: 'file:./.data/db/sqlite.db' },
    },
  },
})
```

NuxtHub applies the committed migrations in `apps/web/server/db/migrations` when you run `nuxt dev` and `nuxt build`.
To start over locally, delete `apps/web/.data`.

## Migrations

Modules register their tables, but that only changes the generated Drizzle schema, not the database. Generate and
commit a migration whenever a module adds or changes columns: after you add a module, upgrade one, or extend a table
yourself.

```bash
pnpm db:generate   # generate migration files from schema changes
pnpm db:migrate    # apply migrations to the development database
```

`pnpm db:generate` prints `No schema changes, nothing to migrate` when the database is already up to date. Commit the
generated SQL, the Drizzle snapshot and the journal together: they are versioned schema history, not build artifacts.

## Add columns to a module's table

A host app extends a table it does not own from its own `server/db/extend.<dialect>.ts`. Export one table or columns
object per table, under the table's name:

```ts [apps/web/server/db/extend.sqlite.ts]
import { text } from 'drizzle-orm/sqlite-core'

export const users = { locale: text().default('da') }
export const posts = { summary: text() }
```

Only the export that matches the table being built is used. The file is merged after every module. Then run
`pnpm db:generate` and commit the migration. Details are in [Database extensions](/guide/concepts/database-extensions)
and, for module authors, [Module Kit](/modules/platform/module-kit).

## SQLite and PostgreSQL

Every module ships its schema for both dialects, so you can run SQLite or libSQL/Turso locally and Cloudflare D1,
libSQL/Turso or Postgres in production. The committed migrations are per dialect: the starter keeps them in
`server/db/migrations/sqlite`. If you change `hub.db.dialect`, generate and commit migrations for the new dialect.

If you extend a table, keep a `.postgresql.ts` twin next to each `.sqlite.ts` file with the same table, column and index
names, and change both in the same commit. In the Postgres twin, use `pgTable` from `drizzle-orm/pg-core` and the
matching types, for example `serial().primaryKey()` for `integer().primaryKey({ autoIncrement: true })`,
`timestamp({ withTimezone: true })` for `integer({ mode: 'timestamp' })` and `jsonb()` for `text({ mode: 'json' })`.
Write runtime queries with Drizzle so they work on both: avoid `db.run`, `db.batch`, `PRAGMA` and other SQLite-only SQL.

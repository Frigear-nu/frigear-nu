**What you'll have afterwards:**

- Every `@frigear-nu/*` package of your workspace on the same, current release.
- The code changes of the breaking releases in between, made or listed with where to make them.
- A database migration for the schema changes.

Frigear packages are still below 1.0, so a minor release can break things. Upgrade them together, not one at a time:
they share build-time state and their releases are tested against each other.

## Prerequisites

A pnpm workspace with a Frigear app, as [Installation](/get-started/installation) creates, and a clean `git status`, so
you can review the upgrade as one diff.

## Run the upgrade

From anywhere in the workspace:

```bash
pnpx @frigear-nu/cli@latest upgrade --dry-run
```

The dry run prints the report and changes nothing. When the version table looks right, run it for real:

```bash
pnpx @frigear-nu/cli@latest upgrade
```

The command:

1. moves every `@frigear-nu/*` pin to the `latest` release: package.json files and the `catalog`, `overrides` and
   `minimumReleaseAgeExclude` entries of `pnpm-workspace.yaml`, keeping each range's operator;
2. rewrites code where a change is mechanical, such as a route that moved;
3. writes `frigear-upgrade.md` at the workspace root, a checklist of everything else;
4. runs `pnpm install`.

The install usually fails until you have worked through the report: `nuxt prepare` throws on the options the new
releases removed (such as `admin.settings.roles`). The command then warns, names the report and exits with an error;
run `pnpm install` again once the to-do items are done.

Pass package names to upgrade only some packages (`upgrade auth users`), or `--to auth@0.6.1` to stop at a version. All
the options are in the [CLI reference](/contribute/tooling/cli#upgrade).

## Work through the report

Each section of the report is one breaking change, with its package, the release that made it and a docs link. A line
with a file and line number is code to change; a line without one is a step for the whole app.

Most of the work since 0.4 is the move to permissions: checks become `authorize(event, permission, record?)`, roles
grant permissions, and hooks become `authorization:before` or policies. [Migrate to the permission model](/guide/going-further/migrate-access-control)
is the full mapping. Choosing the permission names is yours: the command lists each place, but never guesses.

Then:

```bash
pnpm db:generate   # in every app with a database; commit the migration
pnpm lint && pnpm typecheck && pnpm test && pnpm build
```

Delete `frigear-upgrade.md` once every box is ticked, or keep it in the pull request description.

## Breaking changes by release

What the command handles for each release. **Rewritten** means it changes the code; **listed** means it shows you where.

| Release | Change | The command |
| --- | --- | --- |
| auth 0.1.4 | `/api/auth/tokens` → `/api/auth/me/tokens`, `/api/auth/webauthn/credentials` → `/api/auth/me/passkeys`, `/api/_bootstrap` → `/api/auth/bootstrap`, logout is `POST /api/auth/logout` | Rewritten; logout links listed (they must `POST`) |
| users 1.1.4 | `PATCH /api/users/me`, `PUT /api/users/me/email`, `PUT /api/users/me/password` replace the `POST` routes | Rewritten; check the HTTP method |
| admin 0.1.3, account 0.1.3 | `Admin*` components and `AccountHeaderRight` removed | Listed |
| auth 0.4.0 | Sessions are sealed with `NUXT_APP_SECRET`; every user signs in again once; `users.sessionVersion` is new | Adds `NUXT_APP_SECRET` with a development placeholder to `.env.example`, above `NUXT_SESSION_PASSWORD`; set a real one everywhere before you deploy |
| menu 0.3.0, mcp 0.4.0 | Items and MCP definitions take `permission` | Listed |
| admin 0.4.0, account 0.5.0 | `admin.settings.roles`, `documents[].roles` → `permission` (build error) | Listed from `nuxt.config` |
| auth 0.5.0 | Scopes, staff guards and `requireUser(event, { scopes })` removed; `authentication.scopes` ignored; tokens must be minted again | Listed |
| auth 0.5.0 | An admin allowlist (`effectiveRole`, `NUXT_ACL_ADMINS`, a session mapper that sets `role`) grants nothing: use an `authorization:roles` listener | Listed, including the session mapper |
| auth 0.5.0 | `users.role` is copied once into `authorization_user_roles` and never read again: comparisons, role helpers and writes to it are stale | Listed with file and line; assign with `setAuthUserRoles` |
| auth 0.5.0 | Roles add up: with `defaultRoles: ['user']` every user also holds `user` | Listed when the app checks several roles |
| authorization 0.5.0 | Abilities, `bouncer`, `rbac` and the old role options removed; `<Can ability>` gone | Listed, including `nuxt.config` options |
| users 3.0.0 | `users:admin:*` hooks and helpers removed; listing users needs `users:list`; roles move to `authorization_user_roles` | Listed; verify the data with the SQL in the migration guide |
| auth 0.6.0 | `defineAccess`, `registerAccess` and the typed `Permission` | Nothing to do: `addPermission` still works |

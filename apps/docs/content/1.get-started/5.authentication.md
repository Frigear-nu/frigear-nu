**What you'll have afterwards:**

- The sign-in methods you want, such as password, emailed link or passkeys.
- Server routes that only a [signed-in user](/guide/concepts/glossary) can call.
- Pages that a [visitor](/guide/concepts/glossary) is sent away from, to the sign-in page.

[Auth](/modules/identity/auth) lets people sign in and tells every server route who is calling.
[Users](/modules/identity/users) installs Auth for you and stores the users.

## Prerequisites

A project created in [Installation](/get-started/installation#_1-create-the-project).

::warning
The config key of Auth is `authentication`, not `auth`. The `auth` key belongs to nuxt-auth-utils.
::

## 1. Choose the sign-in methods

Turn methods on under `authentication.settings` in `nuxt.config.ts`:

| Method | Option | Default |
| --- | --- | --- |
| Email and password | `password` | `true` (`passwordReset` follows it) |
| Magic link (emailed, single use) | `magicLink` | off |
| Passkeys | `webAuthn` | `false` (the starters set `true`) |
| [OAuth providers](/guide/concepts/glossary) (GitHub, Google, any OpenID Connect server, ...) | credentials in environment variables | off until configured |

```ts [apps/web/nuxt.config.ts]
export default defineNuxtConfig({
  authentication: {
    settings: {
      afterLogin: '/account',
      pages: { login: true, register: true },
      magicLink: true,
    },
  },
})
```

- `pages.login` and `pages.register` add the `/login` and `/register` pages.
- `afterLogin` is where users land after signing in, unless a `?redirect=` was requested.
- Passkeys need `@simplewebauthn/server` and `@simplewebauthn/browser` installed in the app. Users add a passkey on
  `/account/security`, and the sign-in page then shows a passkey button.
- An OAuth provider turns on once its nuxt-auth-utils credentials exist, for example `NUXT_OAUTH_OIDC_CLIENT_ID`.
  Without credentials its route answers `404`.
- Register `<origin>/api/auth/<provider>` as the callback URL at the OAuth provider.

::warning
Magic links and password resets are emailed. Configure a [Notify](/modules/platform/notify) driver before you rely on
them. Until then the `log` driver prints them in the terminal.
::

The full list of options is on the [Auth](/modules/identity/auth) page.

## 2. Protect a server route

`authorize` checks that a request comes from a signed-in user who may do one thing, a
[permission](/guide/concepts/glossary) such as `tickets:read`, and returns who it is. It is auto-imported in server
code. Use it instead of nuxt-auth-utils' `requireUserSession`.

```ts [server/api/tickets.get.ts]
export default defineEventHandler(async (event) => {
  const { user } = await authorize(event, 'tickets:read')
  return getTickets(user.id)
})
```

::note
A request can prove who it is with a cookie session, an [API token](/guide/concepts/glossary) or an
[access token](/guide/concepts/glossary). Auth turns all three into one answer, the
[principal](/guide/concepts/auth-and-scopes#the-principal). What a session may do comes from the user's roles. A token
holds only the permissions it was given, within its user's.
::

| Call | Behaviour |
| --- | --- |
| `authorize(event, permission)` | The principal, when it holds the permission. `401` without a valid credential, `403 insufficient_scope` for a token without it, `403 forbidden` for a user without it. |
| `authorize(event, permission, record)` | Also runs the [policies](/modules/identity/authorization/policies) of the permission against the record. |
| `allows(event, permission, record?)` | The same decision as a boolean. Never throws. |
| `requireAuth(event)` | The principal from any credential, for routes every signed-in user may call. `401` without a valid one. |
| `requireAuth(event, { sessionOnly: true })` | Cookie sessions only. `403 session_required` for tokens. |
| `getAuth(event)` | The principal or `null`. Never throws. |

When you only need the user, `requireUser(event, options)` from [Users](/modules/identity/users) returns just the user.

::caution
Anything that changes who the user is or how they sign in (password, email, passkeys, API tokens), moves money or mints
credentials is a `sessionOnly` permission: `authorize` answers `403 session_required` to a token. A leaked token must
not be able to do that. [sessionOnly](/guide/concepts/auth-and-scopes#sessiononly) explains the rule.
::

A permission has to be registered (modules do it for theirs with `addPermission`). An unregistered name is a `403` for
everyone.

## 3. Protect a page

[Authorization](/modules/identity/authorization) decides who may open a page. The starter installs it. Add a rule to
`routeRules` in `nuxt.config.ts`:

```ts [apps/web/nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    '/members/**': { authenticated: true },
    '/admin/**': { permission: 'admin:access', ssr: false },
  },
})
```

A visitor is sent to `authorization.redirectTo`, which is `/login` in the starter. The requested page goes in
`?redirect=`, and the visitor comes back after signing in. A user without the permission gets `403`.

For one page, use `definePageMeta`. Its rule replaces the matching route rules:

```vue
<script setup lang="ts">
definePageMeta({ authorize: 'events:manage' }) // a registered permission
</script>
```

Rules for `/api/**` are enforced too. So `'/api/admin/**': { permission: 'admin:access' }` guards the
[staff](/guide/concepts/glossary) API of every module.

::callout{color="success" icon="i-lucide-check"}
**What you should see:** a signed-out visit to a guarded page lands on `/login?redirect=…`. After signing in, you are
back on the page.
::

## 4. Roles and the first admin

A user holds [roles](/modules/identity/authorization/roles-and-requirements), and a role is a bundle of permissions.
Define them in `authorization.roles`; every signed-in user holds the `defaultRoles`:

```ts [apps/web/nuxt.config.ts]
export default defineNuxtConfig({
  authorization: {
    defaultRoles: ['user'],
    roles: {
      admin: { label: 'Admin', grant: ['*'] }, // '*' covers every permission except sensitive (:pii) ones
      user: { label: 'User' }, // self-service permissions are implicit: every user holds them anyway
    },
  },
})
```

Admins assign roles on the user's page in the admin. The very first admin comes from the environment:
`server/plugins/authorization-roles.ts` adds `admin` to every user whose email is in `NUXT_ACL_ADMINS`, its access
control list (ACL), in the `authorization:roles` hook. Only once the address is verified (`emailVerifiedAt`): otherwise
anyone could sign up with an address on the list and become admin. The starter turns on `verifyEmail`, so the first
admin verifies through the emailed link.

```ts [apps/web/server/plugins/authorization-roles.ts]
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('authorization:roles', (ctx) => {
    const admins = (process.env.NUXT_ACL_ADMINS ?? '').split(',').map(email => email.trim().toLowerCase())
    if (ctx.user.emailVerifiedAt && admins.includes(ctx.user.email.toLowerCase()) && !ctx.roles.includes('admin')) {
      ctx.roles.push('admin')
    }
  })
})
```

The role is not stored: removing the address removes the access at once. Check what a signed-in user may do with
`GET /api/auth/me/access`.

## `@frigear-nu/base`

The `@frigear-nu/base` package provides a reusable [Nuxt layer](https://nuxt.com/docs/4.x/getting-started/layers) for Frigear websites. It centralizes common module wiring,
styling, UI defaults, and content-driven page conventions so applications can avoid duplicating the same setup.

## Installation

In a workspace app, add the package as a dependency and extend it from the app's `nuxt.config.ts`:

```ts
export default defineNuxtConfig({
  extends: ['@frigear-nu/base'],
})
```

## Content collections

Collections are defined in `content.config.ts` and are relative to the consuming app's `content/` directory:

- `config` — a `data` collection sourced from `content/config.yaml`, containing site-wide configuration such as
  name, logo, navigation, and footer. Validated against `WebsiteConfigSchema` (see below).
- `pages` — a `page` collection sourced from Markdown files under `content/pages/**`. Validated against
  `WebsitePageSchema` (see below).

### Localized vs. non-localized collections

Whether `config`/`pages` or their locale-suffixed equivalents are defined depends entirely on whether the
consuming app's `nuxt.config.ts` has `@nuxtjs/i18n` configured with `locales`:

- **No `i18n.locales` configured (default):** `content.config.ts` defines exactly one `config` collection and one
  `pages` collection, sourced from the flat `content/config.yaml` and `content/pages/**`. This is the behavior for
  apps that don't opt into i18n.
- **`i18n.locales` configured (e.g. `['en', 'no']`):** instead of the flat collections, `content.config.ts` defines
  one locale-suffixed pair per configured locale — `config_en`/`pages_en`, `config_no`/`pages_no`, and so on — built
  with `localizedCollectionName(name, locale)`. Each locale's collection sources content from that locale's folder,
  e.g. `content/en/config.yaml` and `content/en/pages/**`. The flat (non-suffixed) `config`/`pages` collections are
  **not** defined in this case.

This switch happens once, at build time, based on the `i18n` module options read from the Nuxt instance — it isn't
possible to mix flat and locale-suffixed collections in the same app. `useConfig()` and `useCurrentPage()` resolve
which collection (flat or locale-suffixed) to query automatically via `useContentLocale()`, so app code doesn't need
to branch on whether locales are configured.

For example, an app using `@nuxtjs/i18n` can opt into localized collections by configuring locales in
`nuxt.config.ts`:

```ts
export default defineNuxtConfig({
  extends: ['@frigear-nu/base'],
  i18n: {
    locales: [
      { code: 'da', name: 'Danish' },
      { code: 'en', name: 'English' },
    ],
    defaultLocale: 'en',
  },
})
```

With the config above, `content.config.ts` defines `config_da`/`pages_da` and `config_en`/`pages_en`, sourced from
`content/da/**` and `content/en/**` respectively.

### `config` schema (`WebsiteConfigSchema`)

All fields are optional, so an app can start with an empty `content/config.yaml` and add fields incrementally.

| Field | Type | Description |
| --- | --- | --- |
| `name` | `string \| { long: string, short?: string }` | Site name. Either a plain string, or an object with a `long` form and an optional `short` form. |
| `logo` | `string \| { light: string, dark: string, class?: string, alt?: string }` | Logo image(s). Either a single image path, or an object with separate `light`/`dark` images plus optional `class` and `alt`. |
| `navigation` | `Array<{ label: string, description?: string, to: string, icon?: string, tags?: string[] }>` | Navigation entries. `tags` is used by `useNavigation(tags?)` to filter entries (e.g. a `footer` tag). |
| `footer` | `{ sections?: FooterSection[], copyright?: string, right?: FooterLink[] }` | Footer content (see below). |

Footer `sections` entries:

| Field | Type | Description |
| --- | --- | --- |
| `label` | `string` | Section heading. |
| `icon` | `string` (optional) | Section icon. |
| `links` | `Array<{ label: string, to: string, icon?: string }>` | Links listed under the section. |

Footer `right` entries (e.g. legal/secondary links rendered on the right side of the footer):

| Field | Type | Description |
| --- | --- | --- |
| `label` | `string` | Link text. |
| `to` | `string` | Link target. |
| `icon` | `string` (optional) | Link icon. |
| `variant` | `'link' \| 'solid' \| 'outline' \| 'soft' \| 'subtle' \| 'ghost'` (optional) | Button variant used to render the link. |
| `size` | `'xs' \| 'sm' \| 'md' \| 'lg' \| 'xl'` (optional) | Button size used to render the link. |

### `pages` schema (`WebsitePageSchema`)

All fields are optional.

| Field | Type | Description |
| --- | --- | --- |
| `title` | `string` (optional) | Page title, e.g. used for the document `<title>`. |
| `description` | `string` (optional) | Page description, e.g. used for meta tags. |
| `pageHeader` | `{ title?: string, description?: string }` (optional) | Overrides for the page header component, falling back to `title`/`description` when omitted. |

Use `useConfig()`, `useCurrentPage()`, and `useContentLocale()` to access configuration, the current page, and the
current content locale. The layer also provides helpers for working with content and localized collections.

## Composables

These composables are auto-imported in apps that extend the layer.

### `useConfig()`

Returns the site-wide `config` document (or its locale-suffixed equivalent), wrapped in `useAsyncData`.

```ts
const { data: config } = useConfig()
```

The returned `useAsyncData` key and query are re-evaluated whenever the active content locale changes.

### `useContentLocale()`

Resolves the active content locale from `@nuxtjs/i18n` (when configured) and exposes helpers for working with
locale-prefixed routes.

```ts
const { locale, defaultLocale, stripLocalePrefix, localizePath } = useContentLocale()
```

| Property | Type | Description |
| --- | --- | --- |
| `locale` | `ComputedRef<string \| undefined>` | The current locale, limited to the app's configured locale codes; `undefined` when locales aren't configured or the detected locale isn't one of them. |
| `defaultLocale` | `ComputedRef<string \| undefined>` | The app's default locale, as reported by `$i18n`. |
| `stripLocalePrefix` | `(path: string) => string` | Removes the current locale's route prefix from `path` (e.g. `/en/services` → `/services`). |
| `localizePath` | `(path: string, targetLocale: string) => string` | Builds the equivalent of `path` for `targetLocale`, without relying on `@nuxtjs/i18n`'s `switchLocalePath` (which can't resolve the layer's landing/catch-all routes). |

### `useCurrentPage()`

Returns the `pages` collection document (or its locale-suffixed equivalent) matching the current route.

```ts
const { data: page } = useCurrentPage()
```

### `useNavigation(tags?)`

Returns the navigation entries from `useConfig()`, optionally filtered by tag.

```ts
const { data: navigation } = useNavigation()
const { data: footerNavigation } = useNavigation(['footer'])
```

| Parameter | Type | Description |
| --- | --- | --- |
| `tags` | `string[]` (optional) | When provided, only entries whose `tags` include at least one of the given values are returned. Omit to return every navigation entry. |

## Utils

The content utilities below are defined in `app/utils.ts` and, like the composables, are auto-imported in apps
that extend the layer. `landingPageExists` lives outside `app/` and is a build-time helper used internally by the
layer's `routing` module rather than something consuming apps call directly.

### `localizedCollectionName(name, locale?)`

Builds the locale-suffixed collection name used by `content.config.ts` (e.g. `'pages'` + `'no'` → `'pages_no'`).
Returns `name` unchanged when `locale` is omitted.

### `stringOrPropValue(prop, key)`

Resolves a value that may be provided either as a plain string or as an object: returns `prop` itself when it's a
string, or `prop[key]` otherwise.

### `getAvailableLocales(config)`

Extracts the list of locale codes from an `i18n.locales` config, normalizing entries that are either plain strings
or `{ code }` objects.

### `getCollectionsToQuery(locale, availableLocales)`

Returns the `pages` collection name(s) to query: the collection for the given `locale` when it's one of
`availableLocales`, every configured locale's collection when `locale` doesn't match, or the flat `'pages'`
collection when no locales are configured.

### `getCollectionFromPath(path, availableLocales)`

Infers the `pages` collection for a route `path` by checking whether its first path segment matches one of
`availableLocales`.

### `landingPageExists(rootDir)`

Build-time helper used by the layer's routing module. Checks whether the consuming app defines its own
`app/pages/index.vue`; when it does, the layer leaves the index route to the app instead of taking it over.

The [local development guide](/getting-started/local-development) explains how to run the consuming website.

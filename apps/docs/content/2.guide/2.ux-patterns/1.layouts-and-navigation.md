Every module that ships screens follows the same handful of patterns, so the app feels like one product no matter which
modules are installed. The building blocks live in [`@frigear-nu/ui`](/modules/interface/ui); the admin shell is
[`@frigear-nu/admin`](/modules/interface/admin) and the account settings layout is [`@frigear-nu/account`](/modules/identity/account). These pages are
the rulebook: read them before adding a screen, and follow them when reviewing one. This page covers layouts; the others cover
[pages](/guide/ux-patterns/pages), [forms and actions](/guide/ux-patterns/forms-and-actions) and [text and formatting](/guide/ux-patterns/text-and-formatting).

::note
These are patterns, plus a light theme for the admin area: the shell sets the chrome tones (page, sidebar and navbar
backgrounds, a primary-coloured brand tile). Colours, fonts and radius still come from Nuxt UI and your app's
`app.config.ts`; the shared components only add structure and spacing.
::

There are three areas, each with its own layout. A page picks its area by path, not by importing a layout.

| Area | Paths | Layout | What it is |
| --- | --- | --- | --- |
| Public site | everything else | `default` from the [base layer](/modules/platform/base-layer) | Header and footer. Public pages use `UContainer > UPage`. |
| Admin back office | `/admin/**` | `admin` ([Admin](/modules/interface/admin)) | Dashboard shell: a collapsible sidebar with grouped navigation, a ⌘K palette and the account menu in the sidebar footer. |
| Account area | `/account/**` | `account` ([Account](/modules/identity/account)) | The site's `default` layout (header and footer) with a centred settings grid, a left section list and `PageSectionSwitcher` on narrow screens. |

The admin layout is a thin layout around `AppShell`. Pages in both app areas render their own `PageHeading`; the layouts
draw no heading.

### Admin back office

The sidebar navigation is grouped, and each group reads its own [menu](/modules/interface/menu) path:

| Group | Menu path | Put here |
| --- | --- | --- |
| Overview | `admin.nav.overview` | The dashboard. |
| Manage | `admin.nav` (root) | The things staff manage every day: users, events, forms. |
| Settings | `admin.nav.settings` | Configuration: OAuth applications, integrations. |

New features go into one of these groups. A new group needs a reason, such as a whole new class of screens that
does not read as "managing" or "settings". The ⌘K palette lists the same groups, so a page that is in the navigation is
also searchable. Colour mode is not in the chrome: it lives in the account menu under **Appearance**.

The navbar shows a muted "Area › Section" eyebrow (for example "Administration › Users"), not a title, so the page's
`PageHeading` is the only `<h1>`. Pages that need the full width (the form builder) set `definePageMeta({ wide: true })`;
the default body is centred at `max-w-7xl`.

### Account area

`/account/**` renders in the `account` layout, a settings page inside the site: the site header and footer stay, and the
content is a centred `max-w-5xl` grid. A sticky left column shows the signed-in user (a small `UUser`) above the vertical
navigation built from the `account` menu; on narrow screens `PageSectionSwitcher` replaces it above the content. The
`AccountMenu` stays in the site header. The layout renders no heading, so every page renders its own. The signed-in
identity is shown once, in the left column; it is not repeated in headings.

Every page renders its own heading as the first child of its root: `AccountHeader` for the pages of the account package
(a `PageHeading` filled from the current menu item), and `PageHeading` with the menu item's own i18n keys for pages other
modules add, so the label and the title cannot drift. `/account` itself is an overview: a summary card (`UUser` plus
`AccountIdentity`), the `account.overview` [widget](/modules/interface/widget) area and shortcuts to the other pages. A module adds
a page by registering the route and an item in the `account` menu; it never draws its own account navigation.

### Public site

Public pages (events, forms, content) use `UContainer > UPage` with `UPageHeader` for the title and `UPageSection` for
bands. App pages, meaning everything in the admin and account areas, use `PageHeading` instead. Do not mix them: the
public header is a marketing-sized hero, `PageHeading` is a working title with actions.

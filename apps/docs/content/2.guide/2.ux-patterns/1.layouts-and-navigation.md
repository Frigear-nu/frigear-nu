When every [module](/guide/concepts/glossary) draws its screens its own way, the app stops feeling like one product. The
UX pattern pages fix that: each screen follows the same few patterns, whichever modules are installed. This page tells
you which area a new screen belongs in, which layout it gets and where its navigation entry goes.

::callout{icon="i-lucide-users"}
**For:** module authors and app developers who add a screen, and anyone who reviews one.
::

Read the four pattern pages before you add a screen, and follow them when you review one:

- **Layouts and navigation** (this page): the three areas and their navigation.
- [Pages](/guide/ux-patterns/pages): lists, detail pages, overviews and the loading, empty and error states.
- [Forms and actions](/guide/ux-patterns/forms-and-actions): create and edit forms, row menus and confirmations.
- [Text and formatting](/guide/ux-patterns/text-and-formatting): strings, dates, links and a checklist for a new page.

The building blocks come from three modules. [UI](/modules/interface/ui) has the shared components. The
[Admin](/modules/interface/admin) module draws the [admin area](/guide/concepts/glossary). The
[Account](/modules/identity/account) module draws the account settings pages.

::note
These are patterns, plus a light theme for the admin area. The admin shell sets the chrome tones: the page, sidebar and
navbar backgrounds, and a primary-coloured brand tile. Colours, fonts and radius still come from Nuxt UI and your app's
`app.config.ts`. The shared components add only structure and spacing.
::

## Pick the area

There are three areas, and each has its own layout. A page picks its area by its path. It never imports a layout.

| Area | Paths | Layout | What it is |
| --- | --- | --- | --- |
| Public site | Everything else | `default`, from the [base layer](/modules/platform/base-layer) | A header and a footer. Public pages use `UContainer > UPage`. |
| Admin area | `/admin/**` | `admin`, from [Admin](/modules/interface/admin) | A dashboard shell: a collapsible sidebar with grouped navigation, a ⌘K palette and the account menu in the sidebar footer. |
| Account area | `/account/**` | `account`, from [Account](/modules/identity/account) | The site's header and footer around a centred settings grid, with a section list on the left. |

The admin layout is a thin layout around the shared shell (`AppShell`). Neither app area draws a heading. Every page in
the admin and account areas renders its own heading (`PageHeading`).

## Admin area

The admin sidebar groups its navigation. Each group reads its own [menu](/modules/interface/menu) path:

| Group | Menu path | Put here |
| --- | --- | --- |
| Overview | `admin.nav.overview` | The dashboard. |
| Manage | `admin.nav` (the root) | What [staff](/guide/concepts/glossary) manage every day: users, events, forms. |
| Settings | `admin.nav.settings` | Configuration: OAuth applications, integrations. |

The Overview group has no heading in the sidebar: its items, such as **Dashboard**, sit above the **Manage** and
**Settings** headings. In the ⌘K palette the group is called "Go to".

![The admin dashboard: the sidebar shows Dashboard above the Manage and Settings groups, the navbar shows the area and section, and the account menu sits in the sidebar footer.](/images/ux-patterns/layouts-and-navigation-admin.png)

::tip
Put a new feature in one of these groups. A new group needs a reason, such as a whole new class of screens that reads
as neither "managing" nor "settings".
::

- **Search.** The ⌘K palette lists the same groups. So a page that is in the navigation is also searchable.
- **Account menu.** It sits in the sidebar footer as one button: your avatar and name, which opens a dropdown menu.
  When the sidebar is collapsed, the button shrinks to the avatar.
- **Colour mode.** It is not in the chrome. It lives in the account menu, under **Appearance**.
- **Navbar.** The navbar shows a muted "Area › Section" eyebrow, such as "Administration › Users". It is not a
  title, so the page's own heading is the only `<h1>`.
- **Width.** The page body is centred at `max-w-7xl` by default. A page that needs the full width, such as the form
  builder, sets `definePageMeta({ wide: true })`.

## Account area

The account area is a settings page inside the site. Pages under `/account/**` render in the `account` layout.

![The account area inside the site header and footer, with the section list on the left: Overview, Profile, Membership, Security and more.](/images/ux-patterns/layouts-and-navigation-account.png)

- **Chrome.** The site header and footer stay. The account menu (`AccountMenu`) stays in the site header.
- **Grid.** The content is a centred `max-w-5xl` grid.
- **Left column.** A sticky column shows the signed-in user (a small `UUser`). Below it is the vertical navigation,
  built from the `account` menu.
- **Narrow screens.** A section switcher (`PageSectionSwitcher`) replaces the left column, above the content.
- **Identity.** The signed-in user is shown once, in the left column. Headings do not repeat it.

The layout renders no heading, so every page renders its own as the first child of its root:

- Pages of the Account module use `AccountHeader`, a `PageHeading` filled from the current menu item.
- Pages that other modules add use `PageHeading` with the menu item's own i18n keys. The label and the title then
  cannot drift apart.

`/account` itself is an overview. It shows a summary card (`UUser` plus `AccountIdentity`), the `account.overview`
[widget area](/guide/concepts/glossary) and shortcuts to the other pages.

A module adds a page by registering the route and an item in the `account` menu. It never draws its own account
navigation.

## Public site

Public pages, such as events, forms and content, are a different kind of page from app pages.

![A public events page between the site header and the site footer.](/images/ux-patterns/layouts-and-navigation-public.png)

| Page | Container | Title |
| --- | --- | --- |
| Public | `UContainer > UPage`, with `UPageSection` for bands | `UPageHeader` |
| App (admin and account areas) | A plain `<div class="flex flex-col gap-4">` | `PageHeading` |

Do not mix them. The public header is a marketing-sized hero. `PageHeading` is a working title with actions.

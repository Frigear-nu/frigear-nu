Writes follow one path: a button opens a form, the form resolves with the saved record, and an actions composable owns the toasts and the refresh. Screens that show the results are in [Pages](/guide/ux-patterns/pages).


## Create and edit

- Create and edit forms open in a `FormSlideover` containing a `UForm` with a zod schema. Short yes/no choices are a
  modal (`UModal`). Never inline a create form next to a table.
- Open forms through `useOverlay()`; the overlay resolves with the saved record (or `false` when cancelled), so the
  caller can navigate to it.
- Cancel is `color="neutral" variant="outline"` and the primary action comes last. `FormSlideover` does this for you.
- Hints belong in `UFormField`'s `description`, not in extra paragraphs.
- Slideover forms stay vertical (plain `UFormField`). Inline settings forms in a `SectionCard` use `FormRow` rows (see
  [Detail pages](/guide/ux-patterns/pages#detail-pages)).

```vue
<!-- EventFormSlideover.vue -->
<script setup lang="ts">
const props = defineProps<{ event?: EventRow }>()
const emit = defineEmits<{ close: [saved: EventRow | false] }>()

const t = useModuleT('events')
const { busy, run } = useAction()
const state = reactive({ title: props.event?.title ?? '' })

const save = () => run(async () => {
  const saved = await $fetch<EventRow>(props.event ? `/api/admin/events/${props.event.id}` : '/api/admin/events', {
    method: props.event ? 'PATCH' : 'POST',
    body: state,
  })
  emit('close', saved)
}, { success: t('admin.saved', 'Event saved') })
</script>

<template>
  <FormSlideover
    form-id="event-form"
    :title="event ? t('admin.edit', 'Edit event') : t('admin.create', 'New event')"
    :submit-label="event ? t('admin.save', 'Save event') : t('admin.create', 'New event')"
    :loading="busy"
    @close="emit('close', false)"
  >
    <UForm id="event-form" :state="state" class="flex flex-col gap-4" @submit="save">
      <UFormField name="title" :label="t('admin.title', 'Title')" :description="t('admin.titleHint', 'Shown on the public page.')">
        <UInput v-model="state.title" />
      </UFormField>
    </UForm>
  </FormSlideover>
</template>
```

## Create button

The primary create button has `icon="i-lucide-plus"` and a label that names the object ("New event", "Add user"). The
page only calls `actions.create()`. The composable opens the `FormSlideover`, navigates to the detail page when the
entity has one, and returns the record, or `false` when cancelled; the page never navigates itself.

## One actions composable per entity

Every entity has a `use<Entity>Actions()` composable (`useUserActions`, `useEventActions`, `useFormActions`) that
owns create, edit and remove, the toasts and the refresh afterwards. It returns `menu(record)` for the row menu, so
every list and detail page offers the same actions in the same order. Pages stay thin. It lives in the module that owns
the entity, not in `@frigear-nu/ui`. Sub-entities that have no page of their own (an event's ticket types and add-ons)
get the same treatment in a composable of their own, whose menus skip Open: see `useEventCatalogActions`.

```ts
// composables/useEventActions.ts
export function useEventActions() {
  const t = useModuleT('events')
  const overlay = useOverlay()
  const confirm = useConfirmDialog()
  const toast = useToast()
  const { localize } = useLocaleLink()

  async function create() {
    const saved = await overlay.create(EventFormSlideover).open()
    if (saved) await navigateTo(localize(`/admin/events/${saved.id}`))
  }

  async function remove(event: EventRow) {
    const confirmed = await confirm({
      title: t('admin.deleteTitle', 'Delete {name}?', { name: event.title }),
      description: t('admin.deleteBody', 'Its tickets and attendees are deleted too. This cannot be undone.'),
      confirmText: t('admin.delete', 'Delete event'),
      destructive: true,
    })
    if (!confirmed) return
    try {
      await $fetch(`/api/admin/events/${event.id}`, { method: 'DELETE' })
      toast.add({ title: t('admin.deleted', 'Event deleted'), description: event.title })
      await refreshNuxtData('events')
    }
    catch (e) {
      toast.add(errorToToast(e))
    }
  }

  const menu = (event: EventRow) => [
    [{ label: t('open', 'Open'), icon: 'i-lucide-arrow-right', to: localize(`/admin/events/${event.id}`) }],
    [{ label: t('admin.edit', 'Edit event'), icon: 'i-lucide-pencil', onSelect: () => overlay.create(EventFormSlideover).open({ event }) }],
    [{ label: t('admin.delete', 'Delete event'), icon: 'i-lucide-trash-2', color: 'error' as const, onSelect: () => remove(event) }],
  ]

  return { create, remove, menu }
}
```

## Row actions

Row actions go in a `RowMenu` (the `⋯` button) at the end of the row, with groups in this order: **Open** (and "View
public page") first, then the edits and extras, then the destructive action in its own group, coloured red. Icons:
Open `arrow-right`, Edit `pencil`, Duplicate `copy`, Archive `archive`, Delete `trash-2`. Detail pages build the menu with
`open: false` (they are already there), and sub-entities skip Open. There are no loose icon buttons in rows. Pass
`subject` so the button's accessible name reads "Actions for Ada Lovelace".

## Destructive actions

Destructive actions confirm with `useConfirmDialog({ destructive: true })`, never `window.confirm`. The title asks about
the record by name ("Delete Spring Gala?"), the description says what else is affected ("Its tickets and attendees are
deleted too"), and the confirm button names the verb and the object ("Delete event").

## Feedback and errors

- A successful action is a toast with a title and, when useful, the record's name as the description.
- A failed action is a toast built with `errorToToast(e)`, or `useErrorToast()` when you want a ready-made function.
  They read the server's message from the usual places and fall back to a translated generic message.
- Page-level problems that block the page (not found, forbidden) use `UEmpty`, not a toast.
- `useAction()` wraps the common "busy, try, toast on error" block; do not hand-write it again.

## Deep links instead of state hand-offs

A page that needs context from another page reads it from the URL or opens the right form directly. "Add ticket type"
on an event opens the form with the event preselected; a ⌘K entry links to `?application=<id>`. Do not pass state
through stores or `history.state`.

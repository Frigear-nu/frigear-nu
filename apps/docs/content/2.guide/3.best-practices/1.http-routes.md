A client that has called one module's API should be able to guess the next one: its URLs, its errors and the shape of
its responses. That client may be your app, an AI agent over the Model Context Protocol (MCP) or a test. This page
lists the conventions every module API follows, and the helpers that implement them.

::callout{icon="i-lucide-users"}
**For:** module authors. App developers who add API routes to a [host app](/guide/concepts/glossary) can follow the
same conventions; only [Registering routes](#registering-routes) is module-specific.
::

The helpers are the server toolkit of [Module Kit](/modules/platform/module-kit), `@frigear-nu/module-kit/server`.

::note
Import the toolkit explicitly. It is not auto-imported, so nothing clashes with h3's own helpers.
::

## URLs

- **Module prefix.** Everything lives under `/api/<module>`.
- **[Staff](/guide/concepts/glossary) routes.** They live under `/api/admin/<module>/...`, with admin first, like
  the `/admin/<module>` pages. So a host app can guard all of them with one `routeRules['/api/admin/**']`.
- **The main resource.** It is the module path itself: `GET /api/admin/events` lists events, and
  `GET /api/admin/events/:id` reads one.
- **The caller's own things.** Anything that is implicitly the caller's lives under `/api/<module>/me/...`.
- **Ids and collections.** Ids are path params, and collections are plural.
- **Actions.** An action that is not create, read, update or delete (CRUD) is `POST /<resource>/:id/<verb>`.
- **Methods.** A partial update is `PATCH`, and replacing a value is `PUT`. A state change is never `GET`.
- **Exceptions.** Spec endpoints (`/.well-known/*`, `/oauth/*`), webhooks and OAuth callbacks registered at a provider
  keep the paths they need.
- **One place for paths.** Keep the paths as typed builders in `src/runtime/utils/api.ts`. The app, tests and docs
  use them. See [Naming](#naming).

## Registering routes

A module registers every route from one table in `module.ts`, with `addModuleRoutes` from
`@frigear-nu/module-kit/utils`.

| Field | Meaning |
| --- | --- |
| `method` | The HTTP method, in lower case. |
| `path` | Joined onto `base`. `''` is `base` itself, and a path that starts with `/` ignores `base`. |
| `file` | The handler, relative to `./runtime/server/routes/`. |
| `base` (in the third argument) | Required. The prefix for every `path` in the table. |

```ts
import { addModuleRoutes } from '@frigear-nu/module-kit/utils'

addModuleRoutes(resolver, [
  { method: 'get', path: '', file: 'admin/events.get' },
  { method: 'post', path: '', file: 'admin/events.post' },
  { method: 'get', path: ':id', file: 'admin/event.get' },
  { method: 'patch', path: ':id', file: 'admin/event.patch' },
  { method: 'post', path: ':id/clone', file: 'admin/event-clone.post' },
  { method: 'get', path: '/api/events/me/tickets', file: 'me/tickets.get' },
], { base: '/api/admin/events' })
```

## Handler order

Every handler does its work in the same order:

1. **Authenticate and authorize**, with `requireAuth` or the module's staff guard.
2. **Parse the path params**, then the body or query. Use h3's validated helpers with zod:
   `getValidatedRouterParams(event, idParams().parse)`, `readValidatedBody(event, schema.parse)` and
   `getValidatedQuery(event, schema.parse)`.
3. **Load the target**, then act.

::warning
Never answer 404 before 401 or 403. A route that loads the record first tells a visitor which ids exist. See
[Common mistakes](/guide/concepts/auth-and-scopes#common-mistakes).
::

On JSON routes, use no raw `readBody`, `getQuery` or `getRouterParam(...)!`, and no wrappers around the validated
helpers.

### Step 1: who may call the route

The first line of a handler decides who may call it. What you call depends on the route:

| Route | First line | Comes from |
| --- | --- | --- |
| Any signed-in caller | `const { user } = await requireAuth(event)` | `@frigear-nu/auth` |
| The caller's own user record | `const user = await requireUser(event)` | `@frigear-nu/users` |
| Staff only (`/api/admin/...`) | `await myModuleStaff.require(event)` | Your module's own staff guard |

`requireAuth` and `requireUser` are ready to use. A staff guard is not: your module defines it once, with
`defineStaffGuard` from `@frigear-nu/auth`, in a file under `src/runtime/server/utils/`. Files there are auto-imported
into every server route, so routes call the guard without an import. `myModuleStaff` is only the name this page uses;
the Events module calls its guard `eventsStaff`, Forms `formsStaff`. [Staff access](#staff-access) explains what the
guard checks.

### Example

A staff route that renames a thing. First, the guard, defined once per module:

```ts [src/runtime/server/utils/auth.ts]
import { defineStaffGuard } from '@frigear-nu/auth'

// Auto-imported into every server route of the app, so the name carries the module prefix.
export const myModuleStaff = defineStaffGuard({
  hook: 'my-module:authorize', // the host app's policy hook decides who is staff
  scope: 'my-module:manage', // the scope an API token needs
  message: 'You are not allowed to manage things.',
})
```

Then the route, which does the steps in order:

```ts [src/runtime/server/routes/admin/thing.patch.ts]
import { db, schema } from '@nuxthub/db'
import { eq } from 'drizzle-orm'
import { idParams, notFound } from '@frigear-nu/module-kit/server'
import { z } from 'zod'

const body = z.object({ name: z.string().trim().min(1).max(120) })

export default defineEventHandler(async (event) => {
  // 1. Who may call: the module's staff guard (src/runtime/server/utils/auth.ts).
  await myModuleStaff.require(event)
  // 2. Parse the path params, then the body.
  const { id } = await getValidatedRouterParams(event, idParams().parse)
  const input = await readValidatedBody(event, body.parse)
  // 3. Load the target and act. A missing record is a 404, only after the caller passed step 1.
  const [row] = await db.update(schema.things).set(input).where(eq(schema.things.id, id)).returning()
  if (!row) throw notFound('Thing not found.')
  // toThingDto lives in src/runtime/server/utils too. See Responses.
  return toThingDto(row)
})
```

`defineEventHandler`, `getValidatedRouterParams` and `readValidatedBody` are h3's, auto-imported by Nitro. The Events
module's `admin/addon.patch.ts` is a real route built this way.

## Input

Two zod schemas validate ids the same way in every module. Both are for `getValidatedRouterParams`.

| Schema | Accepts |
| --- | --- |
| `idParams(name = 'id')` | A non-empty string. |
| `intIdParams(name = 'id')` | A positive integer, coerced from the path. |

```ts
const { id } = await getValidatedRouterParams(event, idParams().parse)
const { id: userId } = await getValidatedRouterParams(event, intIdParams().parse)
```

## Errors

Errors go through `apiError(status, code, message, data?)` and its shortcuts. Every error has the same shape:

- The message is the `statusMessage`, which the interface shows.
- `data.code` is a snake_case code a client can test for.

| Helper | Status | `data.code` |
| --- | --- | --- |
| `apiError(status, code, message, data?)` | Any | `code` |
| `badRequest(message?, data?)` | 400 | `bad_request` |
| `validationError(issues, message?)` | 400 | `validation_failed`, with the issues in `data.issues` |
| `forbidden(message?, data?)` | 403 | `forbidden` |
| `notFound(message?, data?)` | 404 | `not_found` |
| `conflict(message?, data?)` | 409 | `conflict` |
| `notConfigured(message?, data?)` | 501 | `not_configured` |

Each helper returns an h3 error for you to `throw`. `requireAuth` answers in the same shape, with the codes
`unauthorized`, `session_required` and `insufficient_scope`.

```ts
import { conflict, notFound } from '@frigear-nu/module-kit/server'

if (!form) throw notFound('Form not found.')
if (await slugTaken(body.slug)) throw conflict('That slug is taken.', { field: 'slug' })
```

### Field issues

Use this when a client needs an issue per field, such as a form that marks each input.

h3's `readValidatedBody(event, schema.parse)` answers a failed parse with a 400. Its `data` carries the zod error only
as text. So parse the body yourself with `schema.safeParse`, and throw `validationError(issues)`. The issues arrive in
`data.issues`. The Forms `submit` route is the example:

```ts
const result = definition.schema.safeParse(await readBody(event))
if (!result.success) throw validationError(result.error.issues)
```

## Responses

| Route | Status | Return |
| --- | --- | --- |
| Create | 201 | `created(event, dto)` |
| Update or action | 200 | The DTO |
| Delete or revoke | 204 | `noContent(event)` |

Every response is a data transfer object (DTO) that lists its fields explicitly, never a database row:

- A `to<Entity>Dto()` function in `server/utils` builds it.
- Dates are ISO strings, made with `isoDate`.
- The DTO types live in `src/types.ts`.

| Helper | Purpose |
| --- | --- |
| `created(event, dto)` | Sets 201 and returns `dto`. |
| `noContent(event)` | Sets 204 and returns `null`, for deletes and revokes. |
| `isoDate(value)` | Turns a `Date`, epoch milliseconds or a date string into an ISO string, and `null` or `undefined` into `null`. |

## Pagination

Admin lists are paginated. They answer `{ items, total, page, pageSize }`, built with `pageQuery()` and `paginate()`.

- **Query keys.** They match the table composable `useTableQuery` of [UI](/modules/interface/ui): `page`, `pageSize`,
  `q`, `sort`, `order` and the list's `filters` keys.
- **Page size.** The default is 20, and the most a client may ask for is 100.
- **Small lists.** Small bounded lists, such as tokens, roles and plans, stay plain arrays.

```ts [src/runtime/server/routes/admin/events.get.ts]
import { db, schema } from '@nuxthub/db'
import { and, count, eq } from 'drizzle-orm'
import { likeContains, orderByQuery, pageQuery, pageRange, paginate } from '@frigear-nu/module-kit/server'
import { z } from 'zod'

const listQuery = pageQuery({ sort: ['startsAt', 'slug'], filters: { status: z.enum(['draft', 'published']).optional() } })

export default defineEventHandler(async (event) => {
  // The Events module's staff guard, from its src/runtime/server/utils/auth.ts. See Staff access.
  await eventsStaff.require(event)
  const query = await getValidatedQuery(event, listQuery.parse)
  const where = and(
    query.q ? likeContains(schema.events.slug, query.q) : undefined,
    query.status ? eq(schema.events.status, query.status) : undefined,
  )
  const orderBy = orderByQuery({ startsAt: schema.events.startsAt, slug: schema.events.slug }, query, { tiebreaker: schema.events.id })
  const { limit, offset } = pageRange(query)
  const [rows, [totals]] = await Promise.all([
    db.select().from(schema.events).where(where).orderBy(...orderBy).limit(limit).offset(offset),
    db.select({ total: count() }).from(schema.events).where(where),
  ])
  return paginate({ items: rows.map(toEventDto), total: totals?.total ?? 0, query })
})
```

`toEventDto` is the Events module's DTO function, in its `server/utils` (see [Responses](#responses)).
`likeContains` searches case-insensitively on both [dialects](/guide/concepts/glossary). A `%` or `_` in the search
does not act as a wildcard.

## Staff access

Each module defines one [staff guard](/guide/concepts/glossary) with `defineStaffGuard` from `@frigear-nu/auth`. It
checks sign-in, the module's staff scope and its policy hook in one call:

```ts [src/runtime/server/utils/auth.ts]
import { defineStaffGuard } from '@frigear-nu/auth'

export const myModuleStaff = defineStaffGuard({ hook: 'my-module:authorize', scope: 'my-module:manage', message: 'You cannot manage things.' })
```

The file lives in `src/runtime/server/utils/`, so the guard is auto-imported into the module's routes. Its name must
start with the module's name, because every module's server utils share one namespace (see [Naming](#naming)). The
host app decides who counts as staff in the policy hook (`my-module:authorize`); see
[Policy hooks](/guide/concepts/auth-and-scopes#policy-hooks).

| Call | Use it for |
| --- | --- |
| `myModuleStaff.require(event)` | Reads and ordinary edits. API tokens with the scope work. |
| `myModuleStaff.require(event, { sessionOnly: true })` | Credentials, money and billing. See [sessionOnly](/guide/concepts/auth-and-scopes#sessiononly). |
| `myModuleStaff.can(event, userId)` | A yes or no, such as for MCP tools. |

`require` returns `{ userId, principal }`. Load the full user with `loadAuthUser(userId)` when a route needs it. The
whole model is on [Staff guards](/guide/concepts/auth-and-scopes#staff-guards).

## Naming

**Server utils.** Every module's `server/utils` is auto-imported into one [Nitro](/guide/concepts/glossary)
namespace. So an exported name must be unique across all modules. Prefix it with the module: `toFormTokenDto` and
`toAuthTokenDto`, never a generic `toTokenDto`.

::warning
Two modules that export the same name clash, and one of them silently wins.
::

**Path builders.** Each module keeps typed path builders in `src/runtime/utils/api.ts`, such as `authApi`, `eventsApi`
and `formsApi`. It exports them as `@frigear-nu/<pkg>/api`.

- Import them from there in app code and tests.
- Do not import them from `./utils`, which also holds build-time helpers that pull in `@nuxt/kit`.
- Relative imports inside the package stay relative.

```ts
import { authApi } from '@frigear-nu/auth/api'
```

## Testing routes

`@frigear-nu/module-kit/testing` has two helpers for end-to-end tests. They run against a
[test fixture](/guide/concepts/glossary) started with `setup()` from `@nuxt/test-utils/e2e`.

| Helper | What it does |
| --- | --- |
| `apiClient({ cookie?, bearer? })` | Acts as one caller. |
| `.json<T>(method, path, body?)` | Resolves with the parsed body of a 2xx response, or `null` for 204. Rejects otherwise. |
| `.fetch(method, path, body?)` | Resolves with the raw `Response`, whatever its status. |
| `expectApiError(promise, status, code?)` | Asserts the request failed with `status`, and with `data.code` when given. Resolves with the error body. |

```ts
import { apiClient, expectApiError } from '@frigear-nu/module-kit/testing'

const staff = apiClient({ cookie: staffCookie })
const created = await staff.json<{ id: string }>('POST', '/api/admin/events', { slug: 'party' })
await expectApiError(apiClient({ cookie: memberCookie }).json('DELETE', `/api/admin/events/${created.id}`), 403, 'forbidden')
expect((await staff.fetch('DELETE', `/api/admin/events/${created.id}`)).status).toBe(204)
```

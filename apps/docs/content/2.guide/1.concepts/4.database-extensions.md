Modules own their tables, but other modules and your app often need an extra column on them: a `locale` on users, a
`role` from Authorization. [`@frigear-nu/module-kit`](/modules/platform/module-kit) lets one module own a Drizzle table
while others extend it, without the owner knowing.

## The model

- The **owning module** registers a plain Drizzle schema file with `registerDatabaseTable`.
- **Other modules** add columns with `extendDatabaseTable`.
- The **host app** adds columns from its own `server/db/extend.<dialect>.ts`.

All three work on the generated NuxtHub schema. They change the *schema*, not the database: nothing alters an existing
database until you generate and apply a migration.

## Registering a table

The owner ships a schema file and registers it. Omit `name`: every table export of the file is registered.

```ts
// src/module.ts, in setup()
registerDatabaseTable(nuxt, {
  resolver,
  schema: dialect => `./runtime/server/db/schema.${dialect}`,
})
```

Pass `name` only to restrict which tables are registered. Auth does this because which of its tables exist depends on
the enabled features.

## Extending a table

An extension file is a table definition (or a columns object) exported under the table's name. It is merged into every
registered table it has a matching export for, and only those. When the owner is not installed, nothing matches and
the call has no effect.

```ts
// src/module.ts, in setup()
extendDatabaseTable(nuxt, {
  resolver,
  file: dialect => `./runtime/db/users.${dialect}`,
})
```

```ts
// src/runtime/db/users.sqlite.ts
import { sqliteTable, text } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  locale: text().default('da'),
})
```

A host extends several tables from one file; only the export matching the table being built is used:

```ts
// server/db/extend.sqlite.ts
export const users = defineTableColumns({ locale: text().default('da') })
export const posts = defineTableColumns({ summary: text() })
```

Columns are merged in this order, and a column that appears again replaces the earlier one:

1. The base schema file of the owning module.
2. Files registered with `extendDatabaseTable`, in registration order.
3. For each Nuxt layer, from the base layers towards the host app: the shared `server/db/extend.<dialect>.ts`.

The host generates and commits its own migration for what it adds.

::note
Schema and extension files are parsed as text, not executed. Keep them to imports and table calls. Top-level helpers and
constants are not carried over, and the third argument of an extension table (indexes) is dropped with a warning: put
indexes on extension columns in the base file or in a migration.
::

## One schema file per dialect

NuxtHub resolves schema files for the host's dialect, `sqlite` or `postgresql`. Every schema and extension file
(`schema.sqlite.ts`, `users.sqlite.ts`, `server/db/extend.sqlite.ts`, ...) ships with a `.postgresql.ts` twin next to it,
exporting the same tables with the same table, column and index names. Change both in the same commit.

Runtime code must work on both dialects: no `db.run`, `db.batch`, `PRAGMA`, `rowid` or sqlite-only SQL without a
postgres branch.

| sqlite | postgresql |
| --- | --- |
| `sqliteTable` (`drizzle-orm/sqlite-core`) | `pgTable` (`drizzle-orm/pg-core`) |
| `integer().primaryKey({ autoIncrement: true })` | `serial().primaryKey()` |
| `integer({ mode: 'timestamp' })` | `timestamp({ withTimezone: true })` |
| `integer({ mode: 'boolean' })` | `boolean()` |
| `text({ mode: 'json' })` | `jsonb()` |
| `integer()` holding epoch milliseconds | `bigint({ mode: 'number' })` |
| `customType({ dataType: () => 'text' })` | the same `customType` from `pg-core` |

Keep the twins in sync with a test. Every package that owns a schema has `test/schema-parity.test.ts`:

```ts
import { it } from 'vitest'
import { expectSchemaParity } from '@frigear-nu/module-kit/testing'
import * as sqlite from '../src/runtime/server/db/schema.sqlite'
import * as postgresql from '../src/runtime/server/db/schema.postgresql'

it('schema.postgresql matches schema.sqlite', () => {
  expectSchemaParity(sqlite, postgresql)
})
```

`expectSchemaParity` compares tables, columns (drizzle data type, not null, primary key, unique, defaults,
`$defaultFn`, `$onUpdateFn`), indexes and foreign keys. Add a case when you add a schema file. A module-kit test fails
when a `.sqlite.ts` schema has no `.postgresql.ts` twin.

## Migrations are committed history

Because extensions only change the generated schema, every consumer that has a database needs a migration for them:

- Generate migrations from the application's **complete** module configuration, including every extending module. Do
  not generate them from only the owning module's base schema.
- Commit the SQL, the Drizzle snapshot and the migration journal together. They are versioned schema history, not build
  artifacts. Keep existing history intact.
- Test fixtures are consuming applications too. After changing a schema or an extension, check each fixture that has
  committed migrations, from the repo root with an absolute `--cwd`:

  ```bash
  pnpm --filter @frigear-nu/<pkg> exec nuxt db generate --cwd "$PWD/packages/<pkg>/test/fixtures/<fixture>"
  ```

  It must print `No schema changes, nothing to migrate` and leave `git status` clean. If it creates a migration, the
  fixture needs one; delete any stray migration you do not intend to commit.
- A module that adds routes using `requireAuth` or `requireUser` needs the `auth_user_tokens` migration in every
  fixture that includes it.

::warning
A missing session cookie can be a database error, not disabled authentication. A column added by an extending module
without a matching fixture migration makes every write to that table fail.
::

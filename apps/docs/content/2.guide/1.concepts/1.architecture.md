The Frigear workspace is built from four kinds of things. Applications compose them, and modules never import
applications. Knowing which layer a piece of code belongs in tells you where to put it and what it may depend on.

## The four building blocks

| Block | Where it lives | What it is |
| --- | --- | --- |
| Application | `apps/*` | A deployable Nuxt app, such as the [Frigear website](/examples/apps/frigear-nu-website) or this docs site. It registers modules and adds what is specific to it. |
| Base layer | `packages/base-layer` | `@frigear-nu/base`: shared Nuxt config, UI defaults and content-driven pages for websites. An app extends it. See [Base layer](/modules/platform/base-layer). |
| Module | `packages/<module>` | A [Nuxt module](https://nuxt.com/docs/4.x/guide/modules) for one concern, such as `users` or `stripe`. Published to npm as `@frigear-nu/<module>`. See [Modules](/modules). |
| Package | `packages/*` | Tooling and shared code that is not a Nuxt module, such as the [CLI](/contribute/tooling/cli) and the [ESLint config](/contribute/tooling/eslint-config). |

Apps and packages live in one pnpm workspace and link to each other with the `workspace:*` protocol, so you run every
command from the repository root (see [Local development](/contribute/local-development)). Packages depend on each
other with `workspace:^`, so published versions are carets.

::note
Every module is a Nuxt 4 module: app code lives under `app/` and server code under `server/`. Nuxt 3 is not supported.
::

## What an application does

An application is thin. It lists the modules it wants in `nuxt.config.ts`, configures them, supplies the policy the
modules deliberately leave open, and adds its own pages and tables:

- **Modules in `nuxt.config.ts`.** The host lists only the modules it uses directly (see
  [Adding modules](/get-started/adding-modules)).
- **Policy.** Modules ask the host before they act. Who counts as staff, which roles an OAuth application accepts and
  which claims a token carries are all decided by the host in Nitro hooks (see [Auth and scopes](/guide/concepts/auth-and-scopes)).
- **Its own database columns.** The host extends module tables from `server/db/extend.<dialect>.ts` and commits the
  migrations (see [Database extensions](/guide/concepts/database-extensions)).
- **Its own pages and strings.** A page at the same path as a module page replaces it, and the host can override any
  module string in its own `i18n/locales/<code>.json`.

## How modules depend on each other

A module declares the modules it needs in `moduleDependencies`. Nuxt installs them for you, in the right order, so a
host lists only what it uses directly. For example, adding `@frigear-nu/users` brings in `auth`, `notify` and `menu`.

The main chains:

- **Sign-in.** `users` installs `auth`, `notify` and `menu`. `account`, `authorization`, `preferences` and
  `oauth-server` build on `users` and `auth`.
- **Mobile apps.** `mobile` installs `auth` when `authentication` is configured, and the app sets
  `authentication.mode: 'client'` ([client mode](/modules/identity/auth/client-mode)). It picks its guards with
  `authorization`. The app signs in at an issuer such as `oauth-server`, and each service it calls verifies the token
  with `frigear-resource`. See
  [Identity](/guide/concepts/identity).
- **Commerce.** `subscriptions`, `payments` and `events` build on `stripe` and `auth`. `events` can read memberships
  from `subscriptions`.
- **Admin screens.** `admin` provides the shell. `users`, `subscriptions`, `payments`, `events`, `forms` and
  `oauth-server` add pages when it is installed.
- **Extension points.** `menu`, `widget` and `mcp` are registries that other modules contribute to.

The rule underneath is that dependencies point one way. `auth` sits below `users` and reaches users only through the
`AuthUserStore` that `users` registers. `module-kit` depends on no feature module, and almost every module depends on it. Anything optional, such as menus or widgets, is declared as an optional dependency and guarded, so a module
still works when it is absent.

## Composing without importing

Modules rarely import each other's code. They compose through a small set of mechanisms, covered in
[Extension points](/guide/concepts/extension-points):

- **Registries**, filled at build time. A module calls `extendMenu`, `extendWidgets`, `extendTabs`, `addAuthScope` or
  `addMcpDefinitions`, and the owner of the registry bundles everything once every module has finished setting up.
  Registration order does not matter.
- **Hooks**, answered at run time. A module asks a question (`events:authorize`) and the host answers it.
- **Database extensions.** A module adds columns to a table another module owns, without the owner knowing.
- **Virtual modules.** Registries are compiled into virtual modules the runtime imports, so there is no runtime
  scanning and the result works on Workers.

Because of this, you can install a module and get its pages, menu items, dashboard widgets and MCP tools without
touching any other module.

## Where to put new code

| You are writing | Put it in |
| --- | --- |
| A page or API that only your product needs | The application |
| A feature another app could reuse | A new module under `packages/` (see [Writing a module](/contribute/writing-a-module/scaffold)) |
| A helper for several modules that is not Nuxt-specific | A package under `packages/` |
| A decision about who may do what | A host hook in the application, not the module |

Prefer adding shared logic to a package over duplicating it in applications, but do not create a package for a single
one-off helper.

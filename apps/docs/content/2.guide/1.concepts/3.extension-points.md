Modules do not import each other to add features. They plug into a small number of extension points, so you can install
a module and its pages, menu items, widgets and tools appear. This page lists the points; each module page has the full
API.

## Build time and run time

| Kind | When it runs | Example |
| --- | --- | --- |
| **Registry** | In a module's `setup()`, collected once every module is done | `extendMenu`, `extendWidgets`, `addAuthScope`, `addMcpDefinitions` |
| **Nuxt hook** | At build time | `auth:resolvers`, `widgets:resolved` |
| **Nitro or app hook** | At run time, answered by the host or another module | `events:authorize`, `auth:email`, `widgets:filter` |

Registration order between modules never matters: items are merged after `modules:done`.

## Virtual registries

`defineVirtualRegistry` from `@frigear-nu/module-kit/utils` is the pattern behind most registries. Other modules register
entries during their own `setup()`; once every module is done, the collected entries are bundled into one virtual module
the runtime imports. There is no runtime scanning, which keeps it Workers friendly.

```ts
function defineVirtualRegistry<T>(nuxt: Nuxt, options: VirtualRegistryOptions<T>): void
```

`target` is `app` (writes a template and aliases it) or `server` (a Nitro virtual module). The owning module calls it
from its `setup()`; contributors call the owner's helper. See [Module Kit](/modules/platform/module-kit).

## Hooks: ask the host

A hook is a question a module asks and the host answers. The common shape is a `*:authorize` Nitro hook that is denied
by default:

| Hook | Asked by | The host decides |
| --- | --- | --- |
| `events:authorize`, `forms:authorize`, `payments:authorize` | Staff routes of the module | Who is staff for this module |
| `users:admin:authorize` | The users admin | Who may view, create, update or delete users |
| `oauth:authorize`, `oauth:application:access` | OAuth Server | Who administers applications, and who may sign in to one |
| `widgets:filter`, `tabs:filter` | The widget components | Which widgets and tabs the visitor sees |
| `auth:scope-available` | Auth | Which scopes a user may pick for a token |

Listeners identify the caller from `ctx.userId`, never from the session on `ctx.event`. See
[Auth and scopes](/guide/concepts/auth-and-scopes) for policy gates and staff guards.

## Menus

[`@frigear-nu/menu`](/modules/interface/menu) holds named menus (`main`, `dashboard`, `account`, ...). A menu path is
split on its first dot: `dashboard.more` is group `more` of menu `dashboard`. Items from Nuxt Content, from modules and
from runtime sources are merged and sorted by `order`.

A module contributes static items at build time, and dynamic items from a runtime source file:

```ts
import { extendMenu } from '@frigear-nu/menu/utils'

extendMenu(nuxt, 'dashboard.more', [
  { label: 'Billing', description: 'Manage your subscription', to: '/billing' },
])
```

A module that must work without the menu module registers its source with `addOptionalMenuSource` from
`@frigear-nu/module-kit/utils`, which does nothing when menu is not installed.

## Widget areas and tabs

[`@frigear-nu/widget`](/modules/interface/widget) offers two registries with the same ordering and gating:

- **Widgets** fill a named **area**. The host renders `<WidgetArea name="admin.dashboard">` wherever it likes, and
  modules contribute components with `extendWidgets`.
- **Tabs** fill a detail page. `<WidgetTabs name="admin.users">` renders every registered tab, with the active tab in
  `?tab=`.

```ts
import { extendWidgets, extendTabs } from '@frigear-nu/widget/utils'

extendWidgets(nuxt, 'admin.dashboard', { component: resolver.resolve('./runtime/app/widgets/NewMembers.vue'), order: 10 })
extendTabs(nuxt, 'admin.users', { id: 'payments', component: resolver.resolve('./runtime/app/tabs/Payments.vue'), label: 'Payments' })
```

An entry registered again under the same `id` replaces the earlier one, which is how a host overrides a module's widget.
Use `WidgetTabs` when other modules should add sections to a page, and `PageTabs` when the page owns them (see
[Pages](/guide/ux-patterns/pages)).

::warning
Gating a widget only hides UI. Always enforce permissions on the server for the data a widget loads.
::

## Admin navigation and dashboard

[`@frigear-nu/admin`](/modules/interface/admin) is built entirely from the two registries above. The sidebar is three
menu groups, and the dashboard is three widget areas:

| Group | Menu path | Put here |
| --- | --- | --- |
| Overview | `admin.nav.overview` | The dashboard |
| Manage | `admin.nav` | What staff manage every day |
| Settings | `admin.nav.settings` | Configuration |

| Dashboard area | Put here |
| --- | --- |
| `admin.dashboard.top` | One `StatCard` per widget |
| `admin.dashboard` | Lists and tables |
| `admin.dashboard.side` | Short `ListCard`s |

```ts
import { extendAdminNav, extendAdminDashboard, adminRoute } from '@frigear-nu/admin/utils'

extendAdminNav(nuxt, { label: 'Forms', to: adminRoute(nuxt, 'forms'), icon: 'i-lucide-clipboard-list', order: 20 })
extendAdminDashboard(nuxt, { component: resolver.resolve('./runtime/app/widgets/Submissions.vue'), order: 10 })
```

New features go into one of the existing groups. A module can also call `extendMenu` and `extendWidgets` directly
without depending on the admin package. See [Layouts and navigation](/guide/ux-patterns/layouts-and-navigation).

## Account menu and overview

[`@frigear-nu/account`](/modules/identity/account) uses the same registries for the account area:

- The `account` menu is the account navigation and the overview's shortcuts. `account.dropdown` is the account menu in
  the header. A module adds a page by registering the route and a menu item; it never draws its own account navigation.
- The `account.overview` widget area fills the overview page. Widgets receive the session `user` as a prop.
- `order` slots a page between others. Membership sits at 15, Tickets at 40 and Applications at 50.

## MCP tools

[`@frigear-nu/mcp`](/modules/features/mcp) serves one MCP endpoint for everybody. A module adds tools from its `setup()`
with `addMcpDefinitions` and the scoped definers `defineScopedMcpTool`, `defineScopedMcpResource` and
`defineScopedMcpPrompt`:

```ts
addAuthScope(nuxt, { name: 'notes:read', description: 'Read your notes' })
if (options.settings?.mcp === true) addMcpDefinitions(nuxt, resolver.resolve('./runtime/server/mcp'))
```

Every definition declares the scopes it needs, and a tool is only listed and callable for callers who hold them. A
tool takes the user from `ctx.user`, never as an argument, and staff tools pass the module's gate too. Exposing tools is
opt-in per module through `settings.mcp`.

## Auth extension points

`@frigear-nu/auth/utils` offers three build-time registries: `addAuthScope` (scopes users can pick), `addAuthResolver`
(a custom bearer credential, by prefix or as a JWT) and `setAuthUserStore` (where users are stored; the first
registration wins). Users registers the user store, which is why Auth works without depending on it.

## Bootstrap providers

An area that shows several modules' data for the signed-in user, such as the account pages, would otherwise make one
request per module. `registerBootstrapProvider` adds a module's piece to the area's single
`GET /api/auth/bootstrap?scope=<scope>` request. Register only data a page of the area shows on first render. See
[Module Kit](/modules/platform/module-kit).

Your module has a Billing page. It should appear in the account menu, put a widget on the admin dashboard and offer a
tool to AI agents, without you editing the Account, Admin or MCP modules. After this page you can decide which extension
point to use for each of those, and where its full reference lives.

::callout{icon="i-lucide-users"}
**For:** module authors. App developers can read [Override a module's widget](#widget-areas-and-tabs) and
[Hooks](#hooks-ask-the-host-app).
::

## Which one do I use?

| You want to | Use | Read |
| --- | --- | --- |
| Add a link to a menu, such as the account menu | `extendMenu` | [Menus](#menus) |
| Add a link to the admin sidebar or a card to the admin dashboard | `extendAdminNav`, `extendAdminDashboard` | [Admin navigation and dashboard](#admin-navigation-and-dashboard) |
| Show a component in a named slot, such as the account overview | `extendWidgets` | [Widget areas and tabs](#widget-areas-and-tabs) |
| Add a tab to a detail page another module owns | `extendTabs` | [Widget areas and tabs](#widget-areas-and-tabs) |
| Let the host app decide who may do something | A policy hook | [Hooks](#hooks-ask-the-host-app) |
| Let users give a token access to your routes | `addAuthScope` | [Auth extension points](#auth-extension-points) |
| Offer tools to AI agents | `addMcpDefinitions` | [MCP tools](#mcp-tools) |
| Load your data in one request with other modules' data | `registerBootstrapProvider` | [Bootstrap providers](#bootstrap-providers) |
| Add a column to another module's table | `extendDatabaseTable` | [Database extensions](/guide/concepts/database-extensions) |

## Terms

- **[Extension point](/guide/concepts/glossary).** A place where one module adds things to another without importing
  it, either a registry or a hook.
- **[Registry](/guide/concepts/glossary).** A build-time list that modules add entries to, such as menus, widgets, tabs,
  scopes and Model Context Protocol (MCP) tools.
- **[Hook](/guide/concepts/glossary).** A runtime hook (Nitro or app) that a module calls and that listeners in the host
  app or other modules answer.
- **[Widget area](/modules/interface/widget).** A named slot where the Widget module renders the components modules add.

## How it works

Extension points come in two kinds:

| Kind | When it runs | Example |
| --- | --- | --- |
| **Registry** | In a module's `setup()`, collected once every module is done | `extendMenu`, `extendWidgets`, `addAuthScope`, `addMcpDefinitions` |
| **Hook** | At run time, a Nitro or app hook answered by the host app or another module | `events:authorize`, `auth:email`, `widgets:filter` |

Registration order between modules never matters: items are merged after `modules:done`.

::note
Nuxt build hooks, such as `auth:resolvers` and `widgets:resolved`, run at build time and are not extension points.
[Module Kit](/modules/platform/module-kit) has the build-time helpers for module authors.
::

### Registries

Most registries are built on `defineVirtualRegistry` from `@frigear-nu/module-kit/utils`.

1. The module that owns the registry calls it from its `setup()`.
2. Other modules add entries during their own `setup()`, through the owner's helper.
3. Once every module is done, the entries are bundled into one virtual module that the runtime imports.

There is no scanning at run time, which keeps it working on Cloudflare Workers.

[Registries and menus](/modules/platform/module-kit/registries-and-menus) has the signature and options of
`defineVirtualRegistry`, including its `app` and `server` targets.

### Hooks: ask the host app

A hook is a question a module asks and the host app answers. The common shape is a policy hook named `*:authorize`,
denied by default:

| Hook | Asked by | The host app decides |
| --- | --- | --- |
| `events:authorize`, `forms:authorize`, `payments:authorize` | Staff routes of the module | Who is staff for this module |
| `users:admin:authorize` | User management in the admin area | Who may view, create, update or delete users |
| `oauth:authorize`, `oauth:application:access` | OAuth Server | Who manages OAuth applications, and who may sign in to one |
| `widgets:filter`, `tabs:filter` | The widget components | Which widgets and tabs the user sees |
| `auth:scope-available` | Auth | Which scopes a user may pick for a token |

[Auth and scopes](/guide/concepts/auth-and-scopes#policy-hooks) explains policy hooks and staff guards.

### Menus

[Menu](/modules/interface/menu) holds named menus, such as `main`, `dashboard` and `account`. A menu path is split on
its first dot: `dashboard.more` is group `more` of menu `dashboard`. Items from Nuxt Content, from modules and from
runtime sources are merged and sorted by `order`.

A module adds static items at build time:

```ts
import { extendMenu } from '@frigear-nu/menu/utils'

extendMenu(nuxt, 'dashboard.more', [
  { label: 'Billing', description: 'Manage your subscription', to: '/billing' },
])
```

Dynamic items come from a runtime source file. A module that must work without Menu registers its source with
`addOptionalMenuSource` from `@frigear-nu/module-kit/utils`. It does nothing when Menu is not installed.

### Widget areas and tabs

[Widget](/modules/interface/widget) offers two registries with the same ordering and gating:

- **Widgets** fill a named widget area. The host app renders `<WidgetArea name="admin.dashboard">` wherever it likes.
  Modules add components with `extendWidgets`.
- **Tabs** fill a detail page. `<WidgetTabs name="admin.users">` renders every registered tab, with the active tab in
  `?tab=`.

```ts
import { extendWidgets, extendTabs } from '@frigear-nu/widget/utils'

extendWidgets(nuxt, 'admin.dashboard', { component: resolver.resolve('./runtime/app/widgets/NewMembers.vue'), order: 10 })
extendTabs(nuxt, 'admin.users', { id: 'payments', component: resolver.resolve('./runtime/app/tabs/Payments.vue'), label: 'Payments' })
```

An entry registered again under the same `id` replaces the earlier one. That is how a host app overrides a module's
widget.

::tip
Use `WidgetTabs` when other modules should add sections to a page. Use `PageTabs` when the page owns them (see
[Pages](/guide/ux-patterns/pages)).
::

### Admin navigation and dashboard

[Admin](/modules/interface/admin) draws the admin area entirely from the two registries above. The sidebar is three menu
groups:

| Group | Menu path | Put here |
| --- | --- | --- |
| Overview | `admin.nav.overview` | The dashboard |
| Manage | `admin.nav` | What staff manage every day |
| Settings | `admin.nav.settings` | Configuration |

The dashboard is three widget areas:

| Dashboard area | Put here |
| --- | --- |
| `admin.dashboard.top` | One `StatCard` per widget |
| `admin.dashboard` | Lists and tables |
| `admin.dashboard.side` | Short `ListCard`s |

```ts
import { extendAdminNav, extendAdminDashboard, adminRoute } from '@frigear-nu/admin/utils'

extendAdminNav(nuxt, { label: 'Forms', to: adminRoute(nuxt, 'forms'), icon: 'i-lucide-clipboard-list', order: 20 })
extendAdminDashboard(nuxt, { component: resolver.resolve('./runtime/app/widgets/Submissions.vue'), order: 10 })
```

New features go into one of the existing groups. A module can also call `extendMenu` and `extendWidgets` directly,
without depending on Admin. See [Layouts and navigation](/guide/ux-patterns/layouts-and-navigation).

### Account menu and overview

[Account](/modules/identity/account) uses the same registries for the account pages:

- The `account` menu is the account navigation and the overview's shortcuts.
- `account.dropdown` is the account menu in the header.
- A module adds an account page by registering the route and a menu item. It never draws its own account navigation.
- The `account.overview` widget area fills the overview page. Its widgets receive the session `user` as a prop.
- `order` places a page between others. Membership sits at 15, Tickets at 40 and Applications at 50.

### MCP tools

[MCP](/modules/features/mcp) serves one Model Context Protocol endpoint for everybody. A module adds tools from its
`setup()` with `addMcpDefinitions`. It defines them with `defineScopedMcpTool`, `defineScopedMcpResource` and
`defineScopedMcpPrompt`:

```ts
addAuthScope(nuxt, { name: 'notes:read', description: 'Read your notes' })
if (options.settings?.mcp === true) addMcpDefinitions(nuxt, resolver.resolve('./runtime/server/mcp'))
```

- Every definition declares the scopes it needs.
- A tool is listed and callable only for principals that hold those scopes.
- A tool takes the user from `ctx.user`, never as an argument.
- Staff tools also pass the module's policy hook.
- Exposing tools is opt-in per module, through `settings.mcp`.

### Auth extension points

`@frigear-nu/auth/utils` offers three build-time registries:

| Helper | Registers |
| --- | --- |
| `addAuthScope` | Scopes users can pick for a token. |
| `addAuthResolver` | A custom bearer credential, by prefix or as a JWT. |
| `setAuthUserStore` | Where users are stored. The first registration wins. |

Users registers the user store. That is why Auth works without depending on it.

### Bootstrap providers

Some pages show several modules' data for the signed-in user, such as the account pages. Without help they make one
request per module. `registerBootstrapProvider` adds a module's piece to the single
`GET /api/auth/bootstrap?scope=<scope>` request of that area. See [Module Kit](/modules/platform/module-kit).

::tip
Register only data that a page of the area shows on first render.
::

## Common mistakes

::warning
**Trusting a hidden widget.** Gating a widget only hides it in the interface. Always enforce permissions on the server
for the data a widget loads.
::

::warning
**Reading the session in a hook listener.** Listeners identify the caller from `ctx.userId`, never from the session on
`ctx.event`. The session is empty for bearer requests.
::

Several modules deal with signing people in across applications. They are different roles in one OAuth 2.0 / OpenID
Connect picture, not alternatives for the same job. This page names the roles and tells you which to pick.

## The roles

| Role | Module | Runs in | Does |
| --- | --- | --- | --- |
| **Issuer** | [OAuth Server](/modules/identity/oauth-server) | The server of frigear.nu or your own | Users sign in, applications are registered, tokens are issued. |
| **Server-rendered client** | [Auth](/modules/identity/auth) (Log in with frigear.nu) | A Nuxt app with a server | Confidential OIDC login against an issuer. The server knows who is signed in. |
| **Public client** | [Auth in client mode](/modules/identity/auth/client-mode) | The browser or a phone | PKCE sign-in, keeps and refreshes the tokens, sends them to the API. |
| **Resource server** | [Frigear Resource](/modules/identity/frigear-resource) | Each service the app calls | Verifies the access token a service receives. |
| **App shell** | [Mobile](/modules/interface/mobile) | The phone | The Capacitor shell. Installs Auth when `authentication` is configured; the app sets client mode. |

```text
phone: Mobile + Auth (client) ──sign in──▶ issuer: OAuth Server (frigear.nu or your own)
        │                                       │ access token
        └──────── Bearer token ────────▶ service: Frigear Resource ──▶ requireAuth
```

## Confidential and public clients

An application registered at the issuer is one of two types, fixed when it is created.

- **Confidential.** A server keeps a secret and sends it with every token request, next to PKCE. Use it for a
  server-rendered web app. Config cannot hold one; register it in the admin UI.
- **Public.** Anything shipped to a browser or a device can be extracted, so there is no secret. PKCE with S256 protects
  the code exchange and refresh token rotation protects the refresh token. Use it for a SPA, a Capacitor app, a desktop
  app or a CLI.

PKCE with S256 is mandatory for both. There is no machine-to-machine flow: every token belongs to a signed-in user.

## Which one do I use?

| You are building | Use |
| --- | --- |
| A server-rendered web app with its own users, signing in at an issuer | [Auth](/modules/identity/auth)'s Log in with frigear.nu, as a confidential client |
| A browser SPA | [Auth in client mode](/modules/identity/auth/client-mode) as a public client |
| A mobile app | [Mobile](/modules/interface/mobile) with [Auth in client mode](/modules/identity/auth/client-mode) as a public client |
| The service the mobile app calls | [Frigear Resource](/modules/identity/frigear-resource) |
| Your own identity provider | [OAuth Server](/modules/identity/oauth-server) |
| A different identity provider (Keycloak, Auth0, Zitadel) | [Auth in client mode](/modules/identity/auth/client-mode) pointed at it; see [Use your own OAuth server](/guide/going-further/own-oauth-server) |

Keep a server-rendered web app in Auth's server mode, with its single sign-on. Client mode keeps the tokens in the
browser, where any XSS can read them and the server cannot know who is signed in: moving a web app from server to
client mode is a downgrade. Both modes have the same app API (`useUserSession`, `useAuth`, `$api`) and take their
guards from [Authorization](/modules/identity/authorization). In client mode those guards are UX: the API decides.

## Log in with frigear.nu

`oauth.frigear` in Auth registers `GET /auth/frigear`, an OIDC login against frigear.nu for PR previews and local
development. It is decided per request: it is active when `runtimeConfig.previewDeployment` is `true`, or when
`runtimeConfig.frigear.sso` has a client id and secret. Register `<origin>/auth/frigear` as the callback on the issuer.
Users are matched by email, and the `role` claim can be applied at every login.

## One app for every service

frigear.nu can be the only sign-in of one mobile app that talks to every Frigear service (vouchers, shop, inventory,
...). The flow:

1. The mobile app is a public application at frigear.nu, with a native redirect URI and no secret.
2. It signs in with PKCE, asks for the scopes of the services it needs, and keeps the rotating refresh token.
3. Every access token has one shared audience (`accessTokenAudience`) and is short-lived, because services cannot revoke
   it.
4. Each service installs Frigear Resource. It verifies the token and hands routes the usual Auth principal with the
   granted scopes, so `requireAuth(event, { scopes: ['vouchers:read'] })` works as it does for sessions and API tokens.
5. frigear.nu lists every service's scopes in `oauthServer.scopes` with a `service` name, so the consent screen groups
   them. `staffOnly` scopes are granted only to users the host calls staff.

A token without the scope gets `403 insufficient_scope`. An invalid, expired or foreign token gets `401`.

## Any issuer works

Auth in client mode signs in as a public client with PKCE at any OpenID Connect issuer that meets a checklist:
discovery, PKCE S256, a public client, exact redirect URIs, CORS for the webview, rotating refresh tokens, `iss` in the
response, an id_token and a userinfo endpoint. Point `authentication.client.issuer` at it and the rest of the app is
unchanged. The checklist and provider
notes are in [Use your own OAuth server](/guide/going-further/own-oauth-server).

Every server route has to know who is calling and what they may do. A browser, a script and a mobile app each prove it
differently: with a cookie, an API token or an access token. After this page you can decide which check a route needs:
any signed-in user, a scope, a session only, or staff only.

::callout{icon="i-lucide-users"}
**For:** app developers and module authors.
::

## Which one do I use?

| Your route | Use | Read |
| --- | --- | --- |
| Needs any signed-in user, however they proved it | `requireAuth(event)` | [Check who is calling](#check-who-is-calling) |
| Needs only the user record | `requireUser(event)` | [Check who is calling](#check-who-is-calling) |
| Works with or without sign-in | `getAuth(event)` | [Check who is calling](#check-who-is-calling) |
| Reads or acts on data an integration may need | `requireAuth(event, { scopes })` | [Scopes](#scopes) |
| Changes who the user is, how they sign in, or money | `requireAuth(event, { sessionOnly: true })` | [sessionOnly](#sessiononly) |
| Is for staff, and you write the module | A staff guard | [Staff guards](#staff-guards) |
| Is a module's staff route, and you write the app | An answer to its policy hook | [Policy hooks](#policy-hooks) |

## Terms

- **[Principal](/guide/concepts/glossary).** Who made a request: the signed-in user, how they proved it and the scopes
  that proof carries. In code it is `AuthPrincipal`.
- **[Signed-in user](/guide/concepts/glossary).** The person behind a principal, when only the person matters.
- **[Visitor](/guide/concepts/glossary).** Someone with no valid credential.
- **[Session](/guide/concepts/glossary).** A sealed cookie that keeps a person signed in to one host app in server mode.
  It grants full access (`*`) except PII (personal data) scopes.
- **[Access token](/guide/concepts/glossary).** A short-lived signed JSON Web Token (JWT) that an issuer gives an OAuth
  application for a signed-in user.
- **[Scope](/guide/concepts/glossary).** A permission string in the form `resource:action` that limits what a token may
  do. An example is `tickets:read`.
- **[PII](/guide/concepts/glossary).** Personally identifiable information (personal data). PII scopes such as
  `events:pii` guard it, and wildcards never include them.
- **[Staff](/guide/concepts/glossary).** People your host app lets into management screens and APIs. Your app decides
  who is staff in a policy hook, never a module.
- **[Policy hook](/guide/concepts/glossary).** A Nitro hook that your app answers to allow an action, denied by default.
  Its name is `<module>:authorize`.

## How it works

[Auth](/modules/identity/auth) answers "who is calling?" once, for every kind of credential. It hands the route that
answer, the principal. [Users](/modules/identity/users) owns the users themselves. Auth does not depend on Users: it
knows users only through the user store that Users registers (`AuthUserStore`).

### The principal

Every request with a valid credential becomes a principal. It holds a `user`, a `kind` and the `scopes` the credential
carries. There are three kinds:

| `kind` | Credential | Scopes |
| --- | --- | --- |
| `session` | Sealed cookie from nuxt-auth-utils | Everything (`*`) except PII scopes |
| `user-token` | An [API token](/guide/concepts/glossary): `Authorization: Bearer fnu_…` (prefix configurable), created by the user | The scopes chosen at creation |
| `oauth` | An access token: `Authorization: Bearer <JWT>`, issued to an OAuth application | The scopes the user granted |

```ts
type AuthPrincipal =
  | { kind: 'session', user: AuthUser, scopes: string[] }
  | { kind: 'user-token', user: AuthUser, scopes: string[], token: { id: string, name: string, prefix: string } }
  | { kind: 'oauth', user: AuthUser, scopes: string[], client: { id: string } }
```

**Sessions** are for people in a browser. The cookie names the user, and every request reads that user again from the
database. So a role change applies to the next request, and a deleted account ends the session. A session also ends
when the account's id now belongs to an account with another email.

**API tokens** are created by the user on the account page or through the API, for example for an MCP client. Only a
hash (SHA-256) of the token is stored. Send it in the `Authorization` header; no other place is accepted.

**Access tokens** are issued by [OAuth Server](/modules/identity/oauth-server) to an OAuth application the user signed
in to. `principal.client.id` is that application. Every request checks live state:

- the application must be active,
- the user must still pass its role requirement.

A bearer request loads the user from the database every time. So a role change, a ban or a deleted account applies to
the next call.

::caution
A request whose bearer token looks like one Auth knows (the `fnu_` prefix or a JWT) but is invalid, expired or revoked
is unauthenticated. This holds even when it also carries a valid session cookie.
::

### Check who is calling

Authenticate server routes with `requireAuth` or `requireUser`, never with nuxt-auth-utils' `requireUserSession`. Both
accept all three credential kinds.

| Call | Returns | Use it when |
| --- | --- | --- |
| `requireAuth(event, { scopes?, sessionOnly? })` from `@frigear-nu/auth` | The principal | The route needs to know how the request was authenticated. |
| `requireUser(event, options)` from `@frigear-nu/users` | The user | The route only needs the user. Same options and 401/403 behaviour. |
| `getAuth(event)` | The principal or `null` | Sign-in is optional for the route. Never throws. |

```ts
// server/api/tickets.get.ts
export default defineEventHandler(async (event) => {
  const { user } = await requireAuth(event, { scopes: ['tickets:read'] })
  return getTickets(user.id)
})
```

| Failure | Status |
| --- | --- |
| No valid credential | `401` |
| A token lacks a required scope | `403 insufficient_scope` (sessions pass, except for PII scopes) |
| `sessionOnly: true` and the request used a token | `403 session_required` |

`getUserSession` is only for flows that are session by nature: sign-in, sign-out and OAuth consent.

### sessionOnly

::caution
Pass `sessionOnly: true` for anything that changes **who the user is or how they sign in**. That covers password,
email, passkeys, API tokens, the billing portal, OAuth consent and user management in the admin area. A leaked API
token must not be able to mint more credentials or take over the account.
::

Use `scopes` instead for reads and actions an integration plausibly needs, such as tickets, subscriptions and form
submissions.

### Scopes

A scope is a `resource:action` string. `*` grants everything, and `resource:*` grants every action of one resource.
Scopes only narrow: a token never does more than its owner can.

PII scopes (`resource:pii`) are the exception to the wildcards. Neither `*` nor `resource:*` covers them. So a
token only sees other people's personal data when the user picked that scope by name. A session is full access, so
[MCP](/modules/features/mcp) tools strip personal data for it as well.

A module registers the scopes it understands at build time with `addAuthScope` from `@frigear-nu/auth/utils`:

```ts
addAuthScope(nuxt, { name: 'reports:admin', description: 'Run reports', roles: ['admin'] })
```

A scope is only offered to users who may use it. Restrict it with `roles`. For any other rule, set
`ctx.available = false` in the `auth:scope-available` hook:

```ts
nitroApp.hooks.hook('auth:scope-available', (ctx) => {
  if (ctx.scope.name === 'reports:export') ctx.available = canExport(ctx.user.id)
})
```

### Policy hooks

Whether a user is staff is a decision for your host app, not for the module. A module asks through a policy hook that
is denied by default. In module code, the helper behind it is `definePolicyGate`:

```ts
const gate = definePolicyGate('events:authorize')
await gate.assert(event, userId) // 403 `forbidden` unless a hook listener sets ctx.allowed = true
```

- `isAllowed(event, userId, extra?)` asks the host app and never throws.
- `assert(event, userId, message?, extra?)` throws a 403.
- `extra` is merged into the context the listener receives. User management passes `{ action, target, input }`.
- `extra` cannot override `event`, `userId` or `allowed`.
- Only `ctx.allowed === true` allows.

Your host app answers in a Nitro plugin:

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('users:admin:authorize', async (ctx) => {
    const actor = await findUser(ctx.userId) // identify the caller from ctx.userId
    ctx.allowed = actor.role === 'admin'
  })
})
```

[Authorization](/modules/identity/authorization) adds a `role` column to users, abilities and route rules on top. It
applies them to all three credential kinds.

### Staff guards

This section is for module authors. Most staff routes need three checks: sign-in, the module's staff scope and the
policy hook. A staff guard runs all three, and each module defines one with `defineStaffGuard`:

```ts
// src/runtime/server/utils/staff.ts
export const eventsStaff = defineStaffGuard({
  hook: 'events:authorize',
  scope: 'events:manage',
  message: 'You are not allowed to manage events.',
})

const { userId, principal } = await eventsStaff.require(event) // reads and ordinary edits
await eventsStaff.require(event, { sessionOnly: true }) // credential minting, refunds, billing
if (await eventsStaff.can(event, userId)) { /* MCP tools, menus */ }
```

- `require` calls `requireAuth` with the scope, then asks the policy hook.
- It returns `{ userId, principal }`, not the stored user. Load more with `loadAuthUser(userId)`.
- `can(event, userId)` is the check that never throws.

Offer the staff scopes only to users the policy hook lets in, with `defineStaffScopes`:

```ts
export default defineStaffScopes(['events:manage', 'events:pii'], gate.isAllowed)
```

### Checklist for a new route

1. Authenticate first: `requireAuth`, `requireUser` or the module's staff guard.
2. Pick `sessionOnly: true` when the route changes identity, credentials or money.
3. Otherwise declare the scope an integration needs, and register it with `addAuthScope`.
4. A module that adds routes using `requireAuth` or `requireUser` lists `@frigear-nu/auth` in its `moduleDependencies`
   and `package.json`. For `requireUser` it lists `@frigear-nu/users` too.

## Common mistakes

::warning
**Answering 404 before 401 or 403.** A route that loads the record first tells a visitor which ids exist. Authenticate
and authorize before you load anything.
::

::warning
**Reading the session in a policy hook.** Policy hooks (`*:authorize`) must identify the caller from `ctx.userId`, never
from the session on `ctx.event`. The session is empty for bearer requests.
::

::warning
**A missing module dependency.** A module whose routes call `requireAuth` without listing `@frigear-nu/auth` breaks in
any app that does not install Auth some other way.
::

Every server route asks the same question: who is calling, and how? [`@frigear-nu/auth`](/modules/identity/auth)
answers it once, for every kind of credential, and hands the route a **principal**. [`@frigear-nu/users`](/modules/identity/users)
owns the user entity. Auth depends on none of them and knows users only through the `AuthUserStore` that Users registers.

## The principal

A caller is one of three kinds. All of them resolve into the same `AuthPrincipal`: a `user`, a `kind` and the `scopes` the
credential carries.

| `kind` | Credential | Scopes |
| --- | --- | --- |
| `session` | Sealed cookie from nuxt-auth-utils | Everything (`*`) |
| `user-token` | `Authorization: Bearer fnu_…` (prefix configurable), a static token the user created | The scopes chosen at creation |
| `oauth` | `Authorization: Bearer <JWT>`, an access token issued to an application | The scopes the user granted |

```ts
type AuthPrincipal =
  | { kind: 'session', user: AuthUser, scopes: string[] }
  | { kind: 'user-token', user: AuthUser, scopes: string[], token: { id: string, name: string, prefix: string } }
  | { kind: 'oauth', user: AuthUser, scopes: string[], client: { id: string } }
```

- **Cookie sessions** are for people in a browser. A session holds a snapshot of the user from login time, so a role
  change reaches it after the next sign-in.
- **User API tokens** are created by the user on the account page or through the API, for example for an MCP client.
  Only the SHA-256 is stored, and they are accepted in the `Authorization` header only.
- **OAuth access tokens** are issued by [OAuth Server](/modules/identity/oauth-server) to an application the user signed
  in to. `principal.client.id` is the application. Every request checks live state: the application must be active and
  the user must still pass its role requirement.

A bearer request loads the user from the database every time, so a role change, a ban or a deleted account applies to
the next call. A token a resolver claims (the `fnu_` prefix or a JWT) that is invalid, expired or revoked is
unauthenticated, even with a valid session cookie.

## requireAuth and requireUser

Authenticate server routes with `requireAuth` or `requireUser`, never with nuxt-auth-utils' `requireUserSession`. Both
resolve all three credential kinds.

| Call | Returns | Use it when |
| --- | --- | --- |
| `requireAuth(event, { scopes?, sessionOnly? })` from `@frigear-nu/auth` | The principal | The route needs to know how the caller authenticated. |
| `requireUser(event, options)` from `@frigear-nu/users` | The user | The route only needs the user. Same options and 401/403 behaviour. |
| `getAuth(event)` | The principal or `null` | The route is optional-auth. Never throws. |

```ts
// server/api/tickets.get.ts
export default defineEventHandler(async (event) => {
  const { user } = await requireAuth(event, { scopes: ['tickets:read'] })
  return getTickets(user.id)
})
```

| Failure | Status |
| --- | --- |
| No valid credential | `401` |
| A token lacks a required scope | `403 insufficient_scope` (sessions pass) |
| `sessionOnly: true` and the caller used a token | `403 session_required` |

`getUserSession` is only for flows that are session by nature: login, logout and OAuth consent.

## sessionOnly

Pass `sessionOnly: true` for anything that changes **who the user is or how they sign in**: password, email, passkeys,
API tokens, the billing portal, OAuth consent, the users admin. A leaked API token must not be able to mint more
credentials or take over the account. Use `scopes` for reads and actions an integration plausibly needs: tickets,
subscriptions, form submissions.

## Scopes

Scopes are `resource:action` strings. `*` grants everything and `resource:*` every action of one resource. Scopes only
narrow: a token never does more than its owner can.

Personal-data scopes (`resource:pii`) are the exception to the wildcards. Neither `*` nor `resource:*` covers them, so a
token only sees other people's personal data when the user picked that scope by name. Sessions are full access, so
[MCP](/modules/features/mcp) tools strip personal data for them as well.

A module registers the scopes it understands at build time with `addAuthScope` from `@frigear-nu/auth/utils`:

```ts
addAuthScope(nuxt, { name: 'reports:admin', description: 'Run reports', roles: ['admin'] })
```

A scope is only offered to users who may use it. Restrict it with `roles`, or for other policy set `ctx.available = false`
in the `auth:scope-available` hook:

```ts
nitroApp.hooks.hook('auth:scope-available', (ctx) => {
  if (ctx.scope.name === 'reports:export') ctx.available = canExport(ctx.user.id)
})
```

## Policy gates

Whether a user is staff is a decision for the host, not for the module. A module defines a **gate** backed by a Nitro
hook that is denied by default:

```ts
const gate = definePolicyGate('events:authorize')
await gate.assert(event, userId) // 403 `forbidden` unless a hook listener sets ctx.allowed = true
```

`isAllowed(event, userId, extra?)` asks the host and never throws. `assert(event, userId, message?, extra?)` throws a 403.
`extra` is merged into the context the listener receives (the users admin passes `{ action, target, input }`), and it
cannot override `event`, `userId` or `allowed`. Only `ctx.allowed === true` allows.

The host answers in a Nitro plugin:

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('users:admin:authorize', async (ctx) => {
    const actor = await findUser(ctx.userId) // identify the caller from ctx.userId
    ctx.allowed = actor.role === 'admin'
  })
})
```

::warning
Host policy hooks (`*:authorize`) must identify the caller from `ctx.userId`, never from the session on `ctx.event`. The
session is empty for bearer requests.
::

[Authorization](/modules/identity/authorization) adds a `role` column to users, abilities and route rules on top, and
applies them to all three credential kinds.

## Staff guards

Most staff routes need authentication, the module's staff scope and the gate. `defineStaffGuard` combines them, one per
module:

```ts
// src/runtime/server/utils/staff.ts
export const eventsStaff = defineStaffGuard({
  hook: 'events:authorize',
  scope: 'events:manage',
  message: 'You are not allowed to manage events.',
})

const { userId, principal } = await eventsStaff.require(event) // reads and ordinary edits
await eventsStaff.require(event, { sessionOnly: true }) // credential minting, refunds, billing
if (await eventsStaff.can(event, userId)) { /* MCP tools, menus */ }
```

`require` calls `requireAuth` with the scope, then the gate. It returns `{ userId, principal }`, not the stored user; load
more with `loadAuthUser(userId)`. `can(event, userId)` is the non-throwing check. Offer the staff scopes only to
users the gate lets in with `defineStaffScopes`:

```ts
export default defineStaffScopes(['events:manage', 'events:pii'], gate.isAllowed)
```

## Checklist for a new route

1. Authenticate first: `requireAuth`, `requireUser` or the module's staff guard. Never answer 404 before 401/403.
2. Pick `sessionOnly: true` when the route changes identity, credentials or money.
3. Otherwise declare the scope an integration needs, and register it with `addAuthScope`.
4. A module that adds routes using `requireAuth` or `requireUser` lists `@frigear-nu/auth` (and `@frigear-nu/users` for
   `requireUser`) in its `moduleDependencies` and `package.json`.

An app can sign its users in at your [issuer](/guide/concepts/glossary) only after it is registered there. That
registration is an [OAuth application](/guide/concepts/glossary). It gives the app a `client_id`, the redirect URIs
the issuer accepts and, optionally, the roles that may sign in. This page registers one at an issuer that runs
[OAuth Server](/modules/identity/oauth-server), and picks its type.

::callout{icon="i-lucide-users"}
**For:** whoever runs the issuer, and app developers who connect an app to it.
::

The other side of the sign-in depends on the app:

- A browser or mobile app uses [Auth in client mode](/modules/identity/auth/client-mode).
- A web app with its own server uses [Auth](/modules/identity/auth) in [server mode](/guide/concepts/glossary).

## Pick the application type

An application is **confidential** or **public**. The type is fixed when the application is created. Why the two exist
is on [Public and confidential applications](/guide/concepts/identity#public-and-confidential-applications).

| Your app | Type | Why |
| --- | --- | --- |
| A web app with its own server, such as Nuxt with [Sign in with frigear.nu](/guide/concepts/identity#sign-in-with-frigearnu) | **Confidential** | The secret stays on your server. It is sent on every token request, next to PKCE (Proof Key for Code Exchange). |
| A single-page app (SPA), a Capacitor or mobile app, a desktop app or a CLI | **Public** | Anything shipped to a browser or a device can be extracted, so a secret there is not a secret. PKCE protects the code exchange, and refresh token rotation protects the refresh token. |
| Machine to machine, with no user | Not supported | `/oauth/token` takes only the `authorization_code` and `refresh_token` grants. Every token belongs to a signed-in user, and there is no `client_credentials` grant. |

- **PKCE with S256 is mandatory for both types.** A request without `code_challenge_method=S256` is a `400`.
- **A public application has no secret at all.** The server stores a throwaway hash and never shows it.
- **A `client_secret` sent to a public application is refused**, with `401 invalid_client`. It is not ignored.
- **A confidential application without its secret** gets `401 invalid_client` on every token and revoke request.
- **Client mode is public by design.** A production build that embeds
  `NUXT_PUBLIC_AUTHENTICATION_CLIENT_CLIENT_SECRET` fails.
- **The type cannot be changed afterwards.** Register a new application instead.

## Create it in the admin area

Use the admin area for a confidential application, or for a public one that does not need the same `client_id` in
every environment.

::warning
Without these two things nobody can manage applications:

- The admin page: `oauthServer.settings.pages.admin: true`, with [Admin](/modules/interface/admin) installed.
- A user that your app's `oauth:authorize` [policy hook](/guide/concepts/glossary) allows. It is denied by default.
  See [Who is an admin](/modules/identity/oauth-server/hooks#who-is-an-admin).
::

1. Open **OAuth applications** in the **Settings** group of the admin sidebar (`/admin/oauth`). Choose **Add
   application**.
2. Pick the **Client type**: *Confidential* or *Public*.
3. Fill in the **Name**, which the consent screen shows.
4. Fill in the **Website URL**: the origin of the app, without a path, such as `https://app.example.com`. Use `http`
   only for localhost. A confidential application needs it. A public application needs it or at least one redirect
   URI, so a native app can leave it empty and list its callback under **Redirect URIs**.
5. Fill in the **Redirect URIs**. See [Redirect URIs](#redirect-uris).
6. Optional: a **Preview URL pattern**, such as `https://*.vercel.app`. It accepts the callback path on preview
   deployments, where `*` is one hostname label.
7. Set the **Allowed roles**. Leave them empty to let every signed-in user in, or list the roles that may. Roles come
   from your app's `oauth:user:roles` hook.
8. Optional: **Login URL**, **Description**, **Icon**, **Priority** and **Tags**. The Login URL is where the **Open**
   button of the user's application list goes, and it defaults to the website URL. **Priority** orders that list.
9. Choose **Add application**.

::caution
A modal shows the **Client ID** (`app_…`) and, for a confidential application, the **Client secret**. The secret is
shown only this once. Store it before you close the modal. See [Secrets](#secrets).
::

::callout{color="success" icon="i-lucide-check"}
**What you should see:** the new application in the list at `/admin/oauth`. Its edit form opens at
`/admin/oauth?application=<id>`.
::

A row's menu has **Edit application**, **Copy client ID**, **Disable application**, **New client secret**, **Sign
everyone out** and **Delete application**. **Disable application** sets `isActive` to false.

## Create it in nuxt.config

`oauthServer.clients` defines public applications in config. These are
[configured clients](/guide/concepts/glossary). Use them when:

- the app ships with its `client_id` compiled in, such as a mobile app, an SPA or a starter, and the id must be the
  same in every environment;
- the registration should be versioned with the app.

Ids are free-form, such as `mobile` or `com.example.app`. `app_…` is reserved for applications created in the admin
area.

```ts [nuxt.config.ts (the issuer)]
export default defineNuxtConfig({
  oauthServer: {
    cors: { paths: ['/api/'] },
    clients: [
      {
        // Mobile (Capacitor): custom-scheme redirect, webview origins for CORS.
        id: 'bills-mobile',
        name: 'Bills (mobile)',
        redirectUris: ['nu.frigear.bills:/auth/callback'],
        // Accepted under `nuxt dev` only.
        devRedirectUris: ['http://localhost:3001/auth/callback'],
        corsOrigins: ['capacitor://localhost', 'https://localhost'],
      },
      {
        // Web SPA: the origin is taken from the redirect URI.
        id: 'bills-web',
        name: 'Bills (web)',
        redirectUris: ['https://bills.example.com/auth/callback'],
        devRedirectUris: ['http://localhost:3000/auth/callback'],
      },
    ],
  },
})
```

::warning
Config cannot hold a confidential application. `type` accepts only `'public'`, because a secret does not belong in
config, and an invalid entry fails the build. Register confidential applications in the admin area, or with
`createApplication`.
::

- **Other fields.** `websiteUrl`, `description`, `icon`, `allowedRoles`, `tags` and `corsOrigins`. See
  [CORS](#cors-for-browser-and-capacitor-clients). The full table is on
  [Configured clients](/modules/identity/oauth-server/routes-and-clients#configured-clients).
- **Runtime override.** `NUXT_OAUTH_SERVER_CLIENTS`, as JSON, replaces the list at runtime.
- **The stored row.** The row is created on the first OAuth request, and the config wins on every read.
- **In the admin area.** The application shows **Managed in nuxt.config**. Staff can disable it and change its priority
  and login URL. Any other change, or a delete, is `409 managed_by_config`.
- **Turning it back.** Remove the entry from config to turn it into an ordinary application.
- **Id clashes.** An id that already belongs to a confidential application is ignored, with a warning in the server
  log.

## Redirect URIs

The server accepts a `redirect_uri` only when it is an **exact string match** of one of these. No prefixes, wildcards,
query strings or fragments.

- **The website URL plus `callbackPath`**, which defaults to `/auth/frigear`. This applies to applications created in
  the admin area. Configured clients do not get it implicitly: list every URI.
- **An entry of Redirect URIs** (`redirectUris`, at most 20). It is `https`, or `http` for `localhost`, `127.0.0.1`
  and `[::1]`. Loopback is matched exactly, so list the port you use.
- **The Preview URL pattern**, for web redirects.

Native redirects are for public applications only. A confidential application is limited to `https` and loopback.

- A native redirect is a private-use scheme with one slash, such as `nu.frigear.bills:/auth/callback`, with the app id
  in lowercase.
- A webview origin also works, such as `capacitor://localhost/auth/callback`.
- Web schemes, `javascript:`, `data:`, `file:`, credentials and fragments are rejected.

| App | Register |
| --- | --- |
| [Auth client mode](/modules/identity/auth/client-mode) in a browser | `<origin>/auth/callback` (its `callbackPath` default), plus `http://localhost:3000/auth/callback` for development |
| [Auth client mode](/modules/identity/auth/client-mode) in a native app | `<native.scheme in lowercase>:/auth/callback` |
| Sign in with frigear.nu, in [Auth](/modules/identity/auth) | `<origin>/auth/frigear`: the website URL plus the server's default `callbackPath`, so no extra entry |

`devRedirectUris` exist for configured clients only. For an application created in the admin area, add the localhost
URI to **Redirect URIs**.

::warning
Remove a localhost redirect URI before production. Nothing marks it as development.
::

## Scopes, consent and roles

- **Scopes.** An app may request `openid`, `profile`, `email`, `oauthServer.scopes` and the API scopes that modules
  register. Unsupported scopes are dropped silently. A request whose scopes are all unsupported is a `400`. No `scope`
  means `openid profile email`. `staffOnly` and role-restricted scopes are dropped for users who may not hold them. See
  [API access](/modules/identity/oauth-server/server#api-access).
- **Consent.** Every sign-in shows the consent screen (`/authorize`) with the requested scopes. It cannot be skipped
  per application.
- **Allowed roles.** An application with roles refuses other users: with `403` at the authorization request, and with
  `access_denied` at the token endpoint. The check runs again on every refresh. So removing a role, or disabling the
  application, stops the next refresh.
- **Refresh tokens.** The server always issues one with a user grant. There is no `offline_access` scope: it is
  dropped as unsupported, so asking for it is harmless. Each refresh replaces the token, and using an old one revokes
  its whole family.
- **Lifetimes.** They are server options, not per application: `accessTokenTtl` (default 900 s), `refreshTokenTtl`
  (30 days) and `codeTtl` (600 s).

## Secrets

A confidential application's secret is **shown once**: in the modal after creating the application, and after **New
client secret**. Only a hash is stored, so a lost secret is replaced, not recovered.

::caution
Store the secret in the server's runtime config, set through the environment. For Sign in with frigear.nu that is
`NUXT_FRIGEAR_SSO_CLIENT_SECRET`. Never put it in `runtimeConfig.public`, a committed file, or a browser or mobile
bundle.
::

| Action | What it does |
| --- | --- |
| **New client secret** | Rotates the secret (`POST /api/admin/oauth-server/applications/:id/secret`). The old secret stops working at once, and every refresh token of the application is revoked, so everyone is signed out. A public application has no secret to rotate (`400`). |
| **Sign everyone out** | Revokes all refresh tokens and keeps the secret. Use it after a leak of tokens. |
| **Disable application** | Blocks new sign-ins and refreshes. |
| **Delete application** | Also removes the application's codes and tokens. |

Access tokens already issued stay valid until they expire, after 15 minutes by default. To end one user's sessions,
call `revokeUserGrants(userId, applicationId?)`. See the
[OAuth Server server API](/modules/identity/oauth-server/server).

## CORS for browser and Capacitor clients

Native redirects need no cross-origin requests (CORS). Two kinds of app do call the server from a browser on another
origin, so CORS applies to them:

- the webview of a Capacitor app: `capacitor://localhost` on iOS, and `https://localhost` on Android;
- an SPA on another origin.

| Setting | What it does |
| --- | --- |
| `oauthServer.cors.origins` | Exact origins, never `*`, that may call `/oauth/token`, `/oauth/revoke`, `/oauth/userinfo` and the `/.well-known` documents. `NUXT_OAUTH_SERVER_CORS_ORIGINS` takes a comma separated list. |
| A configured client's `corsOrigins` | The client's own origins. By default, those of its redirect URIs that have one: a native `nu.frigear.bills:/…` has none. `false` adds none. For a mobile app, list the two webview origins here. |
| `oauthServer.cors.paths` | Path prefixes of your own API, such as `['/api/']`, that the same origins may call with a bearer token. |

- An application created in the admin area adds no origins. List them in `cors.origins`.
- `/oauth/authorize` is never opened to CORS. It is a navigation, with cookies.
- Cookies never travel cross-origin. So session-only routes answer `401` to these apps.

## Connect the app

**A public application, in a browser or mobile app.** Point Auth in client mode at the issuer. There is no secret
option.

```ts [nuxt.config.ts (the app)]
export default defineNuxtConfig({
  modules: ['@nuxt/ui', '@frigear-nu/auth'],
  authentication: {
    mode: 'client',
    client: {
      issuer: 'https://id.example.com',
      clientId: 'bills-mobile', // or app_… for an admin-created application
      scopes: ['openid', 'profile', 'email'], // must contain 'openid'
      discovery: false, // the Frigear OAuth server's own paths
      native: { scheme: 'nu.frigear.bills' }, // nu.frigear.bills:/auth/callback
    },
  },
})
```

**A confidential application, in a web app with its own server.** Use Sign in with frigear.nu (`oauth.frigear`), with
the Client ID and secret from the modal. Create the application with the app's origin as the **Website URL**.
`<origin>/auth/frigear` is then accepted without a **Redirect URIs** entry.

```bash [.env (the app)]
NUXT_FRIGEAR_SSO_URL=https://id.example.com
NUXT_FRIGEAR_SSO_CLIENT_ID=app_…
NUXT_FRIGEAR_SSO_CLIENT_SECRET=…
```

With both set, `GET /auth/frigear` signs users in at the issuer. The options are on [Auth](/modules/identity/auth).

**A service that only receives the tokens**, such as an API behind the app, is not an OAuth application. It verifies
the access token with [OAuth Resource](/modules/identity/oauth-resource), and needs no application of its own.

For other issuers, and the full checklist of what the app needs, see
[Use your own OAuth server](/guide/going-further/own-oauth-server).

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `401 invalid_client` at `/oauth/token` | A wrong `client_id`; a confidential application without its secret, or with an old one after rotation; or a **secret sent to a public application**. Remove the secret from a public application's app. |
| The authorize page says "The redirect_uri is not allowed for this application" | Not an exact match. Compare scheme, case, port, trailing slash and path (`appid:/auth/callback`, one slash). A native URI on a confidential application is never accepted. |
| "Unknown or disabled application" | A wrong `client_id`, or the application is disabled. |
| `invalid_grant` on a refresh | The refresh token was already used, was revoked or expired. Reuse happens when two tabs or devices share one, or a response was lost after rotation. Revocation comes from **Sign everyone out** or a rotated secret. The whole family is revoked: sign in again. |
| `invalid_grant`: redirect_uri does not match | The token request's `redirect_uri` differs from the authorization request's, or the code was reused or expired (`codeTtl`). |
| `access_denied` at the token endpoint, or `403` at authorize | The user lacks an allowed role, the application is disabled, or `oauth:application:access` vetoed. |
| `409 managed_by_config` in the admin area | The application is a configured client. Edit `oauthServer.clients`. |
| `500 not_configured` | `oauthServer.clients`, or `NUXT_OAUTH_SERVER_CLIENTS`, is invalid. The server log names the problem. |
| A browser CORS error on the token request or the API | The origin is not in `cors.origins` or the client's `corsOrigins`, or the API path is not under `cors.paths`. The authorization endpoint is never CORS-enabled, by design. |
| A confidential application in a mobile app or SPA | Do not. Register a public application: a secret in the bundle is public, and Auth's client mode fails the build for it. |

---
title: OAuth Server
description: Let users sign in to your applications through an OAuth 2.0 / OpenID Connect server, with roles and claims supplied by the host app.
---

This [Nuxt module](https://nuxt.com/docs/4.x/guide/modules) turns an app into an OAuth 2.0 / OpenID Connect **server**.
You register **applications** (OAuth clients), restrict each one to users with certain roles, and those users sign in to
the application through your app: authorization code flow with mandatory PKCE, rotating refresh tokens and RS256 signed
ID tokens. The module is deliberately bare-bone: it knows nothing about roles, admins or what belongs in a token, and the
host decides through [Nitro hooks](#hooks).

::note
**Requires** `@nuxthub/core`, `@frigear-nu/module-kit`, [`@frigear-nu/auth`](/modules/auth),
[`@frigear-nu/users`](/modules/users), [`@frigear-nu/mcp`](/modules/mcp) and [`@frigear-nu/ui`](/modules/ui); all are
installed automatically. **Optional:** [`@frigear-nu/admin`](/modules/admin) (the admin page) and
[`@frigear-nu/menu`](/modules/menu) (menu items). The consent, admin and applications pages need `@nuxt/ui`.
::

## Quick setup

```bash
pnpm add @frigear-nu/oauth-server @nuxthub/core
```

```ts
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/menu', '@frigear-nu/users', '@frigear-nu/oauth-server'],
  oauthServer: {
    issuer: 'https://id.example.com',
    settings: {
      pages: { admin: true, applications: true },
    },
  },
})
```

Then:

1. [Generate a signing key](#signing-keys) and set `NUXT_OAUTH_SERVER_PRIVATE_KEY`.
2. Generate and commit a migration for the `oauth_applications`, `oauth_authorization_codes` and `oauth_refresh_tokens`
   tables (see [Module Kit](/modules/module-kit)). The module only adds tables; it does not change `users`.
3. Implement the [hooks](#hooks). Without them nobody is an admin and nobody has a role.

## Options

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `issuer` | `string` | request origin | The `iss` claim and discovery issuer. Set it explicitly behind proxies. |
| `keyId` | `string` | `key-1` | `kid` of the signing key published in the JWKS. |
| `accessTokenTtl` | `number` | `900` | Access and ID token lifetime in seconds. Keep it at 5 to 15 minutes when other services accept the tokens: they cannot be revoked, only not refreshed. |
| `accessTokenAudience` | `string \| string[]` | the `client_id` | The `aud` of every access token, e.g. `frigear-services`. Set it when [other services](#one-app-for-every-service) accept the tokens. ID tokens keep the `client_id`. |
| `refreshTokenTtl` | `number` | 30 days | Refresh token lifetime in seconds. |
| `codeTtl` | `number` | `600` | Authorization code lifetime in seconds. |
| `callbackPath` | `string` | `/auth/frigear` | Appended to an application's website URL to form its redirect URI. |
| `scopes` | `Array<string \| OAuthScopeDefinition>` | `[]` | The [scope registry](#one-app-for-every-service): extra scopes next to `openid profile email`; enrich their claims with `oauth:claims`. Pass `{ name, label?, description?, icon?, service?, staffOnly? }` to describe one on the consent screen, group it under its service and keep it for staff. Modules add theirs with `addOAuthScope`. |
| `cors.origins` | `string[]` | `[]` | Exact origins (never `*`) that browser apps may call the token, revoke, userinfo and discovery endpoints from, e.g. `capacitor://localhost` for a [Capacitor](https://capacitorjs.com) app. See [Public clients](#public-clients). |
| `settings.pages.authorize` | `string \| boolean` | `true` (`/authorize`) | Consent screen. `false` = bring your own page at `/authorize`. |
| `settings.pages.admin` | `string \| boolean` | off | Admin UI for applications. `true` = the `admin` route of Admin + `/oauth` (e.g. `/admin/oauth`). Only registered when `@frigear-nu/admin` is installed. |
| `settings.pages.applications` | `string \| boolean` | off | The signed-in user's applications. `true` = `/account/applications`. |
| `settings.signInPath` | `string` | the Auth login page | Where unauthenticated users are sent to sign in. |
| `settings.mcp` | `boolean` | `false` | Expose `my-oauth-applications` on the [MCP](/modules/mcp) endpoint (scope `oauth:read`). |

### Runtime config

The keys are secrets and are set through runtime config, not module options.

| Runtime config | Env var | Purpose |
| --- | --- | --- |
| `oauthServer.privateKey` | `NUXT_OAUTH_SERVER_PRIVATE_KEY` | PKCS#8 RSA private key (PEM). Required. |
| `oauthServer.publicKey` | `NUXT_OAUTH_SERVER_PUBLIC_KEY` | Overrides the public key derived from the private key. |
| `oauthServer.accessTokenAudience` | `NUXT_OAUTH_SERVER_ACCESS_TOKEN_AUDIENCE` | The shared audience of access tokens, comma separated. |
| `oauthServer.corsOrigins` | `NUXT_OAUTH_SERVER_CORS_ORIGINS` | The CORS origins as a comma separated list, when they differ per environment (for example the dev server of a mobile app). |
| `oauthServer.previousPublicKeys` | `NUXT_OAUTH_SERVER_PREVIOUS_PUBLIC_KEYS` | Public keys of retired keys during a rotation: `{ "<kid>": "<SPKI PEM>" }`, or the same as a JSON string. |

### Signing keys

ID tokens and access tokens are signed with an **RSA key (RS256)**. The matching public key is derived from the private
key and published at `/.well-known/jwks.json`, which applications use to verify tokens.

Generate a key pair with [OpenSSL](https://www.openssl.org/):

```bash
# 2048-bit RSA private key, PKCS#8 (-----BEGIN PRIVATE KEY-----)
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out oauth-private.pem

# Optional: the matching public key, e.g. to compare with the JWKS
openssl pkey -in oauth-private.pem -pubout -out oauth-public.pem
```

Without OpenSSL, Node.js can generate the same thing:

```bash
node -e "const {generateKeyPairSync}=require('node:crypto');const k=generateKeyPairSync('rsa',{modulusLength:2048,privateKeyEncoding:{type:'pkcs8',format:'pem'},publicKeyEncoding:{type:'spki',format:'pem'}});console.log(k.privateKey)" > oauth-private.pem
```

::warning
Keep `oauth-private.pem` out of git and delete the local file once the secret is stored; anyone with this key can mint
tokens for every application. The format must be PKCS#8 (`BEGIN PRIVATE KEY`); `BEGIN RSA PRIVATE KEY` is PKCS#1 and is
rejected. Convert it with `openssl pkcs8 -topk8 -nocrypt -in old.pem -out oauth-private.pem`.
::

Environment variables are single-line, so newlines are written as a literal `\n` (wrapping quotes are stripped). This
prints the value ready to paste:

```bash
awk 'NF {printf "%s\\n", $0}' oauth-private.pem
```

::code-group

```bash [.env (local)]
NUXT_OAUTH_SERVER_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMIIEvQIBADANBgkq...\n-----END PRIVATE KEY-----"
```

```bash [Cloudflare Workers]
# Stored as an encrypted secret on the worker, not in wrangler.json
awk 'NF {printf "%s\\n", $0}' oauth-private.pem | pnpm dlx wrangler secret put NUXT_OAUTH_SERVER_PRIVATE_KEY
```

```bash [GitHub Actions]
# Repository secret, passed to the deploy step as NUXT_OAUTH_SERVER_PRIVATE_KEY
awk 'NF {printf "%s\\n", $0}' oauth-private.pem | gh secret set NUXT_OAUTH_SERVER_PRIVATE_KEY
```

::

Use a **different key per environment**. Check it by opening `/.well-known/jwks.json`: it returns one key with
`kty: "RSA"`, your `kid` and no `d` field. A missing or malformed key answers `500` "The OAuth server signing keys are
not configured."

#### Rotating a key

Rotation has an **overlap period**: new tokens are signed with the new key while the old key's *public* half stays in
the JWKS and keeps verifying tokens already issued. Nobody is signed out. Refresh tokens are opaque and unaffected.

1. Generate a new pair.
2. Move the old public key into `previousPublicKeys`, keyed by its old `keyId`, and switch to the new private key and a
   new `keyId`.
3. Deploy. The JWKS lists both keys, and applications that cache it pick up the new key when they meet an unknown `kid`.
4. After the longest token lifetime (`accessTokenTtl` plus the time applications cache your JWKS), remove the old entry.

```bash
# The public key of the key you are retiring, as a JSON object keyed by its kid (single line, ready for an env var)
node -e "console.log(JSON.stringify({ 'key-1': require('fs').readFileSync('oauth-public-old.pem','utf8') }))"
```

::code-group

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  oauthServer: {
    keyId: 'key-2', // the new key
  },
})
```

```bash [.env]
NUXT_OAUTH_SERVER_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n…new key…\n-----END PRIVATE KEY-----"
# The retired key: public half only, nothing is signed with it any more
NUXT_OAUTH_SERVER_PREVIOUS_PUBLIC_KEYS='{"key-1":"-----BEGIN PUBLIC KEY-----\n…old key…\n-----END PUBLIC KEY-----\n"}'
```

::

::warning
If a private key **leaked**, do not keep it in `previousPublicKeys`: its tokens would stay valid for the overlap period.
Replace the key, leave `previousPublicKeys` empty, and use **Sign everyone out** on each application in the admin UI.
::

## Server

Server utilities are auto-imported in Nitro. Pure helpers (`matchesAllowedRoles`, `validateRedirectUri`, `parseScope`,
`resolveScope`, `normalizeWebsiteUrl`, `DEFAULT_SCOPES`, `DEFAULT_CALLBACK_PATH`), the typed route paths
(`oauthServerApi`, `oidc`, see [Routes](#routes)) and all types are importable from `@frigear-nu/oauth-server/utils`.

| Helper | Purpose |
| --- | --- |
| `requireOAuthAdmin(event)` | The admin gate (session only + `oauth:authorize`). Returns `{ userId }` or throws 401 / 403 `forbidden`. |
| `getApplication(id)` | Read an application (never includes the secret hash). |
| `requireApplication(id)` | `getApplication` or a `404 not_found`. |
| `toAdminApplicationDto(application, activeGrants?)`, `applicationCallbackUrl(application)` | The admin DTO, and the redirect URI an application has to accept (`websiteUrl` + `callbackPath`). |
| `createApplication(input, ownerId?)` | Returns `{ application, secret }`. The secret is only available now, and is `null` for a [public client](#public-clients). |
| `updateApplication(id, patch)`, `deleteApplication(id)` | Validated like the admin API. |
| `rotateApplicationSecret(id)` | New secret; the old one stops working and refresh tokens are revoked. Throws `400` for public clients. |
| `authenticateClient(event, body)` | Authenticates the client of a token or revocation request (secret for confidential clients, `client_id` only for public ones). |
| `listUserApplications(userId, event?)` | Active applications the user may sign in to, highest priority first. |
| `userCanAccessApplication(userId, application, event?)` | Role check plus `oauth:application:access`. |
| `resolveUserRoles(userId, event?)` | Runs `oauth:user:roles`. |
| `revokeUserGrants(userId, applicationId?)` | Ends a user's refresh tokens (all, or for one application). Call it when a user loses a role. |
| `revokeApplicationGrants(applicationId)` | Signs everyone out of an application. |
| `getOAuthUser(userId)` | The user without the password hash, including host-added columns. |

```ts
// server/api/shop/connect.post.ts
export default defineEventHandler(async (event) => {
  const { userId } = await requireOAuthAdmin(event)
  const { application, secret } = await createApplication({
    name: 'Shop',
    websiteUrl: 'https://shop.example.com',
    allowedRoles: ['member'],
    tags: ['shop'],
  }, userId)
  return { clientId: application.id, clientSecret: secret }
})
```

```ts
interface ApplicationInput {
  clientType?: 'confidential' | 'public' // default confidential; fixed after creation
  name: string
  websiteUrl: string // an origin without a path; https (http only for localhost)
  description?: string | null
  icon?: string | null
  priority?: number
  loginUrl?: string | null
  previewUrlPattern?: string | null // e.g. https://*.vercel.app
  redirectUris?: string[] // extra exact redirect URIs; public clients may list custom-scheme URIs
  allowedRoles?: string[] // empty = every signed-in user
  tags?: string[]
  isActive?: boolean
}

interface OAuthApplication extends Omit<Required<ApplicationInput>, 'isActive'> {
  id: string // `app_` + random id: the OAuth `client_id`
  ownerId: number | null
  isActive: boolean
  createdAt: Date
  updatedAt: Date
}
```

`OAuthApplication` never includes the secret hash. The admin API returns `AdminApplicationDto`
(`OAuthApplication` with ISO date strings, `activeGrants?` and `callbackUrl`) and creation returns
`CreatedApplicationDto` (that plus `clientId` and `clientSecret`, which is `null` for a public client).

### API access

An application can call this app's API as the user who signed in to it. Send the access token as
`Authorization: Bearer <access_token>`: routes that use `requireAuth` / `requireUser` from [Auth](/modules/auth) see the
user, and `principal.client.id` identifies the application.

- **Scopes.** An application may request `openid profile email`, the scopes in `oauthServer.scopes` and every API scope
  that modules register (`tickets:read`, `subscriptions:read`, ...). The consent screen lists them, and a route that
  requires a scope the user did not grant answers `403 insufficient_scope`.
- **Scopes a user may not hold are dropped.** An API scope is only granted to users who may pick it for an API token
  (the scope's `roles`, the `auth:scope-available` hook of [Auth](/modules/auth)). `users:read` of
  [Users](/modules/users#reading-users-with-a-token-usersread) is staff only: a plain user who approves
  `scope=openid users:read` gets a token with `openid` only, and the consent screen does not list it. The check runs
  again at every token exchange and refresh, so a user who loses the scope gets tokens without it. Routes still apply
  their own policy on every request.
- **How scopes read on the consent screen.** `openid`, `profile` and `email` have built-in, translated labels. For
  your own scopes, pass details in `oauthServer.scopes`; otherwise an API scope shows the `description` it was
  registered with through `addAuthScope`, and anything else its name:

  ```ts
  oauthServer: {
    scopes: [
      { name: 'bills:read', label: 'View your bills', description: 'See bills, due dates and amounts', icon: 'i-lucide-receipt' },
      'groups',
    ],
  }
  ```
- **Live checks.** On every call the application must still be active and the user must exist and pass the
  application's role requirement and `oauth:application:access`. Otherwise the call is `401`.
- **Not everything.** Account-level routes are session-only, so an access token never changes a password or passkeys.
- **Only access tokens.** ID tokens (`typ: JWT`) are not accepted as credentials.

### One app for every service

frigear.nu can be the only sign-in of one mobile app that talks to every Frigear service (vouchers, shop, inventory,
...). The app is one [public client](#public-clients); the services are resource servers that run no OAuth server of
their own and accept frigear.nu's access tokens with [Frigear Resource](/modules/frigear-resource).

```ts
oauthServer: {
  issuer: 'https://frigear.nu',
  // Every access token is for all services, and short-lived: services cannot revoke it.
  accessTokenAudience: 'frigear-services',
  accessTokenTtl: 600,
  scopes: [
    { name: 'vouchers:read', description: 'See your vouchers', service: 'Vouchers' },
    { name: 'vouchers:write', description: 'Redeem your vouchers', service: 'Vouchers' },
    { name: 'shop:order', description: 'Place orders in the shop', service: 'Shop' },
    { name: 'inventory:read', description: 'See the inventory', service: 'Inventory', staffOnly: true },
  ],
  cors: { origins: ['capacitor://localhost', 'https://localhost'] },
}
```

- **The scope registry.** `oauthServer.scopes` lists the scopes of every service. A module adds its own from `setup()`;
  the host's entry for the same name wins, so the host can reword it:

  ```ts
  import { addOAuthScope } from '@frigear-nu/oauth-server'

  addOAuthScope(nuxt, { name: 'inventory:write', description: 'Change the inventory', service: 'Inventory', staffOnly: true })
  ```
- **Staff-only scopes.** A `staffOnly` scope is only granted to users the host calls staff through the
  `oauth:scope:staff` hook (denied by default). Like `users:read`, it is dropped for everyone else at consent, at the
  code exchange and at every refresh: the token simply lacks it, and the service answers `403 insufficient_scope`.

  ```ts
  nitroApp.hooks.hook('oauth:scope:staff', async (ctx) => {
    ctx.allowed = await isStaff(ctx.userId) // ctx.scope names the scope, to decide per scope
  })
  ```
- **One consent.** The consent screen lists the requested scopes grouped by `service` (`ConsentDto.groups`), the
  account's own scopes (`openid`, `profile`, `email`, API scopes of this app) first. A scope with only a `description`
  shows it as its title.
- **The mobile app** is a public application with its native redirect URI (`nu.frigear.app:/callback`) and no
  secret. It signs in with PKCE, asks for `openid profile email vouchers:read shop:order ...` and keeps the rotating
  refresh token.
- **Access tokens** are `at+jwt` (RFC 9068) with `iss`, `sub`, `aud` (the shared audience), `exp`, `iat`, `jti`,
  `client_id` and `scope`, signed with the key in the [JWKS](#signing-keys). They carry no profile: a service reads it
  once from userinfo with the token (so ask for `email`).
- **Not yet:** [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707) resource indicators (one audience per service). Every
  service accepts every token of the shared audience and relies on the scopes.

## App

```ts
const { query } = useTableQuery({ sort: { id: 'createdAt', desc: true } })
const admin = await useOAuthApplications(query) // admin CRUD and one page of the list (applications, total, loading, refreshing, error, refresh)
const mine = await useMyApplications() // the signed-in user's applications: { applications, loading, error, refresh }
```

`useOAuthApplicationActions()` owns the admin actions for one application: `create` and `edit` (a `FormSlideover`
opened through `useOverlay()`), `remove` and `signOutEveryone` (confirm dialogs), `toggle`, `rotateSecret`,
`copyClientId` and `menu(application)` for the row menu. Creating an application or replacing its secret shows the
credentials once in a modal.

`useOAuthApplications(query?)` is awaitable, like `useMyApplications()`, so the admin page renders its list on the
server. The list is paginated: pass `useTableQuery().query` (`page`, `pageSize`, `q` over the name and client id,
`sort` = `createdAt` | `name` | `priority`, `order`) and read `applications` (the page's items) and `total`. It has no
`default` data, so `applications` is empty until loaded and after an error (check `loading` and `error` first).
`oauthApplicationsApi` holds the same endpoints as plain calls (`remove` resolves with `null`, `revokeGrants` with the
application).

All three are auto-imported and also exported from `@frigear-nu/oauth-server/composables`.

The pages follow the [UX patterns](/getting-started/ux-patterns): the admin page is a `PageHeading` with an
**Add application** action over a search `PageToolbar` and a paginated `TableCard` with a `RowMenu` per row (Edit, Copy client ID, Disable, New client
secret, Sign everyone out, then **Delete application**), the consent screen is a card in the `AuthCard` style (the
application's icon or initial, its domain, the signed-in account with a **Not you?** switch, the scopes with icon, label
and description, and full-width **Allow** / **Deny** buttons on phones) and `/account/applications`
renders its own `PageHeading` over a `SectionCard` with a divided list of the user's applications (icon, name, website
and an **Open** button).

An application is a light entity, so its edit form lives in the URL: `/admin/oauth?application=<id>`. Opening the form
from a row sets the parameter (with `replace`, so Back leaves the page), closing it clears the parameter, and loading
the URL opens that application's form. Link to it from ⌘K or another page instead of passing state.

With [Menu](/modules/menu), the module adds an **Applications** item (order 50) to the `account` menu (the account
tile and left navigation), and with the admin page an **OAuth applications** item to the Settings group of the admin
sidebar (`admin.nav.settings`, order 40). The admin item is a link only: the page and API stay gated by
`oauth:authorize`.

## Hooks

Nitro runtime hooks; implement them from a Nitro plugin in the host app.

| Hook | When | Payload |
| --- | --- | --- |
| `oauth:authorize` | An admin request needs a decision | `AuthorizeContext`: set `allowed = true`. **Denied by default.** |
| `oauth:user:roles` | The roles of a user are needed | `UserRolesContext`: push to `roles`. **No roles by default.** |
| `oauth:scope:staff` | A `staffOnly` scope is about to be granted | `StaffScopeContext`: set `allowed = true` for staff. **Denied by default.** |
| `oauth:application:access` | After the role check | `ApplicationAccessContext`: set `allowed = false` (and `reason`) to veto. |
| `oauth:claims` | An ID token, access token or userinfo response is built | `ClaimsContext`: mutate `claims`. |
| `oauth:token:issued` | Tokens were issued (code exchange or refresh) | `TokenIssuedContext` |
| `oauth:token:revoked` | A refresh token family was revoked | `TokenRevokedContext` |

```ts
type AuthorizeContext = { event: H3Event, userId: number, allowed: boolean }

type StaffScopeContext = { event: H3Event, userId: number, scope: string, allowed: boolean }

type UserRolesContext = {
  event?: H3Event // undefined for background calls such as listUserApplications(userId)
  userId: number
  roles: string[] // several listeners add up
}

type ApplicationAccessContext = {
  event?: H3Event
  user: OAuthUser
  application: OAuthApplication
  roles: string[] // resolved through oauth:user:roles
  allowed: boolean // true when the role check passed
  reason?: string // shown to the user as the 403 message
}

type ClaimsContext = {
  user: OAuthUser
  application: OAuthApplication
  scope: string[] // granted scopes
  roles: string[]
  tokenType: 'id_token' | 'access_token' | 'userinfo'
  claims: Record<string, unknown> // standard registered claims are re-applied afterwards
}

type TokenIssuedContext = { userId: number, applicationId: string, scope: string[], grant: 'authorization_code' | 'refresh_token' }
type TokenRevokedContext = { applicationId: string, userId: number | null, reason: 'revoked' | 'reuse_detected' | 'user_grants_revoked' }

type OAuthUser = { id: number, name: string, email: string, avatar: string | null } & Record<string, unknown>
```

### Resolving roles

An application has `allowedRoles: string[]`. A user may sign in when they hold **at least one** of them; an **empty list
means every signed-in user**. A non-empty list with a host that reports no roles locks everybody out. The module has no
role model: you push roles onto `ctx.roles`.

::code-group

```ts [A role column on users]
// With @frigear-nu/authorization the `users` table has a `role` column
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId) // the users row, including host-added columns
    if (user?.role) ctx.roles.push(String(user.role))
  })
})
```

```ts [A separate user_roles table]
import { eq } from 'drizzle-orm'
import { db, schema } from '@nuxthub/db'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const rows = await db.select({ role: schema.userRoles.role })
      .from(schema.userRoles)
      .where(eq(schema.userRoles.userId, ctx.userId))
    ctx.roles.push(...rows.map(row => row.role))
  })
})
```

```ts [Derived from other data]
import { hasActiveSubscription } from '@frigear-nu/subscriptions/utils'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId)
    if (user?.email.endsWith('@frigear.nu')) ctx.roles.push('staff')
    if (await hasActiveSubscription(ctx.userId)) ctx.roles.push('member')
  })
})
```

```ts [A role hierarchy]
// `admin` implies `manager` implies `member`: expand so applications only list the lowest one.
const implied: Record<string, string[]> = { admin: ['manager', 'member'], manager: ['member'] }

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId)
    const role = String(user?.role ?? 'user')
    ctx.roles.push(role, ...(implied[role] ?? []))
  })
})
```

::

Load what you need by `ctx.userId`; do not depend on the session in this hook. Roles are checked at the authorization
entry, on the consent page, on approval, on every token exchange and on `userinfo`.

### Who is an admin

The admin routes call `requireOAuthAdmin(event)`: `401` when signed out, `403` unless a listener sets
`ctx.allowed = true`.

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:authorize', async (ctx) => {
    const user = await getOAuthUser(ctx.userId) // identify the caller from ctx.userId
    ctx.allowed = user?.role === 'admin'
  })
})
```

### Enriching tokens and userinfo

`oauth:claims` runs for every token and for `userinfo`. The module has already put the standard profile claims there for
the granted scopes. Registered claims (`iss`, `sub`, `aud`, `exp`, `iat`, `nbf`, `jti`, `nonce`, `auth_time`, `scope`,
`client_id`) are re-applied afterwards, so they cannot be overwritten.

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:claims', async (ctx) => {
    // Access tokens stay bare, so only the ID token and userinfo get identity claims.
    if (ctx.tokenType === 'access_token') return

    ctx.claims['https://frigear.nu/claims/role'] = ctx.roles[0] ?? 'user'

    // A custom scope: list it in `oauthServer.scopes: ['groups']`, applications then request `scope=openid groups`
    if (ctx.scope.includes('groups')) ctx.claims.groups = ctx.roles

    // Per application
    if (ctx.application.tags.includes('shop')) ctx.claims.customer_id = await customerIdFor(ctx.user.id)

    // Remove something
    if (!ctx.scope.includes('email')) delete ctx.claims.email
  })
})
```

[Preferences](/modules/preferences#oauth-claims) uses this hook to forward user preferences as claims.

### Vetoing access and auditing

```ts
export default defineNitroPlugin((nitro) => {
  // After the role check: e.g. only users with a verified email, or a suspended flag
  nitro.hooks.hook('oauth:application:access', (ctx) => {
    if (ctx.user.suspended) {
      ctx.allowed = false
      ctx.reason = 'Your account is suspended.'
    }
  })

  nitro.hooks.hook('oauth:token:issued', ({ userId, applicationId, grant }) => {
    console.info(`[oauth] tokens issued to user ${userId} for ${applicationId} (${grant})`)
  })
  nitro.hooks.hook('oauth:token:revoked', ({ applicationId, userId, reason }) => {
    console.warn(`[oauth] revoked ${applicationId}/${userId}: ${reason}`)
  })
})
```

## Routes

Paths are typed in `@frigear-nu/oauth-server/utils`: `oauthServerApi` for the module API
(`oauthServerApi.admin.application(id)`, ...) and `oidc` for the spec endpoints (`oidc.token`, ...). Use them instead of
string literals.

The OAuth / OpenID Connect endpoints keep their standard paths and answer spec-shaped bodies: `token` and `revoke` reply
`{ error, error_description }` (RFC 6749 §5.2) to every failure, including a malformed body (`400 invalid_request`).

| Method | Path | Auth | Status | Purpose |
| --- | --- | --- | --- | --- |
| `GET` | `/.well-known/openid-configuration` | none | 200 | Discovery document. |
| `GET` | `/.well-known/jwks.json` | none | 200 | Public signing keys. |
| `GET` | `/oauth/authorize` | none (signed-out users go to the login page) | 302 | Authorization request: validates it (`400` otherwise), checks access (`403`), then redirects to the consent page. |
| `POST` | `/oauth/authorize` | session only | 200 | The consent decision; answers `{ redirectUrl }` (the callback with `code` and `state`, or `error=access_denied`). |
| `POST` | `/oauth/token` | client credentials, or `client_id` for [public clients](#public-clients) | 200 | `authorization_code` and `refresh_token` grants. HTTP Basic or `client_id` + `client_secret` in the body. |
| `POST` | `/oauth/revoke` | client credentials, or `client_id` for [public clients](#public-clients) | 200 | Revokes a refresh token and the rest of its family (RFC 7009). |
| `GET` | `/oauth/userinfo` | bearer access token | 200 | Claims filtered by scope. |
| `GET` | `/api/oauth-server/consent` | session only | 200 | Data for the consent screen (`ConsentDto`); the query is the authorization request. |
| `GET` | `/api/oauth-server/me/applications` | session only | 200 | Applications the user may sign in to (`UserApplicationDto[]`). |
| `GET` | `/api/admin/oauth-server/applications` | session + `oauth:authorize` | 200 | One page `{ items, total, page, pageSize }` of `AdminApplicationDto`; `page`, `pageSize` (max 100), `q` (name or client id), `sort` (`createdAt`, `name`, `priority`), `order`. |
| `POST` | `/api/admin/oauth-server/applications` | session + `oauth:authorize` | 201 | Create; returns `CreatedApplicationDto` (the secret, shown once). |
| `GET` | `/api/admin/oauth-server/applications/:id` | session + `oauth:authorize` | 200 | One application (`AdminApplicationDto`). |
| `PATCH` | `/api/admin/oauth-server/applications/:id` | session + `oauth:authorize` | 200 | Update; returns the application. Disabling it signs everyone out. |
| `DELETE` | `/api/admin/oauth-server/applications/:id` | session + `oauth:authorize` | 204 | Delete, with its codes and refresh tokens. |
| `POST` | `/api/admin/oauth-server/applications/:id/secret` | session + `oauth:authorize` | 200 | Rotate the client secret; `{ clientSecret }` once (`400 bad_request` for public clients). |
| `POST` | `/api/admin/oauth-server/applications/:id/revoke` | session + `oauth:authorize` | 200 | Sign everyone out of the application; returns the application. |

The module API fails with the [toolkit errors](/modules/module-kit#server-toolkit): `401`, `403 forbidden` (the
`oauth:authorize` gate), `404 not_found`, `400 bad_request`, and h3's `400` validation error for a malformed body or
query.

### How a sign-in works

```text
application ──▶ GET  /oauth/authorize?client_id&redirect_uri&response_type=code&state&code_challenge&code_challenge_method=S256[&scope&nonce]
                 not signed in ──▶ <login page>?redirect=/oauth/authorize?… ──▶ back here
                 role/access check (403 if denied) ──▶ /authorize?… (consent page)
user approves ──▶ POST /oauth/authorize {…, approved: true} ──▶ redirect to the application's callback with ?code&state
application ──▶ POST /oauth/token (code + code_verifier + client credentials) ──▶ access_token, id_token, refresh_token
```

- **PKCE (S256) is mandatory.** Applications are **confidential** clients with a secret, shown once when created, unless
  you register them as [public clients](#public-clients).
- **Redirect URIs are derived**, not free-form: `websiteUrl + callbackPath`, the application's explicit `redirectUris`, or
  its `previewUrlPattern` (`https://*.vercel.app`, where `*` is one hostname label). `https` is required except for
  `localhost`. Public clients may also list [native redirect URIs](#native-redirect-uris).
- **Refresh tokens rotate.** Presenting an already-used refresh token is treated as theft and revokes the whole family.
- Access is re-checked on every token exchange, `userinfo` call and API call, so disabling an application or removing a
  role also stops refreshes and API calls.
- **Access tokens are bare** (`sub`, `scope`, `client_id`, `aud`, `iss`, `exp`, `iat`, `jti`, header `typ: at+jwt`);
  identity claims (`name`, `picture`, `email`) live in the ID token and `userinfo`, per granted scope.
- Unsupported scopes are dropped; a request with no `scope` gets `openid profile email`, and one whose scopes are all
  unsupported is rejected with `400`.

### Public clients

A native app or single-page app cannot keep a secret: anything compiled into the app is public. Register it as a
**public client** (`clientType: 'public'`, or *Client type* in the admin form; it cannot be changed afterwards):

- It gets **no client secret**. `/oauth/token` and `/oauth/revoke` identify it by `client_id` alone
  (`token_endpoint_auth_methods_supported` lists `none`), and `createApplication` returns `secret: null`.
- **PKCE (S256) is what protects the code exchange**, exactly as for confidential clients. It is already mandatory.
- **Refresh tokens rotate** and a replayed one revokes the family, which is the compensating control for a refresh token
  that can be used without a secret. Tokens stay bound to the client they were issued to: another client cannot refresh
  or revoke them.
- Sending a `client_secret` to a public client is refused (`401 invalid_client`) rather than ignored, because it means the
  app was configured with the wrong kind of client. An empty `client_secret` field is accepted.
- Confidential clients are unchanged: without their secret every token and revoke request is `401`.

#### Native redirect URIs

A public client may add **custom-scheme redirect URIs** to `redirectUris`, for the app to receive the code after the
system browser step:

- a private-use scheme, preferably the reverse of a domain you control: `com.example.app:/callback` (RFC 8252 §7.1);
- a webview origin such as `capacitor://localhost/auth/callback`.

They are matched **exactly**: no prefixes, wildcards or query strings. Web and dangerous schemes (`javascript:`, `data:`,
`file:`, `blob:`, ...), credentials and fragments are rejected when the application is saved, and a confidential client
cannot use custom schemes at all. `https` redirects (for example universal / app links) work for both client types.

::warning
A custom scheme can be claimed by any app on the device, which PKCE makes harmless for the code itself, but where the
platform offers it prefer an `https` universal/app link as the redirect.
::

#### Calling from a browser on another origin

The webview of a Capacitor app runs at `capacitor://localhost` (iOS) or `https://localhost` (Android), so its requests to
this server are cross-origin. List those origins in `cors.origins`:

```ts
export default defineNuxtConfig({
  oauthServer: {
    cors: { origins: ['capacitor://localhost', 'https://localhost'] },
  },
})
```

- Only `/oauth/token`, `/oauth/revoke`, `/oauth/userinfo` and the `/.well-known` documents answer CORS requests, and only
  for listed origins. `/oauth/authorize` is a top-level navigation with the user's cookie session, and is never opened up.
- No `Access-Control-Allow-Credentials` is sent, so cookies never travel cross-origin; the app authenticates with
  its client id and bearer tokens.
- Your own API routes are not covered: add CORS for them in the host app (the access token is sent as
  `Authorization: Bearer`).
- Origins must be exact (`scheme://host[:port]`). `*` is rejected when the app starts.

### The application side

Register the application in the admin UI (or with `createApplication`), then configure it with the **client ID**
(`app_…`) and **client secret**. The whole flow with `curl`:

```bash
# 1. PKCE pair
VERIFIER=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)
CHALLENGE=$(printf %s "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')

# 2. Open in a browser, sign in and approve. You are redirected to the callback with ?code=…&state=…
echo "https://id.example.com/oauth/authorize?client_id=$CLIENT_ID&redirect_uri=https://app.example.com/auth/frigear&response_type=code&state=xyz&scope=openid%20profile%20email&nonce=n1&code_challenge=$CHALLENGE&code_challenge_method=S256"

# 3. Exchange the code
curl -s https://id.example.com/oauth/token \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=authorization_code -d code="$CODE" -d code_verifier="$VERIFIER" \
  -d redirect_uri=https://app.example.com/auth/frigear

# 4. Refresh (the returned refresh_token replaces the old one)
curl -s https://id.example.com/oauth/token -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=refresh_token -d refresh_token="$REFRESH_TOKEN"

# 5. Userinfo
curl -s https://id.example.com/oauth/userinfo -H "Authorization: Bearer $ACCESS_TOKEN"
```

Verify the ID token with any JOSE library against the JWKS (`iss`, `aud` = client ID, `nonce`):

```ts
import { createRemoteJWKSet, jwtVerify } from 'jose'

const jwks = createRemoteJWKSet(new URL('https://id.example.com/.well-known/jwks.json'))
const { payload } = await jwtVerify(idToken, jwks, { issuer: 'https://id.example.com', audience: clientId })
```

## Database

Three tables, registered through `registerDatabaseTable`; `users` is untouched and the tables store the user id without a
foreign key. Client secrets, codes and refresh tokens are stored only as SHA-256 hashes.

| Table | Holds |
| --- | --- |
| `oauth_applications` | Name, `clientType`, website/login URL, preview pattern, extra redirect URIs, `allowedRoles`, `tags`, `priority`, `isActive`, hashed secret (a public client stores the hash of a random value nobody sees, so the column stays `NOT NULL`). |
| `oauth_authorization_codes` | Single-use codes (hash only), PKCE challenge, nonce, 10 minute lifetime. |
| `oauth_refresh_tokens` | Hashed refresh tokens grouped in families for rotation and reuse detection. |

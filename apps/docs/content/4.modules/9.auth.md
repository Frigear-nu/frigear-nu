title: Auth Module
description: Sign-in (password, magic link, OAuth, passkeys), user API tokens and one requireAuth for cookie sessions, tokens and OAuth access tokens, with scopes.
---

[Nuxt module](https://nuxt.com/docs/4.x/guide/modules) that owns **authentication**: how people sign in (password, magic
link, OAuth, passkeys), and for every server route, **who is calling, and how?** It sits at the bottom of the stack:
[`@frigear-nu/users`](/modules/users), the [authorization](/modules/authorization) module, the
[OAuth server](/modules/oauth-server) and every feature module build on it, and it does not depend on any of them. It
knows users only through a small store that `@frigear-nu/users` provides (see [Provide the user store](#provide-the-user-store)).

A caller is one of three things, all resolved into the same `AuthPrincipal`:

| `kind`       | Credential                                                | Scopes                         |
| ------------ | --------------------------------------------------------- | ------------------------------ |
| `session`    | The sealed cookie from [nuxt-auth-utils](https://github.com/atinux/nuxt-auth-utils) | Everything (`*`)               |
| `user-token` | `Authorization: Bearer fnu_…`, a static token the user created | The scopes chosen at creation  |
| `oauth`      | `Authorization: Bearer <JWT>`, an access token issued to an application | The scopes the user granted    |

## Quick Setup

```bash
pnpm add @frigear-nu/auth
```

`@frigear-nu/users` installs it for you. Add it yourself when you use it on its own:

```ts
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/auth'],
})
```

The module owns these tables: `auth_user_tokens`, and, when the feature is on, `user_credentials` (passkeys),
`password_resets` and `magic_links`. None has a foreign key to `users`: this module sits below it, so whoever deletes a
user calls `deleteUserAuthData(userId)` (the users admin does). It also adds the credential columns `password`,
`email_verified_at` and `last_login_at` to the `users` table owned by `@frigear-nu/users` (ignored without it). It only
changes the generated Drizzle schema, so generate and commit a migration in your app, and in every fixture that includes
the module - see [Migrations and database-backed module tests](/modules/module-kit).

::note
The config key is `authentication`, not `auth`: `auth` belongs to nuxt-auth-utils.
::

## Signing in

### Settings

Configure email/password, password reset, passkeys, pages, session mapping and OAuth under `authentication.settings`:

```ts
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/auth'],
  authentication: {
    settings: {
      // Enable/disable email + password login & register routes, composables and pages.
      // Defaults to `true`.
      password: true,
      // Enable/disable the "forgot password"/"reset password" routes & composable. Requires
      // `password` to be enabled. Defaults to `true` whenever `password` is enabled.
      passwordReset: true,
      // Enable passkey (WebAuthn) registration/authentication routes, composables and DB table.
      // Requires the optional `@simplewebauthn/browser` and `@simplewebauthn/server` peer deps.
      // Defaults to `false`.
      webAuthn: false,
      // Passwordless sign-in by emailed link. Following the link also verifies the email address.
      // `{ signUp: true }` creates an account for unknown addresses; `{ cooldown: 60 }` is the minimum seconds
      // between two links for one user. Defaults to off.
      magicLink: false,
      // Users who register with email/password must verify their address (emailed link) before they
      // can log in; registration creates no session. Defaults to off.
      verifyEmail: false,
      // Cron for `auth:clear-expired-tokens` (expired magic links/password resets), `false` to not
      // schedule it. Defaults to daily at 03:00.
      cleanup: '0 3 * * *',
      // Registers the login/register pages, built with `@nuxt/ui` (an optional peer dependency,
      // required only when a page is enabled). Off by default; set to `true` for the default
      // path (`/login`, `/register`) or a custom path string to opt in.
      pages: {
        login: true,
        register: '/sign-up',
      },
      session: {
        // Path to a function (default export) mapping the raw DB user to the session user shape.
        mapper: '~/server/utils/map-session-user',
      },
      // Registers the "simple" OAuth routes we ship (`/api/auth/github`, `/api/auth/google`).
      // Each provider's client id/secret are read by nuxt-auth-utils itself from the standard
      // `NUXT_OAUTH_<PROVIDER>_CLIENT_ID` / `NUXT_OAUTH_<PROVIDER>_CLIENT_SECRET` env vars.
      // Route registration depends only on these flags. Any other provider supported by
      // nuxt-auth-utils can be added directly in the consuming app.
      oauth: {
        github: true,
        google: true,
        facebook: true,
        // "Log in with frigear.nu" (OIDC), see "Log in with frigear.nu" below.
        frigear: true,
      },
    },
  },
})
```


### Log in with frigear.nu

`oauth.frigear` registers `GET /api/auth/frigear`, an OIDC login against frigear.nu built on nuxt-auth-utils'
`defineOAuthOidcEventHandler`. It is meant for PR previews and local development, and is decided **per request**:
it is active when `runtimeConfig.previewDeployment` is `true` or `runtimeConfig.frigear.sso` has a client id and secret.
Otherwise the route answers `404` and the login button is hidden (`public.authentication.frigearSso`).

```ts
// nuxt.config.ts
runtimeConfig: {
  previewDeployment: !!process.env.PR_NUMBER, // NUXT_PREVIEW_DEPLOYMENT
  frigear: {
    sso: {
      url: process.env.FRIGEAR_SSO_URL || '', // https://frigear.nu
      clientId: process.env.FRIGEAR_SSO_CLIENT_ID || '',
      clientSecret: process.env.FRIGEAR_SSO_CLIENT_SECRET || '',
    },
    forceId: false, // NUXT_FRIGEAR_FORCE_ID
  },
}
```

Instead of `frigear.sso` the credentials can come from nuxt-auth-utils' own `NUXT_OAUTH_OIDC_CLIENT_ID`,
`NUXT_OAUTH_OIDC_CLIENT_SECRET` and `NUXT_OAUTH_OIDC_OPENID_CONFIG`. The OAuth app on frigear.nu needs the callback
`<origin>/api/auth/frigear` (for example `http://localhost:3045/api/auth/frigear`).

- The `id_token` is verified against the keys at frigear.nu's `jwks_uri` (`/.well-known/jwks.json`, cached for an hour),
  including issuer and audience. Users are matched by email; a verified `email_verified` claim verifies the address.
- `forceId: true` makes the local `users.id` equal to the frigear.nu user id. A user with that id is updated, an
  existing user with the same email is re-keyed to it (rows in other tables that reference `users.id` follow in one
  batch; a different user holding the id moves to the next free id), otherwise a user is created with that id.
- The optional `color_mode` claim (`light`, `dark` or `system`) is kept on the session as `frigear.colorMode` and
  applied once per login.
- `settings.pages.register` may be an absolute URL (such as `https://frigear.nu/sign-up`): the login page links to it
  and no local register page is added.

The password-reset email is dispatched as an `EmailNotification` through [`@frigear-nu/notify`](/modules/notify),
which this module declares as a `moduleDependency` (it's installed automatically - no need to add it to `modules`
yourself). Which driver actually delivers it is an app/deployment concern, so it's configured separately, under the
`notify` key - see the [notify module docs](/modules/notify) for the available drivers.


### Routes


| Route | Enabled by | Description |
| --- | --- | --- |
| `POST /api/auth/login` | `settings.password` | Email/password login |
| `POST /api/auth/register` | `settings.password` | Email/password registration |
| `POST /api/auth/forgot-password` | `settings.passwordReset` | Request a password reset email for an `email` |
| `POST /api/auth/reset-password` | `settings.passwordReset` | Reset the password given a reset `code`, `password` & `confirmPassword`, and sign in |
| `POST /api/auth/webauthn/register` | `settings.webAuthn` | Register a new passkey |
| `POST /api/auth/webauthn/authenticate` | `settings.webAuthn` | Authenticate with a passkey |
| `GET /api/auth/webauthn/credentials` | `settings.webAuthn` | List the current user's passkeys |
| `DELETE /api/auth/webauthn/credentials/:id` | `settings.webAuthn` | Remove one of the current user's passkeys |
| `POST /api/auth/magic-link` | `settings.magicLink` | Email a single-use sign-in link (always answers `{ ok: true }`; one link per user per minute) |
| `GET /auth/magic-link?code=` | `settings.magicLink` or `settings.verifyEmail` | Consumes the link, verifies the email, signs in and redirects (bad links go to the login page with `?error=magic-link`) |
| `GET /api/auth/github`, `/google`, `/facebook` | `settings.oauth.<provider>` | "Simple" OAuth login |
| `GET /api/auth/frigear` | `settings.oauth.frigear` | Log in with frigear.nu (previews, or when `runtimeConfig.frigear.sso` is set; `404` otherwise) |

### Composables


#### `useLogin`

Handles everything to do with regular login - e.g email / password.

`login(payload: { email: string, password: string }): Promise<void>`

Additional exported properties:

```ts
const {
  isEnabled,
  passwordLoginEnabled,
  passkeyLoginEnabled,
  oauthProviders,
  login,
} = useLogin();
```

#### `usePasskeys`

This composable handles passkeys, auth and storage as a user.

```ts
const {
  isEnabled,
  registerPasskey,
  authenticateWithPasskey,
  listPasskeys,
  removePasskey,
} = usePasskeys();

await registerPasskey(user.email, 'MacBook') // the name is optional and shown in the passkey list
const passkeys = await listPasskeys() // [{ id, name, createdAt, counter, backedUp, transports }] - never the public key
await removePasskey(passkeys[0].id) // only removes passkeys owned by the signed-in user (404 otherwise)
```

#### `useRegistration`

Handles all sign-up related activity
`async function register(payload: { name: string, email: string, password: string }): Promise<void>`

Additional exports:

```ts
const {
  register,
  pending,
  error,
  isEnabled,
} = useRegistration();
```

#### `usePasswordReset`

Wraps the forgot/reset-password routes, enabled via `settings.passwordReset`.

```ts
const {
  requestReset,
  resetPassword,
  pending,
  error,
  isEnabled,
} = usePasswordReset();
```

- `requestReset(payload: { email: string }): Promise<void>` - requests a password reset email for `email`.
- `resetPassword(payload: { code: string, password: string, confirmPassword: string }): Promise<void>` - resets the
  password given the reset `code` from the email, then signs the user in.

All composables are registered via Nuxt's import ecosystem, so they can be overridden by re-declaring a composable of
the same name in the consuming app.


### Auth emails

Magic link and verification emails are built as `EmailNotification`s and dispatched through
[`@frigear-nu/notify`](/modules/notify). To brand them, replace the subject/body in the `auth:email` Nitro hook
(`ctx.type` is `magic-link` or `verify-email`; `ctx.data` has the recipient's `name` and the link `url`):

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('auth:email', (ctx) => {
    ctx.notification.subject = 'Velkommen til Frigear'
    ctx.notification.body = renderMyTemplate(ctx.data)
  })
})
```

#### `useMagicLink`

`sendMagicLink({ email, name?, redirect? })`, plus `pending`, `error` and `isEnabled`. `redirect` must be a same-origin
path. The shipped login page renders the form and the "invalid link" alert when this is enabled.


The login page reads where it lives with `useAuthPages()` (`{ login, register }`, `/login` by default), and server code with `getLoginPath(event)`, so a host's custom path (`pages.login`) is respected everywhere.

The session user is built by `mapUserToSession(storedUser)`, which strips the password hash and applies `session.mapper`. Modules that change the user (the profile, email and password routes of `@frigear-nu/users`) use it to refresh the session.

### Tables

`user_credentials` (one row per passkey, only with `webAuthn`), `password_resets` (a unique reset `code` with `expiresAt` / `usedAt`, only with `passwordReset`) and `magic_links` (a unique single-use `code`, an optional internal `redirectUrl`, `expiresAt` / `usedAt`; with `magicLink` or `verifyEmail`). Links expire after 2 hours and are consumed atomically, so a link can't be replayed.

### Translations

The module registers `da` and `en` locale files with [module-kit](/modules/module-kit#translations-i18n). The auth
pages and forms read them from the `auth.*` namespace through `@nuxtjs/i18n`; when it is not installed the English
defaults are used. Override any string in your app's `i18n/locales/<code>.json` (see
[overriding module strings](/modules/module-kit#overriding-module-strings-in-your-app)):

```json
{ "auth": { "signIn": "Log in", "email": { "label": "Your email" } } }
```

Key groups: `signIn`, `signUp`, `signOut`, `signedInAs`, `name.*`, `email.*` (including `email.sent.*`), `password.*`,
`forgotPassword.*`, `resetPassword.*`, `magicLink.*`, `verifyEmail.*`, `confirm.*`, `passkey.*`, `emailPassword.*`,
`passkeys.*`, `oauth.<provider>.label` and `errors.*`.


## Protecting a route

Use `requireAuth` instead of `requireUserSession`. Both are auto-imported in server code.

```ts
// server/api/tickets.get.ts
export default defineEventHandler(async (event) => {
  const { user } = await requireAuth(event, { scopes: ['tickets:read'] })
  return getTickets(user.id)
})
```

| Call                                         | Behaviour                                                                          |
| -------------------------------------------- | ---------------------------------------------------------------------------------- |
| `requireAuth(event)`                         | The principal (`kind`, `user`, `scopes`, `client`, `token`), from any credential. `401` without a valid one. |
| `requireAuth(event, { scopes: [...] })`      | Also needs every scope. `403 insufficient_scope` otherwise. Sessions pass.         |
| `requireAuth(event, { sessionOnly: true })`  | Cookie sessions only. `403 session_required` for tokens.                           |
| `getAuth(event)`                             | The principal or `null`. Never throws.                                             |

[`@frigear-nu/users`](/modules/users) builds the user-shaped helpers on top: `requireUser(event, options)` returns just
the user and `getUser(event, { scopes })` the user or `null`, for routes open to everyone that personalise for a
signed-in user. Use `requireAuth` when the route only needs to know who and how, and `requireUser` when it needs the user.

### Which routes should accept tokens?

Choose per route, and default to **session only** for anything that changes who the user is or how they sign in:

- **Scopes** (`scopes: [...]`): reads and actions an integration plausibly needs - tickets, subscriptions, form
  submissions.
- **`sessionOnly: true`**: changing the password or email, passkeys, the profile, cookie consent, the billing portal,
  OAuth consent, the users admin, and managing API tokens. A leaked token must not be able to take over the account.

Roles stay authoritative. A token never carries a role: the user is loaded from the database on **every** request, so
a role change, a ban or a deleted account applies to the next call. This differs from the cookie session, which holds a
snapshot from login time. Policy hooks such as `events:authorize` receive the user id from `requireAuth` and keep
working unchanged. A module defines such a hook with `definePolicyGate('events:authorize')` and offers staff-only scopes
with `defineStaffScopes([...], isAllowed)`.

## Scopes

Scopes are `resource:action` strings. `*` grants everything, and `resource:*` grants every action of one resource.
Personal-data scopes (named `resource:pii`, e.g. `events:pii`) are the exception: neither `*` ("Full access") nor `resource:*`
covers them, so a token only sees other people's personal data when the user picked that scope explicitly. Sessions are
full access too, so tools that return personal data through [MCP](/modules/mcp) strip it for them as well.
A token can never do more than its owner can: scopes only narrow.
A scope is also only offered to users who may use it: the token UI lists, and `POST /api/auth/tokens` accepts, just the
scopes available to the signed-in user. Restrict a scope to roles with `roles` in `addAuthScope`, or for policy that is
not role based (like the `events:authorize` and `forms:authorize` staff hooks, which hide `events:manage` / `forms:manage`
and their `:pii` scopes from non-staff) set `ctx.available = false` in the `auth:scope-available` Nitro hook:

```ts
addAuthScope(nuxt, { name: 'reports:admin', description: 'Run reports', roles: ['admin'] })

nitroApp.hooks.hook('auth:scope-available', (ctx) => {
  if (ctx.scope.name === 'reports:export') ctx.available = canExport(ctx.user.id)
})
```

Modules register the scopes they understand, and they show up in the token UI and are accepted from OAuth applications:

```ts
// in a module's setup()
import { addAuthScope } from '@frigear-nu/auth/utils'

addAuthScope(nuxt, { name: 'tickets:read', description: 'Read your tickets' })
```

The built-in modules register `events:manage`, `tickets:read`, `tickets:write`, `forms:manage`, `forms:submit`,
`payments:read`, `payments:write`, `subscriptions:read` and `subscriptions:write`. A host can add more with
`authentication.scopes`.

## User API tokens

Users create tokens on their account page (`/account/api-tokens`) or through the API. Tokens look like `fnu_…`.

| Route                        | Purpose                                                              |
| ---------------------------- | -------------------------------------------------------------------- |
| `GET /api/auth/tokens`       | Your tokens: name, prefix, last 4, scopes, expiry, last use, status. |
| `POST /api/auth/tokens`      | `{ name, scopes, expiresInDays? }`. The plaintext `token` is in this response only. |
| `DELETE /api/auth/tokens/:id`| Revoke. The row is kept for the audit trail.                         |
| `GET /api/auth/scopes`       | The scopes that can be granted.                                      |

All four are session-only. Use a token like this, for example from an MCP client:

```bash
curl -H "Authorization: Bearer fnu_…" https://example.com/api/tickets
```

Security properties:

- Only the SHA-256 of a token is stored, plus a prefix and the last four characters for display. The plaintext cannot
  be recovered, so a lost token is replaced, not looked up.
- Tokens are accepted in the `Authorization` header **only**. Query-string tokens are ignored, because URLs end up in
  logs.
- Tokens can expire (`expiresInDays`, or the `authentication.tokenTtlDays` default) and can be revoked at any time.
- `lastUsedAt` is written at most every five minutes, and a failure to write it never fails a request.

### A bad token never turns into the session

If a request carries a token the module recognises (`fnu_…`, or a JWT) and it is invalid, expired or revoked, the
request is **unauthenticated** (`401` with `WWW-Authenticate: Bearer error="invalid_token"`), even if a valid session
cookie is sent too. Tokens that no resolver claims, such as the per-form `ffk_` tokens, are ignored and the other
credentials apply as usual.

## OAuth applications calling back as the user

With the [OAuth server](/modules/oauth-server), an application the user signed in to can call this API as that user.
The access token identifies both: `principal.user` is the user and `principal.client.id` is the application.

```ts
const principal = await requireAuth(event, { scopes: ['tickets:read'] })
if (principal.kind === 'oauth') console.log(`called by application ${principal.client.id}`)
```

The OAuth server accepts every registered API scope in addition to `openid profile email`, so an application requests
what it needs (`scope=openid tickets:read`) and the consent screen lists it. On every request the token is checked
against the live state: the application must still be active, the user must still exist, and the user must still pass
the application's role requirement and the `oauth:application:access` hook. Disabling an application or changing a role
cuts access immediately instead of when the token expires.

ID tokens are not credentials. Only access tokens (`typ: at+jwt`) authenticate API calls.

::note
The token's audience is the application, so this API does not require `aud` to match the server. Verification is
signature (JWKS), issuer and type, plus the live checks above.
::

## Protecting routes of your own app

Any app that installs `@frigear-nu/auth` gets the same behaviour, including role checks built on `requireAuth`:

```ts
// server/utils/roles.ts
export async function requireRole(event: H3Event, ...roles: string[]) {
  const { user } = await requireAuth(event)
  if (!roles.includes(user.role)) throw createError({ statusCode: 403, statusMessage: 'Forbidden' })
  return user
}
```

Because the user comes from the store on token requests, `user.role` is current. For `routeRules`-based gates see the
[authorization module](/modules/authorization), whose default server resolver uses `getAuth`.

## Extending

### Provide the user store

The sign-in flows and bearer credentials read and write users through an `AuthUserStore`:
`findById`, `findByEmail`, `create`, `update`, `remove` and `changeId`. `@frigear-nu/users` registers one over the
`users` table (`setAuthUserStore(nuxt, path)` from `@frigear-nu/auth/utils`), and token requests run the loaded user
through your session mapper, so they see the same user shape as sessions. To override it, point
`authentication.userStore` at a module whose default export is an `AuthUserStore`.

### Add a credential type

A module registers a resolver for bearer tokens it recognises, by prefix or by JWT shape:

```ts
import { addAuthResolver } from '@frigear-nu/auth/utils'

addAuthResolver(nuxt, {
  name: 'my-tokens',
  prefix: 'mt_',
  resolver: resolver.resolve('./runtime/server/resolvers/my-token'),
})
```

```ts
// runtime/server/resolvers/my-token.ts: return a principal, or null when the token is invalid
export default async function (event: H3Event, token: string): Promise<AuthPrincipal | null> { … }
```

## Options

| Option        | Default | Description                                                          |
| ------------- | ------- | -------------------------------------------------------------------- |
| `tokenTtlDays`| `null`  | Default lifetime for new user tokens. `null` means they never expire. |
| `userStore`   | -       | Path to a custom `AuthUserStore` (default: the one from `@frigear-nu/users`). |
| `scopes`      | `[]`    | Extra scopes, `{ name, description }`.                               |
| `settings`    | see below | The sign-in flows.                                                 |

## MCP

A static user token is enough for an MCP server or client that sends `Authorization: Bearer …`. The
[MCP module](/modules/mcp) serves the endpoint and exposes each module's tools within the scopes of the token. Clients that expect
the full OAuth flow additionally need protected-resource metadata ([RFC 9728](https://www.rfc-editor.org/rfc/rfc9728))
and dynamic client registration, which this module does not provide yet.

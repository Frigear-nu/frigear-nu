## `@frigear-nu/users`

This [Nuxt module](https://nuxt.com/docs/4.x/guide/modules) owns **who the users are**: the `users` table, the staff
administration of users, and what a signed-in user can change about themselves (profile, email, password). How people
sign in is [`@frigear-nu/auth`](/modules/auth), which it installs and plugs into; the account pages are
[`@frigear-nu/account`](/modules/account), which call its routes.

It requires [`@nuxthub/core`](https://hub.nuxt.com) and uses [`@frigear-nu/module-kit`](/modules/module-kit) to register
its database schema.

```ts
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/users'],
  users: {
    settings: {
      // Staff user administration (`/api/admin/users`, a page, a "new members" widget). Who may do what is decided
      // by the `users:admin:authorize` hook (denied by default). `{ page: '/admin/users' }`, `{ page: false }` = API only.
      // The admin pages need `@frigear-nu/admin`; without it only the API is registered.
      admin: true,
      // A new email address only takes effect once confirmed from its inbox; the old address gets a revert link.
      verifyEmailChange: true,
      // Where the confirmation link lands (`?email-changed=1` / `?error=email-change`). Defaults to `/`.
      profilePath: '/account/profile',
      // Expose the `get-my-profile` MCP tool (installs `@frigear-nu/mcp`). Defaults to `false`.
      mcp: false,
    },
  },
})
```

### `requireUser` and `getUser`

Server routes call `requireUser(event, options)` for the signed-in user and `getUser(event, { scopes })` for the user or
`null`. They are thin helpers over [`requireAuth` / `getAuth`](/modules/auth#protecting-a-route) with the same options
(`scopes`, `sessionOnly`) and the same `401` / `403` behaviour; use `requireAuth` when the route needs the principal
(how the caller authenticated) rather than the user. Anything that changes who the user is or how they sign in must pass
`{ sessionOnly: true }`.

### Self-service routes

All require a cookie session and refresh the session user afterwards.

| Route | Description |
| --- | --- |
| `POST /api/users/me/profile` | Updates `name` / `avatar`. |
| `POST /api/users/me/change-email` | Updates `email` (`409` when taken). With `verifyEmailChange` it only stores the request and emails the new address. |
| `POST /api/users/me/change-password` | Verifies `currentPassword`, updates to `newPassword` and emails a notice (a failing mail never undoes the change). |
| `GET /auth/verify-email-change?code=` | `verifyEmailChange`: applies the change (single use, valid 24 hours), marks the address verified and emails the old address a revert link. |
| `GET /auth/revert-email-change?code=` | `verifyEmailChange`: puts the old address back (valid 7 days), signs the user out and redirects to the login page with `?email-reverted=1`. |

With `verifyEmailChange` requests are kept in `account_email_changes`. The notices go through
[`@frigear-nu/notify`](/modules/notify).

With `settings.mcp` the module registers the `get-my-profile` MCP tool (scope `profile:read`), which returns only the
caller's own `id`, `name`, `email` and `role`. See [MCP](/modules/mcp).

### User administration

With `settings.admin`, staff get `GET` / `POST /api/admin/users`, `PATCH` / `DELETE /api/admin/users/:id`,
`POST /api/admin/users/:id/resend`, `GET /api/admin/users/roles` and `GET /api/admin/users/new-members`, an admin page (default `/admin/users`, listed in the `admin.nav` menu of
[`@frigear-nu/admin`](/modules/admin)) and a "new members" widget for its dashboard. The module knows nothing about
roles or staff; every request asks the host through the `users:admin:authorize` Nitro hook, **denied by default**:

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('users:admin:authorize', async (ctx) => {
    // ctx.action: 'view' | 'create' | 'update' | 'delete'; ctx.userId: the signed-in user
    // ctx.input: what is being written ({ role, email, name }); ctx.target: the user being edited ({ id, email, role })
    const actor = await findUser(ctx.userId)
    ctx.allowed = actor.role === 'admin'
  })
})
```

#### Extending the user page

The admin user page is a tab view over the `admin.users` tab area of [`@frigear-nu/widget`](/modules/widget), which
this module owns (the admin module knows nothing about it). It registers an **Overview** tab itself; any module can add
more with `extendTabs(nuxt, 'admin.users', { ... })`. Each tab component receives `user` (the response of
`GET /api/admin/users/:id`) as a prop and may emit `refresh` to reload it. [`@frigear-nu/subscriptions`](/modules/subscriptions)
adds *Subscription* and [`@frigear-nu/payments`](/modules/payments) adds *Payments*.

The Overview tab renders the `admin.users.overview` **widget** area at its top, for summary cards: register them with
`extendWidgets(nuxt, 'admin.users.overview', { component, order, span })`; they receive the same `user` prop. Without
`@frigear-nu/widget` the page shows the Overview tab alone. Each tab's API calls must authorize on the server through
`users:admin:authorize` (action `view` with `target`); hiding a tab is not access control.

`role` is only read and written when [`@frigear-nu/authorization`](/modules/authorization) added the column; its
`canManageRole(roles, actor, target, { equalAllowedFor })` helper is the building block for "nobody can hand out a role
above their own". Passwords are never returned. A staff-changed email is marked unverified, and creating a user can
email them a sign-in link (which also verifies the address).

Deleting a user also removes everything [`@frigear-nu/auth`](/modules/auth) keeps for them (tokens, passkeys, reset codes
and sign-in links). The hook `users:admin:roles` narrows or extends the roles the signed-in user may assign (`ctx.roles`).

#### Adding to the user page from another module

`extendUsersAdmin(nuxt, { routes, tab, widget })` from `@frigear-nu/users/utils` registers a module's staff routes below
`/api/admin/users/:id/`, a tab and an overview card in one call. Authorize in those routes with
`loadUsersAdminTarget(event, 'view' | 'update')`, which loads the target user and runs the policy (`400` / `401` /
`403` / `404`).

### Becoming the user store of auth

The module registers the `AuthUserStore` that `@frigear-nu/auth` reads and writes users through, over the `users` table
(`findById`, `findByEmail`, `create`, `update`, `remove`, `changeId`). It reads the database on every call, so a role
change applies to the next bearer request.

## Translations

The module registers `da` and `en` locale files under `users.admin.*` for the admin pages. Override any string in your
app's `i18n/locales/<code>.json` (see
[overriding module strings](/modules/module-kit#overriding-module-strings-in-your-app)).

## Database

### `users`

The [default SQLite schema](../../../../packages/users/src/runtime/db/schema.sqlite.ts) has an auto-incrementing `id`, a
required `name`, a unique required `email`, an optional `avatar`, a nullable `acceptedTermsAt` and `createdAt` /
`updatedAt` timestamps. Other modules add columns through the [module-kit](./module-kit) schema extension helpers:
[`@frigear-nu/auth`](/modules/auth) adds `password`, `emailVerifiedAt` and `lastLoginAt`,
[`@frigear-nu/authorization`](/modules/authorization) adds `role`, and so on.

> See the [module-kit guide](/modules/module-kit) for how table extensions are registered and merged.

### `accountEmailChanges`

Registered with `verifyEmailChange` (table `account_email_changes`): one row per "change my email" request with the old
and new address, the confirmation `code`, the `revertCode` and their timestamps.

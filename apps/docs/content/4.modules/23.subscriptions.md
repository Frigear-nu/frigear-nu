title: Subscriptions Module
description: Recurring Stripe subscriptions - host-defined plans, checkout, upgrade/downgrade, billing portal, entitlements and account UI.

Recurring subscriptions on top of [`@frigear-nu/stripe`](/modules/stripe) and [`@frigear-nu/users`](/modules/users), as a
[Nuxt module](https://nuxt.com/docs/4.x/guide/modules). It handles **only** recurring subscriptions; one-off payments
belong to a separate module. "Membership" is just a label a host chooses for its plans.

## Design

- **Stripe owns the catalog; the module mirrors per-user state.** No products/prices tables, no sync task. Plans are
  declared in config and prices are resolved live from Stripe, cached in NuxtHub KV for about five minutes.
- **Generic, with host policy through hooks.** Seasonal windows, member discounts, student pricing and so on are not
  built in; the host injects them via hooks (see [Policy hooks](#policy-hooks)).
- **No copy in Stripe.** Labels come from config and, for the UI, from optional i18n keys with English defaults. The UI
  is headless-first (composables) with replaceable components and slots; pages are opt-in.
- **Entitlements, not roles.** Other code asks "does this user hold plan X?".

## Quick Setup

Setup has five steps: install the packages, register the modules in the right order, set the environment variables,
configure the Stripe dashboard, and generate your app's migration.

### 1. Install

```bash
pnpm add @frigear-nu/subscriptions @frigear-nu/stripe @frigear-nu/users @nuxthub/core @nuxt/ui
pnpm add @frigear-nu/menu # optional
```

From the workspace use `"@frigear-nu/subscriptions": "workspace:*"` (and the same for the other `@frigear-nu/*` packages).

### 2. Register the modules

Subscriptions does not work on its own. It builds on the modules below, and each one has its own setup:

| Module | Required | Why |
| --- | --- | --- |
| [`@nuxthub/core`](https://hub.nuxt.com) | Yes | Provides the database and **KV**. `hub: { kv: true }` is mandatory: KV caches the Stripe prices, and the module throws at build time without it. |
| [`@frigear-nu/users`](/modules/users) | Yes | Subscriptions belong to a user. Use `users: { mode: 'server' }` (the default): the webhook resolves the user through `users.stripeCustomerId`, and the routes need a session. |
| [`@frigear-nu/stripe`](/modules/stripe) | Yes | Stripe client, webhook endpoint, customer handling and the `users.stripe_customer_id` column. See [Stripe](/modules/stripe#quick-setup) for its full setup. |
| [`@nuxt/ui`](https://ui.nuxt.com) | For the UI | The `SubscriptionPlans` / `SubscriptionStatus` components and the pages. Skip it if you only use the composables and server API. |
| [`@frigear-nu/menu`](/modules/menu) | No | Adds a "Subscription" item to the `account` menus when the membership page is enabled. |
| `@nuxtjs/i18n` | No | Translated labels. Without it the English defaults are used. |

List the module after the ones it builds on, and enable KV and a database:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: [
    '@nuxthub/core',
    '@nuxt/ui',
    '@frigear-nu/users',
    '@frigear-nu/menu', // optional
    '@frigear-nu/stripe',
    '@frigear-nu/subscriptions',
  ],
  hub: { db: { dialect: 'sqlite', driver: 'libsql' }, kv: true },
  users: { mode: 'server' },
  subscriptions: {
    plans: {
      member: { label: 'Member', rank: 1, prices: [{ lookupKey: 'member_yearly' }] },
    },
    settings: { pages: { membership: true, success: true, cancel: true } },
  },
})
```

Without `plans` the module works as "any active subscription" (see [Configuration](#configuration)). The `settings.pages`
are opt-in; leave them out to build your own UI with the [composables](#composables).

### 3. Environment variables

These belong to `@frigear-nu/stripe`; use test keys in development.

```bash
NUXT_STRIPE_SECRET_KEY=sk_test_...
NUXT_STRIPE_WEBHOOK_SECRET=whsec_...
NUXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_...
```

### 4. Stripe dashboard

Create recurring prices (with lookup keys), point a webhook at `/api/stripe/webhook` for the five
`customer.subscription.*` events and configure the billing portal. See [Stripe dashboard setup](#stripe-dashboard-setup).
For local development, forward events with the Stripe CLI (`stripe listen --forward-to localhost:3000/api/stripe/webhook`)
and use the `whsec_...` it prints.

### 5. Generate and commit your migration

::warning
The module ships no migration. Generate one in your app that covers the `subscriptions` table **and** the
`users.stripe_customer_id` column added by `@frigear-nu/stripe`. See [Migrations](#migrations). Skipping this is the most
common cause of failing webhooks and checkouts.
::

### Verify

Run the app, sign in, open `/account/membership` (if enabled) and subscribe with Stripe's test card `4242 4242 4242 4242`.
After the redirect, `GET /api/subscriptions/me` should return the subscription once the webhook has landed.

## Configuration

```ts
export default defineNuxtConfig({
  hub: { kv: true },
  subscriptions: {
    plans: {
      member: {
        label: 'Member',
        description: 'Basic membership', // optional
        rank: 1,
        prices: ['price_123', { lookupKey: 'member_yearly' }],
      },
      patron: {
        label: 'Patron',
        rank: 2,
        prices: [{ lookupKey: 'patron_monthly' }, { lookupKey: 'patron_yearly' }],
      },
    },
    settings: {
      pages: {
        membership: true, // or a custom path, default '/account/membership'
        success: true, // default '/account/membership/success'
        cancel: true, // default '/account/membership/cancel'
      },
      allowChangeInPortal: false, // default
    },
  },
})
```

| Option                           | Default | Description                                                                                   |
| -------------------------------- | ------- | --------------------------------------------------------------------------------------------- |
| `plans`                          | `{}`    | Plans keyed by plan key.                                                                      |
| `plans.<key>.prices`             | -       | Stripe price ids (`'price_...'`) and/or `{ lookupKey }` refs. Several per plan (monthly/yearly). |
| `plans.<key>.rank`               | -       | Number deciding upgrade vs. downgrade (higher is a higher tier). Price amounts are never compared. |
| `plans.<key>.label`              | the key | Display label (English fallback; see i18n).                                                           |
| `plans.<key>.description`        | -       | Optional description.                                                                         |
| `plans.<key>.features`           | -       | Optional bullet points shown on the plan card.                                                |
| `plans.<key>.availability.disabledRanges` | - | `{ from, to }[]` date windows (inclusive; `{fullYear}` is replaced by the current year, e.g. `{fullYear}-06-01`) in which the plan is hidden from visitors without an active subscription. Subscribers still see it, and checkout rejects a hidden plan. |
| `settings.pages.membership`      | off     | `true` for `/account/membership`, a string for a custom path, `false`/omitted to disable.     |
| `settings.pages.success`         | off     | `true` for `/account/membership/success`, or a custom path.                                   |
| `settings.pages.cancel`          | off     | `true` for `/account/membership/cancel`, or a custom path.                                    |
| `settings.allowChangeInPortal`   | `false` | A hint exposed to the app as `useRuntimeConfig().public.subscriptions.allowChangeInPortal`. The module does not enforce it; it should mirror what you enabled in the Stripe billing portal. |

`plans` may be empty (the default), in which case the module works as "any active subscription": checkout then requires
a `priceId` and accepts any active recurring Stripe price, and stored rows get `planKey = null`.

The module also exposes `useRuntimeConfig().public.subscriptions` (`pages`, the plans sorted by `rank` without prices,
and `allowChangeInPortal`) and a private `useRuntimeConfig().subscriptions.plans`.

## Database

The module registers a single `subscriptions` table: `id` (the Stripe subscription id, primary key), `userId`, `planKey`,
`priceId`, `status` (raw Stripe status), `cancelAtPeriodEnd`, `currentPeriodStart` / `currentPeriodEnd`, `endedAt`,
`rawItems` (JSON: item id, price id, lookup key, quantity), `createdAt` and `updatedAt`.

- Rows are never deleted; ended subscriptions get `endedAt`.
- Prices not in a configured plan are stored with `planKey = null`, so changing config never loses data.
- `userId` is an indexed integer without a foreign key (the `users` table is registered from another file); the webhook
  resolves the user through `users.stripeCustomerId`.

### Migrations

::warning
The module does not ship a migration for your app. **Every host app must generate and commit its own** after adding the
module: the `subscriptions` table plus the `users.stripe_customer_id` column from
[`@frigear-nu/stripe`](/modules/stripe#database), together in the app's complete module configuration (SQL, Drizzle
snapshot and journal). Follow the migration workflow in [Module Kit](/modules/module-kit) and the repository
`AGENTS.md`. Test fixtures are consuming apps too and need their own migrations.
::

## Webhook handling

The module registers itself with the core's [`registerStripeEventHandler`](/modules/stripe#in-a-module-build-time) for
`customer.subscription.created`, `updated`, `deleted`, `paused` and `resumed`. Each event is an idempotent upsert keyed by
the Stripe subscription id:

- The user is resolved from the Stripe customer id. For an unknown customer the event is logged and ignored (the webhook
  still succeeds); users are never created from webhooks.
- `planKey` is taken from the first subscription item's price (by price id or lookup key), else `null`.
- The period start/end are derived from the subscription items; `deleted` events store the status `canceled` and set
  `endedAt`.

Duplicate and retried deliveries are safe. Delivery semantics (retries, KV idempotency) are those described in
[Stripe](/modules/stripe#delivery-idempotency-and-retries). The module does not handle `invoice.payment_failed`; use
`onStripeEvent` in your app if you want to react to it.

## Server API

All routes live under `/api/subscriptions/*`. All except `plans` require a session (`401` otherwise) and validate their
body.

| Route                                | Description                                                                |
| ------------------------------------ | -------------------------------------------------------------------------- |
| `GET /api/subscriptions/plans`       | Public. `{ plans: ResolvedPlan[] }`, filtered by `subscriptions:plans:filter`. |
| `GET /api/subscriptions/me`          | `{ subscriptions: SubscriptionDto[], activePlan: string \| null }`.         |
| `POST /api/subscriptions/checkout`   | Body `{ planKey?, priceId?, successUrl?, cancelUrl? }`. See below.         |
| `POST /api/subscriptions/portal`     | Body `{ returnUrl? }`. Returns `{ url }` of a Stripe billing portal session. |

A `ResolvedPlan` is `{ key, label, description?, rank, prices: PlanPrice[] }` with
`PlanPrice = { id, amount (minor units, or null), currency, interval ('day'|'week'|'month'|'year'), intervalCount, trialPeriodDays, lookupKey }`.
Inactive and non-recurring prices are left out. A `SubscriptionDto` is
`{ id, planKey, priceId, status, cancelAtPeriodEnd, currentPeriodStart, currentPeriodEnd, endedAt }` with ISO date
strings. `activePlan` is the plan key of the entitled (`active`/`trialing`, not ended) subscription with the latest period
end, or `null`.

### Staff routes

Staff manage a user's membership through `/api/admin/users/:id/subscription` (`GET` the current membership and plans,
`POST` grant free, `DELETE` revoke, `POST .../payment-link`) and read the whole history with
`GET /api/admin/users/:id/subscriptions` (same `{ subscriptions, activePlan }` shape as `/me`, including ended rows).
All of them are authorized through the `users:admin:authorize` hook of [`@frigear-nu/users`](/modules/users) (`view` for
reads, `update` for changes). With [`@frigear-nu/widget`](/modules/widget) installed, the module adds a *Subscription* tab
(grant/revoke, payment link and history) and a *Current subscription* card to the admin user page
(`admin.users` tab area, `admin.users.overview` widget area).

### Checkout

Provide `planKey` or `priceId` (otherwise `400`). With a `planKey`, a plan with several prices requires a `priceId` that
belongs to it. The plan must be in the filtered plan list (a hidden plan is `400`). `successUrl` / `cancelUrl` /
`returnUrl` must be a relative path or a URL on the request's origin (`400` otherwise); they default to the configured
success/cancel page (or the membership page, or `/`).

The response is one of:

- `{ url }` - a new Stripe Checkout Session (the user has no `active`, `trialing` or `past_due` subscription). Redirect to it.
- `{ updated: true, kind: 'upgrade' | 'downgrade' }` - an existing subscription was changed in place.

`409` is returned when the user already holds the requested price. The change `kind` follows the plan `rank` rule:

- **Higher rank = upgrade**: applied immediately with `always_invoice` proration (a pending schedule is released and
  `cancel_at_period_end` cleared).
- **Lower or equal rank = downgrade**: deferred to the end of the current period through a subscription schedule. This
  also covers a billing-interval change within one plan (for example monthly to yearly of `member`).
- A current plan that is not configured counts as the lowest rank; a target price outside the configured plans (only
  possible with no plans configured) counts as an upgrade.

The local row is updated by the webhook afterwards. Cancellation is done in the billing portal.

## Policy hooks

Host customization is done with Nitro hooks, typically in a server plugin. The module itself contains no seasonal or
pricing rules.

```ts
// server/plugins/subscription-policy.ts
export default defineNitroPlugin((nitro) => {
  // Deny or adjust a checkout (promo codes, tax, trial, metadata, ...). Throw to deny.
  nitro.hooks.hook('subscriptions:checkout:before', async (ctx) => {
    if (!isSignupSeason(new Date())) {
      throw createError({ statusCode: 403, statusMessage: 'Sign-up is closed' })
    }
    if (ctx.kind === 'checkout') {
      ctx.params.metadata = { ...ctx.params.metadata, source: 'website' }
    }
  })

  // Hide or reorder plans, per request.
  nitro.hooks.hook('subscriptions:plans:filter', async (ctx) => {
    const session = ctx.event ? await getUserSession(ctx.event) : null
    ctx.plans = ctx.plans.filter(plan => plan.key !== 'patron' || session?.user)
  })
})
```

| Hook                              | Payload `ctx`                                                                                    |
| --------------------------------- | ------------------------------------------------------------------------------------------------ |
| `subscriptions:checkout:before`   | `{ event: H3Event, userId: number, planKey: string \| null, priceId: string, kind: 'checkout' \| 'upgrade' \| 'downgrade', params: Stripe.Checkout.SessionCreateParams }` |
| `subscriptions:plans:filter`      | `{ event: H3Event \| undefined, plans: ResolvedPlan[] }`                                         |

- `checkout:before` runs after validation and the kind decision, for new checkouts and plan changes. Throw (for example
  `createError`) to deny. `params` is what is sent to `stripe.checkout.sessions.create` and is **only used when
  `kind === 'checkout'`**; the default is `mode: 'subscription'`, the line item, `success_url`, `cancel_url`,
  `client_reference_id` (the user id) and `subscription_data.metadata` (`userId`, `planKey`). The Stripe `customer` is added
  afterwards.
- `plans:filter` receives a copy of the cached plans; change `ctx.plans` in place or reassign it. `event` is `undefined`
  outside a request. It also applies to checkout, so a filtered-out plan cannot be subscribed to.

## Entitlements

```ts
// server (auto-imported in Nitro, or import from '@frigear-nu/subscriptions/utils')
const sub = await getUserSubscription(userId) // the subscriptions row, or null
const ok = await hasActiveSubscription(userId, { plans: ['member', 'patron'], statuses: ['active', 'trialing'] })
```

| Utility                                  | Description                                                                                  |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `getUserSubscription(userId, { statuses? })`   | The entitled row with the latest `currentPeriodEnd`, or `null`.                        |
| `hasActiveSubscription(userId, { plans?, statuses? })` | Whether the user holds an entitled subscription, optionally on one of `plans`.   |

`statuses` defaults to `active` and `trialing` (`DEFAULT_ENTITLED_STATUSES`); rows with `endedAt` never count. These
utilities are meant for other modules (e.g. payments), server middleware and event gating. `@frigear-nu/subscriptions/utils`
also exports the pure helpers `decideChangeKind`, `resolvePlanKey` and `resolveSameOriginUrl`.

### Middleware

```ts
definePageMeta({
  middleware: 'subscription',
  subscription: { plans: ['member'], redirectTo: '/join' }, // both optional
})
```

The route middleware `subscription` redirects to `redirectTo`, or else to the membership page path, with the original
route in `?redirect=`. Without either target it does nothing. Anonymous users and users without an active plan are
redirected; a subscription on a price outside every configured plan has no `activePlan` and is not let through. `plans`
restricts access to those plan keys. This guards navigation only; enforce access in API routes with
`hasActiveSubscription`.

## Composables

Auto-imported, and also available from `@frigear-nu/subscriptions/composables`.

- `usePlans()` returns `{ plans, status, error, refresh }`; `plans` is sorted by `rank`.
- `useSubscription()` returns `{ subscription, plan, status, isActive, cancelsAt, has(planKey), pending, error, refresh, subscribe, openPortal }`.
  - `subscribe(planKeyOrPriceId, { successUrl?, cancelUrl? })` - strings starting with `price_` are sent as `priceId`,
    anything else as `planKey`. The URLs default to the configured pages. It redirects to Stripe Checkout, or refreshes
    when an existing subscription was changed, and resolves with the checkout response.
  - `openPortal(returnUrl?)` - redirects to the Stripe billing portal; `returnUrl` defaults to the current page.

## Components

`SubscriptionPlans` and `SubscriptionStatus` are built on `@nuxt/ui` and expose scoped slots so hosts can restyle or
replace any part.

**`SubscriptionPlans`** - props: `locale`, `currency` (formatting override), `interval` (which price to show per plan,
default the first price), `plans` (only show these keys), `confirmChange` (default `false`, asks for confirmation
before changing an existing subscription), `mode` (`'auto'` default: tabs on small screens, side-by-side cards from `sm` up; or `'list'` / `'tabs'`), `highlight` (plan key to emphasise, defaults to the current plan). Cards are Nuxt UI pricing plans. Visitors who are not signed in are sent to the users register page with `?redirect=<membership page>?plan=<key>`; the membership page then opens the confirmation for that plan. Emits `select(plan, price)`. Each plan has a `state`:
`'current' | 'upgrade' | 'downgrade' | 'subscribe'`. Slots: `loading`, `empty`, `header` and `badge` (`{ plan, state }`),
`price` (`{ plan, price, formatPrice, intervalLabel }`), `features` (`{ plan }`), `action` (`{ plan, state, pending, select }`),
`confirm` (`{ plan, price }`) and `confirm-actions` (`{ plan, price, confirm }`).

**`SubscriptionStatus`** - props: `locale`. Slots: `header`, `loading`, `empty`, `plan` (`{ plan, label, subscription }`),
`badge` (`{ subscription, badge }`), `dates` (`{ subscription, cancelsAt, dateText }`) and `actions`
(`{ manage, resubscribe, cancelling, pending }`).

### Labels and i18n

The module registers `da` and `en` locale files with [module-kit](/modules/module-kit#translations-i18n) and the
components read them through `useModuleT('subscriptions.<group>')`. Without `@nuxtjs/i18n`, English defaults are used.
Override any key in the host's `i18n/locales/<code>.json` (see
[overriding module strings](/modules/module-kit#overriding-module-strings-in-your-app)). Keys (parameters use
`{name}`):

- `plans.*`: `loading`, `empty`, `current`, `subscribe`, `upgrade`, `downgrade`, `trial` (`{days}`), `confirmTitle`,
  `confirmBody` (`{plan}`), `confirm`, `cancel`.
- `interval.*`: `day`, `week`, `month`, `year` and their plurals `days`, `weeks`, `months`, `years`.
- `status.*`: `loading`, `title`, `none`, `renews` (`{date}`), `cancels` (`{date}`), `manage`, `resubscribe`, `active`,
  `trialing`, `pastDue`, `canceled`, `other`.
- `success.*` and `cancel.*` (pages): `title`, `body`, and `continue` / `back`.
- `errors.*`: `checkout`, `portal`.
- `catalog.<planKey>.label` and `catalog.<planKey>.description`: plan names, which are host-defined. They fall back
  to the `label` and `description` in the plan config.

### Pages and menu

Each page in `settings.pages` that is enabled is added at its path (skipped if the path already exists in the app): the
membership page (the status card when subscribed, plus the plans with confirmation), a success page (polls `me` up to five
times, two seconds apart, while the webhook lands) and a cancel page. With [`@frigear-nu/menu`](/modules/menu) installed
and the membership page enabled, the module registers a menu source that adds a "Subscription" item (order 30) to the
`account` and `dashboard.account` menus.

## Stripe dashboard setup

1. **API keys and webhook** - configure [`@frigear-nu/stripe`](/modules/stripe#stripe-dashboard-setup) and subscribe the
   endpoint to:
   - `customer.subscription.created`
   - `customer.subscription.updated`
   - `customer.subscription.deleted`
   - `customer.subscription.paused`
   - `customer.subscription.resumed`
2. **Products and prices** - create recurring prices. Use lookup keys if you want config to be environment-independent
   (test and live have different price ids). No metadata or copy is needed in Stripe.
3. **Billing portal** (Settings > Billing > Customer portal) - enable cancellation and payment method updates. Enable
   subscription updates only if you set `allowChangeInPortal: true`, and list the products/prices the portal may switch
   between.

## `@frigear-nu/oauth-server`

This [Nuxt module](https://nuxt.com/docs/4.x/guide/modules) turns an app into an OAuth 2.0 / OpenID Connect **server**.
You register **applications** (OAuth clients), restrict each one to users with certain roles, and those users can then
sign in to the application through your app: authorization code flow with mandatory PKCE, rotating refresh tokens and
RS256 signed ID tokens.

The module is deliberately bare-bone. It knows nothing about roles, admins or what belongs in a token. The consuming app
decides through [Nitro hooks](#hooks).

It builds on [`@frigear-nu/auth`](/modules/auth) and [`@frigear-nu/users`](/modules/users) for the sign-in session, and registers its own tables
through [`@frigear-nu/module-kit`](/modules/module-kit). With [`@frigear-nu/menu`](/modules/menu) installed, an
**Applications** tile shows up in the account area.

## Setup

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/menu', '@frigear-nu/users', '@frigear-nu/oauth-server'],
  oauthServer: {
    issuer: 'https://id.example.com',
    settings: {
      pages: { admin: true, applications: true },
    },
  },
})
```

Then:

1. [Generate a signing key](#signing-keys) and set `NUXT_OAUTH_SERVER_PRIVATE_KEY`.
2. Generate and commit a migration for the `oauth_applications`, `oauth_authorization_codes` and `oauth_refresh_tokens`
   tables (see [Migrations](/modules/module-kit)). The module only adds new tables, it does not change `users`.
3. Implement the [hooks](#hooks). Without them nobody is an admin and nobody has a role.

### Options

| Option | Default | |
| --- | --- | --- |
| `issuer` | request origin | The `iss` claim. Set it explicitly behind proxies. |
| `keyId` | `key-1` | `kid` of the signing key published in the JWKS. |
| `accessTokenTtl` | `3600` | Access and ID token lifetime in seconds. |
| `refreshTokenTtl` | 30 days | Refresh token lifetime in seconds. |
| `codeTtl` | `600` | Authorization code lifetime in seconds. |
| `callbackPath` | `/auth/frigear` | Appended to an application's website URL to form its redirect URI. |
| `scopes` | `[]` | Extra scopes next to `openid profile email`. |
| `settings.pages.authorize` | `true` | Consent screen at `/authorize`. `false` = bring your own page at that path. |
| `settings.pages.admin` | off | Admin UI, `true` = `/admin/oauth`. Needs `@nuxt/ui`. |
| `settings.pages.applications` | off | The user's applications, `true` = `/account/applications`. Needs `@nuxt/ui`. |
| `settings.signInPath` | users login page | Where unauthenticated users are sent to sign in. |

## Signing keys

ID tokens and access tokens are signed with an **RSA key (RS256)**. The server needs the private key. The matching
public key is derived from it and published at `/.well-known/jwks.json`, which is what applications use to verify
tokens, so you normally only configure the private key. (`NUXT_OAUTH_SERVER_PUBLIC_KEY` exists to override the derived
one.)

### Generate a key pair

You need [OpenSSL](https://www.openssl.org/) (preinstalled on macOS and most Linux distributions).

```bash
# 2048-bit RSA private key, PKCS#8 (-----BEGIN PRIVATE KEY-----)
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out oauth-private.pem

# Optional: the matching public key (-----BEGIN PUBLIC KEY-----), e.g. to hand to an application or compare with the JWKS
openssl pkey -in oauth-private.pem -pubout -out oauth-public.pem
```

::warning
Keep `oauth-private.pem` out of git and delete the local file once the secret is stored. Anyone with this key can mint
tokens for every application. The format must be PKCS#8 (`BEGIN PRIVATE KEY`); a key starting with
`BEGIN RSA PRIVATE KEY` is PKCS#1 and is rejected. Convert it with
`openssl pkcs8 -topk8 -nocrypt -in old.pem -out oauth-private.pem`.
::

If you do not have OpenSSL, Node.js can generate the same thing:

```bash
node -e "const {generateKeyPairSync}=require('node:crypto');const k=generateKeyPairSync('rsa',{modulusLength:2048,privateKeyEncoding:{type:'pkcs8',format:'pem'},publicKeyEncoding:{type:'spki',format:'pem'}});console.log(k.privateKey)" > oauth-private.pem
```

### Provide it to the app

Environment variables are single-line, so the newlines are written as a literal `\n` (the module also strips wrapping
quotes). This prints the value ready to paste:

```bash
awk 'NF {printf "%s\\n", $0}' oauth-private.pem
```

::code-group

```bash [.env (local)]
NUXT_OAUTH_SERVER_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMIIEvQIBADANBgkq...\n-----END PRIVATE KEY-----"
```

```bash [Cloudflare Workers]
# Stored as an encrypted secret on the worker, not in wrangler.json
awk 'NF {printf "%s\\n", $0}' oauth-private.pem | pnpm dlx wrangler secret put NUXT_OAUTH_SERVER_PRIVATE_KEY
```

```bash [GitHub Actions]
# Repository secret, passed to the deploy step as NUXT_OAUTH_SERVER_PRIVATE_KEY
awk 'NF {printf "%s\\n", $0}' oauth-private.pem | gh secret set NUXT_OAUTH_SERVER_PRIVATE_KEY
```

::

Use a **different key per environment** (local, preview, production), so a leaked development key is worthless in
production. Check that it works by opening `/.well-known/jwks.json`: it should return one key with `kty: "RSA"`, your
`kid` and no `d` field. A missing or malformed key answers with a 500 *"The OAuth server signing keys are not
configured."*

### Rotating a key

Rotation has an **overlap period**: the server signs new tokens with the new key, while the old key's *public* half
stays in the JWKS and keeps verifying tokens that were already issued. Nobody is signed out.

1. Generate a new pair (see [above](#generate-a-key-pair)).
2. Move the old public key into `previousPublicKeys`, keyed by its old `keyId`, and switch to the new private key and a
   new `keyId`.
3. Deploy. `/.well-known/jwks.json` now lists both keys, new tokens carry the new `kid`, and applications that cache
   the JWKS pick the new key up when they meet an unknown `kid`.
4. After the longest token lifetime has passed (`accessTokenTtl`, an hour by default, plus the cache time applications
   keep your JWKS), remove the old entry from `previousPublicKeys`.

```bash
# The public key of the key you are retiring, as a JSON object keyed by its kid (single line, ready for an env var)
node -e "console.log(JSON.stringify({ 'key-1': require('fs').readFileSync('oauth-public-old.pem','utf8') }))"
```

::code-group

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  oauthServer: {
    keyId: 'key-2', // the new key
  },
})
```

```bash [.env]
NUXT_OAUTH_SERVER_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n…new key…\n-----END PRIVATE KEY-----"
# The retired key: public half only, nothing is signed with it any more
NUXT_OAUTH_SERVER_PREVIOUS_PUBLIC_KEYS='{"key-1":"-----BEGIN PUBLIC KEY-----\n…old key…\n-----END PUBLIC KEY-----\n"}'
```

::

Refresh tokens are opaque and not signed, so they are not affected by rotation at all.

::warning
If a private key **leaked**, do not keep it in `previousPublicKeys`: its tokens would stay valid for the overlap
period. Replace the key, leave `previousPublicKeys` empty, and use **Sign everyone out** on each application in the
admin UI. Users have to sign in again.
::

## How a sign-in works

```text
application ──▶ GET  /oauth/authorize?client_id&redirect_uri&response_type=code&state&code_challenge&code_challenge_method=S256[&scope&nonce]
                 not signed in ──▶ <login page>?redirect=/oauth/authorize?… ──▶ back here
                 role/access check (403 if denied) ──▶ /authorize?… (consent page)
user approves ──▶ POST /oauth/authorize {…, approved: true} ──▶ redirect to the application's callback with ?code&state
application ──▶ POST /oauth/token (code + code_verifier + client credentials) ──▶ access_token, id_token, refresh_token
```

| Endpoint | |
| --- | --- |
| `GET /.well-known/openid-configuration` | Discovery document. |
| `GET /.well-known/jwks.json` | Public signing key. |
| `GET`/`POST /oauth/authorize` | Authorization request and the consent decision. |
| `POST /oauth/token` | `authorization_code` and `refresh_token` grants. Client auth by HTTP Basic or `client_id` + `client_secret` in the body. |
| `POST /oauth/revoke` | Revokes a refresh token and the rest of its family (RFC 7009). |
| `GET /oauth/userinfo` | Claims for a bearer access token, filtered by scope. |

Good to know:

- **PKCE (S256) is mandatory.** Applications are confidential clients with a secret (shown once when created).
- **Redirect URIs are derived**, not free-form: `websiteUrl + callbackPath` (`https://app.example.com/auth/frigear`), the
  application's explicit extra `redirectUris`, or its `previewUrlPattern` (`https://*.vercel.app`, where `*` is one
  hostname label). `https` is required except for `localhost`.
- **Refresh tokens rotate.** Presenting an already-used refresh token is treated as theft and revokes the whole family.
- Access is re-checked on every token exchange, every `userinfo` call and every API call made with an access token (see
  [API access](#api-access)), so disabling an application or removing a role also stops refreshes and API calls.
- **Access tokens are bare** (`sub`, `scope`, `client_id`, `aud`, `iss`, `exp`, `iat`, `jti`, header `typ: at+jwt`);
  identity claims (`name`, `picture`, `email`) live in the ID token and `userinfo`, per granted scope.

## API access

An application can call this app's API as the user who signed in to it. Send the access token as
`Authorization: Bearer <access_token>`: routes that use `requireUser` / `requireAuth` from
[`@frigear-nu/auth`](/modules/auth) see the user, and `principal.client.id` identifies the application.

- **Scopes.** The scopes an application may request are `openid profile email`, the ones in `oauthServer.scopes`, and every
  API scope modules register (`tickets:read`, `subscriptions:read`, …). The user sees them on the consent screen, and a route
  that requires a scope the user did not grant answers `403 insufficient_scope`.
- **Live checks.** On every call the application must still be active and the user must still exist and pass the
  application's role requirement and the `oauth:application:access` hook. Otherwise the call is `401`.
- **Not everything.** Account-level routes are session-only, so an access token never changes a password or passkeys.
- **Only access tokens.** ID tokens (`typ: JWT`) are not accepted as credentials.

## Hooks

Every hook is a Nitro runtime hook; implement them from a Nitro plugin in the consuming app.

| Hook | Purpose |
| --- | --- |
| `oauth:authorize` | Who may manage applications. **Denied by default.** |
| `oauth:user:roles` | The roles of a user, matched against an application's `allowedRoles`. **No roles by default.** |
| `oauth:application:access` | Extra veto after the role check. |
| `oauth:claims` | Enrich ID tokens, access tokens and userinfo. |
| `oauth:token:issued` / `oauth:token:revoked` | Audit logging. |

### Resolving roles

An application has `allowedRoles: string[]`. A user may sign in when they hold **at least one** of those roles. An
**empty list means every signed-in user**. A non-empty list with a host that reports no roles locks everybody out.

The module has no role model of its own. You tell it who has which roles by pushing them onto `ctx.roles`. Several
listeners add up, so modules and the app can each contribute.

::code-group

```ts [A role column on users]
// server/db/extend.sqlite.ts adds `role: text().default('member')` to `users`
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId) // the users row, including host-added columns
    if (user?.role) ctx.roles.push(String(user.role))
  })
})
```

```ts [A separate user_roles table]
import { eq } from 'drizzle-orm'
import { db, schema } from '@nuxthub/db'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const rows = await db.select({ role: schema.userRoles.role })
      .from(schema.userRoles)
      .where(eq(schema.userRoles.userId, ctx.userId))
    ctx.roles.push(...rows.map(row => row.role))
  })
})
```

```ts [Derived from other data]
import { hasActiveSubscription } from '@frigear-nu/subscriptions/utils'

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId)
    if (user?.email.endsWith('@frigear.nu')) ctx.roles.push('staff')
    if (await hasActiveSubscription(ctx.userId)) ctx.roles.push('member')
  })
})
```

```ts [A role hierarchy]
// `admin` implies `manager` implies `member`: expand the roles so applications only list the lowest one.
const implied: Record<string, string[]> = { admin: ['manager', 'member'], manager: ['member'] }

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:user:roles', async (ctx) => {
    const user = await getOAuthUser(ctx.userId)
    const role = String(user?.role ?? 'user')
    ctx.roles.push(role, ...(implied[role] ?? []))
  })
})
```

::

`ctx.event` is set when the check runs inside a request (it is `undefined` for background calls such as
`listUserApplications(userId)`), so do not depend on the session in this hook, load what you need by `ctx.userId`.

Roles are checked at the authorization entry, on the consent page, on approval, on every token exchange and on
`userinfo`. When a user loses a role, call [`revokeUserGrants(userId)`](#helpers) to end their refresh tokens.

### Who is an admin

The admin routes (`/api/oauth-server/admin/**`) call `requireOAuthAdmin(event)`: 401 when signed out, 403 unless a
listener sets `ctx.allowed = true`.

::code-group

```ts [By role]
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:authorize', async (ctx) => {
    const user = await getOAuthUser(ctx.userId)
    ctx.allowed = user?.role === 'admin'
  })
})
```

```ts [By email allowlist]
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:authorize', async (ctx) => {
    const admins = useRuntimeConfig().oauthAdminEmails.split(',').map(email => email.trim().toLowerCase())
    const user = await getOAuthUser(ctx.userId)
    ctx.allowed = !!user && admins.includes(user.email.toLowerCase())
  })
})
```

::

### Enriching ID tokens, access tokens and userinfo

`oauth:claims` runs for every token and for `userinfo`. Mutate `ctx.claims`. The module has already put the standard
profile claims there for the granted scopes. Registered claims (`iss`, `sub`, `aud`, `exp`, `iat`, `nbf`, `jti`,
`nonce`, `auth_time`, `scope`, `client_id`) are re-applied afterwards, so they cannot be overwritten.

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('oauth:claims', async (ctx) => {
    // ctx.tokenType: 'id_token' | 'access_token' | 'userinfo'
    // ctx.user, ctx.application, ctx.scope (granted scopes), ctx.roles (resolved by oauth:user:roles)

    // Access tokens stay bare, so only the ID token and userinfo get identity claims.
    if (ctx.tokenType === 'access_token') return

    // A namespaced role claim, as the previous Frigear apps used
    ctx.claims['https://frigear.nu/claims/role'] = ctx.roles[0] ?? 'user'

    // A custom scope: list it in `oauthServer.scopes: ['groups']`, applications then request `scope=openid groups`
    if (ctx.scope.includes('groups')) ctx.claims.groups = ctx.roles

    // Per application
    if (ctx.application.tags.includes('shop')) ctx.claims.customer_id = await customerIdFor(ctx.user.id)

    // Remove something
    if (!ctx.scope.includes('email')) delete ctx.claims.email
  })
})
```

Add extra scopes with `oauthServer: { scopes: ['groups'] }`. They are advertised in discovery and accepted in
authorization requests, and unsupported scopes are dropped (a request with no supported scope is rejected).

### Vetoing access and auditing

```ts
export default defineNitroPlugin((nitro) => {
  // After the role check: e.g. only users with a verified email, or a suspended flag
  nitro.hooks.hook('oauth:application:access', (ctx) => {
    if (ctx.user.suspended) {
      ctx.allowed = false
      ctx.reason = 'Your account is suspended.' // shown to the user as the 403 message
    }
  })

  nitro.hooks.hook('oauth:token:issued', ({ userId, applicationId, grant }) => {
    console.info(`[oauth] tokens issued to user ${userId} for ${applicationId} (${grant})`)
  })
  nitro.hooks.hook('oauth:token:revoked', ({ applicationId, userId, reason }) => {
    console.warn(`[oauth] revoked ${applicationId}/${userId}: ${reason}`) // 'revoked' | 'reuse_detected' | 'user_grants_revoked'
  })
})
```

## Helpers

Server utilities are auto-imported in Nitro. Pure helpers are importable from `@frigear-nu/oauth-server/utils`.

| Helper | |
| --- | --- |
| `requireOAuthAdmin(event)` | The admin gate. Returns `{ userId }` or throws 401/403. |
| `listApplications()`, `getApplication(id)` | Read applications (never includes the secret hash). |
| `createApplication(input, ownerId?)` | Returns `{ application, secret }`. The secret is only available now. |
| `updateApplication(id, patch)`, `deleteApplication(id)` | Validated the same way as the admin API. |
| `rotateApplicationSecret(id)` | New secret, old one stops working, refresh tokens are revoked. |
| `listUserApplications(userId, event?)` | Active applications the user may sign in to, highest priority first. |
| `userCanAccessApplication(userId, application, event?)` | Role check plus `oauth:application:access`. |
| `resolveUserRoles(userId, event?)` | Runs `oauth:user:roles`. |
| `revokeUserGrants(userId, applicationId?)` | Ends a user's refresh tokens (all, or for one application). |
| `revokeApplicationGrants(applicationId)` | Signs everyone out of an application. |
| `getOAuthUser(userId)` | The `users` row without the password hash. |
| `matchesAllowedRoles(allowed, roles)`, `validateRedirectUri(uri, rules)` | Pure, from `/utils`. |

Build your own admin endpoint on top of them:

```ts [server/api/shop/connect.post.ts]
export default defineEventHandler(async (event) => {
  const { userId } = await requireOAuthAdmin(event)
  const { application, secret } = await createApplication({
    name: 'Shop',
    websiteUrl: 'https://shop.example.com',
    allowedRoles: ['member'],
    tags: ['shop'],
  }, userId)
  return { clientId: application.id, clientSecret: secret }
})
```

End a user's sessions when they are deactivated or lose a role:

```ts
await revokeUserGrants(user.id) // every application
await revokeUserGrants(user.id, 'app_…') // just one
```

In the app, `useOAuthApplications()` (admin CRUD) and `useMyApplications()` are auto-imported composables.

## The application side

Register the application in the admin UI (or with `createApplication`), then configure it with the **client ID**
(`app_…`) and **client secret**. This is the whole flow with `curl`:

```bash
# 1. PKCE pair
VERIFIER=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)
CHALLENGE=$(printf %s "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')

# 2. Open in a browser, sign in and approve. You are redirected to the callback with ?code=…&state=…
echo "https://id.example.com/oauth/authorize?client_id=$CLIENT_ID&redirect_uri=https://app.example.com/auth/frigear&response_type=code&state=xyz&scope=openid%20profile%20email&nonce=n1&code_challenge=$CHALLENGE&code_challenge_method=S256"

# 3. Exchange the code
curl -s https://id.example.com/oauth/token \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=authorization_code -d code="$CODE" -d code_verifier="$VERIFIER" \
  -d redirect_uri=https://app.example.com/auth/frigear

# 4. Refresh (the returned refresh_token replaces the old one)
curl -s https://id.example.com/oauth/token -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=refresh_token -d refresh_token="$REFRESH_TOKEN"

# 5. Userinfo
curl -s https://id.example.com/oauth/userinfo -H "Authorization: Bearer $ACCESS_TOKEN"
```

Verify the ID token with any JOSE library against the JWKS (`iss`, `aud` = client ID, `nonce`):

```ts
import { createRemoteJWKSet, jwtVerify } from 'jose'

const jwks = createRemoteJWKSet(new URL('https://id.example.com/.well-known/jwks.json'))
const { payload } = await jwtVerify(idToken, jwks, { issuer: 'https://id.example.com', audience: clientId })
```

## Database

The module registers three tables through `registerDatabaseTable`; `users` is untouched. Tables have no foreign key to
`users` (it is registered from another file), they store the user id.

| Table | |
| --- | --- |
| `oauth_applications` | Name, website/login URL, preview pattern, extra redirect URIs, `allowedRoles`, `tags`, `priority`, `isActive`, hashed secret. |
| `oauth_authorization_codes` | Single-use codes (hash only), PKCE challenge, nonce, 10 minute lifetime. |
| `oauth_refresh_tokens` | Hashed refresh tokens grouped in families for rotation and reuse detection. |

Client secrets, codes and refresh tokens are only stored as SHA-256 hashes.

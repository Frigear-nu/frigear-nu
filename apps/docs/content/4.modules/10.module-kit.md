---
title: Module Kit
description: Helpers for building Frigear Nuxt modules - pages, URLs, translations, menu sources, virtual registries and extendable database tables.
---

The shared toolkit behind every Frigear [Nuxt module](https://nuxt.com/docs/4.x/guide/modules). Use it to register
pages and translations, to let modules contribute to each other, and to let one module add columns to a table another
module owns, without replacing its schema. Almost every `@frigear-nu/*` module depends on it (account, admin, auth,
authorization, cookie-consent, events, forms, mcp, menu, oauth-server, payments, preferences, stripe, subscriptions,
users, widget); `notify` and `ui` do not.

::note
**Requires** `@nuxthub/core`; the table helpers also need the `drizzle-orm` and `drizzle-kit` peer dependencies. The
Frigear modules declare it as a `moduleDependency`, so it installs automatically in a host app; add it to `modules`
yourself only to author a module. It adds the `useModuleT` auto-import; the `@frigear-nu/module-kit/utils` helpers are
plain imports.
::

## Quick setup

```bash
pnpm add @frigear-nu/module-kit
```

```ts
// A module's setup(), importing the helpers it needs
import { defineNuxtModule, createResolver } from '@nuxt/kit'
import { registerModule, registerLocales } from '@frigear-nu/module-kit/utils'

export default defineNuxtModule({
  meta: { name: '@frigear-nu/events', configKey: 'events' },
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)
    registerModule('@frigear-nu/events', nuxt)
    registerLocales(nuxt, resolver.resolve('./runtime/i18n/lang'))
  },
})
```

## Options

The module has one config key, `moduleKit`. It is internal: `registerModule` writes to it, and you do not set it by
hand.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `_modules` | `string[]` | `[]` | Names of the Frigear modules registered in the current Nuxt app (see `registerModule`). |

## Exports

| Import | Contains |
| --- | --- |
| `@frigear-nu/module-kit` | The Nuxt module and everything from `/utils`. |
| `@frigear-nu/module-kit/utils` | Every helper below, except `/schedule`. |
| `@frigear-nu/module-kit/schedule` | The `Schedule` type, `scheduleSchema` (zod), `isScheduleOpen` and `nextScheduleOpening`. Used by forms and events. |

`useModuleT` is auto-imported in app code wherever the module is installed.

## Module helpers

| Helper | Signature | Purpose |
| --- | --- | --- |
| `registerModule` | `(moduleName: string, nuxt: Nuxt) => void` | Adds the name to `nuxt.options.moduleKit._modules`, de-duplicated. |
| `defineModulePage` | `(moduleName: string, page: NuxtPage) => NuxtPage` | Tags a page with `meta.moduleName`, so module pages can be identified later. |
| `resolvePagePath` | `(setting: string \| boolean \| undefined, defaultPath: string) => string \| undefined` | Turns an opt-in page setting into a path: a string is the custom path, `true` the default, anything else no page. |
| `addModulePages` | `(moduleName: string, resolver, pages: ModulePageDefinition[]) => void` | Registers a module's pages through `extendPages`, tagged with the module name. A page whose path is unset or already taken by the host app or another module is skipped, so a host can replace a shipped page by declaring its own at that path. |
| `registerTailwindSource` | `(nuxt: Nuxt, dir: string) => void` | Makes Tailwind scan a module's runtime folder (usually `./runtime/app`). Needs `@nuxt/ui`; does nothing without it. |

```ts
import { addModulePages, resolvePagePath } from '@frigear-nu/module-kit/utils'

addModulePages('@frigear-nu/events', resolver, [
  {
    name: 'events',
    path: resolvePagePath(options.settings?.pages?.events, '/events'),
    file: './runtime/app/pages/events.vue',
  },
])
```

```ts
interface ModulePageDefinition {
  name: string
  /** The route path; when `undefined` the page is not registered. */
  path: string | undefined
  /** The page component, relative to the module's `resolver`. */
  file: string
}
```

`registerTailwindSource` is needed because Tailwind only scans the host app and its layers, so classes used in a
module's components would otherwise never be generated. The source is appended to the `ui.css` that `@nuxt/ui`
generates; the host app needs no setup.

### `inlineModuleRuntime`

`inlineModuleRuntime(nuxt, resolver)` makes Nitro bundle the module's `runtime` directory instead of externalizing it.
An installed module lives in `node_modules`, which Nitro externalizes, so the server auto-imports registered with
`addServerImportsDir` (and virtual modules such as `#auth/*`) would not resolve in the consuming app. Call it right after
`addServerImportsDir` so hosts need no `nitro.externals.inline` of their own.

## URL helpers

`moduleUrl` and `moduleApiUrl` build kebab-cased paths. A `path` that starts with `/` is absolute, so the module name is
not prefixed.

```ts
import { moduleUrl, moduleApiUrl } from '@frigear-nu/module-kit/utils'

moduleUrl('OAuthServer') // => '/o-auth-server'
moduleUrl('OAuthServer', 'login') // => '/o-auth-server/login'
moduleApiUrl('OAuthServer', 'token') // => '/api/o-auth-server/token'
```

## Menu helpers

Let a module contribute items to a [Menu](/modules/menu) without importing it.

| Helper | Signature | Purpose |
| --- | --- | --- |
| `addMenuSource` | `(nuxt: Nuxt, options: MenuSourceOptions) => void` | Registers a menu source file. The menu module reads them once every module is done. Duplicates are ignored. |
| `addOptionalMenuSource` | `(nuxt: Nuxt, options: MenuSourceOptions) => boolean` | Same, but only when `@frigear-nu/menu` is installed. Returns whether it registered. |

```ts
interface MenuSourceOptions {
  /** The menu the items belong to, for example `dashboard.account`. */
  menu: string
  /** Absolute path of the source file (a `defineMenuSource` default export). */
  file: string
}

addOptionalMenuSource(nuxt, {
  menu: 'dashboard.account',
  file: resolver.resolve('./runtime/menus'),
})
```

The source file imports `@frigear-nu/menu/utils` itself, which only resolves when the file runs.

Modules should use `addOptionalMenuSource` and declare `@frigear-nu/menu` as an optional `moduleDependencies` entry and an optional peer dependency, so menu is never required. Module-kit does not depend on menu or widget. For widgets and tabs, guard the call in `setup()` yourself: check `hasNuxtModule('@frigear-nu/widget')`, then `await import('@frigear-nu/widget/utils')` and call `extendWidgets` / `extendTabs`.

## Virtual registries

`defineVirtualRegistry` is the "registry" pattern of the Frigear modules. Other modules register entries in any order
during their own `setup()`; once every module is done (`modules:done`), the collected entries are bundled into one
virtual module the runtime imports. There is no runtime scanning, which keeps it Workers friendly. Call it from the
owning module's `setup()`.

```ts
function defineVirtualRegistry<T>(nuxt: Nuxt, options: VirtualRegistryOptions<T>): void

interface VirtualRegistryOptions<T> {
  /** Template file name, for example `#widgets/registry.mjs`. */
  filename: string
  /** `app` writes the template and aliases it; `server` adds a Nitro virtual module. Defaults to `app`. */
  target?: 'app' | 'server'
  /** The import path of the virtual module (`app` target only), for example `#widgets/registry`. */
  alias?: string
  /** Reads what modules registered during their own `setup()`. */
  collect: () => T
  /** The source of the virtual module. */
  contents: (data: T) => string
  /** Called with the collected data after the template is registered. */
  resolved?: (data: T) => void | Promise<void>
}
```

## Translations (i18n)

Modules ship their own translations as one JSON file per locale and contribute them to `@nuxtjs/i18n`, which merges
every registered file per locale into one message tree. Namespace keys by module (`users.*`, `events.*`, ...) so slices
never collide; `@:path` links can reference keys from any slice.

| Helper | Signature | Purpose |
| --- | --- | --- |
| `registerLocales` | `(nuxt: Nuxt, langDir: string, codes?: string[]) => void` | Registers `<langDir>/<code>.json` for each code (default `da`, `en`). Missing files are skipped; does nothing without `@nuxtjs/i18n`. |
| `useModuleT` | `(namespace: string) => (key: string, fallback: string, params?: Record<string, string \| number>) => string` | Auto-imported composable for module UI that must work without i18n. Resolves `<namespace>.<key>` when the key exists, otherwise returns the English `fallback`. `{param}` placeholders are replaced either way. |

```ts
// in setup(options, nuxt)
registerLocales(nuxt, resolver.resolve('./runtime/i18n/lang')) // reads da.json / en.json
```

```ts
const t = useModuleT('events')
t('ongoing.title', 'Happening now')
t('detail.tickets.atLeastOneProductRequired', '{addonTitle} is required.', { addonTitle })
```

### Overriding module strings in your app

Every module that ships translations can be overridden the same way, with no module option. Redefine the key in your
app's own `i18n/locales/<code>.json`:

```json
{
  "payments": {
    "status": { "paid": "Payment received" }
  },
  "forms": {
    "actions": { "submit": "Send inquiry" }
  }
}
```

- Keys are namespaced by module. A module's full key list is its `src/runtime/i18n/lang/en.json`.
- Only list what you change: messages are deep-merged, so the rest keep the module's text.
- Your app wins. `@nuxtjs/i18n` merges module slices first, then extended layers, then your project's files last.
  Overrides therefore work for every locale, including ones a module does not ship.
- Keep parameters such as `{date}` or `{plan}` in your text; the component supplies them.
- Without `@nuxtjs/i18n`, nothing is registered and components use their English fallbacks.

## Database

These helpers let one module own a Drizzle table while other modules, layers and host apps extend it with columns,
without the owner knowing about them. All of them work on the generated NuxtHub schema.

| Helper | Signature | Purpose |
| --- | --- | --- |
| `registerDatabaseTable` | `(nuxt: Nuxt, options: DatabaseTableOptions) => void` | The owning module registers its schema. Generates the merged table. |
| `extendDatabaseTable` | `(nuxt: Nuxt, options: TableExtensionOptions) => void` | Another module registers a column file for a named table. |
| `defineTableColumns` | `<T extends Record<string, ColumnBuilderBase>>(columns: T) => T` | Typed identity helper for extension column objects. |
| `defineExtendableTable` | `<T>(table: ({ name, columns }) => T) => ({ name, columns }) => T` | Wraps a table factory so it receives `{ name, columns }`. Only for the `factory` option. |
| `onDatabaseSchemaExtend` | `(nuxt: Nuxt, extender: ({ dialect, paths }) => void \| Promise<void>) => void` | Lower-level primitive behind `registerDatabaseTable`: hooks `hub:db:schema:extend` to add schema files by hand. |

Extension merging also fires the `module-kit:db:table:extend` Nuxt hook, which `registerDatabaseTable` listens to.

### `registerDatabaseTable` options

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `name` | `string \| string[]` | every table export in `schema` | Export name(s) of the table(s). An array, or omitting it, generates all tables into one file so they can reference each other (foreign keys). Only allowed when `factory` is omitted. |
| `factory` | `string` | none | Exported factory (from `defineExtendableTable`) to call with `{ name, columns }`. Needs a single string `name`; passing an array or omitting `name` throws. |
| `resolver` | `ReturnType<typeof createResolver>` | required | Resolves the `schema` path. |
| `schema` | `(dialect: string) => string` | required | Path of the schema file for a dialect, for example `` dialect => `./runtime/db/schema.${dialect}` ``. |
| `override` | `string` | none | A path, resolved from the app's root, that replaces the generated table entirely. `'default'` keeps the generated table. |
| `extensionFile` | `(dialect: string) => string` | `server/db/extend.<dialect>.ts` | Changes the per-layer extension file location. |

### `extendDatabaseTable` options

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `name` | `string \| string[]` | every table | Table(s) the file extends. When omitted, every table whose export the file matches picks up its columns; other tables are untouched. |
| `resolver` | `ReturnType<typeof createResolver>` | required | Resolves the `file` path. |
| `file` | `(dialect: string) => string` | required | Path of the column file for a dialect. Files missing for a dialect are skipped. |

### Registering a table

With no `factory`, `schema` is a regular Drizzle file:

```ts
// runtime/db/schema.sqlite.ts
import { sqliteTable, text, integer } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  id: integer().primaryKey({ autoIncrement: true }),
  email: text().notNull().unique(),
})

export const userPasskeys = sqliteTable('user_passkeys', {
  id: integer().primaryKey({ autoIncrement: true }),
  userId: integer().notNull().references(() => users.id, { onDelete: 'cascade' }),
})
```

```ts
// Registers both tables (omit `name` to register every table export)
registerDatabaseTable(nuxt, {
  name: ['users', 'userPasskeys'],
  resolver: createResolver(import.meta.url),
  schema: dialect => `./runtime/db/schema.${dialect}`,
})
```

The base `schema` file must export a genuine table call (for example `sqliteTable('users', { ... })`) matching `name`.
It decides which factory (`sqliteTable`, `pgTable`, ...) and which SQL table name the merged result uses.

### Extending a table

A column file is a regular table definition or a plain columns object, with no helper wrapper:

```ts
extendDatabaseTable(nuxt, {
  name: 'users',
  resolver: createResolver(import.meta.url),
  file: dialect => `./runtime/db/extra.${dialect}`,
})
```

```ts
// runtime/db/extra.sqlite.ts
import { sqliteTable, text } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  locale: text().default('da'),
})
```

Columns are merged in registration order: later registrations replace earlier columns with the same key. Then the
Nuxt layers' `server/db/extend.<dialect>.ts` files are merged, from base layers toward the host app, and a single table
call is generated with the merged columns and deduplicated imports. Older `server/db/<name>.extend.<dialect>` files with
default exports still load, before each layer's shared file.

A layer or the host app can extend several tables from one file with `defineTableColumns`; only the export matching the
table being built is used:

```ts
// server/db/extend.sqlite.ts
export const users = defineTableColumns({ locale: text().default('da') })
export const posts = defineTableColumns({ summary: text() })
```

### Using a `factory`

Pass `factory` when you need shared defaults, for example timestamps, applied the same way for every dialect. The
factory must spread `columns` last, so extension columns end up last in the generated migration.

```ts
import { sqliteTable, integer, text } from 'drizzle-orm/sqlite-core'
import type { ColumnBuilderBase } from 'drizzle-orm'
import { defineExtendableTable } from '@frigear-nu/module-kit/utils'

export const defineUsersTable = defineExtendableTable(
  ({ name, columns }: { name: string, columns: Record<string, ColumnBuilderBase> }) => {
    return sqliteTable(name, {
      id: integer().primaryKey({ autoIncrement: true }),
      email: text().notNull().unique(),
      createdAt: integer({ mode: 'timestamp' }).notNull().$defaultFn(() => new Date()),
      ...columns,
    })
  },
)
```

```ts
registerDatabaseTable(nuxt, {
  name: 'users',
  factory: 'defineUsersTable',
  resolver: createResolver(import.meta.url),
  schema: dialect => `./runtime/db/schema.${dialect}`,
  override: options.settings?.schemas?.users,
})
```

### Migrations and database-backed module tests

`extendDatabaseTable` updates the generated Drizzle schema; it does not alter an existing database. Generate
migrations from the consuming application's complete module configuration, including every module that extends a
table. Test fixtures are consuming applications too: their committed migrations must match the merged schema, not just
the owning module's tables.

#### Updating a fixture's migrations

Run from the workspace root:

```bash
pnpm --filter <package-name> exec nuxt prepare "$PWD/packages/<package>/test/fixtures/<fixture>"
pnpm --filter <package-name> exec drizzle-kit generate \
  --dialect sqlite \
  --schema "$PWD/packages/<package>/test/fixtures/<fixture>/.nuxt/hub/db/schema.mjs" \
  --out test/fixtures/<fixture>/server/db/migrations/sqlite \
  --name <migration-name>
pnpm --filter <package-name> test test/<fixture>.test.ts
```

The filtered `exec` runs in the selected package, so `--out` is package-relative; use an absolute schema path. Preparing
the fixture first makes `.nuxt/hub/db/schema.mjs` include every schema extension.

Review and commit the generated SQL together with `meta/*_snapshot.json` and `meta/_journal.json`. Keep existing
migration history intact, and do not commit `.nuxt`, `.data`, `node_modules` or `dist` output.

#### Database-backed fixture requirements

- Configure a test-only session password and a local SQLite/libsql database.
- Use `dev: true` in `@nuxt/test-utils/e2e` setup so NuxtHub applies the fixture's committed migrations at startup.
  Disabling build-time migrations does not disable these development migrations.
- Remove only the fixture's dedicated `.data` directory before the suite and clean it up afterwards.
- Assert a request's HTTP status, with the response body as the message, before asserting its side effects (for
  example a session cookie). This surfaces the underlying HTTP or database error.
- Run the suite twice to verify migration application and database isolation. [Users](/modules/users) and
  [Account](/modules/account) have working fixture lifecycles.

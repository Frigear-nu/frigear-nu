---
title: Module Kit
description: Helpers for building Frigear Nuxt modules - pages, URLs, translations, menu sources, virtual registries and extendable database tables.
---

The shared toolkit behind every Frigear [Nuxt module](https://nuxt.com/docs/4.x/guide/modules). Use it to register
pages and translations, to let modules contribute to each other, and to let one module add columns to a table another
module owns, without replacing its schema. Almost every `@frigear-nu/*` module depends on it (account, admin, auth,
authorization, cookie-consent, events, forms, mcp, menu, oauth-server, payments, preferences, stripe, subscriptions,
users, widget); `notify` and `ui` do not. New to writing a module? Start with
[Writing a module](/getting-started/writing-a-module).

::note
**Requires** `@nuxthub/core` only for the [Database](#database) helpers, which also need the `drizzle-orm` and
`drizzle-kit` peer dependencies. Everything else works without NuxtHub. A module opts in with a `moduleDependencies`
entry, which installs module-kit in the host app and is what provides the `useModuleT` auto-import. Hosts need not add
`@frigear-nu/module-kit` to `modules` themselves. The `@frigear-nu/module-kit/utils` helpers are plain imports.
::

## Quick setup

```bash
pnpm add @frigear-nu/module-kit drizzle-orm drizzle-kit
```

```ts
// A module's setup(), importing the helpers it needs
import { defineNuxtModule, createResolver } from '@nuxt/kit'
import { registerModule, registerLocales } from '@frigear-nu/module-kit/utils'

export default defineNuxtModule({
  meta: { name: '@frigear-nu/events', configKey: 'events' },
  moduleDependencies: {
    // Installs module-kit in the host app and provides the `useModuleT` auto-import
    '@frigear-nu/module-kit': { version: '>=0.0.1' },
  },
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)
    registerModule('@frigear-nu/events', nuxt)
    registerLocales(nuxt, resolver.resolve('./runtime/i18n/lang'))
  },
})
```

## Options

The module has one config key, `moduleKit`. It is internal: `registerModule` writes to it, and you do not set it by
hand.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `_modules` | `string[]` | `[]` | Names of the Frigear modules registered in the current Nuxt app (see `registerModule`). |

## Exports

| Import | Contains |
| --- | --- |
| `@frigear-nu/module-kit` | The Nuxt module and everything from `/utils`. |
| `@frigear-nu/module-kit/utils` | Every helper below, except `/schedule`, `/server` and `/testing`. Includes `defaultLocaleNames` (`da: 'Dansk'`, `en: 'English'`), the locales `registerLocales` registers by default. |
| `@frigear-nu/module-kit/schedule` | `Schedule` and `ScheduleMoment` (types), `scheduleSchema` (zod), `isScheduleOpen` and `nextScheduleOpening`. Used by forms and events. |
| `@frigear-nu/module-kit/server` | The [server toolkit](#server-toolkit) for route handlers: errors, param schemas, pagination, responses. |
| `@frigear-nu/module-kit/testing` | `expectSchemaParity` and `compareSchemaDialects` (see [One schema file per dialect](#one-schema-file-per-dialect)), `apiClient` and `expectApiError` (see [Testing routes](#testing-routes)). |

`useModuleT` is auto-imported in app code wherever the module is installed.

### `/schedule`

A schedule is a recurring sale season or a fixed range. Both functions treat an `undefined` schedule as always open.

```ts
import { isScheduleOpen, nextScheduleOpening, scheduleSchema } from '@frigear-nu/module-kit/schedule'
import type { Schedule, ScheduleMoment } from '@frigear-nu/module-kit/schedule'

function isScheduleOpen(schedule: Schedule | undefined, now?: Date): boolean
function nextScheduleOpening(schedule: Schedule | undefined, now?: Date): Date | null
```

## Module helpers

| Helper | Signature | Purpose |
| --- | --- | --- |
| `registerModule` | `(moduleName: string, nuxt: Nuxt) => void` | Adds the name to `nuxt.options.moduleKit._modules`, de-duplicated. |
| `defineModulePage` | `(moduleName: string, page: NuxtPage) => NuxtPage` | Tags a page with `meta.moduleName`, so module pages can be identified later. |
| `resolvePagePath` | `(setting: string \| boolean \| undefined, defaultPath: string) => string \| undefined` | Turns an opt-in page setting into a path: a string is the custom path, `true` the default, anything else no page. |
| `addModulePages` | `(moduleName: string, resolver, pages: ModulePageDefinition[]) => void` | Registers a module's pages through `extendPages`, tagged with the module name. A page whose path is unset or already taken by the host app or another module is skipped, so a host can replace a shipped page by declaring its own at that path. |
| `registerTailwindSource` | `(nuxt: Nuxt, dir: string) => void` | Makes Tailwind scan a module's runtime folder (usually `./runtime/app`). Needs `@nuxt/ui`; does nothing without it. |

```ts
import { addModulePages, resolvePagePath } from '@frigear-nu/module-kit/utils'

addModulePages('@frigear-nu/events', resolver, [
  {
    name: 'events',
    path: resolvePagePath(options.settings?.pages?.events, '/events'),
    file: './runtime/app/pages/events.vue',
  },
])
```

```ts
interface ModulePageDefinition {
  name: string
  /** The route path; when `undefined` the page is not registered. */
  path: string | undefined
  /** The page component, relative to the module's `resolver`. */
  file: string
}
```

`registerTailwindSource` is needed because Tailwind only scans the host app and its layers, so classes used in a
module's components would otherwise never be generated. The source is appended to the `ui.css` that `@nuxt/ui`
generates; the host app needs no setup.

### `inlineModuleRuntime`

`inlineModuleRuntime(nuxt, resolver)` makes Nitro bundle the module's `runtime` directory instead of externalizing it.
An installed module lives in `node_modules`, which Nitro externalizes, so the server auto-imports registered with
`addServerImportsDir` (and virtual modules such as `#auth/*`) would not resolve in the consuming app. Call it right after
`addServerImportsDir` so hosts need no `nitro.externals.inline` of their own. It also pushes the runtime directory onto
`build.transpile`, so the app side is transpiled too.

## URL helpers

`moduleUrl` and `moduleApiUrl` build kebab-cased paths. They take the module's short name, not the scoped package name
(`'OAuthServer'`, not `'@frigear-nu/oauth-server'`, which would kebab-case to `/frigear-nu-oauth-server`). A `path`
that starts with `/` is absolute, so the module name is not prefixed.

```ts
import { moduleUrl, moduleApiUrl } from '@frigear-nu/module-kit/utils'

moduleUrl('OAuthServer') // => '/o-auth-server'
moduleUrl('OAuthServer', 'login') // => '/o-auth-server/login'
moduleApiUrl('OAuthServer', 'token') // => '/api/o-auth-server/token'
```

## Server toolkit

`@frigear-nu/module-kit/server` holds what every module route needs, so routes answer the same way everywhere (see
[HTTP route conventions](/getting-started/writing-a-module#http-route-conventions)). Import it explicitly: it is not
auto-imported, so nothing clashes with h3's own helpers.

### Registering routes

`addModuleRoutes` (from `/utils`) registers a module's routes from one table in `setup()`. `file` is relative to
`./runtime/server/routes/`; `path` is joined onto `base` (required), and a path starting with `/` ignores `base` (as with
`moduleApiUrl`); `''` is `base` itself.

```ts
import { addModuleRoutes } from '@frigear-nu/module-kit/utils'

addModuleRoutes(resolver, [
  { method: 'get', path: '', file: 'admin/events.get' },
  { method: 'post', path: '', file: 'admin/events.post' },
  { method: 'get', path: ':id', file: 'admin/event.get' },
  { method: 'patch', path: ':id', file: 'admin/event.patch' },
  { method: 'post', path: ':id/clone', file: 'admin/event-clone.post' },
  { method: 'get', path: '/api/events/me/tickets', file: 'me/tickets.get' },
], { base: '/api/admin/events' })
```

### Errors

| Helper | Status | `data.code` |
| --- | --- | --- |
| `apiError(status, code, message, data?)` | any | `code` |
| `badRequest(message?, data?)` | 400 | `bad_request` |
| `validationError(issues, message?)` | 400 | `validation_failed`, issues in `data.issues` |
| `forbidden(message?, data?)` | 403 | `forbidden` |
| `notFound(message?, data?)` | 404 | `not_found` |
| `conflict(message?, data?)` | 409 | `conflict` |
| `notConfigured(message?, data?)` | 501 | `not_configured` |

Each returns an h3 error to `throw`: `statusMessage` is the human message (what `errorMessage()` in `@frigear-nu/ui`
shows in a toast), `data` is `{ ...data, code }` (`ApiErrorData`). `requireAuth` answers the same way, with the codes
`unauthorized`, `session_required` and `insufficient_scope`.

```ts
import { conflict, notFound } from '@frigear-nu/module-kit/server'

if (!form) throw notFound('Form not found.')
if (await slugTaken(body.slug)) throw conflict('That slug is taken.', { field: 'slug' })
```

### Params

`idParams(name = 'id')` (a non-empty string) and `intIdParams(name = 'id')` (a positive integer, coerced) are zod
schemas for `getValidatedRouterParams`, so ids are validated the same way in every module.

```ts
const { id } = await getValidatedRouterParams(event, idParams().parse)
const { tokenId } = await getValidatedRouterParams(event, idParams('tokenId').parse)
const { id: userId } = await getValidatedRouterParams(event, intIdParams().parse)
```

### Pagination

`pageQuery({ sort, defaultSort?, defaultOrder?, defaultPageSize?, maxPageSize?, filters? })` returns the zod schema of
a list query in the vocabulary of `useTableQuery`: `page` (from 1), `pageSize` (default 20, at most 100), `q`, `sort`
(one of `sort`, default `defaultSort` or the first), `order` (`asc`/`desc`, default `desc`) and the `filters` keys.
`paginate({ items, total, query })` returns `Page<T>`, `{ items, total, page, pageSize }`, and `pageRange(query)` the
`{ limit, offset }`. `orderByQuery(columns, query, { tiebreaker })` turns `query.sort`/`query.order` into an
`orderBy` (a sort key mapped to `undefined` falls back to the tiebreaker), with the tiebreaker (usually the id)
descending so pages stay stable. `escapeLike`, `likeEscaped(column, pattern)` and `likeContains(column, value)` search
case-insensitively with `lower(...) LIKE lower(...)` on both dialects, without letting `%` and `_` in the search act as
wildcards.

```ts
import { likeContains, orderByQuery, pageQuery, pageRange, paginate } from '@frigear-nu/module-kit/server'

const listQuery = pageQuery({ sort: ['startsAt', 'slug'], filters: { status: z.enum(['draft', 'published']).optional() } })

export default defineEventHandler(async (event) => {
  await eventsStaff.require(event)
  const query = await getValidatedQuery(event, listQuery.parse)
  const where = and(
    query.q ? likeContains(schema.events.slug, query.q) : undefined,
    query.status ? eq(schema.events.status, query.status) : undefined,
  )
  const orderBy = orderByQuery({ startsAt: schema.events.startsAt, slug: schema.events.slug }, query, { tiebreaker: schema.events.id })
  const { limit, offset } = pageRange(query)
  const [rows, [totals]] = await Promise.all([
    db.select().from(schema.events).where(where).orderBy(...orderBy).limit(limit).offset(offset),
    db.select({ total: count() }).from(schema.events).where(where),
  ])
  return paginate({ items: rows.map(toEventDto), total: totals?.total ?? 0, query })
})
```

### Responses and helpers

| Helper | Purpose |
| --- | --- |
| `created(event, dto)` | Sets 201 and returns `dto`. |
| `noContent(event)` | Sets 204 and returns `null`, for deletes and revokes. |
| `isoDate(value)` | A `Date`, epoch milliseconds or date string as an ISO string; `null`/`undefined` as `null`. |
| `uniqueCopySlug(base, exists)` | The first free `<base>-copy`, `<base>-copy-2`, ... `exists(slug)` may return any truthy value for taken. |
| `resolveSameOriginUrl(event, url, { fallback?, name? })` | A client-supplied return URL as an absolute URL on the request's origin; `fallback` (a path) when `url` is empty; 400 `bad_request` when it points elsewhere. |
| `sameOriginUrl(input, origin)` | The check behind it, without an event: the normalised absolute URL (`URL.href`), or `null`. |

### Field issues

h3's `readValidatedBody(event, schema.parse)` answers a failed parse with a 400 whose `data` carries the zod error only
as text. When the client needs per-field issues (a form that marks each input), parse yourself with `schema.safeParse`
and throw `validationError(issues)`; the issues arrive in `data.issues`. Forms `submit` is the example:

```ts
const result = definition.schema.safeParse(await readBody(event))
if (!result.success) throw validationError(result.error.issues)
```

### Naming server utils

Every module's `server/utils` is auto-imported into one Nitro namespace, so an exported name must be unique across all
modules: prefix it with the module (`toFormTokenDto`, `toAuthTokenDto`, never a generic `toTokenDto`). Two modules
exporting the same name clash and one silently wins.

### Path builders

Each module keeps typed path builders in `src/runtime/utils/api.ts` (`authApi`, `eventsApi`, `formsApi`, ...) and
exports them as `@frigear-nu/<pkg>/api`. Import them from there in app code and tests, not from `./utils`: the `./utils`
entry also holds build-time helpers that pull in `@nuxt/kit`. Relative imports inside the package stay relative.

```ts
import { authApi } from '@frigear-nu/auth/api'
```

### Testing routes

`@frigear-nu/module-kit/testing` has two helpers for e2e tests against a fixture started with `setup()` from
`@nuxt/test-utils/e2e`:

- `apiClient({ cookie?, bearer? })` acts as one caller. `json<T>(method, path, body?)` resolves with the parsed body
  of a 2xx response (`null` for 204) and rejects otherwise; `fetch(method, path, body?)` resolves with the raw
  `Response` whatever its status.
- `expectApiError(promise, status, code?)` asserts that the request of either failed with `status` (and `data.code`),
  and resolves with the error body.

```ts
import { apiClient, expectApiError } from '@frigear-nu/module-kit/testing'

const staff = apiClient({ cookie: staffCookie })
const created = await staff.json<{ id: string }>('POST', '/api/admin/events', { slug: 'party' })
await expectApiError(apiClient({ cookie: memberCookie }).json('DELETE', `/api/admin/events/${created.id}`), 403, 'forbidden')
expect((await staff.fetch('DELETE', `/api/admin/events/${created.id}`)).status).toBe(204)
```

## Menu helpers

Let a module contribute items to a [Menu](/modules/menu) without importing it.

| Helper | Signature | Purpose |
| --- | --- | --- |
| `addMenuSource` | `(nuxt: Nuxt, options: MenuSourceOptions) => void` | Registers a menu source file. The menu module reads them once every module is done. Duplicates are ignored. |
| `addOptionalMenuSource` | `(nuxt: Nuxt, options: MenuSourceOptions) => boolean` | Same, but only when `@frigear-nu/menu` is installed. Returns whether it registered. |

```ts
interface MenuSourceOptions {
  /** The menu the items belong to, for example `dashboard.account`. */
  menu: string
  /** Absolute path of the source file (a `defineMenuSource` default export). */
  file: string
}

addOptionalMenuSource(nuxt, {
  menu: 'dashboard.account',
  file: resolver.resolve('./runtime/menus'),
})
```

The source file imports `@frigear-nu/menu/utils` itself, which only resolves when the file runs.

Modules should use `addOptionalMenuSource` and declare `@frigear-nu/menu` as an optional `moduleDependencies` entry and an optional peer dependency, so menu is never required. Module-kit does not depend on menu or widget. For widgets and tabs, guard the call in `setup()` yourself: check `hasNuxtModule('@frigear-nu/widget')`, then `await import('@frigear-nu/widget/utils')` and call `extendWidgets` / `extendTabs`.

## Virtual registries

`defineVirtualRegistry` is the "registry" pattern of the Frigear modules. Other modules register entries in any order
during their own `setup()`; once every module is done (`modules:done`), the collected entries are bundled into one
virtual module the runtime imports. There is no runtime scanning, which keeps it Workers friendly. Call it from the
owning module's `setup()`.

```ts
function defineVirtualRegistry<T>(nuxt: Nuxt, options: VirtualRegistryOptions<T>): void

interface VirtualRegistryOptions<T> {
  /** Template file name, for example `#widgets/registry.mjs`. */
  filename: string
  /** `app` writes the template and aliases it; `server` adds a Nitro virtual module. Defaults to `app`. */
  target?: 'app' | 'server'
  /** The import path of the virtual module (`app` target only), for example `#widgets/registry`. */
  alias?: string
  /** Reads what modules registered during their own `setup()`. */
  collect: () => T
  /** The source of the virtual module. */
  contents: (data: T) => string
  /** Called with the collected data after the template is registered. */
  resolved?: (data: T) => void | Promise<void>
}
```

## Bootstrap providers

An area such as the account pages shows several modules' data for the signed-in user. Without bootstrap providers,
each module's composable makes its own request. A bootstrap provider adds your module's piece to the area's single
request, `GET /api/auth/bootstrap?scope=<scope>`. The area loads that request before its pages set up and primes the
`useCachedFetch` cache, so your composable renders without a request of its own.

```ts
function registerBootstrapProvider(nuxt: Nuxt, provider: {
  /** The area, e.g. `account`. */
  scope: string
  /** The response key, and the `useCachedFetch` key your composable already uses for the same data. */
  key: string
  /** Server file whose default export is `(event: H3Event) => Promise<data>`; absolute or relative to rootDir. */
  handler: string
}): void

getBootstrapProviders(nuxt: Nuxt, scope?: string): BootstrapProvider[] // what is registered so far
defineBootstrapRegistry(nuxt: Nuxt): void // bundles them into `#bootstrap/providers` (called by @frigear-nu/auth)
```

Share one function between your endpoint and the provider, so the two always return the same shape. Events does it
like this:

```ts [runtime/server/bootstrap/my-tickets.ts]
export default async function myTickets(event: H3Event): Promise<TicketDto[]> {
  const user = await requireUser(event, { scopes: ['tickets:read'] })
  return listUserTickets(user.id)
}
```

```ts [runtime/server/routes/public/tickets-me.get.ts]
import myTickets from '../../bootstrap/my-tickets'

export default defineEventHandler(myTickets)
```

```ts [module.ts]
registerBootstrapProvider(nuxt, {
  scope: 'account',
  key: 'events:tickets:mine', // what useMyTickets() passes to useCachedFetch
  handler: resolver.resolve('./runtime/server/bootstrap/my-tickets'),
})
```

Nothing changes in the composable: `useCachedFetch` finds the primed entry under its key, on the server, while
hydrating and on client navigation.

How it fits together:

- **Route (`@frigear-nu/auth`).** It calls `requireAuth` once (401 when signed out), then runs the scope's providers
  side by side on the same event and returns `{ [key]: data }`. A missing `scope` is a 400 and a scope without
  providers is a 404. The response is `private, no-store`. Module-kit cannot serve the route, because auth already
  depends on module-kit.
- **Authorization.** The principal is resolved once and cached on the event, so call `requireUser` /
  `requireAuth` with your route's scopes in the provider, as your route does.
- **Failures.** A provider that throws (a token without your scope, a database error) is left out of the response and
  logged. Your composable then fetches from your own endpoint. Providers must not write to the response (status,
  headers): they share it.
- **Client (`@frigear-nu/ui`).** The area's owner calls `loadBootstrap(scope)` from a route middleware on its pages.
  It primes each key and fetches again only when the last bootstrap is older than its `ttl` (one minute). See
  [Loading data that survives navigation](/modules/ui#one-request-for-an-area-loadbootstrap).
- **The `account` scope.** `@frigear-nu/account` adds the middleware to every account page (when any `account`
  provider is registered) and resets the bootstrap when the signed-in user changes. Today subscriptions
  (`subscriptions:me`), events (`events:tickets:mine`) and oauth-server (`oauth-server:mine`) provide data for it.
- **Keep it small.** Register only data a page of the area shows on first render. Data a page loads later, or lists
  that grow without bound, belong in the module's own endpoint.

## Translations (i18n)

Modules ship their own translations as one JSON file per locale and contribute them to `@nuxtjs/i18n`, which merges
every registered file per locale into one message tree. Namespace keys by module (`users.*`, `events.*`, ...) so slices
never collide; `@:path` links can reference keys from any slice.

| Helper | Signature | Purpose |
| --- | --- | --- |
| `registerLocales` | `(nuxt: Nuxt, langDir: string, codes?: string[]) => void` | Registers `<langDir>/<code>.json` for each code (default `da`, `en`). Missing files are skipped; does nothing without `@nuxtjs/i18n`. |
| `useModuleT` | `(namespace: string) => (key: string, fallback: string, params?: Record<string, string \| number>) => string` | Auto-imported composable for module UI that must work without i18n. Resolves `<namespace>.<key>` when the key exists, otherwise returns the English `fallback`. `{param}` placeholders are replaced either way. |

```ts
// in setup(options, nuxt)
registerLocales(nuxt, resolver.resolve('./runtime/i18n/lang')) // reads da.json / en.json
```

```ts
const t = useModuleT('events')
t('ongoing.title', 'Happening now')
t('detail.tickets.atLeastOneProductRequired', '{addonTitle} is required.', { addonTitle })
```

### Overriding module strings in your app

Every module that ships translations can be overridden the same way, with no module option. Redefine the key in your
app's own `i18n/locales/<code>.json`:

```json
{
  "payments": {
    "status": { "paid": "Payment received" }
  },
  "forms": {
    "actions": { "submit": "Send inquiry" }
  }
}
```

- Keys are namespaced by module. A module's full key list is its `src/runtime/i18n/lang/en.json`.
- Only list what you change: messages are deep-merged, so the rest keep the module's text.
- Your app wins. `@nuxtjs/i18n` merges module slices first, then extended layers, then your project's files last.
  Overrides therefore work for every locale, including ones a module does not ship.
- Keep parameters such as `{date}` or `{plan}` in your text; the component supplies them.
- Without `@nuxtjs/i18n`, nothing is registered and components use their English fallbacks.

## Database

These helpers let one module own a Drizzle table while other modules, layers and host apps extend it with columns,
without the owner knowing about them. All of them work on the generated NuxtHub schema. The calls are synchronous:
they only register hooks, and the work happens when NuxtHub builds the schema. Code that still writes `await` in front
of them keeps working.

| Helper | Signature | Purpose |
| --- | --- | --- |
| `registerDatabaseTable` | `(nuxt: Nuxt, options: DatabaseTableOptions) => void` | The owning module registers its schema file. Generates the merged tables. |
| `extendDatabaseTable` | `(nuxt: Nuxt, options: TableExtensionOptions) => void` | Another module registers a column file for the tables it extends. |
| `defineTableColumns` | `<T extends Record<string, ColumnBuilderBase>>(columns: T) => T` | Typed identity helper for extension column objects. |
| `onDatabaseSchemaExtend` | `(nuxt: Nuxt, extender: DbExtenderFn) => void` | Lower-level primitive behind `registerDatabaseTable`: hooks `hub:db:schema:extend` to add schema files by hand. |
| `defineExtendableTable` | `<T>(table: ({ name, columns }) => T) => ({ name, columns }) => T` | Deprecated. Wraps a table factory, see [Advanced: factory](#advanced-deprecated-factory). |

The option and callback types are exported from `@frigear-nu/module-kit/utils`: `DatabaseTableOptions`,
`TableExtensionOptions`, `DbExtenderFn` and `TableExtenderFn` (and `TableDefinerProps` for factories).

### Registering a table

The owning module ships a plain Drizzle schema file and registers it. There is no wrapper, no `name` and nothing to
`await`:

```ts
// src/runtime/server/db/schema.sqlite.ts
import { sqliteTable, text, integer } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  id: integer().primaryKey({ autoIncrement: true }),
  email: text().notNull().unique(),
})

export const userPasskeys = sqliteTable('user_passkeys', {
  id: integer().primaryKey({ autoIncrement: true }),
  userId: integer().notNull().references(() => users.id, { onDelete: 'cascade' }),
})
```

```ts
// src/module.ts, in setup()
import { createResolver } from '@nuxt/kit'
import { registerDatabaseTable } from '@frigear-nu/module-kit/utils'

const resolver = createResolver(import.meta.url)

registerDatabaseTable(nuxt, {
  resolver,
  schema: dialect => `./runtime/server/db/schema.${dialect}`,
})
```

Every export of the file that is initialised by a table call (`sqliteTable(...)`, `pgTable(...)`) is registered, and
all of them are generated into one file so they can reference each other (the foreign key above). Exported values
that are not table calls are ignored. The base file decides which factory (`sqliteTable`, `pgTable`, ...) and which SQL
table name the merged result uses.

#### `registerDatabaseTable` options

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `resolver` | `ReturnType<typeof createResolver>` | required | Resolves the `schema` path. |
| `schema` | `(dialect: string) => string` | required | Path of the schema file for a dialect, for example `` dialect => `./runtime/db/schema.${dialect}` ``. |
| `name` | `string \| string[]` | every table export in `schema` | Restricts which table exports are registered, see below. |
| `override` | `string` | none | A path, resolved from the app's root, that replaces the generated table entirely. `'default'` keeps the generated table. |
| `extensionFile` | `(dialect: string) => string` | `server/db/extend.<dialect>.ts` | Changes the per-layer extension file location. Also turns off the legacy `<name>.extend.<dialect>` lookup. |
| `factory` | `string` | none | Deprecated, see [Advanced: factory](#advanced-deprecated-factory). |

Leave `name` out. Pass it only to **restrict** the tables that are registered. Auth does this because which of its
tables exist depends on the enabled features:

```ts
// packages/auth/src/module.ts
const tables = ['authUserTokens']
if (withWebAuthn) tables.push('userCredentials')
if (withPasswordReset) tables.push('passwordResets')
if (withMagicLink || withVerifyEmail) tables.push('magicLinks')

registerDatabaseTable(nuxt, {
  name: tables,
  resolver,
  schema: dialect => `./runtime/db/schema.${dialect}`,
})
```

A `name` that is not exported by the file throws, and so does one that points at an export that is not a table call
("export exists but is not a table call").

### One schema file per dialect

NuxtHub resolves `schema` and `file` for the host's dialect (`sqlite` or `postgresql`), so every module ships both
`schema.sqlite.ts` and `schema.postgresql.ts`, with the same exports and the same table, column and index names.
`registerDatabaseTable` throws when the file for the active dialect does not exist; the error names the dialect, the
expected file and the `override` option that points at a file of your own.

```ts
// src/runtime/server/db/schema.postgresql.ts
import { pgTable, text, serial, integer } from 'drizzle-orm/pg-core'

export const users = pgTable('users', {
  id: serial().primaryKey(),
  email: text().notNull().unique(),
})

export const userPasskeys = pgTable('user_passkeys', {
  id: serial().primaryKey(),
  userId: integer().notNull().references(() => users.id, { onDelete: 'cascade' }),
})
```

| sqlite | postgresql |
| --- | --- |
| `integer().primaryKey({ autoIncrement: true })` | `serial().primaryKey()` |
| `integer({ mode: 'timestamp' })` | `timestamp({ withTimezone: true })` |
| `integer({ mode: 'boolean' })` | `boolean()` |
| `text({ mode: 'json' })` | `jsonb()` |
| `integer()` holding epoch milliseconds | `bigint({ mode: 'number' })` |

Keep the two files in sync with a test. `expectSchemaParity` from `@frigear-nu/module-kit/testing` throws, listing
every difference in tables, columns (drizzle data type, not null, primary key, unique, defaults, `$defaultFn`,
`$onUpdateFn`), indexes and foreign keys; `compareSchemaDialects` returns the same list instead.

```ts
// test/schema-parity.test.ts
import { it } from 'vitest'
import { expectSchemaParity } from '@frigear-nu/module-kit/testing'
import * as sqlite from '../src/runtime/server/db/schema.sqlite'
import * as postgresql from '../src/runtime/server/db/schema.postgresql'

it('schema.postgresql matches schema.sqlite', () => {
  expectSchemaParity(sqlite, postgresql)
})
```

### Extending a table

Another module adds columns to a table it does not own with `extendDatabaseTable`. The column file is a regular table
definition, a plain columns object or a `defineTableColumns` call, exported under the table's name. Again, no `name`:

```ts
// src/module.ts, in setup()
extendDatabaseTable(nuxt, {
  resolver,
  file: dialect => `./runtime/db/users.${dialect}`,
})
```

```ts
// src/runtime/db/users.sqlite.ts
import { sqliteTable, text } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  locale: text().default('da'),
})
```

```ts
// src/runtime/db/users.postgresql.ts
import { pgTable, text } from 'drizzle-orm/pg-core'

export const users = pgTable('users', {
  locale: text().default('da'),
})
```

The file is merged into every registered table it has a matching export for, and only into those: a table with no
matching export is untouched, and so are other exports of the same file. A module that extends `users` therefore never
needs to name the table. When the owning module is not installed nothing matches and the call has no effect.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `resolver` | `ReturnType<typeof createResolver>` | required | Resolves the `file` path. |
| `file` | `(dialect: string) => string` | required | Path of the column file for a dialect. A file missing for a dialect is skipped, with a warning when the `sqlite` file exists. |
| `name` | `string \| string[]` | every table | Only offer the file to these tables. Rarely needed: matching exports already decide. |

#### Merge order

Columns are merged in this order, and a column that appears again replaces the earlier one:

1. The base schema file of the owning module.
2. Files registered with `extendDatabaseTable`, in registration order.
3. For each Nuxt layer, from the base layers towards the host app: the legacy `server/db/<name>.extend.<dialect>`
   file, then the shared `server/db/extend.<dialect>.ts`. A layer or the host app extends several tables from one
   file; only the export matching the table being built is used:

   ```ts
   // server/db/extend.sqlite.ts
   export const users = defineTableColumns({ locale: text().default('da') })
   export const posts = defineTableColumns({ summary: text() })
   ```

A replaced column moves to the end of the generated table (its position in the column list changes, not its name).
Legacy `<name>.extend.<dialect>` files with a `default` export are still honoured. Passing `extensionFile` replaces the
`server/db/extend.<dialect>.ts` location and also disables the legacy lookup.

#### Constraints of schema files

::note
Schema and extension files are **parsed as text, not executed**. The generated file is assembled from what the parser
finds, so keep them simple:

- Only top-level exports initialised by a table call (`sqliteTable('users', { ... })`) are registered. In an
  extension file a plain columns object or a single-argument wrapper such as `defineTableColumns({ ... })` works too.
- Named imports are carried over, de-duplicated (a value import wins over `type X`). Relative specifiers such as
  `'../types'` are rewritten to absolute paths, and `type` is kept on type-only imports. Default and namespace imports
  are not carried over.
- Top-level helpers, constants and type aliases are **not** carried over. Declare what a column needs inline, or import
  it by name. `packages/events/src/runtime/server/db/schema.sqlite.ts` is the pattern: a `customType` written inline
  in the column and everything else imported from `drizzle-orm`.
- Indexes and constraints (the third argument of the table call) of the **base** file are kept. The third argument of
  an **extension** file is dropped with a warning, and so is a different SQL table name than the base declares. Put
  indexes on extension columns in the base file or in a migration.
::

#### Hooks

| Hook | Payload | Purpose |
| --- | --- | --- |
| `hub:db:schema:extend` | `{ dialect: string, paths: string[] }` | NuxtHub's hook. `registerDatabaseTable` pushes the path of each generated file to `paths`; `onDatabaseSchemaExtend` hooks it directly. |
| `module-kit:db:table:extend` | `{ name: string, dialect: string, paths: string[] }` | Called once per registered table. `extendDatabaseTable` pushes its file to `paths`; hook it yourself to contribute files by hand. |

#### Generated files

Merged tables are written to `.nuxt/module-kit/db/<kebab-case table names>.<dialect>.ts`, for example
`.nuxt/module-kit/db/users-user-passkeys.sqlite.ts`. A file name over 80 characters is shortened and gets a short hash
suffix. Open them when a migration does not look like you expect: they are exactly what NuxtHub builds the schema from.

NuxtHub bundles them into `.nuxt/hub/db/schema.mjs` with tsdown on every boot and `nuxt prepare`. The workspace patches
`@nuxthub/core` (`patches/`) to skip that bundle when the inputs are unchanged, keyed by `.nuxt/hub/db/schema.hash`
(a hash of the entry and every local file it imports): it saves about three seconds per dev boot. Delete the hash file
to force a rebuild.

### Advanced (deprecated): `factory`

Passing `factory` is deprecated: it logs a one-time warning, and plain tables above cover the same need. It remains for
existing schemas that must apply shared defaults, for example timestamps, to a table. The factory is exported from the
schema file, wrapped in `defineExtendableTable`, and must spread `columns` last so extension columns end up last in the
generated migration. It needs a single string `name`, and passing an array or omitting it throws.

```ts
import { sqliteTable, integer, text } from 'drizzle-orm/sqlite-core'
import type { ColumnBuilderBase } from 'drizzle-orm'
import { defineExtendableTable } from '@frigear-nu/module-kit/utils'

export const defineUsersTable = defineExtendableTable(
  ({ name, columns }: { name: string, columns: Record<string, ColumnBuilderBase> }) => {
    return sqliteTable(name, {
      id: integer().primaryKey({ autoIncrement: true }),
      email: text().notNull().unique(),
      createdAt: integer({ mode: 'timestamp' }).notNull().$defaultFn(() => new Date()),
      ...columns,
    })
  },
)
```

```ts
registerDatabaseTable(nuxt, {
  name: 'users',
  factory: 'defineUsersTable',
  resolver: createResolver(import.meta.url),
  schema: dialect => `./runtime/db/schema.${dialect}`,
})
```

Migrate away by exporting the table directly (`export const users = sqliteTable('users', { ... })`, with the shared
columns written out) and dropping `factory` and `name`. Extension files keep working unchanged.

### Migrations and database-backed module tests

`extendDatabaseTable` updates the generated Drizzle schema; it does not alter an existing database. Generate
migrations from the consuming application's complete module configuration, including every module that extends a
table. Test fixtures are consuming applications too: their committed migrations must match the merged schema, not just
the owning module's tables. Modules that have database fixtures include [Users](/modules/users) (`self-service`,
`admin-db`, `magic-link-db`, `verified-email-change`), [Auth](/modules/auth) (`auth-db`) and [Events](/modules/events)
(`authenticated`); the account module has none.

#### Checking and updating a fixture's migrations

Run from the workspace root. `nuxt db generate` prepares the fixture, so the generated schema includes every
extension, and compares it with the committed migrations:

```bash
pnpm --filter @frigear-nu/<package> exec nuxt db generate --cwd "$PWD/packages/<package>/test/fixtures/<fixture>"
```

- **Pass `--cwd` as an absolute path.** A relative path is resolved twice and fails.
- A fixture that is in sync prints `No schema changes, nothing to migrate` and leaves `git status` clean. Run it after
  changing a schema or an extension; any other output means the fixture needs a new migration.
- With NuxtHub `0.10.8` the command does not pass `--name` on correctly. To pick the migration's name, use the manual
  flow below, which gives the same result.

To generate a named migration:

```bash
pnpm --filter @frigear-nu/<package> exec nuxt prepare "$PWD/packages/<package>/test/fixtures/<fixture>"
pnpm --filter @frigear-nu/<package> exec drizzle-kit generate \
  --dialect sqlite \
  --schema "$PWD/packages/<package>/test/fixtures/<fixture>/.nuxt/hub/db/schema.mjs" \
  --out test/fixtures/<fixture>/server/db/migrations/sqlite \
  --name <migration-name>
pnpm --filter @frigear-nu/<package> test
```

The filtered `exec` runs in the selected package, so `--out` is package-relative; use an absolute schema path. Use
`generate`, not `drizzle-kit check`: it creates the migration only when something changed. Review and commit the
generated SQL together with `meta/*_snapshot.json` and `meta/_journal.json`. Keep existing migration history intact, and
do not commit `.nuxt`, `.data`, `node_modules` or `dist` output.

#### Database-backed fixture requirements

- Configure a test-only session password and a local SQLite/libsql database.
- A fixture that includes a module using `requireAuth` or `requireUser` needs the `auth_user_tokens` migration; the
  [Auth](/modules/auth) fixtures show it.
- Use `dev: true` in `@nuxt/test-utils/e2e` setup so NuxtHub applies the fixture's committed migrations at startup.
  Disabling build-time migrations does not disable these development migrations.
- Remove only the fixture's dedicated `.data` directory before the suite and clean it up afterwards.
- Assert a request's HTTP status, with the response body as the message, before asserting its side effects (for
  example a session cookie). This surfaces the underlying HTTP or database error.
- Run the suite twice to verify migration application and database isolation. [Users](/modules/users) and
  [Events](/modules/events) have working fixture lifecycles.

## `@frigear-nu/module-kit`

A shared toolkit for building Nuxt modules in the Frigear workspace. It provides helpers for composing and
extending database schemas, as well as small utilities for registering modules, pages, and URLs, while keeping
table-specific behavior in the modules that own those tables.

### Purpose

- Share common module-development utilities across Frigear packages.
- Let one module add columns to a table owned by another module without replacing its schema.

This [Nuxt module](https://nuxt.com/docs/4.x/guide/modules) is consumed by modules such as [`@frigear-nu/users`](/modules/users).

## Utils & composables

All of the helpers below are exported from `@frigear-nu/module-kit/utils`.

### Module helpers

#### `registerModule`

Registers a module name against `nuxt.options.moduleKit._modules`, de-duplicating entries. Useful during a module's
`setup()` to keep track of which Frigear modules are active in the current Nuxt app:

```ts
import { registerModule } from '@frigear-nu/module-kit/utils'

registerModule('@frigear-nu/users', nuxt)
```

#### `defineModulePage`

Tags a `NuxtPage` with the owning module's name in `page.meta.moduleName`, so pages registered by a module can be
identified later (e.g. for navigation or permission checks):

```ts
import { defineModulePage } from '@frigear-nu/module-kit/utils'

extendPages((pages) => {
  pages.push(defineModulePage('@frigear-nu/users', {
    name: 'users-profile',
    path: '/users/profile',
    file: resolver.resolve('./runtime/pages/profile.vue'),
  }))
})
```

### URL helpers

#### `moduleUrl` and `moduleApiUrl`

Build consistent, kebab-cased URLs for a module's pages and API routes. If `path` starts with `/` it is treated as
absolute and the module name is not prefixed:

```ts
import { moduleUrl, moduleApiUrl } from '@frigear-nu/module-kit/utils'

moduleUrl('OAuthServer') // => '/o-auth-server'
moduleUrl('OAuthServer', 'login') // => '/o-auth-server/login'
moduleApiUrl('OAuthServer', 'token') // => '/api/o-auth-server/token'
```

## Translations (i18n)

Modules ship their own translations as one JSON file per locale and contribute them to `@nuxtjs/i18n`, which merges every
registered file per locale into a single message tree. Namespace keys by module (`users.*`, `events.*`, ...) so slices never collide;
`@:path` links can reference keys from any slice.

### `registerLocales`

```ts
import { registerLocales } from '@frigear-nu/module-kit/utils'

// in setup(options, nuxt)
registerLocales(nuxt, resolver.resolve('./runtime/i18n/lang')) // reads da.json / en.json
```

Missing files are skipped, and nothing happens when `@nuxtjs/i18n` is not installed. Pass a third argument to register other locale codes.

### `useModuleT`

Auto-imported composable for module UI that must keep working without i18n. It resolves `<namespace>.<key>` through `@nuxtjs/i18n` when
the key exists, otherwise returns the English fallback (`{param}` placeholders are replaced either way).

```ts
const t = useModuleT('events')
t('ongoing.title', 'Happening now')
t('detail.tickets.atLeastOneProductRequired', '{addonTitle} is required.', { addonTitle })
```

### Overriding module strings in your app

Every module that ships translations can be overridden the same way, with no module option. Redefine the key in your
app's own `i18n/locales/<code>.json` (the file `@nuxtjs/i18n` already loads for your app):

```json
// i18n/locales/en.json
{
  "payments": {
    "status": { "paid": "Payment received" }
  },
  "forms": {
    "actions": { "submit": "Send inquiry" }
  }
}
```

- **Keys are namespaced by module** (`users.*`, `auth.*`, `events.*`, `forms.*`, ...). The full key list of a module is
  its `src/runtime/i18n/lang/en.json`, and each module page lists its keys.
- **Only list what you change.** Messages are deep-merged, so keys you leave out keep the module's text.
- **Your app wins.** `@nuxtjs/i18n` merges the files of each locale in order: module slices first, then extended layers,
  then your project's own files last. Overrides therefore work for every locale, including ones a module does not ship
  (`da` and `en` ship by default).
- **Parameters** such as `{date}` or `{plan}` must be kept in your text, as the component supplies them.
- **Without `@nuxtjs/i18n`** nothing is registered and components use their English fallbacks, so there is nothing to
  override.

## Extending a database table

These helpers let one module own a Drizzle table while letting other modules (and host applications) extend it with
additional columns, without the owning module needing to know about them.

### `registerDatabaseTable`

The table-owning module registers its schema with `registerDatabaseTable`. The simplest usage needs no wrapper at
all — `schema` can be a *regular* drizzle file:

```ts
// runtime/db/schema.sqlite.ts
import { sqliteTable, text, integer } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  id: integer().primaryKey({ autoIncrement: true }),
  email: text().notNull().unique(),
})
```

```ts
registerDatabaseTable(nuxt, {
  name: 'users',
  resolver: createResolver(import.meta.url),
  schema: dialect => `./runtime/db/schema.${dialect}`,
})
```

#### Registering multiple tables from one schema file

Pass an array of names, or omit `name` entirely, to register every table exported from the same `schema` file in one
go. This generates all of the tables into a single file instead of one file per table, so tables declared in that
file can reference each other directly - e.g. a foreign key via `.references(() => users.id)` - since they share the
same module scope:

```ts
// runtime/db/schema.sqlite.ts
import { sqliteTable, text, integer } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  id: integer().primaryKey({ autoIncrement: true }),
  email: text().notNull().unique(),
})

export const userPasskeys = sqliteTable('user_passkeys', {
  id: integer().primaryKey({ autoIncrement: true }),
  userId: integer().notNull().references(() => users.id, { onDelete: 'cascade' }),
})
```

```ts
// registers both `users` and `userPasskeys`
registerDatabaseTable(nuxt, {
  name: ['users', 'userPasskeys'],
  resolver: createResolver(import.meta.url),
  schema: dialect => `./runtime/db/schema.${dialect}`,
})

// equivalent - every table-like export in the schema file is auto-discovered when `name` is omitted
registerDatabaseTable(nuxt, {
  resolver: createResolver(import.meta.url),
  schema: dialect => `./runtime/db/schema.${dialect}`,
})
```

Each table's extension files (registered through `extendDatabaseTable`, plus Nuxt-layer `extend.<dialect>.ts` files)
are still merged independently, per table name. An array of names, or omitting `name`, is only supported when
`factory` is also omitted - a `factory` is always called for exactly one, explicitly named table.

### `extendDatabaseTable`

Other modules can register column files during setup. These can be regular files too — either a full table
definition or a plain columns object, both without any helper wrapper:

```ts
extendDatabaseTable(nuxt, {
  name: 'users',
  resolver: createResolver(import.meta.url),
  file: dialect => `./runtime/db/extra.${dialect}`,
})
```

```ts
// runtime/db/extra.sqlite.ts
import { sqliteTable, text } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  locale: text().default('da'),
})
```

Module-kit parses each file's exported table (or plain object) matching `name`, and merges their columns directly —
later registrations override columns from earlier ones with the same key — before generating a single `sqliteTable(...)`
call with the merged columns and deduplicated imports. The base `schema` file must export a genuine table call (e.g.
`sqliteTable('users', { ... })`) matching `name`, since it determines which factory (`sqliteTable`/`pgTable`/etc.) and
SQL table name to use for the merged result.

`name` also accepts an array, so a single `file` can export extension columns for several tables in one go, the same
way `registerDatabaseTable` does:

```ts
extendDatabaseTable(nuxt, {
  name: ['users', 'userPasskeys'],
  resolver: createResolver(import.meta.url),
  file: dialect => `./runtime/db/extra.${dialect}`,
})
```

```ts
// runtime/db/extra.sqlite.ts
export const users = sqliteTable('users', {
  locale: text().default('da'),
})
export const userPasskeys = sqliteTable('user_passkeys', {
  label: text(),
})
```

`name` can also be omitted entirely, in which case `file` is registered against every table that generates a schema -
whichever table(s) it actually has a matching export for pick up its columns, exactly as the shared Nuxt-layer
`server/db/extend.<dialect>.ts` files already do; tables with no matching export in `file` are left untouched:

```ts
extendDatabaseTable(nuxt, {
  resolver: createResolver(import.meta.url),
  file: dialect => `./runtime/db/extra.${dialect}`,
})
```

### Using a `factory`

Pass `factory` to `registerDatabaseTable` when you need shared defaults (e.g. timestamps) applied consistently across
dialects. Wrap the factory with `defineExtendableTable` so it receives a single `{ name, columns }` object instead of
a plain columns object — passing `name` through means the table's name only has to be maintained in one place, the
`registerDatabaseTable` call, instead of being duplicated as a string literal inside the factory itself. The factory
must spread `columns` *last*, after its own fields (including timestamps), so extended columns always end up last in
the generated migration, matching the order they were registered in:

```ts
import type { ColumnBuilderBase } from 'drizzle-orm'
import { defineExtendableTable } from '@frigear-nu/module-kit/utils'

const defineUsersTable = defineExtendableTable(({ name, columns }: { name: string, columns: Record<string, ColumnBuilderBase> }) => {
  return sqliteTable(name, {
    id: serial('id').primaryKey(),
    email: text('email').notNull().unique(),
    password: text('password').notNull(),
    createdAt: timestamp('created_at').defaultNow().notNull(),
    updatedAt: timestamp('updated_at').defaultNow().notNull(),
    ...columns,
  })
})
```

```ts
registerDatabaseTable(nuxt, {
  name: 'users',
  factory: 'defineUsersTable',
  resolver: createResolver(import.meta.url),
  schema: dialect => `./runtime/db/schema.${dialect}`,
  override: options.settings?.schemas?.users,
})
```

### `defineTableColumns`

A typed identity helper for defining a table's extension columns. Each extension file exports column objects named
for their tables. For example, a Nuxt layer can extend multiple tables in `server/db/extend.sqlite.ts`:

```ts
export const users = defineTableColumns({ locale: text().default('da') })
export const posts = defineTableColumns({ summary: text() })
```

Only the export matching the table being built is used. Existing registered files are merged in registration order
(later fields replace earlier fields); missing files for a dialect are skipped. Registered files with legacy default
exports still work. Nuxt layer files are merged next, from base layers toward the host application. Older
`server/db/<name>.extend.<dialect>` files with default exports are also loaded before each layer's shared file, so a
shared export can override them. Pass `extensionFile: dialect => 'path/to/columns.' + dialect + '.ts'` to change the
per-layer file location. If `override` is a path instead of `'default'`, the host schema replaces the generated table
entirely; the path is resolved from the application's root directory.

### Migrations and database-backed module tests

`extendDatabaseTable` updates the generated Drizzle schema; it does **not** alter an existing database. Generate
migrations from the consuming application's complete module configuration, including every module that extends a
table. Test fixtures are consuming applications too: their committed migrations must match the merged schema, not
just the owning module's original tables.

#### Updating a fixture's migrations

Run commands from the workspace root:

```bash
pnpm --filter <package-name> exec nuxt prepare "$PWD/packages/<package>/test/fixtures/<fixture>"
pnpm --filter <package-name> exec drizzle-kit generate \
  --dialect sqlite \
  --schema "$PWD/packages/<package>/test/fixtures/<fixture>/.nuxt/hub/db/schema.mjs" \
  --out test/fixtures/<fixture>/server/db/migrations/sqlite \
  --name <migration-name>
pnpm --filter <package-name> test test/<fixture>.test.ts
```

The filtered `exec` runs in the selected package, so `--out` is package-relative; use an absolute schema path.
Preparing the fixture first ensures that `.nuxt/hub/db/schema.mjs` includes all schema extensions.

Review and commit the generated SQL together with `meta/*_snapshot.json` and `meta/_journal.json`. Keep existing
migration history intact, and do not commit `.nuxt`, `.data`, `node_modules`, or compiled `dist` output. Migration
SQL and its metadata are intentional versioned schema history.

#### Database-backed fixture requirements

- Configure a test-only session password and a local SQLite/libsql database.
- Use `dev: true` in `@nuxt/test-utils/e2e` setup so NuxtHub applies the fixture's committed migrations at startup.
  Disabling build-time migrations does not disable these development migrations.
- Remove only the fixture's dedicated `.data` directory before the suite and clean it up afterward, to avoid
  conflicts with data left behind by a previous run.
- Assert a request's HTTP status with the response body as the assertion message before asserting on its side
  effects (e.g. a session cookie). This reveals the underlying HTTP/database error instead of a less helpful failure.
- Run the suite twice to verify migration application and database isolation. See
  [`@frigear-nu/users`](/modules/users) and [`@frigear-nu/account`](https://github.com/Frigear-nu/frigear-nu/tree/main/packages/account)
  for modules with working fixture lifecycles.

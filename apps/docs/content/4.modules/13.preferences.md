---
title: Preferences Module
description: Typed per-user preferences that modules and the host app register, stored on the user and optionally forwarded to OAuth applications as claims.
---

Per-user preferences (color mode, table density, notification digests, ...) as a
[Nuxt module](https://nuxt.com/docs/4.x/guide/modules). Each preference is declared once, with a zod schema, by the host
app or by any module. The schemas are the single source of truth: they validate the API and generate the TypeScript types.

## Design

- **One JSON column.** Every preference lives in `users.preferences`, so adding a preference never needs a migration.
  Only installing the module does. SQLite and Postgres can both filter and index JSON keys when a preference needs to be
  queried (`json_extract(preferences, '$.colorMode')`, `preferences->>'colorMode'`).
- **Registered, not free-form.** Unknown keys and invalid values are rejected, and a stored value that no longer
  satisfies its schema reads as unset.
- **Typed.** `UserPreferences` is generated from the registered definer files, so a misspelled key or a wrong value does
  not compile.
- **Private by default.** A preference is only forwarded to OAuth applications when its definition says so.

## Setup

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@frigear-nu/users', '@frigear-nu/preferences'],
})
```

Generate and commit a migration for the `preferences` column in your app (see
[Extending a database table](/modules/module-kit)).

## Defining preferences

A definer file default-exports `definePreferences({...})`. Each key is a zod schema, or `{ schema, claim?, scope? }`.
`shared/preferences.ts` is picked up automatically, or list files in the `preferences.definitions` option.

```ts [shared/preferences.ts]
import { z } from 'zod'
import { definePreferences } from '@frigear-nu/preferences/define'

export default definePreferences({
  // Plain schema: stored and readable by this app only.
  compactTables: z.boolean(),

  // Also forwarded to OAuth applications as the `color_mode` claim.
  colorMode: { schema: z.enum(['light', 'dark', 'system']), claim: 'color_mode' },

  // Defaults come from the schema.
  pageSize: z.number().int().min(10).max(100).default(25),
})
```

A module registers its own file from `setup()`, and its keys join `UserPreferences` the same way:

```ts
import { addUserPreferences } from '@frigear-nu/preferences/utils'

addUserPreferences(nuxt, { path: resolver.resolve('./runtime/preferences') })
```

The same key in two files fails at startup.

## Using them

```ts [Client]
const { preferences, get, set, pending } = useUserPreferences()

preferences.value.colorMode // 'light' | 'dark' | 'system' | undefined
await set('colorMode', 'dark') // validated by the server; `null` clears it
```

```ts [Server]
const user = await requireUser(event)
getUserPreference(user, 'colorMode') // typed, `undefined` when unset or no longer valid
```

`PATCH /api/preferences` takes a partial object (`{ "colorMode": "dark" }`, `null` clears a key), answers with the
resulting preferences and refreshes the session. It needs a cookie session; API tokens and OAuth access tokens are refused.

## OAuth claims

When [`@frigear-nu/oauth-server`](/modules/oauth-server) is installed, preferences with a `claim` are added to the ID
token and `userinfo`, for applications that were granted the definition's `scope` (default `profile`). Access tokens stay
bare, a preference that is not set adds no claim (the application keeps its own default), and an existing claim such as
`name` is never replaced. The OAuth server itself knows nothing about preferences: this module registers an
[`oauth:claims`](/modules/oauth-server) hook.

## Options

| Option | Description |
|---|---|
| `definitions` | A file or list of files default-exporting `definePreferences({...})`. Defaults to `shared/preferences.ts` when it exists. |

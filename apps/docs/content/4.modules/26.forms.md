Forms as a [Nuxt module](https://nuxt.com/docs/4.x/guide/modules). It replaces the old app's three form systems
(YAML metadata + hard-coded Zod + i18n JSON) with one declarative **definition** stored in the database, one renderer
and one server pipeline. The contact form of the website is intentionally not part of it (yet).

## Design

- **A form is data.** The definition is JSON in the `forms` table, so editors can change fields without a deploy.
- **One compiler.** `buildFormSchema(definition, answers)` turns a definition into a zod schema. The client uses it per
  step, the server for the whole form, so both sides agree on what is required.
- **Submissions are snapshots.** Each submission stores the definition (and its `version`) it was answered against, so
  old submissions keep rendering after the form changes.
- **Storing is optional.** `storage: 'none'` never persists answers: they are only emitted through `forms:submitted`
  (and emailed).
- **Delivery never loses a stored submission.** The row is written first; delivery errors are recorded on it and can be
  retried from the admin.
- **Staff access is the host's decision.** There is no shared permission system; see [Authorization](#authorization).

## Quick Setup

From the workspace use `"@frigear-nu/forms": "workspace:*"`. Requires `@frigear-nu/users` and `@frigear-nu/notify`
(email delivery; the host app picks the driver) and NuxtHub with **KV** (rate limiting) and **blob** (uploads).
`@frigear-nu/menu` is optional.

```ts
export default defineNuxtConfig({
  forms: {
    settings: {
      pages: { form: true, admin: true, adminForm: true, adminSubmissions: true, adminSubmission: true },
      rateLimit: 10,              // submissions per client and form per window; 0 disables
      rateLimitWindowSeconds: 600,
    },
    seed: { enabled: false, forms: [] }, // see "Seeding and import"
  },
})
```

Pages are opt-in and use [`@nuxt/ui`](https://ui.nuxt.com): `/forms/:slug`, `/admin/forms`, `/admin/forms/:id`,
`/admin/forms/:id/submissions` and `/admin/forms/:id/submissions/:submissionId`. Any of them can be a custom path
string. `<FormRenderer slug="…" />` can also be placed in any page.

::warning
Every host app and test fixture must generate and commit a migration for the `forms`, `form_submissions` and
`form_submission_files` tables. See [Module Kit](/modules/module-kit) and the repository `AGENTS.md`.
::

## Definition

```ts
{
  mode: 'single' | 'stepped',
  storage: 'db' | 'none',               // default 'db'
  steps: [{
    id: 'who',
    title: { da: 'Om dig', en: 'About you' },
    showIf: { field: 'kind', op: 'eq', value: 'org' },   // optional, hides the whole step
    fields: [{
      key: 'email',                      // unique across the form; the key of the answer
      type: 'email',                     // text email tel number textarea select radio checkbox date file markdown captcha
      label: { da: 'E-mail', en: 'Email' },
      required: true,
      options: [{ value: 'a', label: 'A' }],             // select / radio
      validation: { minLength, maxLength, min, max, pattern, maxFiles, maxSize, accept, message },
      showIf: { field: 'subject', op: 'eq', value: 'other' },  // eq | neq | in | truthy
    }],
  }],
  submit: { label, successMessage, redirect: '/thanks', allowResubmit: { keep: ['email'] } },
  delivery: { email: { to: ['office@example.com'], subject: { en: 'New application' } } },
}
```

- A single page form has exactly one step and no stepper.
- Texts are a string or a `{ da, en }` map (falls back to `en`, then the first value).
- `showIf` only sees answers of fields **earlier** in the form, and a hidden field's stale answer never keeps another
  field shown. Hidden fields are not required and their answers are dropped.
- File fields are bounded: `maxSize` defaults to 10 MB and `maxFiles` to 10 (1 unless `multiple`). They require
  `storage: 'db'`.
- `delivery.email.routes: { field, to: { <answer>: [...] } }` sends to different recipients depending on one field's
  answer (falling back to `to`), and `replyToField` sets the email's `Reply-To` from an email field — this is how the
  website's contact form routes by subject.
- Recipients must be literal email addresses; `${...}` placeholders are rejected so an unresolved variable can never be
  mailed.
- `markdown` fields render static text (bold, italics, safe links, paragraphs) and collect no answer.
- `captcha` fields add a bot check (see [Captcha](#captcha)); they are always required while visible.

Use `defineForm()` from `@frigear-nu/forms/utils` to author definitions with types.

## Email body and variables

Without further settings the notification lists every visible answer. `delivery.email.body` (a string or a map of
locale to string, up to 10,000 characters) replaces that with your own text, and `subject` accepts the same
variables. The text is chosen by the submission's locale (falling back to `en`).

```ts
delivery: {
  email: {
    to: ['office@example.com'],
    subject: 'New message from {{ answer.name }}',
    body: { en: 'Hi team,\n\n{{answer.name}} wrote via {{form.name}}:\n{{answer.message}}\n\nAll answers:\n{{answers}}' },
  },
}
```

| Variable | Replaced with |
| --- | --- |
| `{{form.name}}`, `{{form.slug}}`, `{{form.version}}` | The form's name, slug and version |
| `{{submission.id}}` | The stored submission id (empty when `storage: 'none'`) |
| `{{submission.createdAt}}`, `{{submission.locale}}` | ISO timestamp and locale of the submission |
| `{{answers}}` | All visible answers as `label: value` lines (a table in the HTML version), without captcha |
| `{{answer.<fieldKey>}}` | One answer, formatted like the default email: option labels, joined lists, file names, yes/no per locale |
| `{{files}}` | Names of the files stored with the submission |
| `{{replyTo}}` | The reply-to address taken from `replyToField` |

- Whitespace inside the braces is ignored (`{{ form.name }}`).
- Unknown variables, hidden fields and unanswered fields render empty. The admin definition check warns about unknown
  variables (`unknownBodyVariables(definition)`); it never fails the save.
- Values are inserted once and never re-scanned, so an answer containing `{{form.name}}` stays literal.
- The body is plain text. Newlines are kept; the HTML version escapes every value and literal and turns newlines into
  `<br>`. In the subject, line breaks are collapsed so an answer cannot inject headers.
- The rendering lives in `@frigear-nu/forms/utils` (`composeEmail`, `renderTemplateText`, `renderTemplateHtml`), so the
  builder previews the exact result with sample answers.

## Visual builder

The admin editor (`/admin/forms/:id`) has a **Builder** tab next to **Preview** and **JSON**. Pick *Single page* or
*Stepped*, then drag field types from the palette onto the form (or click to append). Drag fields to re-order them
inside a step or onto another step, and drag step headers to re-order steps. Every row also has up/down buttons, so
re-ordering works without a pointer. Selecting a field or step opens its settings: label, help text, placeholder,
required, options, length/number limits, the step it belongs to, and a `showIf` condition on an earlier field.
Every text (labels, help text, placeholders, text blocks, option labels, step titles) has a language button: plain
text is the same in every language, and translating it turns it into a `{ en, da, ... }` map with one row per locale
(the host's `@nuxtjs/i18n` locales, plus any language code you add). Empty languages are dropped so the renderer falls
back to another one. Switching to *Single page* merges all steps into one. The builder and the JSON tab edit the same definition, and **Save**
is only enabled while it passes validation. Drag-and-drop uses the browser's native API (no extra dependency), so
touch devices use the up/down buttons.

## Seeding and import

Nothing is inserted automatically. Two explicit ways to load definitions:

- `forms.seed: { enabled: true, forms: [...] }` (typically `NUXT_FORMS_SEED_ENABLED=true`) inserts, at startup, forms
  whose slug does not exist yet. Existing forms are never overwritten.
- The admin page has an **Import** button (and `POST /api/forms/admin/import`) taking `{ slug, name, definition }`.

The website ships `project-application` and `board-member-application` (ported from the old app) in
`apps/website/forms`; they are inserted as `draft`, so review and publish them in the admin. Set
`NUXT_FORMS_APPLICATIONS_TO` (comma separated) to add email delivery.

## Embedding in Markdown

`FormEmbed` is registered **globally** by the module, so [Nuxt Content](https://content.nuxt.com) (MDC) resolves it in
any collection without a wrapper in `components/content`. Embed a published form with block syntax:

```md
::form-embed{slug="contact"}
::

::form-embed{slug="contact" title locale="da" class="max-w-2xl my-8"}
::
```

Use the block form (`::`) rather than inline `:form-embed{...}`: the embed renders block elements, and inline use would
place them inside a paragraph. In Vue templates `<FormEmbed slug="contact" />` works the same, and `<FormRenderer>` stays
available for custom flows.

| Prop     | Type      | Default | Notes                                                                    |
| -------- | --------- | ------- | ------------------------------------------------------------------------ |
| `slug`   | `string`  | -       | Required. Slug of a published form.                                      |
| `title`  | `boolean` | `false` | Show the form's name as a heading above the form.                        |
| `locale` | `string`  | app     | Overrides the locale of the form's translated labels and messages.       |
| `class`  | `string`  | -       | Extra classes for the wrapper (width, margins).                          |

The embed follows the form's [access settings](#definition), using the same `GET /api/forms/:slug/access` route as the
`/forms/:slug` page:

- **Open forms** render with a loading skeleton while the definition loads; the success message (or redirect) is handled by
  the renderer.
- **Unknown or unpublished** forms show a "could not be found" alert; the rest of the page is unaffected.
- **`auth: user`** shows a sign-in prompt linking to the login page (with a `redirect` back to the page).
- **`auth: password`** shows the password gate; the form appears after the password was accepted.
- **API-only (`availability: api`) and `auth: token`** forms render nothing (a bearer token cannot be typed into a page);
  in development a console warning names the slug.

The wrapper has the `not-prose` class, so inputs inside `@nuxt/typography`/prose pages are not restyled. The same
component works wherever the host introduces a Markdown renderer (for example a `<MDC>` or `<ContentRenderer>` for event
bodies), as long as `@frigear-nu/forms` is installed in that app.

## Open period (seasonal forms)

`access.schedule` limits when a form accepts answers. Without it a form is always open.

```ts
// Every year from 1 Jan 23:00 to 1 Feb 23:00 (Oslo wall-clock time). `from` is inclusive, `to` exclusive.
access: {
  availability: 'web',
  auth: 'none',
  schedule: {
    type: 'yearly',
    timezone: 'Europe/Oslo',
    from: { month: 1, day: 1, time: '23:00' },
    to: { month: 2, day: 1, time: '23:00' },
  },
}

// One fixed period (either end may be left out for an open-ended window).
schedule: { type: 'range', from: '2026-03-01T10:00:00Z', to: '2026-03-15T10:00:00Z' }
```

A yearly season whose end is before its start wraps over new year (for example 1 Nov to 1 Feb). Outside the
period the public page shows a "closed" notice (with the next opening when there is one) and the definition and
submit endpoints answer `403` with `data: { closed: true, opensAt }`. `isFormOpen` and `nextFormOpening` are exported
from the module's utils for custom UI.

## Cloning

`POST /api/forms/admin/forms/:id/clone` copies a form's name and definition into a new draft (slug
`<slug>-copy`, then `-copy-2`, ...). Submissions, access tokens, the password and secrets are not copied.
The admin list has a duplicate button for it.

## Submitting

`POST /api/forms/:slug/submit` takes JSON `{ answers, locale }`, or `multipart/form-data` with an `answers` JSON part,
a `locale` part and one `file:<key>` part per file. Validation errors are `422` with `data.issues`. The public
`GET /api/forms/:slug` returns the published definition **without** `delivery`.

## Captcha

A `captcha` field renders Cloudflare Turnstile, Google reCAPTCHA v2 (checkbox) or hCaptcha:

```ts
{ key: 'human', type: 'captcha', captcha: { provider: 'turnstile', siteKey: '...', theme: 'auto', size: 'normal' } }
```

- `provider` defaults to `turnstile`; `siteKey` (public) overrides the configured one for this field; `theme` and `size`
  are optional.
- Every provider is configurable purely through the environment (or the matching `forms.captcha` options):

  | Provider | Site key (public) | Secret key (server only) |
  | -------- | ----------------- | ------------------------ |
  | Turnstile | `NUXT_PUBLIC_FORMS_CAPTCHA_TURNSTILE_SITE_KEY` | `NUXT_FORMS_CAPTCHA_TURNSTILE_SECRET_KEY` |
  | reCAPTCHA | `NUXT_PUBLIC_FORMS_CAPTCHA_RECAPTCHA_SITE_KEY` | `NUXT_FORMS_CAPTCHA_RECAPTCHA_SECRET_KEY` |
  | hCaptcha | `NUXT_PUBLIC_FORMS_CAPTCHA_HCAPTCHA_SITE_KEY` | `NUXT_FORMS_CAPTCHA_HCAPTCHA_SECRET_KEY` |

  `NUXT_PUBLIC_FORMS_CAPTCHA_DEFAULT_PROVIDER` (`turnstile`, `recaptcha` or `hcaptcha`; option `forms.captcha.defaultProvider`)
  is the provider of a captcha field that names none. The admin builder warns when the provider has neither a field
  `siteKey` nor an environment site key.
- **Resolution.** Site key: the field's `siteKey`, else the environment/option one. Secret key: the form's own encrypted
  secret (below), else the environment/option one, else the check fails closed.
- **Per-form secret keys.** The captcha settings of a field in the builder show where the secret key comes from
  (configured via form, via environment, or not set) and take a write-only input to set or replace the form's secret and
  a button to remove it. It is saved immediately, independent of the form's Save.
- The provider script loads lazily in the browser only. The response token lives in the form state under the field key,
  the widget resets after every failed submit, and the token is **never** stored, delivered or shown in the preview JSON.
- The server verifies the token (with the visitor's IP) against the provider's siteverify endpoint before storing or
  delivering anything. A missing or invalid token is `422` with an issue on the captcha field key; a provider without a
  secret key fails closed with `500`, an unreachable provider with `502`.
- Submissions authenticated with a valid form API token (`access.auth: 'token'`) skip the captcha.
- In the admin preview and "Try it" modal the field is a stub that supplies a dummy token, so no network or keys are needed.

Hosts and tests can replace the network call with the `forms:captcha:verify` hook: set `ctx.valid` (`{ event, provider,
token, ip, formId, secretKey, secretSource, valid }`, where `secretKey` is the resolved secret and `secretSource` is `form`,
`env` or `unset`); when `valid` stays `undefined` the provider is asked.

## Encrypted per-form secrets

Secrets that belong to one form (today the captcha secret keys, later e.g. webhook signing secrets) live in the
`form_secrets` table, **encrypted on the server** with AES-256-GCM (a random 12-byte IV per write, scrypt-derived key,
stored as `{ ct, iv, tag }`). They are kept apart from the definition, so they never end up in definition versions,
submission snapshots, deliveries, imports or the public API.

- **Key**: `forms.encryptionKey` (env `NUXT_FORMS_ENCRYPTION_KEY`), else `NUXT_ENCRYPTION_KEY`, else the session password
  (`NUXT_SESSION_PASSWORD`), so it works out of the box. Set a dedicated key in production so that changing the session
  password does not affect it.
- **Rotation caveat**: changing the key makes the stored secrets unreadable. The admin API then reports `unreadable: true`
  (the builder shows a warning) and checks fall back to the environment key; admins enter the secrets again, which replaces
  the unreadable ones.
- **Admin API** (staff only, see [Authorization](#authorization)); values are write-only:
  - `GET /api/forms/admin/forms/:id/secrets` returns `{ keys, captcha, unreadable }`: the names that are set and, per captcha
    provider, `source` (`form`, `env` or `unset`). Never values.
  - `PUT /api/forms/admin/forms/:id/secrets` with `{ key, value }` encrypts and stores one secret. Allowed keys:
    `captcha.turnstile.secretKey`, `captcha.recaptcha.secretKey`, `captcha.hcaptcha.secretKey`.
  - `DELETE /api/forms/admin/forms/:id/secrets/:key` removes one.

## Hooks

```ts
nitroApp.hooks.hook('forms:submitted', async (ctx) => {
  // ctx.form, ctx.answers (validated), ctx.files, ctx.locale, ctx.userId,
  // ctx.submissionId (null when storage is 'none'), ctx.stored
  await fetch('https://example.com/hook', { method: 'POST', body: JSON.stringify(ctx.answers) })
  ctx.delivered = true // optional; throw to mark delivery failed
})
```

- The built-in email delivery listens to `forms:submitted` and mails `delivery.email.to` through `@frigear-nu/notify`.
- For `storage: 'db'` a failing listener sets `deliveryStatus = 'failed'` (with the error) and the visitor still gets
  success; **Deliver again** in the admin re-runs the hooks. For `storage: 'none'` nothing else keeps the answers, so a
  failure is returned as `502`.
- `forms:delivered` fires after delivery finished.

## Authorization

Admin routes (`/api/forms/admin/*`, including file downloads) require a signed-in user and the `forms:authorize` hook,
**denied by default**:

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('forms:authorize', async (ctx) => {
    ctx.allowed = await isStaff(ctx.userId)
  })
})
```

The website allows the emails in `NUXT_FORMS_ADMIN_EMAILS` (`apps/website/server/plugins/forms-policy.ts`).

## Internationalisation

- **Module chrome** (buttons, stepper, admin) uses `useModuleT('forms')` with English fallbacks; the module contributes
  `forms.*` messages (`da`/`en`) through `registerLocales` (see [Module Kit](/modules/module-kit#translations-i18n)).
  Override any of them in your app's `i18n/locales/<code>.json`, for example
  `{ "forms": { "actions": { "submit": "Send inquiry" } } }` (see
  [overriding module strings](/modules/module-kit#overriding-module-strings-in-your-app)). Key groups: `actions`, `step`,
  `success`, `error`, `preview`, `value`, `status`, `delivery`, `validation` and `admin`.
- **Form content** lives in the definition as `{ da, en }` texts.
- **Validation messages** of the compiler's own rules use `forms.validation.*`; a field can override them with
  `validation.message`.

## Data model

| Table                  | Purpose                                                                                       |
| ---------------------- | --------------------------------------------------------------------------------------------- |
| `forms`                | `slug`, `name`, `status` (`draft`, `published`, `archived`), `definition`, `version`.         |
| `form_submissions`     | Answers, `definitionSnapshot`, `formVersion`, `userId`, `locale`, `deliveryStatus` / `deliveryError`. |
| `form_submission_files`| Blob pathname, filename, content type and size per uploaded file.                             |
| `form_secrets`         | One row per form: `secrets` (encrypted JSON map of namespaced keys), `updatedAt`.             |

Forms are archived, never deleted. Files are only downloadable by staff through
`/api/forms/admin/submissions/:id/files/:fileId`.

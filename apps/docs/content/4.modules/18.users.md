The [Nuxt module](https://nuxt.com/docs/4.x/guide/modules) that owns **who the users are**: the `users` table, staff
administration of users, and what a signed-in user can change about themselves. How people sign in is
[Auth](/modules/auth), which Users plugs into; the account pages are [Account](/modules/account), which call its routes.

::note
**Requires** `@nuxthub/core`, `@frigear-nu/module-kit`, [`@frigear-nu/auth`](/modules/auth),
[`@frigear-nu/notify`](/modules/notify) (email and password change notices) and [`@frigear-nu/menu`](/modules/menu);
all are installed automatically. **Optional:** [`@frigear-nu/admin`](/modules/admin) (the admin pages),
[`@frigear-nu/widget`](/modules/widget) (tabs and dashboard widget) and [`@frigear-nu/mcp`](/modules/mcp), which is
installed only when `settings.mcp` is on.
::

## Quick setup

```bash
pnpm add @frigear-nu/users @nuxthub/core
```

```ts
export default defineNuxtConfig({
  modules: ['@nuxthub/core', '@frigear-nu/users'],
  users: {
    settings: {
      admin: true,
      verifyEmailChange: true,
      profilePath: '/account/profile',
    },
  },
})
```

## Options

All options live under `users.settings`.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `admin` | `boolean \| { page?: string \| boolean }` | off | Staff user administration: API, an admin page and a "new users" widget. `page` is the page path (`true` = the `admin` route of Admin + `/users`, e.g. `/admin/users`; `false` = API only). Who may do what is decided by the `users:admin:authorize` hook, denied by default. The page needs `@frigear-nu/admin`; without it only the API is registered, with a warning. |
| `verifyEmailChange` | `boolean` | `false` | A new email address takes effect only after its owner confirms it: the emailed link opens a page where the signed-in owner presses "Confirm". The old address gets a notice with a link to undo it. Off = the change is applied immediately. See [Email change](#email-change). |
| `profilePath` | `string` | - | Where a confirmed email change lands (`?email-changed=1`). Without it the confirm page shows the result itself. |
| `mcp` | `boolean` | `false` | Expose the `get-my-profile` MCP tool (installs `@frigear-nu/mcp`). See [MCP](/modules/mcp). |

## Server

The auto-imported server utils:

```ts
// The signed-in user. Same options as `requireAuth` (`scopes`, `sessionOnly`) and the same 401/403 behaviour.
const user = await requireUser(event, { scopes: ['profile:read'], sessionOnly: false })
const maybeUser = await getUser(event, { scopes }) // the user or null; a token missing `scopes` counts as anonymous
```

These are thin helpers over [`requireAuth` / `getAuth`](/modules/auth#protecting-a-route); use `requireAuth` when the
route needs the principal (how the caller authenticated). Anything that changes who the user is or how they sign in
must pass `{ sessionOnly: true }`.

The module registers the `AuthUserStore` that Auth reads and writes users through (`findById`, `findByEmail`, `create`,
`update`, `remove`, `changeId`). It reads the database on every call, so a role change applies to the next bearer
request.

### Admin helpers

For routes of your own below `/api/admin/users`:

```ts
// Runs the users:admin:authorize policy; throws 401/403 otherwise. Returns the signed-in user.
await authorizeUsersAdmin(event, 'view' | 'create' | 'update' | 'delete', { input?, target? })

// Authorizes `action`, then loads `/api/admin/users/:id/...` and runs the policy on that user (`view` for reads,
// `update` for changes). Throws 401 / 403 before it looks anything up, then 400 / 404 / 403. Returns { actor, target }.
const { actor, target } = await loadUsersAdminTarget(event, 'view' | 'update')

// A read route that bearer credentials with `users:read` may call too (the policy still runs on the token's user).
await authorizeUsersAdmin(event, 'view', {}, { scopes: [USERS_READ_SCOPE] })
await loadUsersAdminTarget(event, 'view', { scopes: [USERS_READ_SCOPE] })

// The roles the signed-in user may assign (defaults to roles in use, then the users:admin:roles hook).
await assignableRoles(event, userId)
```

### Reading users with a token (`users:read`)

With `settings.admin`, the module registers the API scope `users:read` ("Read the user directory (staff only)").
An API token or OAuth access token carrying it may call `GET /api/admin/users` and `GET /api/admin/users/:id`, so
another app can sync users; every other admin route still needs a session (`403 session_required`).

- **Staff only, at grant time.** Only a user the `users:admin:authorize` policy lets `view` may hold the scope: it is
  hidden from everyone else (`auth:scope-available`), so they cannot pick it for an API token (`400 unknown_scope`)
  and [OAuth Server](/modules/oauth-server) leaves it out of their tokens.
- **And on every request.** The policy runs against the token's user like it does for a session, so a token whose
  user is no longer staff is refused (`403 forbidden`). A token without the scope gets `403 insufficient_scope`.
- A full-access (`*`) token covers `users:read` like any scope, so the request-time policy is what stops a non-staff
  `*` token.
- `GET /api/admin/users/:id` answers a token with `can.update` and `can.delete` set to `false`.

A module adds its staff routes, a tab and an overview card to the admin user page in one call from its `setup()`:

```ts
import { extendUsersAdmin } from '@frigear-nu/users/utils'

await extendUsersAdmin(nuxt, {
  routes: [{ method: 'get', path: 'payments', handler: resolver.resolve('./runtime/server/routes/payments.get') }], // /api/admin/users/:id/payments
  tab: { /* TabDefinition of @frigear-nu/widget */ }, // area `admin.users`
  widget: { /* WidgetDefinition */ }, // area `admin.users.overview`
})
```

The tab and widget need `@frigear-nu/widget` and `@frigear-nu/admin`; without them they are skipped. Routes are always
registered.

## App

The admin pages are composed from the [UX patterns](/getting-started/ux-patterns) of `@frigear-nu/ui`:

- **Users list** (`<admin page>`): `PageHeading` with an "Add user" button, a `PageToolbar` (debounced search, verified and
  role filters), and a `TableCard` with a clickable, sortable `UTable`. The first column is a `TableIdentity` (name,
  email, initials). Search, filters, sort and page live in the URL (`useTableQuery`), so a filtered list can be
  linked; paging keeps the current rows dimmed until the next page arrives. `TablePagination` sits in the card
  footer, and each row ends in a `RowMenu`: Open, Resend sign-in link, then Delete user in its own red group.
- **`useUserActions()`** owns the staff actions so the list and the detail page offer the same ones: `create()` opens
  the `UserCreateSlideover` (a `FormSlideover`) and resolves with the created user or `false`; `remove(user)` confirms
  with `useConfirmDialog`, deletes, toasts and refreshes; `menu(user, { extra, onRemoved })` returns the `RowMenu`
  groups. Use `extra` to add a group of your own between the sign-in link and Delete.
- **User page**: `PageHeading` with a "Users" breadcrumb, a verified or unverified badge and the same menu as an outline
  `RowMenu`. A missing user shows a `UEmpty` with an "All users" action.
- **Dashboard**: the *New users* `ListCard` and the *New users* `StatCard`.

The admin user page (`<admin page>/:id`) is a tab view over the `admin.users` tab area of
[Widget](/modules/widget), which this module owns. It registers an **Overview** tab (a profile `SectionCard` with its Save button in the footer, account facts in a
`DescriptionList`; deleting the user lives in the heading's `RowMenu`) with an `admin.users.overview` widget area at its top. [Subscriptions](/modules/subscriptions) adds a
*Membership* tab and [Payments](/modules/payments) a *Payments* tab. Each tab receives the response of
`GET /api/admin/users/:id` as a `user` prop and may emit `refresh`. Without Widget the page shows the Overview tab
alone.

Hiding a tab is not access control: each tab's API calls must authorize on the server with `users:admin:authorize`.

`role` is only read and written when [Authorization](/modules/authorization) added the column; its `canManageRole`
helper is the building block for "nobody can hand out a role above their own". Passwords are never returned. A
staff-changed email is marked unverified, and creating a user can email them a sign-in link, which also verifies the
address. Deleting a user also removes everything Auth keeps for them (tokens, passkeys, reset codes, sign-in links).

With Menu and the admin page enabled, an item `users-admin` ("Users", order 10) is added to the `admin.nav` menu.

### Email change

With `verifyEmailChange`, the links in the two emails open pages. Opening a page changes nothing, because mail scanners
and link previews follow links too. Only the button on the page applies the change, with a `POST`:

- **`/auth/verify-email-change?code=`** (emailed to the new address) reads the request through
  `GET /api/users/email-change`.
  - Signed out, while the link still works, it redirects to the login page with `?redirect=` (this URL, code
    included) and `?reason=users.emailChange`. The login page says why you have to sign in
    (`users.emailChange.signInReason`) and returns here afterwards. The code is not used up on the way.
  - Signed in as another account, it says so and offers to sign out.
  - Signed in as the owner, it shows the old and new address and a **Confirm new email address** button. That button
    posts to `/api/users/email-change/confirm`, then goes to `profilePath?email-changed=1`, or shows the result when
    `profilePath` is not set.
- **`/auth/revert-email-change?code=`** (emailed to the old address after the change) shows both addresses and a
  **Restore** button. It works signed out, because whoever changed the address may have locked the owner out; the
  code is the proof. The result shows on the page.

Both pages use the `AuthCard` of [Auth](/modules/auth) and need `@nuxt/ui`. Without `@nuxt/ui` only the API is
registered, with a warning. A host can also replace either page by declaring its own page at that path.

## Emails

Email change and password change notices go through [Notify](/modules/notify). With
[Email Templates](/modules/email-templates) installed, they are rendered from the module's Vue templates
(`users-verify-email-change`, `users-email-changed`, `users-password-changed`). Override one by adding
`app/emails/<name>.vue`.

## Hooks

Nitro hooks, decided by the host. The module knows nothing about roles or staff.

| Hook | When | Payload |
| --- | --- | --- |
| `users:admin:authorize` | Every users admin request | `UsersAdminContext`: set `allowed = true` to allow. Denied by default. |
| `users:admin:roles` | The role list for the admin is computed | `UsersAdminRolesContext`: replace `roles` to narrow or extend. |

```ts
type UsersAdminAction = 'view' | 'create' | 'update' | 'delete'

type UsersAdminContext = {
  event: H3Event
  /** The signed-in user making the request. */
  userId: number
  action: UsersAdminAction
  /** create/update: the values being written (`role` only when Authorization added the column). */
  input?: { role?: string, email?: string, name?: string }
  /** update/delete: the user being changed, as stored. */
  target?: { id: number, email: string, role?: string }
  allowed: boolean
}

type UsersAdminRolesContext = {
  event: H3Event
  userId: number
  /** Roles the user may assign, in display order. Defaults to the roles in use. */
  roles: string[]
}
```

```ts
export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook('users:admin:authorize', async (ctx) => {
    const actor = await findUser(ctx.userId) // identify the caller from ctx.userId
    ctx.allowed = actor.role === 'admin'
  })
})
```

## Routes

Paths come from `usersApi` (`@frigear-nu/users/utils`, or `@frigear-nu/users/api` from another module's app code: it
carries no build-time imports), so app code and tests never spell them out:

```ts
import { usersApi } from '@frigear-nu/users/api'

await $fetch(usersApi.me.profile, { method: 'PATCH', body: { name: 'Ada' } })
await $fetch(usersApi.admin.user(42), { method: 'DELETE' }) // 204
```

Self-service routes require a cookie session (`sessionOnly`), refresh the session user afterwards and answer the
caller's profile (`ProfileDto`: `id`, `name`, `email`, `avatar`, `emailVerifiedAt`), never the stored row. Emails are
trimmed and lowercased wherever they are written, and every "already in use" check ignores case (`409 conflict`).

| Method | Path (`usersApi`) | Auth | Status | Purpose |
| --- | --- | --- | --- | --- |
| `PATCH` | `/api/users/me` (`me.profile`) | session only | 200 | `{ name?, avatar? }`: `name` at most 120 characters, `avatar` an http(s) URL or `null` to clear it. |
| `PUT` | `/api/users/me/email` (`me.email`) | session only | 200 | `{ email }`. Returns the profile plus `verificationRequired`. With `verifyEmailChange` it stores the request and emails the new address instead (`verificationRequired: true`). |
| `PUT` | `/api/users/me/password` (`me.password`) | session only | 200 | `{ currentPassword, newPassword, confirmNewPassword }`: sets the password and emails a notice (`401` when the current one is wrong; a failing mail never undoes the change). |
| `GET` | `/api/users/email-change?code=` (`emailChange`) | none | 200 | `verifyEmailChange`: read-only preview of a request: `{ status: 'pending' \| 'confirmed' \| 'expired', signedIn, owner, newEmail, oldEmail }`. `oldEmail` is masked unless you are the owner. `404` for an unknown code. |
| `POST` | `/api/users/email-change/confirm` (`emailChangeConfirm`) | session only, owner | 200 | `verifyEmailChange`: `{ code }`. Applies the change (single use, valid 24 hours), verifies the address, refreshes the session and emails the old address a revert link. `403` when the request belongs to another account, `400` when used or expired, `409` when the address was taken meanwhile. |
| `GET` | `/api/users/email-change/revert?code=` (`emailChangeRevert`) | none | 200 | `verifyEmailChange`: read-only preview of a revert: `{ status: 'pending' \| 'reverted' \| 'expired', oldEmail, newEmail }`. |
| `POST` | `/api/users/email-change/revert` (`emailChangeRevert`) | none (the code) | 200 | `verifyEmailChange`: `{ code }`. Restores the old address (single use, valid 7 days) and signs out a session of that account. Returns `{ email, signedOut }`. |
| `GET` | `/api/admin/users` (`admin.users`) | session or `users:read`, + hook `view` | 200 | Paginated `{ items, total, page, pageSize, hasRoles, hasSubscriptions, roles }` (`page`, `pageSize` up to 100, `q`, `role`, `verified`, `sort`, `order`). Items are `AdminUserDto` plus `subscription`. |
| `POST` | `/api/admin/users` (`admin.users`) | session + hook `create` | 201 | `{ name, email, role?, emailVerified?, sendWelcomeEmail? }`. Returns the `AdminUserDto` (`409` when the email is taken). |
| `GET` | `/api/admin/users/new` (`admin.new`) | session + hook `view` | 200 | The newest sign-ups of the last 30 days, for the dashboard widget. |
| `GET` | `/api/admin/users/stats` (`admin.stats`) | session + hook `view` | 200 | `{ total, newUsers, days }` for the dashboard stat card. |
| `GET` | `/api/admin/users/roles` (`admin.roles`) | session + hook `view` | 200 | `{ roles }` the signed-in user may assign. |
| `GET` | `/api/admin/users/:id` (`admin.user(id)`) | session or `users:read`, + hook `view` | 200 | One user: the `AdminUserDto` plus `hasPassword`, `passkeys`, `subscription`, `hasRoles`, `roles`, `can`. |
| `PATCH` | `/api/admin/users/:id` (`admin.user(id)`) | session + hook `update` | 200 | `{ name?, email?, role?, emailVerified? }`. Returns the `AdminUserDto`. |
| `DELETE` | `/api/admin/users/:id` (`admin.user(id)`) | session + hook `delete` | 204 | Deletes a user (not yourself: `400`). |
| `POST` | `/api/admin/users/:id/resend` (`admin.resend(id)`) | session + hook `update` | 200 | Resends the sign-in link (`501 not_configured` when sign-in links are off). |

`AdminUserDto` is an allowlist: `id`, `name`, `email`, `role` (only with a roles column), `avatar`,
`emailVerifiedAt`, `lastLoginAt`, `createdAt` (dates as ISO strings). It never carries the password hash or columns
other modules add.

The admin routes exist with `settings.admin`; all of them are session only and run the `users:admin:authorize`
hook, whose name and context (`action`, `input`, `target`, `userId`, `event`, `allowed`) are unchanged. Routes on one
user authorize before they look the user up: a guest gets `401` and a caller the host denies gets `403` even for an
unknown id, and only then `400` (malformed id) or `404`. The hook is asked once for the action and again with the
`target` (and, for create and edit, the `input`) once those are known. Errors carry a snake_case `data.code`
(`not_found`, `forbidden`, `conflict`, ...). The emailed links point at the pages `/auth/verify-email-change` and
`/auth/revert-email-change` (see [Email change](#email-change)); no `GET` changes anything.

## Database

### `users`

The [default SQLite schema](../../../../packages/users/src/runtime/db/schema.sqlite.ts) has an auto-incrementing `id`, a
required `name`, a unique required `email`, an optional `avatar`, a nullable `acceptedTermsAt` and `createdAt` /
`updatedAt`. Other modules add columns through the [Module Kit](/modules/module-kit) extension helpers: Auth adds
`password`, `emailVerifiedAt` and `lastLoginAt`; Authorization adds `role`.

### `account_email_changes`

Registered with `verifyEmailChange` (the table is named after Account although Users owns it): one row per "change my
email" request with the old and new address, the confirmation `code`, the `revertCode` and their timestamps.

for the email change pages. Override strings in your

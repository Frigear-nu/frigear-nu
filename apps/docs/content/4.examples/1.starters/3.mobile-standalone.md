This guide creates a project with its own users, server and mobile app, from the published `@frigear-nu` modules. It is
the [workspace starter](/examples/starters/workspace) plus the app of the [mobile starter](/examples/starters/mobile), wired
together:

- **`apps/web`** has registration and login, `/account` pages and an `/admin` area with user management, and is the
  [OAuth server](/modules/identity/oauth-server) and the API of the mobile app.
- **`apps/mobile`** is a Capacitor app on [Mobile](/modules/interface/mobile) that signs in at `apps/web` with
  [Auth in client mode](/modules/identity/auth/client-mode), picks its guards with
  [Authorization](/modules/identity/authorization), and calls `/api/me` with its access token.

There is nothing to register by hand: `apps/web` reads the app's client id and redirect URIs from
`apps/mobile/identity.ts`.

## Requirements

| Tool | Version |
| --- | --- |
| Node.js | `24` (the starter pins `24.22.1` in `.nvmrc`) |
| pnpm | `12.10.0` (pinned in the starter's `package.json`, use `corepack enable`) |
| Xcode | For iOS: a recent Xcode with an iOS simulator. The native project uses Swift Package Manager, no CocoaPods. |
| Android Studio | For Android: a JDK and the Android SDK. |

## Create the project

The starter lives in this repository under
[`.starters/mobile-standalone`](https://github.com/Frigear-nu/frigear-nu/tree/main/.starters/mobile-standalone). Copy
it with [giget](https://github.com/unjs/giget):

```bash
pnpx giget@latest gh:Frigear-nu/frigear-nu/.starters/mobile-standalone my-app
cd my-app
git init
corepack enable
pnpm install
pnpm prepare:env
```

`pnpm prepare:env` creates `apps/web/.env` and `apps/mobile/.env` from their examples and generates the secrets
(it never overwrites a value, so it is safe to run again):

| Variable | Where | What it is |
| --- | --- | --- |
| `NUXT_SESSION_PASSWORD` | `apps/web/.env` | Encrypts the session cookie. Generated. |
| `NUXT_OAUTH_SERVER_PRIVATE_KEY` | `apps/web/.env` | Signs the OAuth tokens, a PKCS#8 RSA key. Generated. |
| `NUXT_ACL_ADMINS` | `apps/web/.env` | Comma separated emails that are always admins. **Put your own email here.** |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_ISSUER` | `apps/mobile/.env` | `http://localhost:3000`, the web app. |
| `NUXT_PUBLIC_AUTHENTICATION_CLIENT_API_BASE` | `apps/mobile/.env` | `http://localhost:3000`, the web app's API. |

## First run

```bash
pnpm dev
```

This starts `apps/web` on `http://localhost:3000` and `apps/mobile` on `http://localhost:3001`. On the first start,
NuxtHub creates a local SQLite database in `apps/web/.data/` and applies the committed migrations, including the OAuth
server's tables.

## Sign in

1. Open `http://localhost:3000`, choose **Create account** and register with the email you put in `NUXT_ACL_ADMINS`.
   `/admin` is the admin dashboard; `/admin/oauth` lists the OAuth applications, with the mobile app's `mobile` client
   marked **Managed in nuxt.config**.
2. Open `http://localhost:3001`, the mobile app in a browser. Its `'/**': { authenticated: true }` route rule sends you
   to its `/login` page.
3. **Sign in** sends you to `apps/web`, which asks you to approve the app, then returns to
   `http://localhost:3001/auth/callback`. **Home** shows your sign-in (`useUserSession().user`, from the ID token) and
   `GET /api/me`, called cross-origin with the access token. A reload keeps you signed in.
4. **Account**, **Sign out** revokes the refresh token and returns to `/`, which the route rule sends on to the login
   page.

Both apps use the same app API: `useUserSession()`, `useAuth()` and `$api` / `useApi()`. `apps/web` runs Auth in server
mode (a cookie session), `apps/mobile` in client mode (tokens on the device). The app's
[guards](/examples/starters/mobile#guards) only decide what it shows: `apps/web` checks every API request.

Emails such as password resets are printed in the terminal running `pnpm dev` (the `log` driver of
[Notify](/modules/platform/notify)) until you configure a real driver.

## How the two apps fit together

`apps/mobile/identity.ts` is exported as `@workspace/mobile/identity`, and `apps/web` depends on `@workspace/mobile`
to read it:

```ts [apps/web/nuxt.config.ts]
import { appName, clientId, devRedirectUri, nativeRedirectUri } from '@workspace/mobile/identity'

export default defineNuxtConfig({
  modules: [
    // ... the workspace starter's modules
    '@frigear-nu/oauth-server',
  ],
  oauthServer: {
    cors: {
      // The webviews of the native app: iOS and Android.
      origins: ['capacitor://localhost', 'https://localhost'],
      // Your API: the same origins may call it with `Authorization: Bearer`.
      paths: ['/api/'],
    },
    clients: [{
      id: clientId, // 'mobile'
      name: appName,
      redirectUris: [nativeRedirectUri], // 'com.example.mobile:/auth/callback'
      devRedirectUris: [devRedirectUri], // 'http://localhost:3001/auth/callback', under `nuxt dev` only
    }],
    settings: { pages: { admin: true } },
  },
})
```

| Piece | What it does |
| --- | --- |
| `oauthServer.clients` | A [configured client](/guide/going-further/oauth-application#create-it-in-nuxtconfig): a public client (PKCE, no secret) with the fixed id `mobile`, created in the database on the first OAuth request. The dev redirect URI, and its origin for CORS, only exist under `nuxt dev`, so production never accepts them. `NUXT_OAUTH_SERVER_CLIENTS` (JSON) replaces the list per environment. |
| `cors.origins` | The webview origins may call the token, revoke, userinfo and discovery endpoints. |
| `cors.paths` | The same origins may call `/api/**` with a bearer token. Cookies never travel cross-origin. |
| `server/api/me.get.ts` | `requireUser(event)` accepts the session cookie and the access token, and the route returns an allowlisted `{ id, name, email }`. Write your API routes the same way. |
| `server/plugins/oauth-policy.ts` | The OAuth server has no role model: this plugin makes admins the OAuth admins (`oauth:authorize`) and gives every user their effective role (`oauth:user:roles`). The `mobile` client has no `allowedRoles`, so every signed-in user may use it. |
| `NUXT_OAUTH_SERVER_PRIVATE_KEY` | The signing key. Without it, `nuxt dev` keeps a dev key in `apps/web/.data/oauth-server/dev-key.pem` and a production server answers `500`. |

To register more applications (another app, a confidential web client), or to change this one, see
[Create an OAuth application](/guide/going-further/oauth-application): this one is created
[in nuxt.config](/guide/going-further/oauth-application#create-it-in-nuxtconfig).

The rest of `apps/web` is the workspace starter's, and `apps/mobile` is the mobile starter's, file for file. The
[mobile starter guide](/examples/starters/mobile) explains the app.

## Run it on the iOS simulator

Keep the web app running (`pnpm dev`, or `pnpm dev:web`), then in a second terminal:

```bash
pnpm mobile:ios
```

The script creates the native projects the first time (`cap add ios` and `cap add android`, plus the URL scheme
`com.example.mobile` in `Info.plist` and `AndroidManifest.xml`), builds the SPA, syncs it into `ios/` and asks which
simulator to run. The simulator shares your Mac's network, so the app reaches `http://localhost:3000`. **Sign in** opens
the in-app browser at `apps/web`; it has its own cookies, so you sign in there once. After you approve, the redirect to
`com.example.mobile:/auth/callback` returns to the app, signed in.

Run `pnpm mobile:sync` after every change to the app or its `.env`, and after every `pnpm install`.

## Run it on an iPhone

A phone cannot reach `localhost` on your Mac. Start the web app on every interface, and build the app against your
Mac's LAN address:

```bash
pnpm dev:lan             # apps/web on 0.0.0.0:3000
pnpm mobile:ios:device   # MOBILE_LAN=1 build, then opens Xcode
```

`MOBILE_LAN=1` rewrites `localhost` in the issuer and API base to this Mac's LAN address (`MOBILE_LAN=192.168.1.20`
picks it). The OAuth server takes its issuer from the request, so it matches. In Xcode:

1. Select the **App** target, **Signing & Capabilities**, and pick your team (a free Apple ID works; the install then
   expires after 7 days). Do not commit the team id.
2. Connect the phone, turn on **Developer Mode** on it (Settings, Privacy & Security), choose it as the run destination
   and press **Run**.
3. The first time, trust the developer profile on the phone (Settings, General, VPN & Device Management), and allow
   local network access when asked.

The phone and the Mac must be on the same network. A LAN build never ships: the build fails when `MOBILE_RELEASE=1` is
also set.

## Android

```bash
pnpm mobile:android
```

The same steps for Android. The Android WebView runs at `https://localhost`, so calls to the plain `http` dev server are
mixed content: test Android against an `https` deployment of `apps/web`, or use live reload (see
[Device development](/modules/interface/mobile)).

## Rename the app

Change `apps/mobile/identity.ts` (app id, name, client id, scopes), then:

1. Restart `pnpm dev`: `apps/web` reads the new client id and redirect URIs from the same file. The old client stays in
   the database as an ordinary application, so its users stay signed in; delete it in `/admin/oauth` when you no longer
   need it.
2. Delete `apps/mobile/ios` and `apps/mobile/android`, then run `pnpm mobile:native` (or `pnpm mobile:ios`) to create
   them with the new id and URL scheme.

The [mobile starter guide](/examples/starters/mobile#rename-the-app) lists the fields.

## Commands

Run everything from the repository root:

| Command | What it does |
| --- | --- |
| `pnpm prepare:env` | Create each app's `.env` from `.env.example` and fill in empty secrets |
| `pnpm dev` | `apps/web` on `http://localhost:3000` and `apps/mobile` on `http://localhost:3001` |
| `pnpm dev:web` / `pnpm dev:mobile` | One of them |
| `pnpm dev:lan` | `apps/web` on every interface, for a phone on the same network |
| `pnpm build` | Build every app and package |
| `pnpm lint` / `pnpm lint:fix` / `pnpm typecheck` / `pnpm test` | Checks across the workspace |
| `pnpm db:generate` | Generate a migration after adding or upgrading a module (commit it) |
| `pnpm db:migrate` | Apply migrations without starting the dev server |
| `pnpm mobile:native` | Create `ios/` and `android/` and register the URL scheme (safe to rerun) |
| `pnpm mobile:doctor` | List missing Capacitor plugins and URL schemes |
| `pnpm mobile:sync` | `nuxt generate` and `cap sync`, after every app change |
| `pnpm mobile:ios` | Build and run on an iOS simulator |
| `pnpm mobile:ios:device` | Build against this Mac's LAN address and open Xcode, to run on a phone |
| `pnpm mobile:android` | Build and run on an Android emulator or device |

## Production checklist

The server:

- [ ] Pick the production database in `hub.db` (see the [NuxtHub database docs](https://hub.nuxt.com/docs/database))
  and generate and commit the migrations for that dialect.
- [ ] Set `oauthServer.issuer` to the public `https` origin, so tokens do not depend on the request host behind a proxy.
- [ ] Set `NUXT_SESSION_PASSWORD` and `NUXT_OAUTH_SERVER_PRIVATE_KEY` in the host's environment: new values, one key
  per environment, never the ones in your local `.env` (see [Signing keys](/guide/going-further/signing-keys)).
- [ ] Set `NUXT_ACL_ADMINS`, or give the first admin the `admin` role and empty the list.
- [ ] Configure a real [Notify](/modules/platform/notify) driver, so password resets are sent instead of logged.

The app:

- [ ] Set your own `appId`, `appName` and `clientId` in `identity.ts`, and recreate `ios/` and `android/`.
- [ ] Point `NUXT_PUBLIC_AUTHENTICATION_CLIENT_ISSUER` and `NUXT_PUBLIC_AUTHENTICATION_CLIENT_API_BASE` at the production server in the
  environment of the release build, and build with `MOBILE_RELEASE=1`.
- [ ] Keep `@aparajita/capacitor-secure-storage` installed, and run `pnpm mobile:doctor`.
- [ ] Replace the icon and splash screen, set the version and build number, and set up signing for the App Store and
  Google Play.

The [Mobile release checklist](/modules/interface/mobile) and the [OAuth Server](/modules/identity/oauth-server) page
have the details.

## Add a database table

Write the schema twice, once per dialect, as plain drizzle tables:

```ts
// src/runtime/server/db/schema.sqlite.ts
import { sqliteTable, text, integer } from 'drizzle-orm/sqlite-core'

export const things = sqliteTable('things', {
  id: integer().primaryKey({ autoIncrement: true }),
  name: text().notNull(),
})
```

```ts
// src/runtime/server/db/schema.postgresql.ts
import { pgTable, text, serial } from 'drizzle-orm/pg-core'

export const things = pgTable('things', {
  id: serial().primaryKey(),
  name: text().notNull(),
})
```

Register the file as in the [setup checklist](/contribute/writing-a-module/setup-checklist). Omit `name`: every table export is registered. The files are parsed as text, so keep
them to imports and table calls, as described under
the schema file constraints on the [Module Kit](/modules/platform/module-kit) page.

Every module schema and extension file ships with a `.postgresql.ts` twin next to its `.sqlite.ts` file, exporting the
same tables with the same table, column and index names. Change both in the same commit. Map the types like this, so
the drizzle data types match:

| sqlite | postgresql |
| --- | --- |
| `sqliteTable` (`drizzle-orm/sqlite-core`) | `pgTable` (`drizzle-orm/pg-core`) |
| `integer().primaryKey({ autoIncrement: true })` | `serial().primaryKey()` |
| `integer({ mode: 'timestamp' })` | `timestamp({ withTimezone: true })` |
| `integer({ mode: 'boolean' })` | `boolean()` |
| `text({ mode: 'json' })` | `jsonb()` |
| `integer()` holding epoch milliseconds | `bigint({ mode: 'number' })` |
| `customType({ dataType: () => 'text' })` | the same `customType` from `pg-core` |

Runtime code must work on both dialects: no `db.run`, `db.batch`, `PRAGMA`, `rowid` or other sqlite-only SQL without a
postgres branch (see `changeId` in `packages/users/src/runtime/server/user-store.ts`).

Every package that owns a schema has a `test/schema-parity.test.ts` calling `expectSchemaParity`. It compares tables,
columns (drizzle data type, not null, primary key, unique, defaults, `$defaultFn` and `$onUpdateFn`), indexes and
foreign keys. Add a case when you add a schema file; a module-kit test fails when a `.sqlite.ts` schema has no
`.postgresql.ts` twin.

```ts
import { it } from 'vitest'
import { expectSchemaParity } from '@frigear-nu/module-kit/testing'
import * as sqlite from '../src/runtime/server/db/schema.sqlite'
import * as postgresql from '../src/runtime/server/db/schema.postgresql'

it('schema.postgresql matches schema.sqlite', () => expectSchemaParity(sqlite, postgresql))
```

## Extend another module's table

To add columns to a table that another module owns, for example `users`, ship the columns as an exported table of the
same name and register the file. The columns arrive in every app that installs both modules, and nothing happens when
the owner is absent:

```ts
// in setup()
extendDatabaseTable(nuxt, {
  resolver,
  file: dialect => `./runtime/server/db/users.${dialect}`,
})
```

```ts
// src/runtime/server/db/users.sqlite.ts
import { sqliteTable, text } from 'drizzle-orm/sqlite-core'

export const users = sqliteTable('users', {
  nickname: text(),
})
```

Ship a `users.postgresql.ts` too. Because `extendDatabaseTable` only changes the generated schema, document that host
apps must generate and commit a migration; your own fixtures need one as well (see [Testing](/contribute/writing-a-module/testing)).

## Fixture migrations

`registerDatabaseTable` and `extendDatabaseTable` change the generated Drizzle schema, not the database itself. Whenever a
module adds or changes columns, generate and commit migrations for every affected fixture, using its complete module
configuration including the extending modules. Commit the SQL, Drizzle snapshot and migration journal together: they
are versioned schema history, not build artifacts.

From the repository root, with an absolute `--cwd`:

```bash
pnpm --filter @frigear-nu/<pkg> exec nuxt db generate --cwd "$PWD/packages/<pkg>/test/fixtures/<fixture>"
```

After changing a schema or an extension, run it for every fixture that has committed migrations. It must print
`No schema changes, nothing to migrate` and leave `git status 'packages/*/test/fixtures'` clean. If it creates a
migration, the fixture needs one: commit it, or delete a stray one you do not intend to keep. Prepare the fixture
first so `.nuxt/hub/db/schema.mjs` includes every registered extension; never generate from only the owning module's
base schema.

A host application extends tables from its own `server/db/extend.<dialect>.ts` and generates and commits its own
migration for it. The [database extensions](/guide/concepts/database-extensions) concept explains the model.

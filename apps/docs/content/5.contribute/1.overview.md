This tab is for people and coding agents who change the Frigear repository itself: fixing a module, writing a new one,
updating a starter, or editing these docs. If you only build an app on the published modules, start at
[Get Started](/get-started/introduction) instead.

## Repository layout

This is a pnpm workspace monorepo.

| Folder | Contents |
| --- | --- |
| `apps/*` | Applications: the [frigear.nu website](/examples/apps/frigear-nu-website) (`apps/website`) and this documentation site (`apps/docs`). |
| `packages/*` | The `@frigear-nu/*` modules, layers and tools, published to npm. Packages depend on each other with `workspace:^`. |
| `.starters/*` | Templates for new projects outside this repository (`workspace`, `mobile`, `mobile-standalone`). They are not part of the workspace and use published versions. See [Starters](/contribute/starters). |

The root `README.md` lists the current apps and packages.

## Conventions

- **Run everything from the repository root**, including commands for one app or package. Scope them with `--filter`
  (spelled out: `-f` means `--force` in pnpm), for example `pnpm --filter @frigear-nu/docs dev`. Never `cd` into a
  package to run `pnpm`, and never run `npm install` or `yarn` in a subfolder: it desyncs the lockfile.
- **Nuxt 4 only.** Every module targets Nuxt 4, with app code under `app/`.
- **Conventional Commits** (`feat:`, `fix:`, `chore:`).
- **Changesets.** If the repository has a `.changeset/` folder, add one for any change to a published `packages/**`
  package (`pnpm changeset`). Apps need none.
- **Before you finish**, run `pnpm lint`, `pnpm typecheck` and `pnpm test` from the root, and `pnpm build` for changes to
  `nuxt.config.ts`, package `exports` or build tooling.
- **Never commit generated or dependency files**: `node_modules/`, `.nuxt/`, `.output/`, `.data/` and `dist/`.

The full rules, for agents and humans alike, are in `AGENTS.md` at the repository root. They cover authentication in
server routes, HTTP route conventions, database schemas per dialect, test fixtures and UX patterns. If a script or a
package README differs from `AGENTS.md`, the local source wins; update `AGENTS.md` when you notice a mismatch.

This page is for anyone who adds or edits a page on this documentation site. It tells you where a page goes, which
template it follows and how to write it. It ends with the link check every pull request runs.

The site is `@frigear-nu/docs`, a [Docus](https://docus.dev) app under `apps/docs`. It documents the whole repository
for developers who build on the Frigear modules. Product documentation for end users belongs in `apps/website`.

Run it from the repository root:

```bash
pnpm install
pnpm --filter @frigear-nu/docs dev
pnpm --filter @frigear-nu/docs build
```

## Where a page belongs

Content lives in `apps/docs/content/`, in five numbered folders that are the header tabs:

| Folder | Tab | Put here |
| --- | --- | --- |
| `1.get-started` | Get Started | The step-by-step path from zero to a running, deployed app. |
| `2.guide` | Guide | Concepts, UX patterns, best practices and going further. |
| `3.modules/<category>` | Modules | One reference page per module, in its category folder: `1.identity`, `2.commerce`, `3.features`, `4.interface` or `5.platform`. |
| `4.examples` | Examples | Starters, reference apps and short task examples. |
| `5.contribute` | Contribute | Working on this repository: development, writing a module, publishing, starters, docs and tooling. |

## Add or update a page

1. Pick the folder from the table above. A new section gets a numbered folder with a `.navigation.yml` for its title and
   icon.
2. Add a numbered Markdown file, for example `3.modules/3.features/5.my-module.md`. Docus sorts navigation by file name
   as a string, so use unique two-digit prefixes; the name after the number becomes the route
   (`/modules/features/my-module`). Inserting a page in the middle may mean renumbering its siblings, which keeps
   their routes.
3. Add frontmatter with a `title`, a one-sentence `description` and, optionally, a navigation icon:

   ```yaml
   ---
   title: My module
   description: One sentence on what the page covers.
   navigation:
     icon: i-lucide-puzzle
   ---
   ```

4. Write focused Markdown about the repository, using the [page templates](#page-templates) below. Check code and
   package READMEs before documenting behavior.
5. Run the docs app and check the page and its navigation.
6. Run `pnpm docs:check` and fix what it reports.

::warning
Moving or renaming a page changes its route and breaks every link to the old one. Do it only when you also:

1. Add an old to new entry in the `redirects` of `apps/docs/nuxt.config.ts`.
2. Update every link to the old route.
3. Run `pnpm docs:check` and make it pass.
::

## Conventions

- **Titles.** Use the plain name (`Auth`, `Cookie consent`), never a `Module` suffix. Headings are sentence case.
- **Page layout.** Use the [page templates](#page-templates) below.
- **Code and reference.** Signatures, types and payloads go in fenced `ts` blocks. Hooks, routes, options and
  environment variables go in tables, not running prose.
- **Accuracy.** Check defaults, routes and hooks against the source before documenting them.
- **Nuxt 4.** Write every example as Nuxt 4 code (`app/` directory, `defineNuxtConfig`), never Nuxt 3 or 2 patterns.
- **Links.** Link to pages by route (`/modules/identity/auth`), never by numbered file name.
- **Starters.** A page that describes a starter stays in step with the files in `.starters/`.

## Writing

Readers told us the docs left them asking "what is this even for?". These rules answer that question on every page.
Each row shows a sentence from the current docs and its rewrite.

| Rule | Before | After |
| --- | --- | --- |
| The first screen says what it is, who it is for and what you get. Code names come after. | "The Nuxt module that owns **authentication**: …" | "Lets people sign in to your app with a password, an emailed link, a passkey or GitHub/Google, and tells every server route who is calling." |
| One fact per sentence. | "Only the SHA-256 is stored, and they are accepted in the `Authorization` header only." | "Only a hash of the token is stored. Send it in the `Authorization` header." |
| Inline code at most once per sentence, and never before its plain explanation. | "A caller is one of three kinds, all resolved into the same `AuthPrincipal`" | "Auth works out who made the request and how they proved it. It hands your route that answer, the principal (`AuthPrincipal`)." |
| Expand acronyms on first use per page. | "PKCE sign-in for SPAs and Capacitor apps" | "sign-in with PKCE (Proof Key for Code Exchange) for single-page apps (SPAs) and Capacitor apps" |
| Link the glossary term on first use per page. | The first "staff" on a page has no link. | "[staff](/guide/concepts/glossary)" on first use, plain afterwards. |
| Never two names for one concept. | "OAuth client" and "application" on the same page. | "OAuth application" throughout. |
| Number procedures in execution order, with prerequisites before step 1. | "Then: 1. … 3. Implement the hooks. Without them nobody is an admin." | A `::warning` "Without these hooks no one can manage applications" before step 3. |
| Put a `::warning` before the step it protects, never after. | The migration warning follows the config block. | The migration is its own step, with the warning first. |
| Use `::caution` for irreversible or security-relevant steps. | Key rotation written as plain prose. | `::caution` "Use a different signing key per environment." |
| A table cell holds one fact in under about 25 words. | A 45-word purpose cell for `afterLogin`. | The cell "Where users land after signing in.", plus an **`afterLogin`** paragraph below the table. |
| No wall of prose. | Three unbroken paragraphs after an options table. | At most about six paragraphs between a table, callout or code block. |

Most pages carry several callouts. Pick each one by its job:

| Callout | Use it for |
| --- | --- |
| `::note` | Background the reader needs for the next step. |
| `::tip` | A recommendation or the shortest path. |
| `::warning` | What breaks if a step is skipped. It goes before that step. |
| `::caution` | A step that is irreversible or affects security. |
| `::callout{color="success" icon="i-lucide-check"}` | **What you should see** after a procedure. |

**Options.** The lead sentence of an options section is always "Options go under the `x` key." The table then shows
each option's full path from that key, for example `settings.pages.admin`. Long explanations go below
the table as paragraphs that start with the option name in bold.

## Page templates

Most pages follow one of five templates. Pick the tab for the page you are writing.

Other pages, such as best practices, UX patterns, going further and contribute pages, have no fixed template. They still
open by saying what the page is for and who it is for, and they end with `## Next steps`.

::tabs
:::tabs-item{label="Module overview"}
For the `index.md` of a module folder, or a module that has a single file. The front matter `description` says what the
module is for in one sentence, not a feature list.

1. **No heading.** Two to four plain sentences: what the module does for the host app and its users, when to use it,
   and when to use something else (one link). The package name does not appear before the second sentence.
2. **`## What you get`.** Bullets in reader terms, grouped as Pages (paths), Admin area (screens), Server routes,
   Composables and helpers, and Emails. Mark each item as on by default or opt-in.
3. **`:module-runtime{…}`.** The badge row, unchanged.
4. **`::note` with requirements.** Exactly three lines: **Installed for you:**, **You add:** and **Optional:**. Put
   nothing else in this note.
5. **`## Quick setup`.** A `::steps` block: install, then `nuxt.config.ts`, then a migration if the module adds tables,
   then its policy hooks if it has any. A `::warning` comes before the migration step and before the hooks step
   ("without this nobody can …"). A config-key gotcha such as "`authentication`, not `auth`" gets its own `::warning`
   here. End with a **What you should see** success callout.
6. **`## Options`.** The lead sentence "Options go under the `x` key.", then a table of option
   (full path), type, default and purpose. Long explanations follow as paragraphs led by the option name in bold.
   Runtime config and environment variables go under `### Runtime config`.
7. **Module with a single file:** `## Server`, `## App`, `## Hooks`, `## Routes`, `## Database` and
   `## Translations`, in that order. Each opens with one sentence, as on a sub-page.
   **Module with a folder:** `## Module pages`, a table of page, what it covers and who it is for or which auth mode.
   It sits after Options.
8. **`## Next steps`.** See the closing rule below.
:::

:::tabs-item{label="Module sub-page"}
For any other page in a module folder. Files are not renamed just to fit a role: set the page's role through
`navigation.title` and its opening paragraph.

1. **No heading.** One or two sentences: what the page covers, who it is for (app developer or module author) and which
   auth mode it applies to ("Server mode only", "Both modes"). Then: "Set up the module first: [Overview](…)."
2. **H2s in the order of the page's role** (table below). Every H2 opens with one sentence before any table or code:
   - Hooks: "Your app answers these Nitro hooks from a server plugin (`server/plugins/*.ts`)."
   - Routes: "Routes the module registers, and who may call them."
   - Database: "Tables the module adds. Generate and commit a [migration](…) after installing."
   - Translations: "Override any string in your app's `i18n/locales/<code>.json`."
3. **`## Next steps`.** See the closing rule below.

| Role | Nav title | Section order |
| --- | --- | --- |
| Overview (`index.md`) | Overview | The module overview template. |
| Server | Server API | One H2 per job, such as protecting a route or defining scopes. |
| App | App | Pages, Components, Composables, Utils. |
| Reference | Reference | Hooks, Routes, Database, Translations. An App section moves to the top, or to the App page if there is one. |
| Topic | Its own name | Any page shaped around one task. |

How the existing module folders map to these roles:

| Module | Mapping |
| --- | --- |
| auth | `2.server` is Server, `3.reference` is Reference, `4.client-mode` is a Topic. |
| oauth-server | `2.server` is Server (nav title "Server API"), `3.hooks` is the Topic "Policy hooks", `4.routes-and-clients` is Reference. |
| forms | `2.definition` is a Topic, then `3.server`, `4.app` and `5.reference`. |
| ui | All five pages are Topics, plus `6.reference`. |
| events, subscriptions | `2.server`, `3.app` and `4.reference`. |
:::

:::tabs-item{label="Concept page"}
For pages under `/guide/concepts`.

1. **No heading.** The problem in one or two sentences, then "After this page you can decide …".
2. **`::callout{icon="i-lucide-users"}`.** One line: **For:** app developers, module authors or both.
3. **`## Which one do I use?`** A table of what you are building, what to use and a link. It comes before any mechanism.
4. **`## Terms`.** Three to six bullets, one for each glossary term this page owns, each defined in one sentence.
5. **`## How it works`.** The mechanism, with an H3 per mechanism. Add a text diagram where a flow crosses apps.
6. **`## Common mistakes`** (optional). One `::warning` per mistake, each saying what breaks.
7. **`## Next steps`.** See the closing rule below.
:::

:::tabs-item{label="Task page"}
For pages under `/examples/tasks`.

1. **Bold lead, no heading.** `**What you'll build:**` and one or two sentences.
2. **`## Prerequisites`.** Links only, no explanations. For the toolchain: "See
   [Requirements](/get-started/installation#requirements)."
3. **`## 1. …`, `## 2. …`.** One numbered H2 per step, such as `## 1. Require a signed-in user`. Only task,
   starter and get-started pages use numbered headings, and sub-numbering such as `1.A` is never used. Each step
   gives one sentence of why, then the code. A `::warning` goes before the step it protects, and a `::caution`
   before an irreversible or security-relevant step.
4. **Success callout.** `::callout{color="success" icon="i-lucide-check"}` with **What you should see:** and an
   observable result, such as a URL, a status code or a screen.
5. **`## Troubleshooting`** (optional). A table of symptom, cause and fix.
6. **`## Next steps`.** See the closing rule below.

A numbered heading gets an anchor that starts with `_` and its number. For example, `## 1. Require a signed-in user`
becomes `#_1-require-a-signed-in-user`. [Check links](#check-links) explains the rule.
:::

:::tabs-item{label="Starter and get-started page"}
For the starter guides under `/examples/starters` and the pages under `/get-started`.

1. **Bold lead, no heading.** `**What you'll have afterwards:**` and one to three bullets: a running app, signed in
   as staff, and which screens you can open.
2. **`## Prerequisites`.** A link to [Requirements](/get-started/installation#requirements). List only the extra tools
   here, such as Xcode or Android Studio.
3. **`## 1. …`, `## 2. …`.** Numbered step headings, as on a task page, with the success callout after the step
   that runs the app.
4. **`## What is in the starter`.** Starter pages only: a table of path and what it does.
5. **`## Next steps`.** See the closing rule below.

The requirements table exists only on [Installation](/get-started/installation#requirements).
[Local development](/contribute/local-development) lists only the tools this repository needs beyond those.
:::
::

**Closing section.** Every page ends with `## Next steps`, never `## Next`, `## Related` or `## On this module`. It
holds at most four links. Each is a bullet in the form `[Page](/route) – why you would go there now`, in one
sentence. Put the most likely next action first, and do not repeat links from the opening paragraph.

## Pictures

Use screenshots for layouts, such as those on the [UX pattern](/guide/ux-patterns/layouts-and-navigation) pages. Use
text diagrams in a `text` code block for flows, such as a sign-in across apps. Images live in
`apps/docs/public/images/<section>/<page>-<pattern>.png`, and a pull request that changes a layout in `packages/ui` or
`packages/admin` recaptures them.

## Vocabulary

The [glossary](/guide/concepts/glossary) lists the one word these docs use for each concept, and the words to avoid.
Link a glossary term to it the first time a page uses that term, then write it plainly.

## Check links

`pnpm docs:check` runs `scripts/docs-check-links.mjs`. It is plain Node with no dependencies, so it runs in seconds.
The Docs workflow (`.github/workflows/docs.yml`) runs it on every pull request that touches the docs.

It checks:

| Check | What fails |
| --- | --- |
| Routes | A link to a page that does not exist, or an `/images/…` path missing from `apps/docs/public`. |
| Anchors | A `#anchor` that matches no heading on the target page. |
| Redirects | A redirect target with no page. A link to a redirect source is only a warning: use the new route. |
| External links | A `docs.frigear.dev` URL in package homepages, package READMEs, starter `AGENTS.md` files, the root `README.md` or `AGENTS.md` that no longer resolves. |
| Glossary | A route in the glossary's "Where it is explained" column that does not resolve. |

Anchors follow the rule of `@nuxtjs/mdc`, not plain GitHub slugs. The heading text is lowercased and stripped of
punctuation, and spaces become dashes. Repeated dashes then collapse to one, and a leading digit gets a `_` prefix. So
`## 1. Require a signed-in user` becomes `#_1-require-a-signed-in-user`.

::tip
Add `--terms` to list the words the glossary says to avoid, counted per file. For example,
`pnpm docs:check --terms apps/docs/content/1.get-started` scans one folder. It only reports. Add `--strict` to make
each hit an error once a folder is clean.
::

Errors make the run exit with code 1. Warnings do not.

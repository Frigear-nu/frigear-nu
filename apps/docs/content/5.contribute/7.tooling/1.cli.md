The Frigear CLI saves you from copying and renaming starters by hand. It creates a project from a
[starter](/guide/concepts/glossary), adds an app or a module to a pnpm workspace, and installs Frigear modules in an
app. It works in any pnpm workspace, not only in the [Frigear repository](/guide/concepts/glossary). Its package is
`@frigear-nu/cli`, a [citty](https://github.com/unjs/citty) CLI published to npm.

## Run it

Run it without installing it:

```bash
pnpx @frigear-nu/cli --help
pnpx @frigear-nu/cli <command> --help
```

`pnpm create frigear-app` (or `npm create frigear-app@latest`) does the same as `init` below.

Inside the Frigear repository, use the root `cli` script. It runs `packages/cli/bin/cli.mjs`, which loads the
TypeScript source with jiti, so there is no build step:

```bash
pnpm cli --help
```

::note
The starters and app templates are downloaded from the `Frigear-nu/frigear-nu` GitHub repository with
[giget](https://github.com/unjs/giget). While that repository is not public, set `GIGET_AUTH` to a GitHub token that can
read it, for example `GIGET_AUTH=$(gh auth token)`.
::

## Commands

| Command | Purpose |
| --- | --- |
| `init` | Creates a new project from a starter. |
| `app:create` | Adds an app from a starter to `apps/<name>` of a workspace. |
| `module:create` | Scaffolds a new Nuxt module under `packages/`. |
| `add` | Installs Frigear modules in a Nuxt app and adds them to its `nuxt.config`. |
| `package:rename` | Renames a workspace package and every reference to it. |
| `module:folder` | Turns a single-file local module into a folder module. |
| `module:move` | Moves a local module or a package folder, fixing relative paths. |

Every command takes `--cwd <dir>` (default: `INIT_CWD`, else the current directory).

### `init`

```bash
pnpx @frigear-nu/cli init [dir] [--platform <platform>] [-t <template>] [--ref <ref>] [--force] [--no-install]
```

| Argument | Default | Purpose |
| --- | --- | --- |
| `dir` | `frigear-app` | Directory to create. Its name becomes the root `package.json` `name`. |
| `--platform`, `--starter` | asked, `web` when not interactive | What to build: `web`, `mobile` or `web,mobile`, or the starter's name. See the table below. |
| `-t`, `--template` | | Any [giget](https://github.com/unjs/giget) source to copy instead of a starter, for example `gh:org/repo/path#ref`. Not together with `--platform`. |
| `--ref` | `main` | Branch or tag of the repository to copy the starter from. |
| `--force` | `false` | Write into a directory that is not empty. |
| `--no-install` | | Skip `pnpm install` and `pnpm prepare:env`. |

| `--platform` | Starter (also accepted as the value) | What you get |
| --- | --- | --- |
| `web` | `workspace` | `apps/web` with sign-in, account pages and user management in the admin area |
| `mobile` | `mobile` | `apps/mobile`, a Capacitor app that signs in at an existing issuer |
| `web,mobile` | `mobile-standalone` | both, with `apps/web` as the app's OAuth server and API |

With `-t`, the root `package.json` is still renamed (when there is one), and `pnpm prepare:env` only runs when the
template has that script.

### `app:create`

```bash
pnpx @frigear-nu/cli app:create <name> [--template <template>] [--ref <ref>] [--no-install]
```

| Argument | Default | Purpose |
| --- | --- | --- |
| `name` | required | Folder under `apps/`, kebab-cased. |
| `--template` | `web` | `web` (the `workspace` starter's app), `web-standalone` (the `mobile-standalone` starter's OAuth server app) or `mobile`. |

It needs a `pnpm-workspace.yaml` above `--cwd`. The package is named `<scope>/<name>`, with the scope of the existing
apps (`@workspace` in the starters), else of the root package. It fails when `apps/<name>` already has a
`package.json`, and runs `pnpm install` at the root unless `--no-install` is passed.

### `module:create`

```bash
pnpx @frigear-nu/cli module:create <name> [--template <template>] [--scope <scope>] [--dir <dir>]
```

| Argument | Default | Purpose |
| --- | --- | --- |
| `name` | required | Name of the module, for example `my-module`. It is kebab-cased. |
| `--template` | `gh:nuxt/starter#module` | A giget template source, for example `gh:github.com/my/package`. |
| `--scope` | the root package's scope | npm scope, for example `@acme`. `--scope ""` leaves the name unscoped. In this repository the root is `@frigear-nu/root`, so modules are `@frigear-nu/<name>`. |
| `--dir` | `packages` | Workspace folder to create the module in. |

It downloads the template into `<workspace root>/<dir>/<name>` and sets the `name` in its `package.json`. It exits
with an error, without changing anything, when that folder already contains a `package.json`.

### `add`

```bash
pnpx @frigear-nu/cli add <module...> [--app <app>] [--no-install]
```

| Argument | Default | Purpose |
| --- | --- | --- |
| `module` | required | One or more modules: `forms` means `@frigear-nu/forms`; a scoped name is used as is. |
| `--app` | see below | The app: a path, or a folder under `apps/`. |
| `--no-install` | | Only edit `nuxt.config`. |

Without `--app`, the app is the current directory when it has a `nuxt.config`, else the only app under `apps/` with
one. The command runs `pnpm add` in the app and adds each module to `modules` once. It prints each module's
documentation link.

::warning
Module options and the migration are still yours. A module that adds tables needs `pnpm db:generate`, as
[Adding modules](/get-started/adding-modules) describes.
::

### `package:rename`

```bash
pnpx @frigear-nu/cli package:rename <package> <new-name> [--dir] [--dry-run]
```

| Argument | Default | Purpose |
| --- | --- | --- |
| `package` | required | The package: its current `name`, or its folder (relative to `--cwd` or the workspace root). |
| `new-name` | required | The new name. A bare name keeps the old scope: `forms` renames `@acme/old` to `@acme/forms`. |
| `--dir` | `false` | Also rename the folder to the new unscoped name, and fix paths that point into it. |
| `--dry-run` | | Print what would change; write nothing. |

It changes, across the workspace (skipping `node_modules`, `.nuxt`, `.output`, `.data`, `dist`, hidden folders and
changelogs):

- the package's own `name`;
- the key in the `dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies` and
  `peerDependenciesMeta` of every `package.json`, keeping the spec (`workspace:*` stays `workspace:*`);
- keys and list items of `pnpm-workspace.yaml` (`catalog`, `overrides`, `minimumReleaseAgeExclude`), edited as text so
  comments stay;
- string literals equal to the name or starting with `<name>/` in `.ts`, `.mts`, `.js`, `.mjs`, `.vue` and `.json`
  files: imports, `import('…')`, `nuxt.config` `modules` entries, tsconfig `paths`; and mentions in Markdown.

An unscoped name is too common a word to replace in every string, so for one only manifests and import, export and
`require` specifiers change, and the command says so. Lockfiles are never edited: run `pnpm install` afterwards, then
`nuxi prepare` in the apps that use the package.

### `module:folder`

```bash
pnpx @frigear-nu/cli module:folder <module> [--app <app>] [--runtime] [--dry-run]
```

| Argument | Default | Purpose |
| --- | --- | --- |
| `module` | required | A path to `modules/<name>.ts` in an app or layer, or a bare name looked up in the app's `modules/`. |
| `--app` | as for `add` | The app a bare name is looked up in: a path, or a folder under `apps/`. |
| `--runtime` | `false` | Also create `runtime/plugin.ts`, a plugin stub. |
| `--dry-run` | | Print what would change; write nothing. |

Nuxt registers both `modules/*.ts` and `modules/*/index.ts`, so `modules/foo.ts` can become `modules/foo/index.ts`
with a `runtime/` folder next to it. The command moves the file, rewrites its relative imports (`./x` becomes `../x`)
and updates imports of it that name the file with its extension; an extensionless `../modules/foo` still resolves, so it
stays. It refuses when `modules/foo/` exists. When the module has no `createResolver(import.meta.url)`, it prints how
to add one and register runtime files with `resolve('./runtime/…')`.

### `module:move`

```bash
pnpx @frigear-nu/cli module:move <module> <destination> [--name <name>] [--app <app>] [--dry-run]
```

| Argument | Default | Purpose |
| --- | --- | --- |
| `module` | required | A module file (`modules/foo.ts`), a folder module (`modules/foo/`), a package folder, or a bare name in the app's `modules/`. |
| `destination` | required | The directory to move it into. For a local module, an app or layer folder (one with a `nuxt.config`) means its `modules/`. |
| `--name` | the current name | New file or folder name. A package keeps its `name`: use `package:rename` for that. |
| `--app` | as for `add` | The app a bare module name is looked up in. |
| `--dry-run` | | Print what would change; write nothing. |

It refuses to overwrite. Relative paths inside the moved files that point outside them are made relative to the new
place, and relative or `~~/` paths elsewhere in the workspace that point into it (imports, `nuxt.config` `extends` and
`modules` entries, tsconfig `extends`, Markdown links) follow it. Paths that do not resolve to an existing file are left
alone. It warns when:

- a moved file uses a Nuxt alias (`~/`, `~~/`) that now resolves against another app;
- the module imports a package the source app depends on and the destination does not;
- a package folder lands outside the `packages:` globs of `pnpm-workspace.yaml`, where pnpm will not link it.

Restart `nuxi dev` in both apps after moving a local module, and run `pnpm install` after moving a package.

### `upgrade`

```bash
pnpx @frigear-nu/cli@latest upgrade [package...] [--to <versions>] [--dry-run] [--no-install] [--report <file>]
```

| Argument | Default | Purpose |
| --- | --- | --- |
| `package` | every pinned package | Only these packages: `auth` means `@frigear-nu/auth`. |
| `--to` | the `latest` dist-tag | Target versions, e.g. `auth@0.6.1,users@3.1.0`. |
| `--dry-run` | | Print the report and change nothing. |
| `--no-install` | | Skip `pnpm install` afterwards. |
| `--report` | `frigear-upgrade.md` | Where the report goes, relative to the workspace root. |

It moves every `@frigear-nu/*` pin of the workspace to its target version: the `dependencies`, `devDependencies` and
`peerDependencies` of each workspace package, and the `catalog`, `overrides` and `minimumReleaseAgeExclude` entries of
`pnpm-workspace.yaml`. Each range keeps its operator (`0.3.4`, `^0.5.1` and `>=0.3.4` stay exact, caret and `>=`).
`workspace:` and `catalog:` references are left alone, and it never downgrades.

Then it runs the migrations of every breaking release between the old and the new version. A migration rewrites what is
safe to rewrite, such as moved route paths, and lists everything else with `file:line` and a docs link. The report is a
checklist: the version table, what was rewritten, what to do by hand, and the next commands. [Upgrading](/get-started/upgrading)
walks through it.

::note
A release with a breaking change adds a migration to `packages/cli/src/upgrades/`. The entry names the first version
with the change (`since`) and has rules (a regular expression with a message, and an optional `replace`), a `project`
check for `nuxt.config` options, and `steps` for a person. Add a test for it to `packages/cli/test/upgrade.test.ts`.
::

### `create-frigear-app`

```bash
pnpm create frigear-app [dir] [--platform <platform>] [-t <template>] [--ref <ref>] [--force] [--no-install]
npm create frigear-app@latest [dir] [--platform <platform>]
```

`packages/create-frigear-app` is what `pnpm create` and `npm create` find. It has no dependencies: it runs `init` of
`@frigear-nu/cli@latest` with the package manager that started it (`pnpm dlx`, `npx`, `yarn dlx` or `bunx`), so it takes
the same arguments as `init`, and every CLI release reaches it without releasing `create-frigear-app`. The starters
come from `main` unless you pass `--ref`. Set `FRIGEAR_CLI` to run another CLI, such as `@frigear-nu/cli@0.1.0` or a
packed tarball.

## After `module:create` in the Frigear repository

The command only creates the package. [Scaffold a module](/contribute/writing-a-module/scaffold) starts the path through
the rest: the folder layout, `setup()`, tests, the release config and the module page.

## Developing the CLI

The source is in `packages/cli/src`, with one file per command in `commands/`. Its tests run against the repository's
own `.starters/`, with giget mocked, so nothing is downloaded or installed:

```bash
pnpm --filter @frigear-nu/cli test
```

The published package is built with unbuild into `dist/`, and `publishConfig` points `bin` at `dist/cli.mjs`. It is
released like every other package.

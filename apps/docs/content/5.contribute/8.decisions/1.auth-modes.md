**Status:** accepted (2026-11-03). **Scope:** `@frigear-nu/auth`, `@frigear-nu/oauth-client`, `@frigear-nu/authorization`,
`@frigear-nu/mobile`, the mobile starters and their docs.

## Context

The repo has two answers to "who is signed in" in the browser.

- **Auth** (`packages/auth`) signs people in on the server. It is built on nuxt-auth-utils (a sealed cookie session,
  served by its own `/api/_auth/session` endpoint, so it needs a server but no database), and it installs
  `@nuxthub/core` (`packages/auth/src/module.ts:113-133`). It registers tables (`:167-189`), a user store
  (`:231-243`), around twenty Nitro routes (`:330-379`), a server middleware (`:318-321`), tasks (`:444-460`) and
  pages (`:400-423`). App code reads `useUserSession()`. Its `User` comes from `#auth-utils` and is augmented: the
  host adds `id: number` and more (`apps/website/shared/types/auth.d.ts`), Authorization adds `role`
  (`packages/authorization/src/module.ts:137-146`) and Preferences adds `preferences`
  (`packages/preferences/src/module.ts:87-91`).
- **OAuth Client** (`packages/oauth-client`) is a public PKCE client for SPAs and Capacitor apps, with no server and
  no database. App code reads `useOAuth()` (`packages/oauth-client/src/runtime/app/composables/useOAuth.ts:13`). It
  returns `status`, `claims` (`IdTokenClaims`, `sub: string`, no `role`), `login`, `completeLogin`, `logout` and
  `getAccessToken`. `$api` / `useApi` send the bearer token.

So a developer moving between the web app and the mobile app has to switch composables, user shapes and guard systems.
The server side is already unified. `requireAuth` / `requireUser` turn a cookie session, a user token or an OAuth access
token into one `AuthPrincipal` (`packages/auth/src/runtime/types.ts:16-20`). OAuth Server and Frigear Resource plug in
their resolvers through `auth:resolvers` (`packages/auth/src/module.ts:200-217`).

The guards differ too. Web apps opt in with `@frigear-nu/authorization` rules (on `routeRules`, or with
`definePageMeta({ authorize })`), checked by a global middleware
(`packages/authorization/src/runtime/app/middleware/authorization.global.ts`). OAuth Client has its own guard:
`protect: 'none' | 'all'` plus `publicPaths` (`packages/oauth-client/src/types.ts:61-67`). Its default `'none'` is
sound. The problem is the default that Mobile owns: Mobile installs OAuth Client with `protect: 'all'`
(`packages/mobile/src/module.ts:132-144`), and every tab defaults to `requiresAuth`
(`packages/mobile/src/runtime/shared/tabs.ts:69`), which hides the tab while signed out
(`packages/mobile/src/runtime/shared/chrome.ts:52`). So a mobile app is locked down unless it opts out, with a second
guard vocabulary to learn.

## Decision

1. The public client becomes a mode of Auth: `authentication.mode: 'server' | 'client'`, default `'server'`. Server
   mode is today's Auth, unchanged. Client mode is today's OAuth Client, configured under `authentication.client`.
   The app sets the mode itself, in its own config. No module infers it.
2. Apps and modules get one client API in both modes. `useUserSession()` keeps nuxt-auth-utils' name and shape,
   `useAuth()` holds the actions, and `$api` / `useApi()` call the API.
3. In both modes the app chooses its guards, through `@frigear-nu/authorization`. Mobile protects nothing by default.
   Authorization learns to run in client mode, accepts `definePageMeta({ authorize: false })`, and exempts the
   anonymous auth pages and endpoints itself.
4. `@frigear-nu/oauth-client` is frozen as it is and marked deprecated. It gets no translation layer, and Auth refuses
   to run next to it.
5. Client-mode guards are UX, not access control. The API decides.

### Target API

A server-rendered web app does not change:

```ts [apps/web/nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@frigear-nu/users', '@frigear-nu/auth', '@frigear-nu/authorization'],
  authentication: {
    // mode: 'server' is the default
    settings: { password: true, pages: { login: true } },
  },
  authorization: { redirectTo: '/login' },
  routeRules: {
    '/account/**': { authenticated: true },
    '/admin/**': { roles: ['admin'] },
  },
})
```

The mobile starter signs in at an issuer and chooses its own guards:

```ts [apps/mobile/nuxt.config.ts]
import { appId, appName, callbackPath, clientId, scopes } from './identity'

export default defineNuxtConfig({
  modules: ['@nuxt/ui', '@frigear-nu/mobile', '@frigear-nu/authorization'],
  mobile: {
    appId,
    appName,
    tabs: [
      { id: 'home', to: '/', label: 'Home', icon: 'i-lucide-house', sfSymbol: 'house' },
      { id: 'account', to: '/account', label: 'Account', icon: 'i-lucide-circle-user-round', sfSymbol: 'person.crop.circle', requiresAuth: true },
    ],
  },
  // Mobile installs Auth and fills in native.scheme (from appId) and the LAN rewrite. The mode is the app's to set.
  // Issuer and API come from NUXT_PUBLIC_AUTHENTICATION_CLIENT_ISSUER / _API_BASE.
  authentication: {
    mode: 'client',
    client: { clientId, scopes, callbackPath }, // scopes must include 'openid'
  },
  authorization: { redirectTo: '/login' },
  routeRules: {
    // Signed in everywhere, as the starter is today. Remove it for a public home screen.
    // /login and the callback stay public without a rule (Details 5).
    '/**': { authenticated: true },
  },
})
```

The same page code runs in both apps:

```vue [app/pages/account.vue]
<script setup lang="ts">
const { loggedIn, user } = useUserSession()
const { logout } = useAuth()
const { data: orders } = await useApi<Order[]>('/api/shop/me/orders')
</script>
```

## Details

### 1. Mode and configuration

**One mode resolver.** Nuxt evaluates a module's `moduleDependencies(nuxt)` before it merges the defaults that other
modules pass, so a mode supplied as another module's default would arrive too late for dependency selection. Auth,
Authorization and Mobile therefore all read the mode through one function, `resolveAuthMode(nuxt)`, exported from a new
`@frigear-nu/auth/mode` subpath that does not import `@nuxt/kit`. It reads only the app's own
`authentication.mode`, validates it, and defaults to `'server'`. Auth's `setup` keeps the mode its
`moduleDependencies` saw and throws when the merged options disagree, i.e. when another module tried to set the mode
through a dependency default.

- Mobile installs Auth when `authentication` is configured, but never passes `mode`. Its scalar defaults
  (`client.native.scheme`, `client.dev.rewriteLoopback`) are only read in Auth's `setup`, after the merge, never in
  `moduleDependencies`. Today Auth's dependency function reads only `settings.webAuthn` (`module.ts:131`), which also
  comes from the app.
- At setup, Mobile throws if Auth is installed and the mode is not `'client'`. A Capacitor app cannot carry a
  same-origin cookie to the API.
- A fixture tests module-order permutations (`[mobile, auth, authorization]` in every order) and asserts the same
  installed modules each time. It lives in Mobile's tests (PR4): Auth cannot depend on Mobile without a workspace
  cycle, and before PR4 Authorization still installs Users.

**Options.** OAuth Client's options (`packages/oauth-client/src/types.ts:22-101`) move under `authentication.client`:

| oauth-client (`oauthClient.*`) | Auth | Notes |
| --- | --- | --- |
| `issuer`, `clientId`, `scopes` | `client.*`, same names | `scopes` must contain `openid` (Details 4) |
| `apiBase` | `client.apiBase` | default: the issuer |
| `api.attachTo` | `client.apiOrigins` | flattened |
| `api.onUnauthorized` | `client.onUnauthorized` | flattened, default `signOut` |
| `redirectUri`, `callbackPath`, `native.{scheme,redirectUri}` | `client.*`, same names | |
| `endpoints`, `discovery`, `authorizationParams`, `storage` | `client.*`, same names | |
| `pages.login` | `settings.pages.login` | the same option as server mode; default on in client mode |
| `pages.callback` | `settings.pages.callback` | client mode only, default `true` |
| `redirect.login` | `client.redirect.login` | default: the `settings.pages.login` path |
| `redirect.afterLogin`, `redirect.afterLogout` | `client.redirect.*` | `afterLogout` default `/` |
| `dev.rewriteLoopback`, `allowClientSecretInBundle` | `client.*`, same names | |
| `protect`, `publicPaths`, page meta `oauth` | removed | the guards belong to Authorization (Details 5) |
| (new) | `client.mapUser`, `client.userinfo` | Details 4, PR3b |

`useAuthPages()` (`packages/auth/src/runtime/app/composables/useAuthPages.ts`) keeps working because client mode fills
the same `pages` block.

**Public runtime config.** `public.authentication` gains `mode` in both modes. In client mode it is:

```ts
{
  mode: 'client',
  password: false, passwordReset: false, webAuthn: false, magicLink: false, verifyEmail: false,
  oauth: [], apiTokens: false, frigearSso: false,
  pages: { login: '/login', register: undefined },
  afterLogin: '/',                 // = client.redirect.afterLogin
  publicPaths: ['/login', '/auth/callback'],
  client: {
    issuer: '', clientId: '', scope: 'openid', apiBase: '', apiOrigins: [], onUnauthorized: 'signOut',
    redirectUri: '', nativeRedirectUri: '', callbackPath: '/auth/callback',
    discovery: true, endpoints: {}, authorizationParams: {}, storage: 'auto',
    redirect: { login: '/login', afterLogin: '/', afterLogout: '/' },
    rewriteLoopback: true,
    clientSecret: '',              // declared only in `nuxt dev` or with allowClientSecretInBundle
  },
}
```

Code that checks the server feature flags keeps working, because they are all off. `publicPaths` is new in both modes
(Details 5). The env vars follow Nuxt's mapping: `NUXT_PUBLIC_AUTHENTICATION_CLIENT_ISSUER`, `..._CLIENT_CLIENT_ID`,
`..._CLIENT_SCOPE` and `..._CLIENT_API_BASE`.

**Secret guard.** The production build check (`packages/oauth-client/src/build.ts:56-58`) only knows the old names. In
Auth it checks `NUXT_PUBLIC_AUTHENTICATION_CLIENT_CLIENT_SECRET`, `NUXT_PUBLIC_AUTHENTICATION_CLIENT_SECRET`,
`public.authentication.client.clientSecret`, and the old `NUXT_PUBLIC_OAUTH_CLIENT_SECRET` /
`..._CLIENT_CLIENT_SECRET`. A forgotten old variable in CI then still fails the build. `clientSecret` stays undeclared
in production (`packages/oauth-client/src/module.ts:121-124`). There is one production-build test per name.

### 2. What client mode skips

`moduleDependencies` is already a function of `nuxt` (`packages/auth/src/module.ts:113`). In client mode it returns
only `@frigear-nu/module-kit` (`@nuxt/ui` stays optional). `setup` branches once, at the top, into `setupServerMode`
(today's body, moved verbatim) and `setupClientMode`.

| Piece | Server | Client |
| --- | --- | --- |
| `@nuxthub/core`, `nuxt-auth-utils`, `@frigear-nu/notify`, `@frigear-nu/menu` (`:113-133`) | yes | no |
| `registerDatabaseTable` / `extendDatabaseTable` (`:179-189`) | yes | no |
| `#auth/resolvers`, `#auth/scopes`, `#auth/user-store`, `#auth/session-mapper`, `#auth/oauth` (`:200-311`) | yes | no |
| `addServerImportsDir`, `inlineModuleRuntime`, server middleware (`:315-321`) | yes | no |
| Bootstrap registry and `/api/auth` routes (`:325-379`) | yes | no |
| `useLogin`, `useMagicLink`, `usePasskeys`, `usePasswordReset`, `useRegistration`, `useAfterLogin`, `useWebAuthn` | yes | no |
| Login, register, reset and magic-link pages, `AuthCard` (`:391-423`) | yes | client login and callback pages |
| frigear.nu SSO and the colour-mode plugin (`:428-441`), cleanup task (`:443-460`), account menu (`:462`) | yes | no |
| `registerLocales`, `registerTailwindSource`, `useAuthPages` | yes | yes |
| PKCE client, token storage, `#auth/native`, bearer `$api` | no | yes |

Client mode checks four things at `modules:done`:

- It throws when `nuxt-auth-utils` or `@frigear-nu/users` is installed, naming the module that pulled it in.
  nuxt-auth-utils needs a server for its session endpoints, and Users needs a database.
- It throws when `@frigear-nu/oauth-client` is installed. Server mode throws too, because both would register `$api`
  and `useApi` (`packages/oauth-client/src/module.ts:179-185`).
- It throws when the scopes lack `openid`.
- It warns when `routeRules` carry `authenticated`, `roles`, `guest` or `ability` keys but Authorization is not
  installed: those rules would be silently ignored.

`@nuxthub/core` becomes an optional peer of Auth. Server mode checks for it in `moduleDependencies`, before Nuxt tries
to load it, and fails with a clear message.

**SSR is off.** Client mode sets `ssr: false`. If the app's own config (any of its layers) sets `ssr: true`, the build
throws. Tokens live in
the browser or the Keychain, so a server render would always be signed out and would not match the hydrated markup.
Mobile already sets `ssr: false` (`packages/mobile/src/module.ts:162`). SSR support is an open question.

### 3. The one client API

**`useUserSession()`** answers "who is signed in" in both modes. Server mode uses nuxt-auth-utils' own. In client mode
Auth registers its own auto-import with the same `UserSessionComposable` shape:

| Member | Client mode |
| --- | --- |
| `ready` | `true` once the stored tokens were read |
| `loggedIn` | `true` only when signed in **and** `user` is not `null` |
| `user` | the mapped user (Details 4), `null` signed out |
| `session` | `{ id: <a random id of the sign-in, stored with the tokens and kept across refreshes>, user }` |
| `fetch()` | re-reads the claims and re-runs the mapping, dropping any cached userinfo |
| `clear()` | `useAuth().logout({ redirect: false })` |
| `openInPopup()` | throws: not available in client mode |

**Types.** nuxt-auth-utils is not installed in client mode, so `#auth-utils` does not exist. Auth adds an alias
`#auth-utils` pointing at `runtime/client/auth-utils.ts` (types only, so the module builder emits its `.d.ts`). That file mirrors nuxt-auth-utils' session types
(`dist/runtime/types/session.d.ts`): empty `User` and `SecureSessionData`; `UserSession` with a required `id`,
optional `user` and `secure`, and an index signature; `UserSessionRequired`; and `UserSessionComposable`. Client mode
then adds `sub: string` and `id: string` to `User` through a type template.

**`user.id`.** In client mode `id` is the issuer's `sub`, a string. The stand-in does not widen it to
`string | number`. There are two kinds of `User` augmentation, and they coexist:

- **App-specific** augmentation belongs to one app and one mode. The website's `User extends SessionUser`
  (`id: number`) is server-specific and lives only in the server app.
- **Portable** augmentation is what modules add. Authorization's `role` and Preferences' `preferences` never declare
  `id`. Module code that runs in both modes treats `user.id` as opaque.

No module augments `id` today.

**`useAuth()`** holds the actions. In client mode it is the full `useOAuth()` contract (`useOAuth.ts:19-78`):

```ts
const {
  status, // 'unknown' | 'signed-in' | 'signed-out'
  authenticated,
  signingIn,
  login, // ({ returnTo?, params? }) => Promise<void>
  completeLogin, // (callbackUrl?) => Promise<CallbackResult>, used by the callback page
  logout, // ({ redirect?: boolean | string }) => Promise<void>
  getAccessToken, // (options?: GetAccessTokenOptions) => Promise<string | null>
  isCallbackUrl, // (url) => boolean, for deep-link routers
  claims, // client mode only
  getClient, // client mode only
} = useAuth()
```

`AuthSignInButton` (was `OAuthSignInButton`) and the callback page use `signingIn` and `completeLogin`
(`packages/oauth-client/src/runtime/app/components/OAuthSignInButton.vue:15,35`, `pages/callback.vue:9-16`). The
`./types` subpath export stays, as `@frigear-nu/auth/client-types`.

**`useAuth()` and `$api` in server mode** come in a separate small PR (PR3c):

- `login()` navigates to the login page with `?redirect=`.
- `logout()` posts `/api/auth/logout` and calls `clear()`.
- `getAccessToken()` returns `null`, `completeLogin()` throws and `isCallbackUrl()` returns `false`.
- `$api` uses the request-aware fetch (`useRequestFetch()` on SSR, which forwards the incoming Cookie and
  Authorization headers) **only** for a relative path (`/x`, not `//x`) or a URL on the request's own origin. That
  includes a `baseURL` option, which is validated the same way. Anything else goes through plain `$fetch` without
  forwarded headers.
- `useApi` is `useFetch` through that `$api`.

Nothing else in the repo defines `$api`, `useApi` or `useAuth`.

**Existing `useUserSession` callers** in `packages/*/src/runtime/app`:

- **Work unchanged in client mode:**
  - Authorization's client resolver (`packages/authorization/src/runtime/app/resolver.ts:6`).
  - Cookie Consent (`useCookieConsent.ts:29,65`, `CookieConsentBanner.vue:24`). It reads `loggedIn` only, and
    `persistToUser` is off without Users (`packages/cookie-consent/src/module.ts:52`).
  - App pages that read `loggedIn` / `user`.
- **Server mode only:**
  - Account, Admin (`packages/admin/src/module.ts:34`), Users' email-change pages, and Auth's own server flows.
  - Events, Payments, Subscriptions and Preferences. They install `@frigear-nu/users` themselves
    (`packages/events/src/module.ts:87`, `payments/src/module.ts:86`, `subscriptions/src/module.ts:106`,
    `preferences/src/module.ts:29-35`), and they call `$fetch('/api/...')` on the app's own origin.

Client-mode support for those feature modules is out of scope. It needs dependency gating (splitting the client part
from Users and the database), not only a switch to `$api`.

### 4. The user in client mode

**Identity is required.** Client mode requires the `openid` scope (a build error otherwise). The core already accepts
token responses without an `id_token` (`packages/oauth-client/src/runtime/core/client.ts:189-213`, `getClaims()`
returns `null` at `:398-405`). In client mode a sign-in whose response has no valid `id_token` fails in
`completeLogin` and its tokens are discarded. A stored session that has no decodable claims (a corrupt store, or an
issuer change) is cleared locally (`signOutLocally('no_identity')`) and `auth:user-failed` is called. That keeps the
rule simple: `loggedIn` implies `user !== null`. Authorization relies on that, because it treats a `null` user as a
guest (`packages/authorization/src/runtime/utils/rules.ts:65-66`). A refreshed `id_token` that fails validation
already keeps the previous claims (`client.ts:196-206`).

**Default mapping (PR3a)** is synchronous and uses the `id_token` claims only:
`{ id: sub, sub, name, email, avatar: picture, role }`. `role` is set only when the token carries a string `role`
claim. OAuth Server adds none by default; a host adds it with `oauth:claims`
(`packages/oauth-server/src/runtime/server/utils/oauth-access.ts:73-92`). It needs no request, so a cold start offline
still knows who is signed in.

**Custom and userinfo mapping (PR3b).** `client.mapUser` is a path to a default-export function, as
`settings.session.mapper` is (`packages/auth/src/types.ts:146-148`). `client.userinfo: true` makes the default mapper
merge `/userinfo` as well.

```ts [app/auth/map-user.ts]
import type { AuthClientUserContext } from '@frigear-nu/auth/client-core'

export default async ({ claims, userinfo, api }: AuthClientUserContext) => ({
  id: claims.sub,
  name: claims.name ?? '',
  role: (await userinfo()).role as string | undefined,
})
```

Change listeners in the core are synchronous today (`client.ts:105-113`, `plugins/oauth.client.ts:41-54`), so async
mapping needs these rules:

- **Ordering.** Each mapping run carries a version (incremented on every token change). A result is applied only if
  its version is still current. A run that finishes after logout, or after the `sub` changed, is dropped.
- **Until the first result.** `user` holds the default claims mapping, so `loggedIn` never waits on the network.
- **Identity check.** `userinfo()` rejects a response whose `sub` differs from the `id_token`'s.
  `fetchUserInfo` does not check this today (`client.ts:409-416`).
- **Errors.** Only transient errors (`OAuthTransientError`, offline) fall back to the claims mapping, with
  `auth:user-failed`. A 401 (`OAuthSessionError`) goes through the normal `onUnauthorized` handling. A config error
  surfaces.
- **Cache.** `userinfo()` is memoised per token version and dropped by `useUserSession().fetch()`, by a refresh that
  changes the claims, and by logout.

A role on the client is only a UX hint (see Security).

### 5. Guards

**Authorization's app side already works without a server.** The middleware, `useAuthorization`, `Can` / `Cannot` and
the evaluator only call `resolveClientUser()`, which reads `useUserSession().user.value`
(`runtime/app/resolver.ts:5-7`), and the rules ship in public runtime config (`module.ts:61-74`). PR4 gates the server
side on `resolveAuthMode`:

- `moduleDependencies` (`module.ts:38-51`) becomes a function. In client mode it lists only module-kit and Auth.
  `@nuxthub/core` becomes an optional peer in `packages/authorization/package.json` (`:76-78`).
- Client mode skips `extendDatabaseTable` (`:77-80`), the server templates (`:99-106`), the server imports
  (`:154`, `:164-165`) and the server middleware (`:174-177`).
- The `User` type template emits `role?: string` in client mode (`:137-146`).

**`authorize: false`.** `routeRules` already has an override: `{ authenticated: false }` on a more specific pattern
opens a path (`runtime/utils/rules.ts:38-46`). Page meta has none. Today `authorize: false` falls through to
`routeRules` (`authorization.global.ts:11`) and is not in the type. PR4 makes `AuthorizeMeta` accept `false`,
`normalizeAuthorizeMeta` return `RouteRule | undefined` (`false` → `undefined`, `rules.ts:48-52`), and the middleware
check `meta !== undefined` instead of truthiness. The client-mode login and callback pages carry
`definePageMeta({ authorize: false })`. Server-mode pages do not: they are exempted the way described next.

**Anonymous auth paths are always exempt.** Auth publishes `public.authentication.publicPaths`, the anonymous entry
points it owns, as enabled:

- client mode: the login path and `client.callbackPath`;
- server mode: the login and register pages, `/forgot-password` and `/reset-password`, `/auth/**` (magic link,
  `/auth/frigear`, Users' email-change landing pages), `/api/auth/**` and `/api/_auth/**` (nuxt-auth-utils' session
  endpoint).

At `modules:done` Authorization adds a `{ authenticated: false }` entry for each of them, unless the app has its own
entry for that exact pattern (the app wins). This also covers the server middleware, which applies wildcard rules to
every `/api/` request (`runtime/server/middleware/authorization.ts:10-18`). Without it, `'/**': { authenticated: true }`
would block `/api/auth/login`. Exempting `/api/auth/**` as a whole is safe: every non-anonymous handler in it calls
`requireAuth` / `getUserSession` itself (`me/*`, `bootstrap`, `scopes`, `webauthn/register`). Tests cover `'/**'` and
`'/api/**'` guards in a server fixture (login, register, session fetch and magic-link confirm stay reachable) and in a
client fixture (login and callback stay reachable).

**Mobile stops forcing guards.** The `protect: 'all'` default goes, and a tab's `requiresAuth` defaults to `false`
instead of `mobile.auth` (`tabs.ts:69`). A tab marked `requiresAuth: true` is still hidden while signed out. The
starter marks its Account tab. `mobile.auth` now means "follows the sign-in state of Auth in client mode".

**Safety net.** Because a mobile app is now public by default:

- Mobile warns at build time when Auth runs in client mode and no `routeRules` entry and no page carries an
  `authenticated`, `roles` or `ability` rule. The message names the starter's `'/**'` rule.
- Auth warns when guard keys are present without Authorization (Details 2).

**`protect`, `publicPaths` and page meta `oauth`** do not exist in Auth. They remain only in the frozen OAuth Client
package.

### 6. Hooks

In client mode only:

| oauth-client | Auth | Context |
| --- | --- | --- |
| `oauth:signed-in` | `auth:signed-in` | `{ user, claims }` |
| `oauth:signed-out` | `auth:signed-out` | `{ reason }` |
| `oauth:refresh-failed` | `auth:refresh-failed` | `{ error }` |
| (new) | `auth:user-failed` | `{ error }` |

They fire on the same core events as today (`plugins/oauth.client.ts:47-55`). Restoring a stored session at startup
does not fire `auth:signed-in`. They are runtime app hooks (`RuntimeNuxtHooks`), separate from Auth's build hooks
(`auth:resolvers`, `auth:scopes`, `auth:user-store`) and Nitro hooks (`auth:email`, `auth:scope-available`). Server
mode fires none of them for now (Open questions).

### 7. Package layout

```text
packages/auth/src/
  module.ts             resolveAuthMode, then setupServerMode / setupClientMode
  client-build.ts       from oauth-client src/build.ts (storage, native loader, secret guard)
  types.ts              + ClientModuleOptions, mode
  runtime/
    mode.ts             resolveAuthMode (no @nuxt/kit), exported as ./mode (subpaths live under runtime/ to be built)
    utils/redirect.ts   the one safe-redirect check (Security)
    client/
      core/             from oauth-client runtime/core (no Nuxt imports)
      capacitor/        from oauth-client runtime/capacitor
      app/              useAuth, useUserSession, useApi, plugins, login + callback pages, AuthSignInButton
      types.ts          options, runtime config and core types, exported as ./client-types
      auth-utils.ts     the `#auth-utils` stand-in
    app/ server/ db/    server mode, unchanged (+ useAuth / $api in PR3c)
```

- **Exports:** `./mode`, `./client-core`, `./capacitor` and `./client-types`, following the `publishConfig` pattern in
  `packages/oauth-client/package.json`.
- **Dependencies:** `defu` (imported by `build.ts:1`) is added. The Capacitor plugins (`@capacitor/app`, `/browser`,
  `/core`, `/preferences`, `@aparajita/capacitor-secure-storage`) become optional peers, and so does `@nuxthub/core`.
  `#oauth-client/native` becomes `#auth/native` and still imports only the installed plugins

## Security

- **Client-mode guards are UX.** The `id_token` is decoded without a signature check (TLS to the token endpoint stands
  in for it, `packages/oauth-client/src/runtime/core/jwt.ts:36-39`), and the stored tokens and the mapped user live
  in storage the device owner can edit. A route rule or a `role` in a client-mode app decides what to show, never
  what is allowed. Bundled pages must not contain privileged data. Every protected read and write goes to an API that
  checks `requireAuth` / `requireUser` with scopes.
- **Server to client mode is a downgrade for a web app.** It moves the credential from an httpOnly cookie into
  `localStorage` (or the Keychain on a device), which any XSS can read in a browser. The client-mode docs say so, and
  Identity keeps recommending server mode for server-rendered web apps.
- **One redirect check.** Five copies of the same check exist:
  - `packages/auth/src/module.ts:57`;
  - `packages/auth/src/runtime/server/utils/redirect.ts:4`;
  - `packages/auth/src/runtime/app/pages/magic-link.vue:22`;
  - `packages/authorization/src/runtime/utils/redirect.ts:2`;
  - `packages/oauth-client/src/runtime/utils/index.ts:43`.

  All five accept control characters and any backslash after the first character. PR3a replaces them with one
  `isSafeRedirect` in `runtime/utils/redirect.ts` (also exported from `./mode`, which is free of `@nuxt/kit`). It
  rejects `//`, any `\`, ASCII control characters and anything not starting with `/`. Authorization imports it in PR4.

## Migration

**`@frigear-nu/oauth-client` is frozen.** Its last release is a patch that logs a deprecation warning at build time and
links the migration guide. `npm deprecate` marks it. Its code, middleware and config stay as they are, so an app keeps
working on the versions it has. There is no translation shim: the legacy surface (custom login redirects, the
protected-logout default at `src/module.ts:114-116`, `publicPaths`, page meta, runtime env overrides) costs more to
emulate than to migrate. Auth throws when both are installed.

**`@frigear-nu/mobile`** (minor) depends on Auth instead of OAuth Client:

- It throws when an app still configures `oauthClient`, with the migration steps. That makes the move from
  locked-down to public a conscious one; an app that is not ready stays on Mobile 0.1.
- `useOAuth` in `#mobile/optional` (`module.ts:237`) becomes `useAuth`, available when Auth is in client mode.
- The native manifest reads `public.authentication.client.nativeRedirectUri` (`module.ts:305-321`).
- `usedPlugins({ oauth })` (`build.ts:78-91`) is true for Auth in client mode.

**For an app:**

1. Rename `oauthClient` to `authentication: { mode: 'client', client: {...} }`.
2. Rename `api.attachTo` and the env vars.
3. Add `openid` to the scopes if it is missing.
4. Replace `useOAuth().claims` with `useUserSession().user`, and the other `useOAuth()` calls with `useAuth()`.
5. Replace `protect: 'all'` / `publicPaths` with Authorization rules.

**Releases.** Packages are released with release-it through the Release workflow (`.github/workflows/release.yml`).
The repo has no changesets. A run versions each listed package in sequence, then builds and publishes them all
(`scripts/publish-released.sh`). `pnpm pack` rewrites `workspace:^` to a caret on the version in the workspace at
publish time (`scripts/npm-publish.sh:4-7`).

Auth is `0.2.3`, so a minor (`0.3.0`) falls outside every published `^0.2.x` range. Its `workspace:^` dependents must
be released with it, or after it, or apps get two copies of Auth: account, authorization, events, forms,
frigear-resource, mcp, oauth-server, payments, preferences, subscriptions and users. (Cookie Consent's
`>=0.0.1` peer is unaffected.) So:

1. Merge PR3a and release Auth together with those eleven, in one Release run with `package: all`, or Auth first and
   then each dependent.
2. Release PR3b and PR3c as Auth minors or patches, with the same rule for minors.
3. Merge PR4, then release Authorization and Mobile. Nothing depends on them through `workspace:^`.
4. Merge PR4b only after those releases. Starter CI fails on `main` when a starter needs an unreleased version.
5. PR5: release the OAuth Client patch and run `npm deprecate`.

None of the PRs changes a schema, so no starter or fixture migrations change.

## Alternatives

- **Keep both packages and add a facade** (a shared `useAuth` in module-kit that dispatches to `useUserSession` or
  `useOAuth`). Rejected: two config keys, two user shapes, two hook sets and two guard systems would remain.
- **Keep as is.** Rejected: the context switch is the problem, and the locked-down default sits in Mobile with its own
  guard vocabulary.
- **A third module next to Auth that also provides `useUserSession`.** Rejected: two modules would claim the same
  auto-import and alias, with no single place that decides the mode.
- **A translating OAuth Client shim.** Rejected: the legacy surface to emulate is large (see Migration). Freezing it
  costs nothing.
- **Infer the mode from Mobile.** Rejected: dependency functions run before defaults merge, so the mode would arrive
  too late.

## Consequences

- One config key, one `useUserSession`, one `useAuth`, one `$api`, one guard system. Code that only reads `loggedIn`
  and `user` runs in either app.
- A Capacitor app installs Auth and Authorization, so its `node_modules` gets their server-side dependencies (drizzle,
  libsql, nuxt-auth-utils, notify, users). The bundle tests keep them out of the build.
- Auth's `module.ts` grows a second path. Two functions with one branch keep server mode reviewable.
- Mobile apps are public unless they add rules. Mobile's `oauthClient` error and its no-guard warning make that
  visible, and the API still refuses unauthenticated calls.
- The OAuth Client code exists twice until the frozen package is removed.

## Open questions

- **SSR in client mode.** Nuxt re-runs global middleware on the first client route, but signed-out server HTML would
  not match the hydrated markup. Is a pending shell around identity-dependent content a contract worth supporting?
  It needs a browser fixture before `ssr: true` is allowed.
- **Server-mode hooks.** Should `auth:signed-in` / `auth:signed-out` fire in server mode? It would need one observer
  covering `fetch`, `clear`, logout, initial restore and popup sign-in, without duplicate emissions.
- **Server-only runtime dependencies.** Can Auth's server-only `dependencies` (`drizzle-orm`, `@libsql/client`,
  `nuxt-auth-utils`, `@frigear-nu/notify`) become optional peers without breaking existing server-mode installs?
- **Tabs.** Should Mobile hide tabs whose `to` is guarded by an Authorization rule, instead of a separate
  `requiresAuth` flag?
- **Feature modules.** Which of them (Events, Payments, Subscriptions, Preferences) should get a client-mode split,
  and how do they gate their Users dependency?
- **A default `role` claim.** Should OAuth Server add a `role` claim (behind a `roles` scope) by default, so role rules
  work with the default mapping?
- **Other anonymous endpoints.** Users' email-change endpoints under `/api/users/**` would be blocked by a
  `'/**'` guard in a server app. Should modules other than Auth contribute to `publicPaths`, through a build hook?

## Review log

Changes after two independent reviews (Codex, Opus) of the first draft:

- The mode comes only from the app's config, through one resolver used by Auth, Authorization and Mobile. Mobile no
